# **✦ Race Condition**

## 1. В чём разница между Data Race и Race Condition?

**Короткий ответ:**
- **Data Race** — проблема несинхронизированного доступа к памяти.
- **Race Condition** — проблема зависимости результата от порядка выполнения операций.

**Race Condition может существовать даже при отсутствии Data Race.**

**Развёрнутый ответ:**
**Data Race** возникает, когда несколько горутин одновременно обращаются к одной области памяти, хотя бы одна операция является записью, а необходимая синхронизация отсутствует.

**Race Condition** возникает, когда результат программы зависит от порядка или времени выполнения конкурентных операций.

Например, две горутины могут одновременно проверить баланс, после чего обе выполнить списание. Даже если отдельные операции защищены мьютексом, отсутствие общей критической секции для проверки и списания может привести к логической ошибке.

## 2. Как работает Race Detector *(`-race`)*? Какой оверхед он даёт?

**Короткий ответ:**
- Использует технологию **ThreadSanitizer**.
- Инструментирует операции чтения и записи памяти.
- Отслеживает конкурентные обращения и отношения `happens-before`.
- Оверхед: примерно 2–20 раз по времени и 5–10 раз по памяти.

**Развёрнутый ответ:**
**Race Detector** — динамический инструмент обнаружения Data Race.

**Принцип работы:**
1. Компилятор добавляет проверки к операциям с памятью.
2. Runtime отслеживает обращения горутин.
3. Детектор анализирует синхронизацию между операциями.
    
4. При обнаружении конфликтующих обращений без необходимой синхронизации выводит предупреждение.
    

Запуск:

```
go test -race ./...
go run -race main.go
```

Используется преимущественно при тестировании и отладке, поскольку значительно увеличивает потребление ресурсов.

## 3. Может ли Race Detector гарантировать отсутствие гонок в коде?

**Короткий ответ:**

Нет. Race Detector обнаруживает гонки только в тех участках кода и сценариях, которые фактически выполнялись.

**Развёрнутый ответ:**

Детектор является динамическим, а не статическим анализатором.

Он может не обнаружить проблему, если:

- проблемная функция не была вызвана;
    
- необходимый конкурентный сценарий не возник;
    
- определённая последовательность выполнения не воспроизвелась.
    

Поэтому отсутствие предупреждений `-race` не доказывает отсутствие Data Race.

## 4. Что такое Memory Barrier (барьер памяти)?

**Короткий ответ:**

**Memory Barrier** — механизм, ограничивающий переупорядочивание операций чтения и записи памяти процессором и компилятором, обеспечивая необходимые гарантии видимости изменений между потоками.

**Развёрнутый ответ:**

CPU и компилятор могут менять порядок выполнения операций ради оптимизации.

При конкурентном выполнении это может привести к тому, что другая горутина увидит изменения не в ожидаемом порядке.

В Go необходимые гарантии обеспечиваются примитивами синхронизации:

- `Mutex`, `RWMutex`;
    
- каналами;
    
- `WaitGroup`;
    
- `sync/atomic`.
    

Они формируют отношения `happens-before`.

Важно: Memory Barrier не обязательно является отдельной машинной инструкцией. Конкретная реализация зависит от архитектуры процессора.

# **✦ Планировщик**

## 1. Что означают буквы G, M и P в архитектуре планировщика Go?

**Короткий ответ:**

- **G (Goroutine)** — выполняемая задача.
    
- **M (Machine)** — поток операционной системы.
    
- **P (Processor)** — логический процессор, предоставляющий ресурсы для выполнения Go-кода.
    

**Развёрнутый ответ:**

Планировщик Go использует модель GMP:

1. G представляет горутину и содержит её состояние, стек и другую служебную информацию.
    
2. M представляет реальный поток ОС, на котором выполняется код.
    
3. P предоставляет M право выполнять Go-код и содержит локальную очередь готовых горутин.
    

Для выполнения Go-кода M должен получить P.

Количество P определяется `GOMAXPROCS`, количество M может динамически изменяться.

## 2. Как работает алгоритм Work Stealing?

**Короткий ответ:**

**Work Stealing** — механизм балансировки нагрузки, при котором простаивающий P забирает часть готовых горутин из локальной очереди другого P.

Обычно забирается половина доступных задач.

**Развёрнутый ответ:**

Каждый P имеет собственную локальную очередь готовых горутин.

Если у P заканчиваются задачи:

1. Планировщик проверяет глобальную очередь.
    
2. Проверяет Network Poller.
    
3. Если работы нет, выбирает другой P.
    
4. Забирает часть его локальной очереди.
    
5. Выполняет полученные горутины.
    

Пример:

```
P1: [G1, G2, G3, G4, G5, G6]
P2: []

После Work Stealing:

P1: [G1, G2, G3]
P2: [G4, G5, G6]
```

Это позволяет уменьшить простои процессоров и равномернее распределять нагрузку.

## 3. Что такое P (Processor) и почему их количество обычно равно количеству ядер?

**Короткий ответ:**

**P** — логическая сущность планировщика, необходимая для выполнения Go-кода. Количество P определяется `GOMAXPROCS` и обычно соответствует количеству доступных логических CPU.

**Развёрнутый ответ:**

P содержит:

- локальную очередь горутин;
    
- кеши аллокатора памяти;
    
- другие локальные ресурсы runtime.
    

Одновременно на одном P может выполняться только одна горутина через M.

Ограничение количества P позволяет не создавать избыточную конкуренцию за процессорное время.

Получить текущее значение:

```
runtime.GOMAXPROCS(0)
```

Важно: количество M не ограничивается количеством P. Если M блокируется в системном вызове, P может быть передан другому M.

## 4. Как планировщик обрабатывает системные вызовы (Syscalls)? Что происходит с M и P?

**Короткий ответ:**

Если M блокируется в системном вызове, runtime освобождает P и передаёт его другому M. Заблокированный M может продолжить работу после завершения syscall, когда получит P.

**Развёрнутый ответ:**

Последовательность:

1. G выполняет системный вызов на M.
    
2. M блокируется на уровне ОС.
    
3. Runtime освобождает P.
    
4. Другой M получает P и продолжает выполнять готовые G.
    
5. После завершения syscall исходная G возвращается к выполнению, когда сможет получить P.
    

Схема:

```
До syscall:
G1 → M1 → P1

Во время syscall:
G1 → M1 (blocked)
G2 → M2 → P1
```

Это позволяет не блокировать выполнение остальных горутин из-за одного системного вызова.

## 5. В чём разница между кооперативной и вытесняющей многозадачностью? Как это реализовано в Go 1.14+?

**Короткий ответ:**

- **Кооперативная** — горутина сама уступает управление.
    
- **Вытесняющая (Preemptive)** — runtime может принудительно остановить горутину.
    
- Начиная с Go 1.14 поддерживается асинхронное вытеснение с использованием сигналов ОС.
    

**Развёрнутый ответ:**

При кооперативной многозадачности горутина должна достичь точки, в которой может уступить управление: например, заблокироваться на канале или вызвать `runtime.Gosched()`.

Проблема — бесконечный цикл может надолго занять P.

Начиная с Go 1.14 runtime может инициировать асинхронное вытеснение:

1. Runtime определяет необходимость переключения.
    
2. Отправляет сигнал потоку ОС, например `SIGURG`.
    
3. Выполнение горутины прерывается в подходящей безопасной точке.
    
4. Состояние сохраняется.
    
5. Планировщик запускает другую G.
    

Важно: вытеснение не происходит в произвольной машинной инструкции. Runtime должен остановить выполнение в безопасной точке.

## 6. Что такое Network Poller и как он помогает избежать блокировки потоков ОС?

**Короткий ответ:**

**Network Poller** — механизм runtime для асинхронного ожидания сетевых событий. Он позволяет горутине ждать сетевую операцию, не удерживая отдельный заблокированный поток ОС.

**Развёрнутый ответ:**

Используются системные механизмы:

- `epoll` — Linux;
    
- `kqueue` — BSD/macOS;
    
- `IOCP` — Windows.
    

Принцип работы:

1. Горутина начинает сетевую операцию.
    
2. Если операция пока невозможна, runtime регистрирует ожидание события.
    
3. Горутина паркуется.
    
4. M освобождается для выполнения других задач.
    
5. Network Poller ожидает событие ОС.
    
6. После появления готовности G возвращается в очередь выполнения.
    

Это позволяет эффективно обслуживать большое количество сетевых соединений без отдельного заблокированного потока на каждое соединение.

## 7. Что такое Local Run Queue и Global Run Queue? В каком порядке планировщик берёт задачи?

**Короткий ответ:**

- **LRQ** — локальная очередь готовых горутин конкретного P.
    
- **GRQ** — общая очередь готовых горутин.
    
- При поиске работы планировщик проверяет локальные и глобальные задачи, Network Poller и использует Work Stealing.
    

**Развёрнутый ответ:**

|LRQ|GRQ|
|---|---|
|Принадлежит одному P|Общая для всех P|
|Меньше конкуренции|Требует общей синхронизации|
|Быстрый доступ|Распределяет общую нагрузку|

Упрощённый порядок поиска работы:

1. Периодическая проверка GRQ.
    
2. Проверка LRQ текущего P.
    
3. Проверка Network Poller.
    
4. Work Stealing у другого P.
    

Важно: глобальная очередь не проверяется при каждом поиске. В частности, runtime использует периодическую проверку примерно раз в 61 итерацию.

## 8. Зачем нужен поток sysmon? Какие функции он выполняет?

**Короткий ответ:**

**sysmon (System Monitor)** — специальный поток runtime, который обслуживает систему Go независимо от выполнения пользовательских горутин.

**Развёрнутый ответ:**

Основные задачи:

- Контроль долго выполняющихся горутин и помощь в их вытеснении.
    
- Контроль потоков, находящихся в системных вызовах.
    
- Помощь в возвращении P к выполнению Go-кода.
    
- Обслуживание сетевого poller и таймеров.
    
- Участие в некоторых фоновых операциях runtime.
    

Особенность: sysmon работает без P и не выполняет пользовательские горутины.

## 9. Что такое spinning threads и зачем они нужны?

**Короткий ответ:**

**Spinning Threads** — потоки M, которые активно ищут готовые задачи вместо перехода в спящее состояние.

Они нужны для быстрого обнаружения новой работы и уменьшения задержек пробуждения.

**Развёрнутый ответ:**

Пока M находится в spinning-состоянии, он может:

- проверять очереди;
    
- искать задачи у других P;
    
- проверять готовность сетевых событий.
    

Это ускоряет обнаружение новой работы, но потребляет CPU.

Runtime ограничивает количество spinning threads, чтобы избежать избыточной нагрузки.

## 10. Как runtime.Gosched() влияет на выполнение горутины?

**Короткий ответ:**

`runtime.Gosched()` добровольно уступает управление планировщику, позволяя другим готовым горутинам получить CPU.

**Развёрнутый ответ:**

После вызова:

1. Текущая G уступает управление.
    
2. Остаётся готовой к выполнению.
    
3. Планировщик получает возможность запустить другую G.
    
4. Исходная горутина продолжит выполнение позднее.
    

Важно:

- Не гарантирует запуск конкретной горутины.
    
- Не гарантирует переключение на другой M.
    
- Не является механизмом синхронизации.
    

## 11. Что произойдёт, если горутина попадёт в бесконечный цикл без вызовов функций (до 1.14 и после)?

**Короткий ответ:**

- До Go 1.14 такая горутина могла надолго занять P из-за ограничений кооперативного вытеснения.
    
- С Go 1.14 runtime поддерживает асинхронное вытеснение таких горутин.
    

**Развёрнутый ответ:**

Пример:

```
go func() {
    for {
        // Бесконечный цикл
    }
}()
```

До Go 1.14 runtime в основном зависел от точек, в которых горутина могла уступить управление.

Начиная с Go 1.14 runtime может инициировать вытеснение через сигнал ОС и остановить горутину в безопасной точке.

Таким образом, бесконечный цикл больше не должен бесконечно удерживать P.

## 12. Каков размер стека горутины при создании и как он растёт?

**Короткий ответ:**

Начальный стек горутины обычно составляет **2 КБ**. При нехватке места runtime выделяет стек большего размера и копирует туда содержимое старого.

**Развёрнутый ответ:**

Механизм роста:

1. При вызове функции проверяется доступность места в стеке.
    
2. Если места недостаточно, runtime выделяет новый стек.
    
3. Копирует содержимое старого стека.
    
4. Корректирует указатели и ссылки.
    
5. Продолжает выполнение горутины.
    

Стек может не только расти, но и уменьшаться.

Это позволяет создавать большое количество горутин без необходимости сразу выделять каждой большой стек.

# **✦ Сборщик мусора (Garbage Collector)**

## 1. Какой алгоритм лежит в основе GC в Go?

**Короткий ответ:**

В Go используется конкурентный сборщик мусора, основанный на алгоритме **Tri-color Marking (трёхцветная разметка)**.

**Развёрнутый ответ:**

GC определяет достижимость объектов из корневых ссылок.

Основные этапы:

1. Mark Setup — подготовка к разметке.
    
2. Concurrent Mark — конкурентная разметка объектов.
    
3. Mark Termination — завершение разметки.
    
4. Sweep — освобождение недостижимых объектов.
    

Большая часть разметки выполняется параллельно с пользовательским кодом.

## 2. Опишите три цвета: белый, серый, чёрный.

**Короткий ответ:**

- **Белый** — ещё не проверен; если останется белым, будет удалён.
    
- **Серый** — достижим, но его ссылки ещё не проверены.
    
- **Чёрный** — проверен, все его ссылки обработаны.
    

**Развёрнутый ответ:**

Алгоритм:

1. Все объекты изначально белые.
    
2. GC находит корневые объекты и делает их серыми.
    
3. Выбирает серый объект и проверяет его ссылки.
    
4. Обнаруженные белые объекты становятся серыми.
    
5. Проверенный объект становится чёрным.
    
6. Процесс продолжается, пока серых объектов не останется.
    

Оставшиеся белые объекты считаются недостижимыми и могут быть освобождены.

## 3. Что такое Write Barrier и зачем он нужен во время фазы разметки?

**Короткий ответ:**

**Write Barrier** — механизм отслеживания изменений указателей во время конкурентной разметки GC. Он предотвращает ошибочное удаление объектов, которые продолжают использоваться программой.

**Развёрнутый ответ:**

Проблема возникает потому, что пользовательские горутины продолжают изменять ссылки во время работы GC.

Например:

1. GC сделал объект A чёрным.
    
2. Программа записала в A ссылку на белый объект B.
    
3. Без дополнительной обработки B может остаться белым.
    
4. GC может ошибочно посчитать B недостижимым.
    

Write Barrier отслеживает такие изменения и сохраняет корректность разметки.

В Go используется гибридный Write Barrier, сочетающий подходы Dijkstra и Yuasa.

## 4. Что такое STW (Stop The World)? Когда происходит и как долго длится?

**Короткий ответ:**

**STW** — остановка пользовательских горутин для выполнения определённых операций GC.

В Go основные точки STW:

- Mark Setup — подготовка к разметке.
    
- Mark Termination — завершение разметки.
    

Обычно паузы короткие: от микросекунд до миллисекунд.

**Развёрнутый ответ:**

STW необходим, чтобы runtime мог безопасно изменить состояние GC и завершить текущую фазу разметки.

Между двумя остановками основная работа выполняется конкурентно с приложением.

Продолжительность зависит от:

- количества горутин;
    
- размера и структуры стеков;
    
- количества корневых ссылок;
    
- нагрузки на приложение.
    

Важно: STW не означает, что вся сборка мусора выполняется при остановленной программе.

## 5. Как параметр GOGC влияет на частоту сборки мусора?

**Короткий ответ:**

- Увеличение `GOGC` — сборка происходит реже, но потребление памяти растёт.
    
- Уменьшение `GOGC` — сборка происходит чаще, но объём используемой памяти обычно уменьшается.
    
- Значение по умолчанию — `100`.
    

**Развёрнутый ответ:**

`GOGC` определяет целевой рост кучи относительно объёма живых объектов после предыдущего GC.

Упрощённая формула:

[  
HeapTarget = LiveHeap \times (1 + GOGC/100)  
]

Например, если после GC осталось 100 МБ живых объектов:

|GOGC|Целевой размер|
|---|---|
|50|150 МБ|
|100|200 МБ|
|200|300 МБ|

Также существует `GOMEMLIMIT` — ограничение памяти runtime, влияющее на работу GC.

## 6. В чём разница между стеком и кучей в Go?

**Короткий ответ:**

- **Stack** — память для локальных данных и контекста выполнения функций.
    
- **Heap** — память для объектов, время жизни которых может выходить за пределы вызова функции.
    

**Развёрнутый ответ:**

**Стек:**

- У каждой горутины собственный стек.
    
- Автоматически растёт и уменьшается.
    
- Обычно дешевле в обслуживании.
    

**Куча:**

- Используется для объектов, которые должны жить дольше текущего вызова функции или иметь более широкую область использования.
    
- Память выделяется аллокатором.
    
- Неиспользуемые объекты освобождаются GC.
    

Размещение определяется Escape Analysis.

Важно: не все локальные переменные находятся в стеке, а все объекты, на которые есть указатели, не обязательно находятся в куче.

# **✦ Примитивы синхронизации**

## 1. Как работает sync.Mutex под капотом? (normal и starvation mode)

**Короткий ответ:**

`sync.Mutex` использует два основных поля:

- `state` — состояние блокировки и количество ожидающих горутин.
    
- `sema` — механизм ожидания и пробуждения горутин.
    

Имеет два режима: **normal** и **starvation**.

**Развёрнутый ответ:**

**Normal Mode:**

- Горутина пытается захватить мьютекс.
    
- Если он свободен, получает блокировку.
    
- Если занят, ожидает.
    
- После освобождения ожидающие и новые горутины конкурируют за блокировку.
    

Новая горутина может получить мьютекс раньше ожидающей. Это называется barging.

**Starvation Mode:**

Если ожидание горутины превышает примерно 1 мс, мьютекс может перейти в режим starvation.

- Новые горутины не могут обойти ожидающих.
    
- Освобождение блокировки передаёт владение ожидающей горутине.
    
- После устранения условий голодания возможен возврат в normal mode.
    

Normal mode оптимизирован под производительность, starvation mode — под справедливость.

## 2. Чем sync.RWMutex эффективнее обычного Mutex и когда его использовать?

**Короткий ответ:**

`RWMutex` позволяет нескольким горутинам одновременно читать данные, но запись выполняется эксклюзивно.

Эффективен, когда чтений значительно больше, чем записей.

**Развёрнутый ответ:**

Основные методы:

```
mu.RLock()
mu.RUnlock()

mu.Lock()
mu.Unlock()
```

Особенности:

- Несколько читателей могут одновременно удерживать `RLock`.
    
- `Lock` требует эксклюзивного доступа.
    
- Пока ожидает писатель, новые читатели блокируются, чтобы не допустить голодания писателя.
    

`RWMutex` может быть медленнее обычного `Mutex` при коротких критических секциях и частых записях.

Использовать его стоит после профилирования.

## 3. Что такое starvation mode в мьютексе и как он предотвращается?

**Короткий ответ:**

**Starvation** — голодание горутины, которая долго не может получить блокировку.

Go предотвращает его переключением `Mutex` в starvation mode после длительного ожидания (примерно 1 мс).

**Развёрнутый ответ:**

В normal mode новые горутины могут конкурировать с ожидающими за мьютекс.

При длительном ожидании:

1. Мьютекс переходит в starvation mode.
    
2. Новые горутины не могут перехватывать блокировку.
    
3. Владение передаётся ожидающей горутине.
    
4. После устранения голодания происходит возврат в normal mode.
    

## 4. sync.WaitGroup: что будет, если вызвать Add() после того, как Wait() уже заблокирован?

**Короткий ответ:**

Положительный `Add()` при нулевом счётчике должен выполняться до `Wait()`. Конкурентный вызов `Add()` в такой ситуации нарушает правила использования `WaitGroup` и может привести к panic.

**Развёрнутый ответ:**

`WaitGroup` использует счётчик незавершённых задач.

- `Add(n)` увеличивает счётчик.
    
- `Done()` уменьшает его.
    
- `Wait()` ожидает, пока он станет равен нулю.
    

Правильное использование:

```
var wg sync.WaitGroup

wg.Add(1)

go func() {
    defer wg.Done()
    // Работа
}()

wg.Wait()
```

Если счётчик уже положительный, его можно увеличивать во время ожидания при соблюдении правил синхронизации.

## 5. Как работает sync.Once? Почему недостаточно просто проверить флаг bool?

**Короткий ответ:**

`sync.Once` гарантирует однократное выполнение функции при конкурентных вызовах. Использует атомарное состояние и Mutex для синхронизации.

Обычного `bool` недостаточно из-за Data Race и возможности одновременной инициализации.

**Развёрнутый ответ:**

Пример:

```
var once sync.Once

once.Do(func() {
    initialize()
})
```

Упрощённый алгоритм:

1. Проверяется атомарный флаг выполнения.
    
2. Если функция ещё не запускалась, захватывается Mutex.
    
3. Состояние проверяется повторно.
    
4. Выполняется функция.
    
5. Флаг устанавливается в состояние завершения.
    

Остальные горутины ожидают завершения и не запускают функцию повторно.

Важно: если функция вызывает panic, `sync.Once` всё равно считает её выполненной.

## 6. sync.Cond: зачем ему мьютекс и когда он лучше каналов?

**Короткий ответ:**

`sync.Cond` позволяет горутинам ожидать изменения общего состояния.

Mutex нужен для безопасной работы с данными, от которых зависит условие.

**Развёрнутый ответ:**

Основные методы:

```
cond.Wait()
cond.Signal()
cond.Broadcast()
```

- `Wait()` освобождает Mutex и блокирует горутину. Перед возвратом повторно захватывает его.
    
- `Signal()` пробуждает одну ожидающую горутину.
    
- `Broadcast()` пробуждает все ожидающие горутины.
    

Пример:

```
mu.Lock()

for len(queue) == 0 {
    cond.Wait()
}

item := queue[0]
queue = queue[1:]

mu.Unlock()
```

Используется `for`, чтобы повторно проверить условие после пробуждения.

`Cond` удобен для ожидания изменения общего состояния. Каналы обычно предпочтительнее для передачи данных и организации взаимодействия между горутинами.

## 7. sync.Pool: как он взаимодействует с GC? Когда данные из пула удаляются?

**Короткий ответ:**

`sync.Pool` временно хранит объекты для повторного использования. Во время GC runtime может удалять содержимое пула.

Гарантии сохранения объектов нет.

**Развёрнутый ответ:**

Основные методы:

```
pool.Put(obj)
obj := pool.Get()
```

Если объект отсутствует, может вызываться функция `New`.

В современных реализациях используются:

- **Primary Cache** — основное хранилище.
    
- **Victim Cache** — временное хранилище объектов из предыдущего цикла.
    

При последующих циклах GC объекты могут быть удалены.

Важно:

- `Get()` может вернуть `nil`, если нет объектов и не задан `New`.
    
- Нельзя использовать `sync.Pool` как постоянное хранилище.
    
- Основная задача — уменьшение количества выделений памяти.
    

## 8. В чём преимущество sync/atomic перед мьютексами?

**Короткий ответ:**

`sync/atomic` обеспечивает атомарные операции без необходимости явно захватывать Mutex.

Для простых операций может иметь меньшие накладные расходы.

**Развёрнутый ответ:**

Пример:

```
var counter int64

atomic.AddInt64(&counter, 1)
```

Преимущества:

- Не требуется явная блокировка.
    
- Не нужно парковать горутину при каждой операции.
    
- Удобно реализовывать счётчики и флаги.
    
- Позволяет строить lock-free структуры.
    

Недостатки:

- Сложнее реализовывать составную логику.
    
- Не защищает автоматически несколько связанных переменных.
    
- Требует внимательного отношения к порядку операций.
    

Для сложных критических секций обычно лучше `Mutex`.

## 9. Что такое CAS (Compare-And-Swap)?

**Короткий ответ:**

**CAS** — атомарная операция, которая сравнивает текущее значение с ожидаемым и заменяет его новым, только если значения совпадают.

Возвращает `true`, если замена произошла.

**Развёрнутый ответ:**

CAS принимает:

1. Адрес переменной.
    
2. Ожидаемое старое значение.
    
3. Новое значение.
    

Пример:

```
var counter int64

for {
    old := atomic.LoadInt64(&counter)

    if atomic.CompareAndSwapInt64(
        &counter,
        old,
        old+1,
    ) {
        break
    }
}
```

Если другая горутина успела изменить значение, операция не выполняется и цикл повторяется.

CAS используется для реализации lock-free алгоритмов.

Возможная проблема — **ABA problem**, когда значение изменяется A → B → A, и CAS не замечает промежуточного изменения.

## 10. Как реализовать атомарный инкремент float64?

**Короткий ответ:**

Через преобразование `float64` в `uint64` с помощью `math.Float64bits()` и цикл CAS.

**Развёрнутый ответ:**

`float64` представлен 64-битным значением по стандарту IEEE 754.

Алгоритм:

1. Атомарно читаем текущее значение.
    
2. Преобразуем его в `float64`.
    
3. Выполняем сложение.
    
4. Преобразуем результат обратно в `uint64`.
    
5. Пытаемся выполнить CAS.
    
6. При неудаче повторяем операцию.
    

```
var value uint64

func AddFloat64(delta float64) {
    for {
        old := atomic.LoadUint64(&value)

        oldFloat := math.Float64frombits(old)
        newFloat := oldFloat + delta

        newBits := math.Float64bits(newFloat)

        if atomic.CompareAndSwapUint64(
            &value,
            old,
            newBits,
        ) {
            return
        }
    }
}
```

Атомарной здесь является замена битового представления, а не сама арифметическая операция.

# **✦ Sync.Map**

## 1. Почему обычная map с мьютексом иногда лучше, чем sync.Map?

**Короткий ответ:**

Обычная `map` с `Mutex` или `RWMutex` может быть быстрее и удобнее, когда нужны типобезопасность, частые изменения и сложные операции с несколькими ключами.

**Развёрнутый ответ:**

Преимущества обычной `map`:

- Типобезопасность.
    
- Меньше накладных расходов в некоторых сценариях.
    
- Возможность защищать составные операции одной блокировкой.
    
- Более предсказуемое поведение.
    

`sync.Map` использует `any` и оптимизирована под определённые сценарии конкурентного доступа.

Выбор стоит делать по характеру нагрузки и результатам профилирования.

## 2. Из каких двух структур состоит sync.Map (read и dirty)?

**Короткий ответ:**

- **read** — карта для быстрого чтения без обычной блокировки.
    
- **dirty** — изменяемая карта, доступ к которой защищён Mutex.
    

**Развёрнутый ответ:**

В классической реализации `sync.Map` используются две структуры:

**read:**

- Содержит доступные для чтения записи.
    
- Позволяет выполнять большинство операций чтения без Mutex.
    
- Содержит флаг `amended`, указывающий на наличие дополнительных записей в `dirty`.
    

**dirty:**

- Хранит изменяемые записи.
    
- Защищена Mutex.
    
- Используется при промахах чтения в `read`.
    

Если ключ не найден в `read`, но `amended == true`, выполняется поиск в `dirty`.

Это описание классической внутренней реализации, а не гарантия API.

## 3. Как происходит процесс promotion из dirty в read?

**Короткий ответ:**

**Promotion** — перенос `dirty` в `read`, чтобы новые записи стали доступны через быстрый путь чтения без Mutex.

Запускается после накопления определённого количества промахов при поиске.

**Развёрнутый ответ:**

Алгоритм:

1. Горутина ищет ключ в `read`.
    
2. Ключ отсутствует, поэтому выполняется поиск в `dirty`.
    
3. Увеличивается счётчик `misses`.
    
4. Когда количество промахов достигает размера `dirty`, выполняется promotion.
    
5. `dirty` становится новой `read`.
    
6. Счётчик `misses` сбрасывается.
    

После этого чтения снова преимущественно обслуживаются без блокировки.

## 4. Для каких сценариев оптимизирована sync.Map?

**Короткий ответ:**

`sync.Map` оптимизирована преимущественно для двух сценариев:

1. Значение записывается один раз, а затем многократно читается.
    
2. Разные горутины преимущественно работают с непересекающимися наборами ключей.
    

**Развёрнутый ответ:**

Примеры:

- Кеш конфигураций.
    
- Справочники.
    
- Хранение данных, которые редко изменяются.
    

При частых конкурентных обновлениях одних и тех же ключей или сложных составных операциях обычная `map` с Mutex может оказаться эффективнее.

## 5. Почему в sync.Map не реализован метод Len()?

**Короткий ответ:**

Потому что получение точного количества элементов при конкурентных изменениях требует дополнительной синхронизации или отдельного механизма учёта, что увеличило бы накладные расходы.

**Развёрнутый ответ:**

Представим, что одна горутина подсчитывает элементы, а другие одновременно добавляют и удаляют записи.

Полученное количество может не соответствовать единому согласованному состоянию карты.

Кроме того, `sync.Map.Range()` не гарантирует согласованный снимок карты во время конкурентных изменений.

Если нужен точный `Len()`, можно реализовать собственную обёртку над обычной `map` с Mutex и отдельным счётчиком.
