# **✦ ООП**

## 1. Как в Go реализуется инкапсуляция?

Инкапсуляция в Go реализуется преимущественно **на уровне пакетов**. Имена, начинающиеся с заглавной буквы, экспортируются и доступны из других пакетов. Имена со строчной буквы доступны только внутри своего пакета.

```
type Person struct {
    Name string // доступно извне
    age  int    // доступно только внутри пакета
}
```

Если нужно контролировать изменение `age`, можно предоставить метод:
```
func (p *Person) SetAge(age int) {
    if age >= 0 {
        p.age = age
    }
}
```

**Главное:** в [[1.1.0. Go Basics|Go]] нет модификаторов `private`, `protected` и `public`. Доступ определяется экспортируемостью имён и границами пакетов.

## 2. Чем композиция отличается от классического наследования?

В классических ООП-языках наследование позволяет создать класс на основе другого класса, унаследовав его поля и методы.

В [[1.1.0. Go Basics|Go]] классического наследования нет. Вместо него используют **композицию**: одна структура содержит другую как поле или встраивает её.

```
type Engine struct{}

func (e Engine) Start() {
    fmt.Println("Engine started")
}

type Car struct {
    Engine
}

func main() {  
    car := Car{}  
    car.Start()  
}
```
- Можно вызвать `car.Start()`, поскольку метод `Engine` продвигается через встроенное поле.

**Главное отличие:** композиция позволяет собирать поведение из компонентов, но не создаёт отношения наследования типов. `Car` не становится типом `Engine`.

## 3. Что такое Shadowing полей при embedding?

**Shadowing (затенение)** — ситуация, когда поле или метод внешней структуры скрывает одноимённое поле или метод встроенной структуры при обращении через внешний объект.

```
type A struct {
    Name string
}

type B struct {
    Name string
}

type Person struct {
    A
    B
}
```

Теперь `p.Name` неоднозначно: поле `Name` присутствует в двух встроенных структурах на одинаковой глубине. Компилятор выдаст ошибку.

Но к полям можно обратиться явно:
```
p.A.Name
p.B.Name
```

Если же внешняя структура сама объявит `Name`, оно будет затенять одноимённые продвигаемые поля:
```
type Person struct {
    A
    Name string
}
```
- Теперь `p.Name` означает поле самой `Person`, а `p.A.Name` — поле встроенной структуры.

**Главное:** при совпадении имён учитывается глубина вложенности. Поле на меньшей глубине скрывает одноимённое поле на большей.

## 4. Могут ли методы быть определены для неструктурных типов?

Да. В [[1.1.0. Go Basics|Go]] методы можно определять не только для структур, но и для других типов, например для пользовательских типов на основе `int`, `string` или срезов.

```
type Celsius float64

func (c Celsius) IsFreezing() bool {
    return c <= 0
}
```

Но есть ограничение: **тип получателя метода должен быть определён в том же пакете, где объявляется метод**, и не может быть указателем или интерфейсным типом.

Поэтому нельзя добавить метод непосредственно к встроенному типу `int` или к типу из чужого пакета. Для этого создают собственный тип на его основе.

```
type UserID int

func (id UserID) IsValid() bool {
    return id > 0
}
```

## 5. Как реализовать паттерн «Конструктор» в Go?

В Go нет специального синтаксиса конструктора, как в C++ или Java. Обычно создают функцию, которая инициализирует структуру и возвращает её значение или указатель.

```
type Person struct {
    name string
    age  int
}

func NewPerson(name string, age int) (*Person, error) {
    if age < 0 {
        return nil, fmt.Errorf("age cannot be negative")
    }

    return &Person{
        name: name,
        age:  age,
    }, nil
}
```

**Функция `NewPerson`:**
- проверяет входные данные;
- создаёт структуру;
- устанавливает начальные значения;
- возвращает результат и ошибку, если создание невозможно.

**Что возвращать?**
- `*Person` — если нужен указатель на объект, изменение состояния или избежание копирования крупной структуры.
- `Person` — если удобнее работать со значениями и их копиями.
- Интерфейс — если вызывающему коду достаточно контракта, а конкретную реализацию нужно скрыть.

Интерфейс не обязателен: выбор зависит от [[1.6.2. REST API|API]] и требований к реализации.

## 6. Что такое геттеры и сеттеры? Как они работают при embedding через указатель?

**Геттер** — метод для получения значения поля. **Сеттер** — метод для его изменения.

В Go их не требуется создавать для каждого поля автоматически. Они нужны, когда необходимо контролировать доступ, проверять значения или скрывать внутреннее устройство типа.

```
type Person struct {
    age int
}

func (p *Person) Age() int {
    return p.age
}

func (p *Person) SetAge(age int) error {
    if age < 0 {
        return fmt.Errorf("age cannot be negative")
    }

    p.age = age
    return nil
}
```

Обрати внимание: метод `Age()` — геттер, хотя в Go его обычно не называют `GetAge()`.

### Что меняется при embedding через указатель?

```
type Details struct {
    Name string
}

func (d *Details) SetName(name string) {
    d.Name = name
}

type Person struct {
    *Details
}
```

Теперь метод `SetName` продвигается через `Person`:
```
p := Person{
    Details: &Details{Name: "Alice"},
}

p.SetName("Bob")
fmt.Println(p.Name) // Bob
```

Встроенный указатель позволяет обращаться к методам и полям вложенного объекта. При вызове метода с указательным получателем изменения происходят в исходном объекте `Details`.

**Важно:** если встроенный указатель равен `nil`, обращение к полю или вызов метода, который разыменовывает этот указатель, может привести к панике.

## 7. Как реализовать полиморфизм без наследования?

В Go полиморфизм реализуется через **интерфейсы**. Тип удовлетворяет интерфейсу, если реализует все его методы. Явно объявлять соответствие не нужно.

```
type Speaker interface {
    Speak()
}

type Dog struct{}

func (Dog) Speak() {
    fmt.Println("Woof")
}

type Cat struct{}

func (Cat) Speak() {
    fmt.Println("Meow")
}
```

Теперь одна функция работает с разными типами:
```
func MakeSound(s Speaker) {
    s.Speak()
}
```

Можно передать `Dog` или `Cat`.

**Главное:** функция зависит от поведения, описанного интерфейсом, а не от конкретной структуры. Это позволяет подменять реализации без наследования.

## 8. Почему в Go нет перегрузки методов?

В Go нельзя объявить несколько функций или методов с одинаковым именем в одном пакете или для одного типа, даже если у них разные параметры.

Например, так нельзя:
```
func Add(a int, b int) int {
    return a + b
}

// Ошибка: функция Add уже объявлена
func Add(a float64, b float64) float64 {
    return a + b
}
```

**Вместо перегрузки обычно используют:**
- разные имена (`AddInt`, `AddFloat`);
- интерфейсы;
- обобщённые функции (generics);
- отдельные функции с понятными задачами.

**Главное:** [[1.1.0. Go Basics|Go]] предпочитает явные вызовы и простые правила разрешения имён.

## 9. Как работает `struct{}` и почему она занимает 0 байт?

`struct{}` — пустая структура, у которой нет полей.

```
var x struct{}
fmt.Println(unsafe.Sizeof(x)) // 0
```

Она не хранит данных, поэтому значение пустой структуры занимает 0 байт.
Её часто используют, когда важно обозначить факт, а не передать данные.
Например, в `map`:
```
visited := make(map[int]struct{})

visited[42] = struct{}{}
```

Такая карта может использоваться как множество (`set`): наличие ключа означает, что элемент присутствует. Значение `struct{}` не хранит дополнительной полезной информации.

Также `struct{}` применяют в каналах для передачи сигналов без данных:
```
done := make(chan struct{})

go func() {
    // Выполняем работу
    close(done)
}()

<-done
```
- **Главное:** `struct{}` полезна для обозначения состояния или события без дополнительной нагрузки в виде данных.

## 10. Влияет ли порядок полей в структуре на её размер?

Да. Компилятор может добавлять padding — пустые байты, необходимые для выравнивания полей в памяти.

```
type S1 struct {
    a bool
    b int64
    c bool
}

type S2 struct {
    a bool
    c bool
    b int64
}
```

На типичной 64-битной платформе размеры могут быть такими:
- `S1` — 24 байта;
- `S2` — 16 байт.

В `S1` между `a` и `b` нужно выравнивание, а после `c` добавляется padding в конце. В `S2` два поля `bool` размещаются рядом, что позволяет уменьшить размер.

Проверить размер можно с помощью `unsafe.Sizeof`.

**Главное:** порядок полей может влиять на расход памяти. При работе с большим количеством структур это иногда имеет значение, но конкретный размер зависит от архитектуры и реализации.

## 11. Можно ли расширить функционал типа из чужого пакета, добавив ему метод?

Непосредственно — нет. Go требует, чтобы тип получателя метода был определён в том же пакете, где объявляется метод.

Например, нельзя добавить метод к `time.Time` непосредственно в своём пакете.

Но можно создать новый тип на основе чужого:
```
type MyTime time.Time

func (t MyTime) IsZeroYear() bool {
    return time.Time(t).Year() == 0
}
```

Это создаёт новый тип `MyTime`, которому можно добавлять методы. Однако он не наследует методы `time.Time` автоматически.

Другой вариант — композиция:
```
type MyTime struct {
    time.Time
}

func (t MyTime) IsZeroYear() bool {
    return t.Year() == 0
}
```

Здесь методы `time.Time` могут продвигаться через встроенное поле.

**Главное:** напрямую менять чужой тип нельзя. Для расширения используют собственный тип или композицию.

# **✦ Интерфейсы**

## 1. Как устроены `iface` и `eface` внутри Go?

Внутри [[1.1.0. Go Basics|Go]] [[1.2.1. Интерфейсы в Go|интерфейс]] концептуально хранит два компонента: **информацию о типе и значение**.

- **`iface`** — представление интерфейса, содержащего методы. Хранит указатель на `itab` и указатель на данные.
- **`eface`** — представление пустого интерфейса *(`any`)*. Хранит информацию о конкретном типе и указатель на данные.

```
var x any = 42
```

Интерфейс `x` содержит информацию о типе `int` и само значение `42`.

**Главное:** интерфейс — это не просто указатель на значение. Он также хранит информацию о конкретном типе, находящемся внутри.

_Примечание: `iface` и `eface` — детали реализации runtime Go, а не гарантированная спецификацией структура памяти._

## 2. Что такое `itab` и какую информацию он хранит?

`itab` — внутренняя структура runtime, связывающая конкретный тип с интерфейсом, который он реализует.

Она содержит:
- информацию о типе интерфейса;
- информацию о конкретном типе;
- таблицу указателей на методы, необходимые для реализации интерфейса.

При вызове метода интерфейса runtime использует эту информацию, чтобы обратиться к реализации конкретного типа.

**Главное:** `itab` связывает интерфейс с конкретным типом и помогает находить нужные методы.

## 3. Почему интерфейс может быть не равен `nil`, хотя внутри находится `nil`?

Потому что интерфейс считается `nil`, только если в нём нет ни динамического типа, ни значения.
```
var p *int = nil
var x any = p

fmt.Println(x == nil) // false
```

Здесь:
- динамический тип интерфейса — `*int`;
- динамическое значение — `nil`.

Интерфейс не равен `nil`, поскольку информация о типе присутствует.

**Главное:** интерфейс равен `nil`, только если он не содержит динамического типа и значения.

## 4. Как работает динамическая диспетчеризация методов интерфейса?

Когда вызывается метод через интерфейс, [[1.1.0. Go Basics|Go]] определяет, какая реализация соответствует конкретному типу, находящемуся внутри интерфейса, и вызывает её.

```
type Speaker interface {
    Speak()
}

type Dog struct{}

func (Dog) Speak() {
    fmt.Println("Гав!")
}

type Cat struct{}

func (Cat) Speak() {
    fmt.Println("Мяу!")
}

func MakeSound(s Speaker) {
    s.Speak()
}
```

`MakeSound(Dog{})` вызовет метод `Dog.Speak()`, а `MakeSound(Cat{})` — `Cat.Speak()`.

**Главное:** вызов определяется динамическим типом значения внутри интерфейса, а не именем переменной или типом параметра функции.

## 5. Что такое Duck Typing и почему Go называют языком с неявными интерфейсами?

**Duck typing** — подход, при котором важны поддерживаемые объектом операции, а не его формальная принадлежность к определённой иерархии типов.

В [[1.1.0. Go Basics|Go]] тип реализует интерфейс, если у него есть все необходимые методы. Объявлять реализацию явно не нужно.

```
type Reader interface {
    Read([]byte) (int, error)
}
```

Если тип предоставляет подходящий метод `Read`, он удовлетворяет интерфейсу `Reader`.

**Главное:** реализация интерфейса в Go определяется набором методов, а не явным объявлением вроде `implements`.

## 6. Почему не рекомендуется `interface{}` *(`any`)* использовать повсеместно?

`any` — это псевдоним `interface{}`, то есть пустого интерфейса, который может содержать значение любого типа.

**Но чрезмерное использование `any` имеет недостатки:**
- теряется информация о конкретном типе;
- приходится проверять тип во время выполнения;
- увеличивается вероятность ошибок;
- код становится менее понятным;
- компилятор не может проверить часть ограничений заранее.

```
func PrintValue(v any) {
    fmt.Println(v)
}
```

Такая функция гибкая, но если ей нужно выполнять определённые операции над `v`, потребуется проверять его тип или использовать интерфейс с конкретными методами.

**Главное:** используй конкретные типы, когда они известны, а интерфейсы — когда нужно абстрагироваться от реализации. `any` полезен, когда действительно требуется принимать значения произвольных типов.

## 7. Что произойдёт, если метод реализован с другим receiver: значением или указателем?

В Go набор методов типа зависит от того, использует метод получатель-значение или получатель-указатель.

```
type Speaker interface {
    Speak()
}

type Dog struct{}

func (d *Dog) Speak() {}
```

**Метод имеет получатель `*Dog`, поэтому:**
- `*Dog` реализует `Speaker`;
- `Dog` не реализует `Speaker`.

**Следовательно:**
```
var s Speaker = &Dog{} // корректно
// var s Speaker = Dog{} // ошибка компиляции
```

**Главное:** если метод интерфейса реализован с получателем-указателем, интерфейс реализует указатель на тип, но не сам тип-значение.

## 8. Можно ли создать интерфейс, который нельзя реализовать вне текущего пакета?

Да. Для этого в интерфейс добавляют неэкспортируемый метод.

```
package example

type restricted interface {
    Do()
    restrictedMethod()
}
```

В другом пакете нельзя объявить метод с тем же именем, который удовлетворит этому требованию: неэкспортируемые имена из разных пакетов считаются разными идентификаторами.

Так можно ограничить множество типов, которые способны реализовать интерфейс.

**Главное:** неэкспортируемый метод позволяет контролировать реализацию интерфейса внутри пакета.

## 9. Как работает проверка реализации интерфейса на этапе компиляции?

Для этого часто используют объявление:
```
var _ Speaker = (*Dog)(nil)
```

Оно проверяет, реализует ли `*Dog` интерфейс `Speaker`.

- `(*Dog)(nil)` — типизированный nil-указатель типа `*Dog`;
- `_` — пустой идентификатор, которому не требуется сохранять значение;
- компилятор проверяет соответствие методов интерфейсу.

Если `*Dog` не реализует `Speaker`, программа не скомпилируется.

**Главное:** это compile-time проверка, которая документирует намерение и позволяет обнаружить несовместимость после изменений кода.

## 10. Как реализовать паттерн «Декоратор» через интерфейсы?

**Декоратор** — паттерн, который добавляет объекту поведение, оборачивая его другой реализацией того же интерфейса.

Например, можно добавить логирование к отправке сообщений.

```
type Sender interface {
    Send(message string) error
}

type EmailSender struct{}

func (e EmailSender) Send(message string) error {
    fmt.Println("Отправка:", message)
    return nil
}

type LoggingSender struct {
    next Sender
}

func (l LoggingSender) Send(message string) error {
    fmt.Println("Начало отправки")
    err := l.next.Send(message)
    fmt.Println("Отправка завершена")
    return err
}
```

Использование:
```
sender := LoggingSender{
    next: EmailSender{},
}

_ = sender.Send("Привет")
```

`LoggingSender` реализует тот же интерфейс `Sender`, но добавляет логирование до и после вызова обёрнутого объекта.

**Главное:** декоратор сохраняет интерфейс исходного объекта, добавляя поведение без изменения его кода.

# Ошибки, panic и defer

## 1. Почему `error` — это интерфейс, а не специальный тип данных?

`error` — встроенный [[1.2.1. Интерфейсы в Go|интерфейс]] [[1.1.0. Go Basics|Go]] с одним методом:
```
type error interface {
    Error() string
}
```
- Любой тип, реализующий метод `Error() string`, может использоваться как ошибка.
	Это позволяет создавать собственные типы ошибок с дополнительными данными: кодом ошибки, причиной, названием операции и другими сведениями.

```
type MyError struct {
    Message string
}

func (e MyError) Error() string {
    return e.Message
}
```

**Главное:** интерфейс `error` позволяет разным типам ошибок использоваться единообразно, без необходимости создавать специальный механизм ошибок для каждого случая.

---

## 2. В чём разница между `errors.New()` и `fmt.Errorf()`?

Обе функции создают значения, реализующие интерфейс `error`, но предназначены для немного разных задач.

- **`errors.New()`** создаёт ошибку с фиксированным текстом.
- **`fmt.Errorf()`** позволяет форматировать сообщение и поддерживает оборачивание ошибок с помощью `%w`.

```
err1 := errors.New("file not found")

err2 := fmt.Errorf("failed to open file: %w", err1)
```

Во втором случае `err2` содержит дополнительный контекст и сохраняет связь с исходной ошибкой. Поэтому исходную ошибку можно найти через `errors.Is()` или `errors.As()`.

**Главное:** `errors.New()` — простая ошибка с заданным текстом, `fmt.Errorf()` — форматирование сообщения и, при использовании `%w`, оборачивание другой ошибки.

---

## 3. Как работают `errors.Is()` и `errors.As()`? Когда что применять?

Обе функции позволяют анализировать ошибки, в том числе обёрнутые другими ошибками.

### `errors.Is()`

Проверяет, соответствует ли ошибка определённому значению ошибки, в том числе внутри цепочки обёрток.

```
if errors.Is(err, os.ErrNotExist) {
    fmt.Println("Файл не найден")
}
```

Применяется, когда нужно проверить **конкретную причину ошибки**.

### `errors.As()`

Ищет в цепочке ошибок первую ошибку, которую можно присвоить переменной указанного типа, и при успехе записывает её в эту переменную.

```
var pathErr *os.PathError

if errors.As(err, &pathErr) {
    fmt.Println("Операция:", pathErr.Op)
}
```

Применяется, когда нужно получить **ошибку определённого типа и обратиться к её полям или методам**.

**Главное:**

- `errors.Is()` — проверка на определённую ошибку.
- `errors.As()` — поиск ошибки определённого типа.

---

## 4. Как реализовать кастомный тип ошибки с поддержкой `Unwrap()`?

Нужно создать собственный тип ошибки и реализовать метод `Unwrap() error`, возвращающий исходную ошибку.

```
type MyError struct {
    Message string
    Err     error
}

func (e *MyError) Error() string {
    return e.Message + ": " + e.Err.Error()
}

func (e *MyError) Unwrap() error {
    return e.Err
}
```

Использование:
```
originalErr := errors.New("connection refused")
err := &MyError{
    Message: "database connection failed",
    Err:     originalErr,
}

fmt.Println(errors.Is(err, originalErr)) // true
```

`Unwrap()` позволяет стандартным функциям `errors.Is()` и `errors.As()` исследовать исходные ошибки внутри обёртки.

**Главное:** `Error()` описывает ошибку, а `Unwrap()` предоставляет доступ к ошибке, которую она оборачивает.

---

## 5. Стоит ли возвращать указатель на ошибку (`*MyError`) или само значение?

Универсального правила нет: выбор зависит от реализации типа ошибки.

**Указатель (`*MyError`)** часто удобен, когда:

- ошибка содержит много данных;
- нужно избежать копирования структуры;
- методы ошибки определены с указателем-получателем.

**Значение (`MyError`)** подходит, когда структура небольшая, неизменяемая по смыслу и копирование не создаёт проблем.

Важно учитывать набор методов типа: если `Error()` реализован с указателем-получателем, интерфейс `error` реализует `*MyError`, но не `MyError`.

```
type MyError struct{}

func (e *MyError) Error() string {
    return "something went wrong"
}

var err error = &MyError{} // корректно
```

**Главное:** указатели часто используют для пользовательских типов ошибок, но выбирать нужно с учётом методов, копирования и семантики типа.

---

## 6. Когда логировать ошибку, а когда просто возвращать её выше по стеку?

Ошибка должна обрабатываться на том уровне, где есть достаточно контекста, чтобы принять решение.

**Возвращать выше**, если текущая функция не может исправить проблему и вызывающий код способен решить, что делать дальше.

```
func loadConfig() error {
    data, err := os.ReadFile("config.json")
    if err != nil {
        return fmt.Errorf("load config: %w", err)
    }

    _ = data
    return nil
}
```

**Логировать**, когда текущий уровень действительно обрабатывает ситуацию или является подходящей границей наблюдения за ошибками: например, обработчиком HTTP-запроса или верхним уровнем приложения.

Не стоит без необходимости логировать одну и ту же ошибку на каждом уровне: это создаёт дублирующиеся записи.

**Главное:** добавляй контекст при возврате ошибки, а логируй там, где ошибка окончательно обрабатывается или где логирование действительно нужно.

---

## 7. Почему проверка `if err != nil` считается преимуществом языка, а не недостатком?

Go использует явную обработку ошибок вместо обязательных исключений для обычных ошибочных ситуаций.

```
data, err := os.ReadFile("config.json")
if err != nil {
    return err
}
```

Это позволяет увидеть обработку ошибок непосредственно в коде и контролировать, как они распространяются.

Недостаток — повторяющиеся проверки могут делать код многословным. Но явность помогает не скрывать потенциальные точки отказа за неявным механизмом исключений.

**Главное:** явная обработка делает поток ошибок заметным и позволяет разработчику контролировать реакцию на них.

---

## 8. Что происходит с горутиной при возникновении `panic`?

`panic` начинает раскрутку стека текущей горутины: выполняются отложенные вызовы `defer`, после чего паника продолжает распространяться вверх.

Если панику не перехватить с помощью `recover()`, программа аварийно завершится.

Важные особенности:

- `defer` выполняются в обратном порядке регистрации;
- паника в одной горутине сама по себе не запускает `recover()` в другой;
- неперехваченная паника обычно приводит к завершению всего процесса Go, а не только одной горутины.

**Главное:** паника раскручивает стек текущей горутины; если она остаётся неперехваченной, завершается процесс.

---

## 9. В каких случаях `panic` оправдан в продакшен-коде?

`panic` предназначен прежде всего для ситуаций, когда продолжать выполнение в обычном режиме невозможно или состояние программы нарушает важный инвариант.

Возможные случаи:

- ошибка при инициализации, без которой приложение не может работать;
- обнаружение невозможного состояния, свидетельствующего о серьёзной ошибке программирования;
- внутренние ситуации, которые по контракту функции не должны возникать.

Для ожидаемых проблем — отсутствующего файла, ошибки сети, неверного пользовательского ввода — обычно следует возвращать `error`.

**Главное:** `error` — для ошибок, которые код ожидаемо обрабатывает; `panic` — для критических или недопустимых состояний.

---

## 10. Как работает `recover()`? Где его нужно вызывать?

`recover()` позволяет перехватить панику, происходящую в той же горутине. Чтобы сработать, он должен быть вызван непосредственно внутри отложенной функции `defer`, выполняющейся во время раскрутки паники.

```
func safeRun() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Паника перехвачена:", r)
        }
    }()

    panic("something went wrong")
}
```

Здесь анонимная функция зарегистрирована через `defer`. При возникновении паники она выполняется, вызывает `recover()` и перехватывает её.

Если вызвать `recover()` просто в обычном коде, вне подходящего отложенного вызова, он не перехватит панику.

**Главное:** `recover()` работает только в правильном контексте — внутри отложенной функции той же горутины.

---

## 11. Может ли `recover()` поймать панику в другой горутине?

Нет. `recover()` работает только с паникой, происходящей в той же горутине.

```
go func() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Паника:", r)
        }
    }()

    panic("goroutine panic")
}()
```

Здесь паника перехватывается внутри той же горутины, где она возникла.

Если же `recover()` находится в другой горутине, он не сможет перехватить эту панику.

**Главное:** каждая горутина должна самостоятельно организовать перехват паники, если он необходим.

---

## 12. Что такое `defer`? Каков порядок выполнения нескольких `defer`?

`defer` откладывает вызов функции до момента выхода из окружающей функции. Отложенные вызовы выполняются в обратном порядке регистрации — **LIFO (Last In, First Out)**.

```
func main() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
}
```

Результат:

```
3
2
1
```

`defer` часто используют для освобождения ресурсов, закрытия файлов, разблокировки мьютексов и перехвата паник.

**Главное:** `defer` выполняется при выходе из функции, а несколько отложенных вызовов исполняются в обратном порядке.

---

## 13. Когда вычисляются аргументы функции, переданной в `defer`?

Аргументы вычисляются **в момент выполнения оператора `defer`**, а сам вызов функции откладывается до выхода из окружающей функции.

```
func main() {
    x := 10

    defer fmt.Println(x)

    x = 20
}
```

Результат:

```
10
```

Значение `x` было вычислено при регистрации `defer`.

Но если отложить вызов замыкания, оно может прочитать переменную позднее:

```
func main() {
    x := 10

    defer func() {
        fmt.Println(x)
    }()

    x = 20
}
```

Результат:

```
20
```

Второй пример выводит текущее значение переменной в момент выполнения отложенной функции.

**Главное:** аргументы обычного отложенного вызова вычисляются сразу, а замыкание может обратиться к переменным позже.

---

## 14. Как `defer` влияет на именованные возвращаемые значения?

Если функция использует именованные возвращаемые значения, отложенная функция может изменить их перед фактическим возвратом результата.

```
func example() (result int) {
    defer func() {
        result++
    }()

    return 10
}
```

Результат:

```
11
```

При выполнении `return 10` значение присваивается именованной переменной `result`, затем выполняется `defer`, и только после этого функция возвращает результат.

**Главное:** `defer` может изменить именованные возвращаемые значения до того, как они будут переданы вызывающему коду.

---

## 15. Какова стоимость вызова `defer`?

`defer` имеет некоторую стоимость: runtime должен обеспечить выполнение отложенного вызова при выходе из функции.

Современный компилятор Go умеет оптимизировать многие случаи использования `defer`, поэтому его стоимость зависит от контекста и версии компилятора.

Обычно `defer` стоит применять ради ясности и надёжности кода. Оптимизировать его использование имеет смысл только при подтверждённой проблеме производительности — например, по результатам профилирования.

**Главное:** `defer` не бесплатен, но обычно достаточно эффективен; не стоит отказываться от него без измерений.

---

## 16. Что будет, если вызвать `panic` внутри блока `defer`?

Если отложенная функция вызывает `panic`, начинается новая паника.

Если при этом уже обрабатывается другая паника, новая паника может заменить её как основную распространяющуюся панику. Если новая паника не будет перехвачена, процесс завершится аварийно.

```
func example() {
    defer func() {
        panic("panic in defer")
    }()

    panic("original panic")
}
```

В этом примере во время обработки исходной паники отложенная функция вызывает ещё одну панику.

**Главное:** `panic` внутри `defer` может усложнить обработку исходной паники и привести к аварийному завершению процесса.

---

## 17. Что произойдёт, если вызвать `recover()`, но паники не было?

Вне активной обработки паники `recover()` возвращает `nil`.

```
func main() {
    defer func() {
        fmt.Println(recover())
    }()
}
```

Результат:

```
<nil>
```

Сам по себе вызов `recover()` без активной паники не приводит к ошибке.

**Главное:** `recover()` возвращает значение паники, если успешно перехватывает её; иначе возвращает `nil`.
