# **`map`**

## 1. Как устроена `map` до Go 1.24?

В старой версии использовалась хеш-таблица на основе бакетов *(bucket-based hash table)*.

- `hmap` хранит метаданные: количество элементов, параметры бакетов и указатели на их массив.    
- Каждый основной бакет содержит до 8 записей.
- Хеш ключа определяет бакет, в котором нужно искать запись.
- Если бакет переполняется, используются дополнительные `overflow buckets`.
- При росте `map` записи постепенно переносятся в новый массив бакетов.

Главная идея: сначала быстро определить нужный бакет по хешу, а затем искать ключ внутри него.

## 2. Как выбирается бакет? Роль LOB и HOB

Хеш ключ условно делится на младшие и старшие биты:
- **LOB *(Low Order Bits)*** — младшие биты, определяют индекс бакета.
- **HOB *(High Order Bits)*** — старшие биты, используются для предварительной проверки ключей внутри бакета.

В старой реализации количество основных бакетов связано с параметром \(B\): их число равно \(2^B\). Индекс можно вычислить с помощью маски из \(B\) младших битов хеша.

Это позволяет быстро определить, где искать ключ, не перебирая все бакеты.

## 3. Что такое `tophash`?

`tophash` — небольшая часть хеша, хранящаяся в метаданных слота бакета.

**Она нужна для быстрой предварительной фильтрации:**
1. Runtime сравнивает `tophash` слота с соответствующей частью хеша искомого ключа.
2. Если значения не совпадают, полноценное сравнение ключей не требуется.
3. Если совпадают, runtime проверяет сами ключи.

Совпадение `tophash` не гарантирует совпадение ключей. Это только способ сократить число дорогих сравнений.

## 4. Как обрабатываются коллизии в старой реализации?

Если несколько ключей попадают в один бакет, runtime сначала ищет свободный слот в основном бакете. Если все 8 слотов заняты, создаётся или используется связанный с ним overflow bucket.

Поиск проходит по основному бакету, а затем при необходимости — по цепочке дополнительных бакетов. Чем длиннее цепочка, тем больше сравнений и тем медленнее операция.

## 5. Как работает инкрементальная реаллокация (`evacuation`)?

Когда старая `map` должна вырасти, runtime выделяет новый массив бакетов, обычно вдвое большего размера.

Данные переносятся постепенно:

1. Старая таблица остаётся доступной, пока перенос не завершён.
    
2. При операциях записи и удаления runtime выполняет часть работы по переносу бакетов.
    
3. Во время роста поиск может учитывать старые и новые бакеты.
    
4. После переноса всех данных старая таблица освобождается.
    

Так runtime избегает переноса всей таблицы за одну операцию, хотя отдельные операции во время роста могут быть дороже обычных.

## 6. Каков load factor и когда начинается рост?

Load factor — среднее количество элементов на один основной бакет.

В реализации до Go 1.24 порог роста составлял примерно 6,5 элемента на бакет в среднем. Это компромисс между использованием памяти и количеством переполненных бакетов.

Рост мог начинаться и при чрезмерном количестве overflow buckets, даже если обычный порог заполнения не был превышен.

Важно: `6,5` — деталь старой реализации, а не универсальное правило для любой версии Go.

## 7. Что такое Swiss Tables и почему Go перешёл на них в Go 1.24+?

Swiss Tables — семейство хеш-таблиц, использующих группы слотов и компактные метаданные для эффективного поиска и обработки коллизий.

Начиная с Go 1.24 встроенная `map` получила новую реализацию на основе Swiss Tables. Основные цели — улучшить производительность и уменьшить накладные расходы. В официальных материалах Go отмечено снижение CPU overhead на 2–3% в среднем по набору тестов, хотя результат зависит от нагрузки.

Основные отличия от старой реализации:
- вместо бакетов с цепочками переполнения используются группы слотов и открытая адресация;
- метаданные группы помогают быстро отсеивать неподходящие слоты;
- большая `map` может состоять из нескольких таблиц, выбранных через directory;
- механизм роста отличается от старой схемы с `overflow buckets` и evacuation.

## 8. Как устроена группа (`Group`) в новой реализации?

В реализации Swiss Tables одна группа содержит 8 слотов и 8-байтовое контрольное слово.

- Слоты хранят пары «ключ — значение».
- Control word содержит по одному управляющему байту на слот.
- Управляющий байт показывает, свободен ли слот, удалён ли элемент или занят. Для занятого слота он также хранит 7 бит хеша — `H2`.

При поиске runtime сравнивает `H2` сразу со значениями управляющих байтов группы, чтобы выбрать несколько возможных кандидатов, и затем сравнивает сами ключи.

## 9. Чем отличаются H1 и H2?

В реализации Swiss Tables Go 1.24+ хеш условно разделён на две части:

- H1 — старшие 57 бит хеша. Используются для выбора таблицы и поиска группы в ней.
    
- H2 — младшие 7 бит хеша. Сохраняются в метаданных занятых слотов и позволяют быстро отбирать кандидатов на совпадение.
    

Запомнить: H1 помогает найти нужную область таблицы, H2 — быстро отфильтровать слоты внутри группы. Совпадение H2 ещё не означает совпадения ключей.

## 10. Почему `map` не потокобезопасна?

Обычная Go `map` не синхронизирует конкурентные операции автоматически. Если несколько горутин одновременно обращаются к одной карте и хотя бы одна изменяет её, без синхронизации возникает гонка данных.

Runtime содержит проверки некоторых конфликтующих операций и может завершить программу с ошибками вроде:

- `concurrent map read and map write`;
- `concurrent map writes`;
- `concurrent map iteration and map write`.

Однако это не полноценный детектор всех гонок: отсутствие такого сообщения не означает, что доступ безопасен.

Для защиты используют `sync.Mutex`, `sync.RWMutex`, отдельную синхронизацию или `sync.Map` — когда он подходит по сценарию. Детектор гонок можно запустить через `go test -race`.

## 11. Почему итерация по `map` неупорядоченная?

Спецификация Go не гарантирует порядок обхода `map`. Нельзя рассчитывать на порядок добавления ключей или на сортировку.

В старой реализации runtime выбирал случайную начальную позицию обхода — бакет и слот. Поэтому порядок мог различаться между итерациями. В новой реализации внутренний алгоритм другой, но гарантия языка остаётся той же: порядок обхода не определён.

## 12. Какие типы могут быть ключами `map`? Что такое `comparable`?

Тип ключа должен поддерживать операции ` == ` и ` != `. Это свойство называется comparable.

Подходящие типы:
- числа, `bool`, `string`;
- указатели и каналы;
- массивы, если их элементы сравнимы;
- структуры, если все их поля сравнимы;
- интерфейсные типы — с оговоркой ниже.

Срезы, функции и другие карты нельзя напрямую использовать в качестве ключей.

Нюанс: интерфейсный тип может быть ключом, но если в него поместить динамическое значение несравнимого типа, операция с ключом может вызвать panic.

## 13. Можно ли взять адрес элемента `&m[key]`?

Нет, выражение `&m[key]` не компилируется.

Причина: язык не гарантирует стабильный адрес элемента `map`. При изменении внутренней таблицы элемент может переместиться, поэтому нельзя безопасно предоставить указатель на его ячейку.

Если нужно изменять объект через указатель, можно хранить указатели в самой карте:

```
map[string]*User
```

Или прочитать значение, изменить его копию и записать обратно.

## 14. Что такое SIMD и как это работает?

**SIMD** *(Single Instruction, Multiple Data)* — подход, при котором одна машинная инструкция обрабатывает несколько значений одновременно.

Например, вместо последовательного сравнения нескольких байтов процессор может сравнить сразу целый вектор байтов и вернуть маску совпадений.

Это полезно для хеш-таблиц: управляющие байты группы можно сравнить с `H2` сразу для нескольких слотов, быстро определив кандидатов.

Важный нюанс: Swiss Tables используют групповые метаданные и эффективные операции сравнения, но не следует утверждать, что каждая операция Go `map` обязательно выполняется отдельной SIMD-инструкцией. Конкретная реализация зависит от runtime, компилятора и архитектуры процессора.

## 15. Как очистить `map` через `clear` и чем это отличается от пересоздания?

Начиная с Go 1.21 можно удалить все элементы карты встроенной функцией `clear`:

```
clear(m)
```

После этого карта остаётся существующей, но не содержит элементов.

Другой вариант — создать новую карту:

```
m = make(map[string]int)
```

Разница:

- `clear(m)` очищает существующую карту; все переменные, ссылающиеся на эту же карту, увидят её пустой.
- `m = make(map[string]int)` присваивает переменной ссылку на новую карту. Другие переменные, указывающие на старую карту, продолжат видеть старую карту с её содержимым.
- `clear` не гарантирует немедленного возврата всей ранее занятой памяти операционной системе.

Если важна повторная очистка одной общей карты, обычно используют `clear`. Если требуется отделить текущую переменную от старой карты, можно создать новую.

# Массивы и слайсы

## 1. Из каких полей состоит `SliceHeader`?

**Внутреннее представление слайса состоит из трёх компонентов:**
- **Data** — указатель на базовый массив, где хранятся элементы.
- **Len** — количество элементов, доступных через слайс.
- **Cap** — количество элементов от начала слайса до конца доступной области базового массива.

Условная структура:
```
type SliceHeader struct {
    Data uintptr
    Len  int
    Cap  int
}
```

Это упрощённое представление. `reflect.SliceHeader` существует в стандартной библиотеке, но для обычной работы со слайсами его использовать не следует.

**Главное:** слайс — это дескриптор, который ссылается на базовый массив, а не сам массив.

## 2. В чём разница между передачей массива и слайса в функцию?

**Массив передаётся по значению:** функция получает копию всего массива. Изменение элементов копии не влияет на исходный массив.

**Слайс передаётся по значению:** копируется дескриптор слайса, но он продолжает ссылаться на тот же базовый массив. Поэтому изменение элементов через слайс внутри функции обычно видно вызывающему коду.

При этом изменение длины слайса внутри функции не изменяет длину слайса у вызывающего кода автоматически: для этого нужно вернуть новый слайс или передать указатель на переменную-слайс.

## 3. Что произойдёт, если изменить элемент слайса, созданного на базе другого слайса?

Если оба слайса ссылаются на один базовый массив, изменение общего элемента будет видно через оба слайса.

```
a := []int{10, 20, 30, 40}
b := a[1:3]

b[0] = 99

fmt.Println(a) // [10 99 30 40]
```

`b` использует тот же базовый массив, что и `a`. Он не создаёт копию элементов.

## 4. Как работает `append`? Как расширяется ёмкость?

`append` добавляет элементы в конец слайса и возвращает новый дескриптор слайса.

1. **Если `cap` достаточно, элементы записываются в свободную область базового массива.**
2. **Если ёмкости недостаточно, runtime выделяет новый, более вместительный массив.**
	>*В актуальных версиях Go алгоритм увеличения `cap` нового массива такой:*
	>	*- Если текущая **`cap` < 256**, алгоритм **удваивает** ёмкость;*
	>	*- Если текущая **`cap` ≥ 256**, рост коэффициента для `cap` нового массива становится плавным, постепенно приближаясь к **1,25** - то есть, `cap` нового массива **увеличивается примерно на `1/4`**, относительно текущего.*
3. **Элементы старого слайса копируются в новый массив.**
4. **Новые элементы добавляются, а возвращаемый слайс ссылается на новый массив.**

**Важно:** точный алгоритм роста ёмкости зависит от реализации Go и версии.

## 5. Почему `append` может привести к потере связи с исходным массивом?

Если текущей ёмкости недостаточно, `append` может выделить новый базовый массив. Возвращаемый слайс будет ссылаться на него, а исходный слайс продолжит ссылаться на старый массив.

Если ёмкости достаточно, новый массив обычно не выделяется, и оба слайса могут продолжать использовать один массив.

## 6. Как создать слайс с заранее известной ёмкостью и зачем это нужно?

Можно использовать `make`:
```
s := make([]int, 0, 1000)
```
- Здесь `len(s) == 0`, а `cap(s) == 1000`.

Если известно приблизительное количество элементов, предварительное выделение ёмкости может уменьшить количество реаллокаций и копирований при `append`.

Другой вариант — сразу задать длину:
```
s := make([]int, 1000)
```

В этом случае длина и ёмкость равны 1000, поэтому элементы можно заполнять по индексам без предварительного `append`.

## 7. Что такое memory leak в контексте слайсов?

Слайс может удерживать ссылку на большой базовый массив, даже если сам слайс содержит всего несколько элементов. Пока массив достижим через этот слайс, сборщик мусора не может освободить его память.

```
data := make([]byte, 10_000_000)
small := data[:10]

data = nil
// small всё ещё ссылается на большой базовый массив.
```

Если маленькому слайсу не требуется общий массив, можно скопировать нужные элементы:

```
smallCopy := append([]byte(nil), small...)
```

Теперь `smallCopy` использует отдельный массив, а большой массив можно будет собрать сборщику мусора, если на него больше нет ссылок.

## 8. Чем отличаются `nil`-слайс и пустой слайс?

**`nil`-слайс** не ссылается на базовый массив и имеет нулевые длину и ёмкость.

```
var a []int
fmt.Println(a == nil) // true
```

**Пустой слайс** имеет нулевую длину, но обычно создан как отдельный ненулевой дескриптор.

```
b := []int{}
fmt.Println(b == nil) // false
```

Оба слайса имеют `len == 0` и `cap == 0`. К обоим можно применять `append`.

Различие может быть важно при проверке на `nil`, сериализации и взаимодействии с API.

## 9. Можно ли использовать слайс как ключ `map`?

Нет. Тип ключа `map` должен быть сравнимым (`comparable`), а слайсы нельзя сравнивать между собой через ` == `, кроме сравнения с `nil`.

```
m := map[[]int]string{} // ошибка компиляции
```

Если нужно использовать последовательность элементов как ключ, можно преобразовать её в строку, если это корректно для задачи, или разработать другой сравнимый тип представления.

## 10. Как работает выражение `s[i:j:k]`?

Это **трёхиндексное срезание** (_full slice expression_).

```
s[i:j:k]
```

Результат имеет:
- длину `j - i`;
- ёмкость `k - i`.

При этом должны выполняться условия:
```
0 <= i <= j <= k <= cap(s)
```

Пример:
```
s := []int{10, 20, 30, 40, 50}
sub := s[1:3:4]

fmt.Println(len(sub)) // 2
fmt.Println(cap(sub)) // 3
```

Трёхиндексная форма позволяет ограничить ёмкость результирующего слайса. Это полезно, когда нужно не дать последующему `append` записать новые элементы в область исходного массива за установленной границей.

## 11. Когда массив лучше слайса?

Массив может быть удобнее, если:
- размер данных фиксирован и известен на этапе компиляции;
- требуется тип, включающий размер, например `[32]byte`;
- нужна самостоятельная копируемая последовательность фиксированной длины;
- размер массива должен участвовать в проверке типов.

Слайсы обычно удобнее для коллекций переменного размера и передачи последовательностей элементов в функции.

## 12. Как удалить элемент из середины слайса?

### С сохранением порядка

Сдвинуть элементы после удаляемого влево, затем уменьшить длину слайса:
```
s = append(s[:i], s[i+1:]...)
```

Сложность — `O(n)` в худшем случае, поскольку приходится сдвигать последующие элементы.

Если элементы содержат указатели или другие ссылки на объекты, после сдвига последний слот желательно обнулить перед сокращением длины, чтобы не удерживать ненужные объекты в памяти. Для современных версий Go это можно записать так:

```
copy(s[i:], s[i+1:])
s[len(s)-1] = 0
s = s[:len(s)-1]
```

Здесь `0` — нулевое значение элемента; для обобщённого кода с произвольным типом используют соответствующее нулевое значение.

### Без сохранения порядка

Заменить удаляемый элемент последним и сократить длину:

```
s[i] = s[len(s)-1]
s = s[:len(s)-1]
```

Это выполняется за `O(1)`, но меняет порядок элементов.

## 13. Что происходит с памятью при `s = s[:0]`?

```
s = s[:0]
```

Длина слайса становится равной нулю, но его ёмкость и ссылка на базовый массив сохраняются.

Это не очищает элементы массива и не освобождает выделенную память. Если в массиве остаются указатели на объекты, они могут продолжать удерживать эти объекты в памяти.

При повторном использовании буфера это полезно: можно заполнять слайс заново, не выделяя массив повторно.

## 14. Как работает `copy`? Что если целевой слайс меньше исходного?

`copy(dst, src)` копирует элементы из `src` в `dst` и возвращает количество скопированных элементов.

Копируется минимум из двух длин:

```
n = min(len(dst), len(src))
```

Пример:

```
src := []int{1, 2, 3, 4}
dst := make([]int, 2)

n := copy(dst, src)

fmt.Println(dst) // [1 2]
fmt.Println(n)   // 2
```

Если целевой слайс короче исходного, копируются только элементы, помещающиеся в `dst`. Функция не расширяет целевой слайс автоматически.

`copy` также корректно работает с перекрывающимися областями памяти.

## 15. Как работает выравнивание памяти для массивов разных типов?

**Выравнивание памяти** *(memory alignment)* — требование размещать данные по адресам, подходящим для их типа и архитектуры.

Массив состоит из последовательно расположенных элементов одного типа. Размер массива равен размеру элемента, умноженному на количество элементов:

```
sizeof([N]T) = N * sizeof(T)
```

При этом сам массив должен удовлетворять требованиям выравнивания своего типа. Выравнивание зависит от типа элемента и целевой архитектуры Go.

Например, массив `int64` обычно требует более строгого выравнивания, чем массив `byte`, но конкретные требования зависят от платформы.

В отличие от структур, где между полями может появляться padding, между элементами массива не вставляются дополнительные промежутки произвольно: элементы размещаются с шагом, равным размеру элемента.
