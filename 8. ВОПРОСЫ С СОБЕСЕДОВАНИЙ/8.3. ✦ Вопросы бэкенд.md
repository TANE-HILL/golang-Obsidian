# ✦ SQL и реляционные базы данных

## 1. Что такое реляционная база данных и чем она отличается от NoSQL?

**Реляционная база данных *(RDBMS)*** — база данных, в которой информация хранится в виде таблиц, состоящих из строк и столбцов. Таблицы могут быть связаны между собой через первичные и внешние ключи.

**Основные характеристики:**
- Таблицы — хранят данные определённой сущности.
- Строки (Rows) — отдельные записи.
- Столбцы (Columns) — атрибуты записей с определёнными типами данных.
- Primary Key (PK) — уникально идентифицирует запись.
- Foreign Key (FK) — связывает записи разных таблиц и обеспечивает ссылочную целостность.

**Пример:**
```
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100)
);

CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT REFERENCES users(id),
    amount DECIMAL(10, 2)
);
```

Здесь `orders.user_id` ссылается на `users.id`.

**Чем отличается NoSQL?**

**NoSQL** — общее название нереляционных подходов к хранению данных. В отличие от реляционных БД, они могут использовать другие модели организации информации.

**Основные виды:**
- **Document** — хранение документов, обычно в JSON-подобном формате (MongoDB).
- **Key-Value** — хранение пар «ключ — значение» (Redis).
- **Wide-Column** — хранение данных в широких колонках (Cassandra).
- **Graph** — хранение узлов и связей между ними (Neo4j).

| **Реляционные БД**           | **NoSQL**                                            |
| ---------------------------- | ---------------------------------------------------- |
| Табличная модель             | Разные модели хранения                               |
| Обычно строгая схема         | Часто гибкая схема                                   |
| SQL                          | Разные языки и API запросов                          |
| JOIN и связи между таблицами | Часто используют вложенные данные или денормализацию |
| Транзакции и ACID            | Поддержка транзакций зависит от СУБД                 |
| PostgreSQL, MySQL            | MongoDB, Redis, Cassandra                            |

**Когда использовать:**
- Реляционные БД — когда важны связи между сущностями, целостность данных и сложные запросы.
- NoSQL — когда модель данных, требования к масштабированию или характер нагрузки лучше соответствуют конкретному NoSQL-хранилищу.

**Главное:** NoSQL не означает отсутствие SQL или транзакций во всех случаях. Это альтернативные модели хранения данных, каждая из которых решает определённые задачи.

## 2. Объясните ACID-свойства транзакций.

**ACID** — набор свойств, гарантирующих надёжность транзакций в реляционных СУБД.

**Расшифровка:**
- **Atomicity *(Атомарность)*** — транзакция выполняется целиком или не выполняется вообще.
- **Consistency *(Согласованность)*** — транзакция переводит базу из одного корректного состояния в другое, сохраняя ограничения целостности.
- **Isolation *(Изолированность)*** — параллельные транзакции не должны некорректно влиять друг на друга.
- **Durability *(Долговечность)*** — после успешного `COMMIT` изменения сохраняются даже при сбое системы.

**Пример**

Представим перевод 1000 рублей между двумя счетами:
```
BEGIN;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

Если при выполнении второго `UPDATE` произойдёт ошибка, транзакцию можно отменить:

```
ROLLBACK;
```

**Как проявляются ACID:**
1. Atomicity — нельзя списать деньги с первого счёта, не зачислив их на второй.
2. Consistency — после операции должны соблюдаться ограничения, например баланс не должен становиться отрицательным, если это запрещено бизнес-правилами.
3. Isolation — параллельные переводы не должны приводить к некорректному изменению балансов.
4. Durability — после `COMMIT` результат должен сохраниться при перезапуске сервера.

Главное: ACID обеспечивает корректность транзакций даже при ошибках, сбоях и конкурентном выполнении запросов.

## 3. Что такое JOIN? Перечислите типы JOIN и ситуации, когда каждый из них используется.

JOIN — операция SQL, которая позволяет объединять строки из нескольких таблиц на основании условия связи между ними.

Чаще всего используется для объединения таблиц по первичному и внешнему ключам.

Рассмотрим две таблицы:

```
users
+----+-------+
| id | name  |
+----+-------+
| 1  | Alex  |
| 2  | Bob   |
| 3  | Kate  |
+----+-------+

orders
+----+---------+--------+
| id | user_id | amount |
+----+---------+--------+
| 1  | 1       | 500    |
| 2  | 1       | 700    |
| 3  | 2       | 300    |
+----+---------+--------+
```

**Основные виды JOIN**

1. INNER JOIN

Возвращает только строки, для которых найдено соответствие в обеих таблицах.

```
SELECT users.name, orders.amount
FROM users
INNER JOIN orders
    ON users.id = orders.user_id;
```

Результат:

- Alex — 500
    
- Alex — 700
    
- Bob — 300
    

Kate не попадёт в результат, поскольку у неё нет заказов.

Используется: когда нужны только записи, имеющие соответствие в обеих таблицах.

2. LEFT JOIN (LEFT OUTER JOIN)

Возвращает все строки из левой таблицы и соответствующие строки из правой. Если соответствия нет, значения правой таблицы будут `NULL`.

```
SELECT users.name, orders.amount
FROM users
LEFT JOIN orders
    ON users.id = orders.user_id;
```

В результате Kate тоже попадёт в выборку, но `orders.amount` будет `NULL`.

Используется: когда нужно получить все записи основной таблицы, даже если связанных записей нет.

Например, вывести всех пользователей, включая тех, кто ещё ничего не заказал.

3. RIGHT JOIN (RIGHT OUTER JOIN)

Работает аналогично `LEFT JOIN`, но сохраняет все строки правой таблицы.

```
SELECT users.name, orders.amount
FROM users
RIGHT JOIN orders
    ON users.id = orders.user_id;
```

Используется: когда необходимо сохранить все записи правой таблицы, даже если для них нет соответствий слева.

На практике часто заменяется перестановкой таблиц и использованием `LEFT JOIN`.

4. FULL OUTER JOIN

Возвращает все строки обеих таблиц:

- совпавшие строки объединяются;
    
- несовпавшие строки сохраняются;
    
- отсутствующие значения заполняются `NULL`.
    

```
SELECT users.name, orders.amount
FROM users
FULL OUTER JOIN orders
    ON users.id = orders.user_id;
```

Используется: когда необходимо получить полное объединение данных, включая записи без соответствий с обеих сторон.

5. CROSS JOIN

Возвращает декартово произведение двух таблиц: каждая строка первой таблицы объединяется с каждой строкой второй.

```
SELECT users.name, orders.amount
FROM users
CROSS JOIN orders;
```

Если в первой таблице 3 строки, а во второй 4, результат будет содержать 12 строк.

Используется: для генерации всех возможных комбинаций, например сочетаний товаров и размеров.

6. SELF JOIN

Это не отдельный оператор, а способ соединить таблицу саму с собой.

```
SELECT
    e.name AS employee,
    m.name AS manager
FROM employees e
LEFT JOIN employees m
    ON e.manager_id = m.id;
```

Используется: когда записи одной таблицы связаны друг с другом. Например, сотрудник и его руководитель.

Главное: выбор JOIN зависит от того, какие записи необходимо сохранить: только совпавшие, все записи одной таблицы или все записи обеих таблиц.

## 4. Как работают индексы в СУБД и когда их стоит применять?

Индекс (Index) — дополнительная структура данных, которая ускоряет поиск записей в таблице без необходимости последовательно проверять каждую строку.

Без индекса СУБД может использовать Sequential Scan — последовательное чтение всей таблицы.

С индексом СУБД получает возможность быстрее находить нужные записи, используя специальную структуру поиска.

**Как работает индекс?**

Рассмотрим таблицу:

```
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email VARCHAR(255),
    name VARCHAR(100)
);
```

Создадим индекс по `email`:

```
CREATE INDEX idx_users_email
ON users(email);
```

Теперь запрос:

```
SELECT *
FROM users
WHERE email = 'test@example.com';
```

СУБД может использовать индекс, чтобы найти подходящую запись, не сканируя всю таблицу.

**Основные преимущества индексов**

- Ускоряют поиск по `WHERE`.
    
- Ускоряют соединение таблиц через `JOIN`.
    
- Могут ускорять сортировку через `ORDER BY`.
    
- Помогают при группировке `GROUP BY`.
    
- Позволяют обеспечить уникальность через `UNIQUE INDEX`.
    

**Недостатки индексов**

- Занимают дополнительное место на диске и в памяти.
    
- Замедляют `INSERT`, `UPDATE` и `DELETE`, поскольку индекс тоже необходимо обновлять.
    
- Требуют обслуживания.
    
- Избыточное количество индексов увеличивает нагрузку на СУБД.
    

**Когда стоит создавать индекс?**

Обычно индекс полезен, если:

- столбец часто используется в условиях `WHERE`;
    
- столбец участвует в `JOIN`;
    
- часто выполняется сортировка по этому столбцу;
    
- требуется обеспечить уникальность значений;
    
- таблица достаточно большая, а запрос возвращает небольшую часть её записей.
    

При этом индекс не всегда ускоряет запрос. Если необходимо прочитать большую часть таблицы, последовательное чтение может оказаться дешевле.

Главное: индекс ускоряет чтение данных за счёт дополнительной структуры, но требует памяти и увеличивает стоимость операций записи. Создавать индексы следует исходя из реальных запросов и анализа плана выполнения.

## 5. Расскажи про B-Tree index, какие ещё знаешь?

B-Tree (Balanced Tree) — сбалансированная древовидная структура данных, которая широко используется для реализации индексов в реляционных СУБД.

В PostgreSQL стандартный тип индекса — B-Tree.

**Как устроен B-Tree?**

Индекс представляет собой дерево, состоящее из страниц (узлов).

- Root Page — корневая страница, с которой начинается поиск.
    
- Internal Pages — промежуточные страницы, содержащие ключи и ссылки на дочерние страницы.
    
- Leaf Pages — листовые страницы, содержащие индексные ключи и ссылки на соответствующие записи таблицы.
    

Ключи внутри страниц упорядочены.

При поиске СУБД:

1. Начинает с корневой страницы.
    
2. Сравнивает искомое значение с ключами.
    
3. Переходит в подходящую дочернюю страницу.
    
4. Продолжает поиск до листовой страницы.
    
5. Получает ссылку на нужную запись.
    

Благодаря сбалансированности дерева поиск выполняется за логарифмическое время — приблизительно `O(log n)`.

**Для каких операций подходит B-Tree?**

- ` = ` — поиск по точному совпадению.
    
- `>` и `<` — сравнение.
    
- `>=` и `<=` — диапазонный поиск.
    
- `BETWEEN` — поиск по диапазону.
    
- `ORDER BY` — сортировка.
    
- `LIKE 'abc%'` — поиск по префиксу при подходящей локали и операторном классе.
    

**Какие ещё бывают индексы?**

1. Hash Index

Использует хеш-таблицу для поиска по точному совпадению.

```
CREATE INDEX idx_users_email_hash
ON users USING HASH(email);
```

Особенности:

- подходит для операций равенства (`=`);
    
- не подходит для диапазонного поиска;
    
- не обеспечивает сортировку значений.
    

В PostgreSQL Hash Index не является универсальной заменой B-Tree.

2. GIN (Generalized Inverted Index)

Инвертированный индекс, который хранит информацию о том, в каких записях встречаются определённые элементы.

```
CREATE INDEX idx_posts_tags
ON posts USING GIN(tags);
```

Особенности:

- подходит для массивов;
    
- используется для `JSONB`;
    
- применяется для полнотекстового поиска;
    
- эффективен, когда нужно искать отдельные элементы внутри составных значений.
    

3. GiST (Generalized Search Tree)

Обобщённая древовидная структура, поддерживающая различные способы поиска.

Используется для:

- геометрических объектов;
    
- географических данных;
    
- диапазонов;
    
- поиска по пространственной близости.
    

Например, PostgreSQL вместе с PostGIS использует GiST для пространственных индексов.

4. BRIN (Block Range Index)

Хранит агрегированную информацию о диапазонах физических блоков таблицы, а не отдельную запись для каждой строки.

```
CREATE INDEX idx_events_created_at
ON events USING BRIN(created_at);
```

Особенности:

- занимает мало места;
    
- хорошо подходит для очень больших таблиц;
    
- эффективен, если физический порядок строк коррелирует со значениями индексируемого столбца.
    

Например, таблица событий, в которую записи добавляются преимущественно в хронологическом порядке.

5. Composite Index (Составной индекс)

Индекс, построенный сразу по нескольким столбцам.

```
CREATE INDEX idx_users_status_created
ON users(status, created_at);
```

Особенности:

- позволяет эффективно искать по комбинации столбцов;
    
- порядок столбцов имеет значение;
    
- в B-Tree важен принцип левого префикса.
    

Например, такой индекс подходит для:

```
WHERE status = 'active'
```

И для:

```
WHERE status = 'active'
  AND created_at > '2026-01-01'
```

Но может быть менее полезен для запроса только по `created_at`, поскольку этот столбец не является первым в индексе.

Главное: B-Tree — универсальный индекс для большинства операций поиска и сортировки. GIN подходит для поиска внутри составных данных, GiST — для специализированного поиска, BRIN — для больших таблиц с физически упорядоченными данными, Hash — для точного поиска по равенству.

## 6. Чем отличаются кластеризованные и некластеризованные индексы?

**Кластеризованный индекс *(Clustered Index)*** — индекс, определяющий физический порядок хранения строк таблицы или их расположение в индексной структуре.

**Некластеризованный индекс *(Non-Clustered Index)*** — отдельная структура данных, которая хранит индексные ключи и ссылки на соответствующие записи таблицы.

**Кластеризованный индекс**

В некоторых СУБД, например MySQL InnoDB, данные таблицы физически организованы вокруг первичного ключа.

- Листовые страницы кластеризованного индекса содержат сами строки таблицы.
    
- Поиск по первичному ключу позволяет получить запись непосредственно из индекса.
    
- Вторичные индексы содержат значения индексируемых столбцов и значение первичного ключа для поиска строки.
    

В MySQL InnoDB кластеризованным индексом обычно является `PRIMARY KEY`.

**Некластеризованный индекс**

Хранится отдельно от основного порядка организации данных.

- Содержит индексируемые значения.
    
- Содержит ссылку на соответствующую запись.
    
- Для получения остальных столбцов может потребоваться дополнительное обращение к таблице или кластеризованному индексу.
    

**Сравнение**

|Кластеризованный|Некластеризованный|
|---|---|
|Определяет организацию хранения строк|Отдельная структура|
|Листья содержат данные строк|Листья содержат ключи и ссылки|
|Обычно один на таблицу|Может быть несколько|
|Эффективен для поиска и диапазонов по ключу|Эффективен для поиска по другим столбцам|

Важный нюанс: реализация зависит от СУБД.

- В MySQL InnoDB таблица организована вокруг кластеризованного индекса.
    
- В SQL Server можно создать один кластеризованный индекс и несколько некластеризованных.
    
- В PostgreSQL обычный индекс не является кластеризованным в том же смысле. Команда `CLUSTER` физически перестраивает таблицу в порядке индекса, но последующие изменения не поддерживают этот порядок автоматически.
    

Главное: кластеризованный индекс определяет организацию хранения данных, а некластеризованный представляет собой дополнительную структуру для быстрого поиска.

## 7. Что такое нормализация данных? Приведите примеры нормальных форм (1NF, 2NF, 3NF).

**Нормализация** — процесс организации структуры базы данных, направленный на уменьшение дублирования информации и предотвращение аномалий при добавлении, изменении и удалении данных.

**Основные цели:**
- уменьшить избыточность данных;
- обеспечить целостность;
- избежать противоречий;
- упростить изменение информации.

**1NF *(Первая нормальная форма)***

Таблица находится в первой нормальной форме, если:
- каждая ячейка содержит одно атомарное значение;
- отсутствуют повторяющиеся группы столбцов;
- каждая строка может быть однозначно идентифицирована.

**Неправильная структура:**

|id|name|phones|
|---|---|---|
|1|Alex|111, 222|
|2|Bob|333, 444|

В столбце `phones` хранится несколько значений.

Более правильная структура:

|id|name|
|---|---|
|1|Alex|
|2|Bob|

Отдельная таблица:

|user_id|phone|
|---|---|
|1|111|
|1|222|
|2|333|
|2|444|

Теперь каждое значение атомарно.

**2NF (Вторая нормальная форма)**

Таблица находится во второй нормальной форме, если:

- она соответствует 1NF;
    
- каждый неключевой атрибут полностью зависит от всего составного ключа, а не только от его части.
    

Рассмотрим таблицу:

|student_id|course_id|student_name|course_name|
|---|---|---|---|
|1|10|Alex|Go|
|1|20|Alex|SQL|
|2|10|Bob|Go|

Составной первичный ключ — `(student_id, course_id)`.

Проблема:

- `student_name` зависит только от `student_id`;
    
- `course_name` зависит только от `course_id`.
    

Возникает частичная функциональная зависимость.

Решение — разделить таблицу:

Students

|student_id|student_name|
|---|---|
|1|Alex|
|2|Bob|

Courses

|course_id|course_name|
|---|---|
|10|Go|
|20|SQL|

Enrollments

|student_id|course_id|
|---|---|
|1|10|
|1|20|
|2|10|

Теперь неключевые атрибуты зависят от соответствующих ключей целиком.

**3NF *(Третья нормальная форма)***

**Таблица находится в третьей нормальной форме, если:**
- она соответствует 2NF;
- отсутствуют транзитивные зависимости неключевых атрибутов от ключа.

Рассмотрим таблицу:

|employee_id|department_id|department_name|
|---|---|---|
|1|10|IT|
|2|10|IT|
|3|20|HR|

**Здесь:**
- `employee_id` определяет `department_id`;
- `department_id` определяет `department_name`.

**Получается транзитивная зависимость:**
`employee_id → department_id → department_name`

Решение — вынести информацию об отделах в отдельную таблицу.

Employees

|employee_id|department_id|
|---|---|
|1|10|
|2|10|
|3|20|

Departments

|department_id|department_name|
|---|---|
|10|IT|
|20|HR|

Теперь информация об отделе хранится в одном месте.

Главное: нормализация позволяет избежать избыточности и аномалий данных. 1NF требует атомарности значений, 2NF устраняет частичные зависимости, 3NF — транзитивные зависимости неключевых атрибутов.

## 8. Что делает оператор GROUP BY и когда его применять?

GROUP BY — оператор SQL, который группирует строки по значениям одного или нескольких столбцов, позволяя выполнять агрегатные операции над каждой группой.

Чаще всего используется вместе с агрегатными функциями:

- `COUNT()` — количество строк;
    
- `SUM()` — сумма;
    
- `AVG()` — среднее значение;
    
- `MIN()` — минимальное значение;
    
- `MAX()` — максимальное значение.
    

**Пример**

Есть таблица заказов:

|id|user_id|amount|
|---|---|---|
|1|10|500|
|2|10|700|
|3|20|300|
|4|20|200|

Нужно посчитать общую сумму заказов каждого пользователя:

```
SELECT
    user_id,
    SUM(amount) AS total_amount
FROM orders
GROUP BY user_id;
```

Результат:

|user_id|total_amount|
|---|---|
|10|1200|
|20|500|

**Как работает GROUP BY?**

1. СУБД получает строки из таблицы.
    
2. Объединяет строки с одинаковыми значениями указанных столбцов.
    
3. Вычисляет агрегатные функции для каждой группы.
    
4. Возвращает результат по одной строке на каждую группу.
    

**GROUP BY по нескольким столбцам**

```
SELECT
    user_id,
    status,
    COUNT(*) AS orders_count
FROM orders
GROUP BY user_id, status;
```

В этом случае группировка выполняется по комбинации `user_id` и `status`.

Важное правило: в стандартном SQL столбцы в `SELECT`, которые не используются внутри агрегатных функций, должны присутствовать в `GROUP BY` (если СУБД не допускает их на основании функциональной зависимости).

Главное: `GROUP BY` применяется, когда необходимо получить агрегированную информацию по группам записей, например количество заказов или общую выручку по каждому пользователю.

## 9. Как работают оконные функции (Window Functions)?

Оконные функции (Window Functions) — функции SQL, которые выполняют вычисления над набором строк, связанным с текущей строкой, но при этом не объединяют строки в одну запись, как `GROUP BY`.

Оконные функции позволяют анализировать данные, сохраняя исходное количество строк.

**Синтаксис**

```
function_name() OVER (
    PARTITION BY column
    ORDER BY column
)
```

Основные компоненты:

- PARTITION BY — разделяет строки на независимые группы (окна).
    
- ORDER BY — определяет порядок строк внутри окна.
    
- Frame — задаёт конкретный диапазон строк относительно текущей строки.
    

**Пример: ROW_NUMBER()**

Допустим, нужно пронумеровать заказы каждого пользователя:

```
SELECT
    user_id,
    amount,
    ROW_NUMBER() OVER (
        PARTITION BY user_id
        ORDER BY amount DESC
    ) AS row_num
FROM orders;
```

Результат:

|user_id|amount|row_num|
|---|---|---|
|10|700|1|
|10|500|2|
|20|300|1|
|20|200|2|

Нумерация начинается заново для каждого пользователя.

**Основные оконные функции**

1. ROW_NUMBER()

Присваивает каждой строке уникальный порядковый номер внутри окна.

2. RANK()

Присваивает ранг строкам. При одинаковых значениях ранги совпадают, после чего образуются пропуски.

Например: `1, 1, 3`.

3. DENSE_RANK()

Работает аналогично `RANK()`, но не оставляет пропусков.

Например: `1, 1, 2`.

4. LAG()

Позволяет получить значение из предыдущей строки окна.

```
SELECT
    created_at,
    amount,
    LAG(amount) OVER (
        ORDER BY created_at
    ) AS previous_amount
FROM orders;
```

5. LEAD()

Позволяет получить значение из следующей строки окна.

6. SUM() OVER()

Позволяет рассчитывать накопительные суммы и другие агрегаты без объединения строк.

```
SELECT
    user_id,
    amount,
    SUM(amount) OVER (
        PARTITION BY user_id
        ORDER BY created_at
    ) AS running_total
FROM orders;
```

**Чем оконные функции отличаются от GROUP BY?**

|GROUP BY|Window Functions|
|---|---|
|Объединяет строки в группы|Сохраняет исходные строки|
|Обычно одна строка на группу|Результат для каждой строки|
|Используется для агрегации|Используется для аналитических вычислений|
|Не сохраняет отдельные строки группы|Позволяет анализировать соседние строки|

Главное: оконные функции позволяют выполнять аналитические вычисления внутри групп, сохраняя каждую исходную запись. Особенно полезны для рейтингов, накопительных сумм, сравнения текущих и предыдущих значений.

## 10. Что такое транзакция, и каковы уровни изоляции?

Транзакция (Transaction) — последовательность SQL-операций, которая выполняется как единая логическая операция.

Транзакция начинается командой `BEGIN` и завершается:

- `COMMIT` — подтверждение изменений;
    
- `ROLLBACK` — отмена изменений.
    

Пример:

```
BEGIN;

UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

UPDATE accounts
SET balance = balance + 500
WHERE id = 2;

COMMIT;
```

Если одна из операций завершится ошибкой, можно выполнить `ROLLBACK`, чтобы отменить изменения транзакции.

**Уровни изоляции транзакций**

Isolation Level определяет, насколько изменения одной транзакции видны другим параллельно выполняющимся транзакциям.

Основные уровни:

1. READ UNCOMMITTED

Транзакция может читать изменения других транзакций, которые ещё не были подтверждены через `COMMIT`.

Возможна проблема Dirty Read — чтение неподтверждённых данных.

2. READ COMMITTED

Транзакция видит только подтверждённые изменения других транзакций.

При этом два одинаковых `SELECT` внутри одной транзакции могут вернуть разные результаты, если другая транзакция успела изменить и подтвердить данные.

Возможна проблема Non-Repeatable Read.

3. REPEATABLE READ

Повторное чтение одной и той же строки в рамках транзакции возвращает согласованное значение в соответствии с используемой моделью изоляции СУБД.

В классической модели предотвращает Dirty Read и Non-Repeatable Read.

4. SERIALIZABLE

Самый строгий уровень изоляции.

Результат параллельного выполнения транзакций должен быть эквивалентен некоторому последовательному порядку их выполнения.

Может приводить к дополнительным блокировкам или ошибкам сериализации, после которых транзакцию необходимо повторить.

**Основные проблемы конкурентного доступа**

- Dirty Read — чтение неподтверждённых изменений другой транзакции.
    
- Non-Repeatable Read — повторное чтение одной строки возвращает другое значение.
    
- Phantom Read — повторный запрос по условию возвращает другое множество строк из-за появления или исчезновения подходящих записей.
    
- Lost Update — обновление одной транзакции перезаписывается другой транзакцией.
    

|Уровень|Dirty Read|Non-Repeatable Read|Phantom Read|
|---|---|---|---|
|READ UNCOMMITTED|Возможен|Возможен|Возможен|
|READ COMMITTED|Нет|Возможен|Возможен|
|REPEATABLE READ|Нет|Нет|Возможен в классической модели|
|SERIALIZABLE|Нет|Нет|Нет|

Важный нюанс: реальные гарантии зависят от СУБД. Например, PostgreSQL реализует `READ UNCOMMITTED` как `READ COMMITTED`, а его `REPEATABLE READ` использует Snapshot Isolation и предотвращает фантомные чтения.

Главное: уровни изоляции определяют баланс между согласованностью данных и параллелизмом выполнения транзакций. Чем строже изоляция, тем больше гарантий, но тем выше вероятность конфликтов и необходимости повторять транзакции.

## 11. Объясните разницу между HAVING и WHERE.

**WHERE** и **HAVING** используются для фильтрации данных, но применяются на разных этапах обработки запроса.

- **WHERE** — фильтрует отдельные строки до группировки.
- **HAVING** — фильтрует уже сформированные группы после **`GROUP BY`**.

**Пример**

Нужно получить пользователей, у которых сумма заказов превышает 1000 рублей, учитывая только заказы дороже 100 рублей.

```
SELECT
    user_id,
    SUM(amount) AS total_amount
FROM orders
WHERE amount > 100
GROUP BY user_id
HAVING SUM(amount) > 1000;
```

Последовательность:

1. `WHERE` исключает заказы стоимостью 100 рублей и меньше.
    
2. `GROUP BY` группирует оставшиеся заказы по пользователям.
    
3. `SUM()` рассчитывает сумму заказов каждой группы.
    
4. `HAVING` оставляет только группы с суммой больше 1000.
    

**Основные отличия**

|WHERE|HAVING|
|---|---|
|Фильтрует строки|Фильтрует группы|
|До GROUP BY|После GROUP BY|
|Обычно не использует агрегатные функции напрямую|Может использовать агрегатные функции|
|Может уменьшить объём данных до группировки|Фильтрует уже сформированные группы|

Главное: `WHERE` используется для предварительной фильтрации строк, а `HAVING` — для фильтрации результатов группировки.

## 12. Что такое CTE и почему он полезен?

**CTE *(Common Table Expression)*** — временный именованный результат запроса, который объявляется с помощью `WITH` и используется внутри основного SQL-запроса.

**CTE** позволяет разбивать сложные запросы на логические части, повышая читаемость и упрощая поддержку SQL.

**Пример**

Допустим, необходимо найти пользователей, сумма заказов которых превышает 1000 рублей.

**Без CTE:**
```
SELECT user_id, total_amount
FROM (
    SELECT
        user_id,
        SUM(amount) AS total_amount
    FROM orders
    GROUP BY user_id
) AS user_totals
WHERE total_amount > 1000;
```

**С использованием CTE:**
```
WITH user_totals AS (
    SELECT
        user_id,
        SUM(amount) AS total_amount
    FROM orders
    GROUP BY user_id
)
SELECT *
FROM user_totals
WHERE total_amount > 1000;
```

**Виды CTE**

1. Обычный CTE

Используется для выделения промежуточной логики запроса.

2. Рекурсивный CTE

Позволяет выполнять запросы, которые обращаются к результатам предыдущей итерации.

Используется для:

- обхода деревьев;
    
- построения иерархий;
    
- поиска всех потомков определённого узла;
    
- работы с графоподобными структурами.
    

Пример:

```
WITH RECURSIVE numbers AS (
    SELECT 1 AS n

    UNION ALL

    SELECT n + 1
    FROM numbers
    WHERE n < 5
)
SELECT * FROM numbers;
```

Результат: `1, 2, 3, 4, 5`.

**Преимущества CTE**

- Улучшает читаемость сложных запросов.
    
- Позволяет повторно обращаться к именованному результату.
    
- Упрощает разделение сложной логики на этапы.
    
- Поддерживает рекурсивные запросы.
    

Важный нюанс: CTE не обязательно ускоряет запрос. В PostgreSQL начиная с версии 12 обычные CTE могут встраиваться в основной запрос (inlining), если оптимизатор считает это целесообразным. Также поддерживается `MATERIALIZED`, позволяющий принудительно материализовать результат.

Главное: CTE — инструмент структурирования SQL-запросов, а не гарантированная оптимизация производительности.

## 13. Как оценить и оптимизировать производительность SQL-запроса?

Оптимизация SQL-запросов — процесс уменьшения времени выполнения запросов и потребления ресурсов СУБД при сохранении корректности результата.

Основной инструмент анализа — `EXPLAIN ANALYZE`.

**Основные этапы оптимизации**

1. **Изучить план выполнения**
```
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE user_id = 100;
```
Позволяет увидеть:
- какие операции выполняет СУБД;
- используются ли индексы;
- сколько строк обрабатывается;
- сколько времени занимает выполнение;
- сколько раз выполняются отдельные узлы плана.

2. **Проверить использование индексов**

Если запрос часто фильтрует данные по определённому столбцу, стоит проверить необходимость индекса.

```
CREATE INDEX idx_orders_user_id
ON orders(user_id);
```

При этом необходимо убедиться, что индекс действительно улучшает план выполнения.

3. **Не использовать `SELECT *`**

Вместо получения всех столбцов выбирать только необходимые:

```
SELECT id, amount, created_at
FROM orders;
```

Это уменьшает объём передаваемых данных и может позволить использовать покрывающий индекс.

4. **Оптимизировать JOIN**

- Проверить условия соединения.
- Убедиться, что подходящие столбцы индексированы.
- Избегать соединения больших таблиц без необходимости.
- Проверять количество строк, получаемых на каждом этапе.

4. **Сократить количество обрабатываемых строк**

Использовать `WHERE` для фильтрации данных до группировки и других дорогостоящих операций.

6. **Проверить сортировки и группировки**

Операции `ORDER BY`, `GROUP BY`, `DISTINCT` могут требовать дополнительной памяти и сортировки.

При необходимости можно рассмотреть индексы, соответствующие условиям сортировки.

7. **Проверить статистику**

Оптимизатор использует статистику таблиц для выбора плана выполнения.

В PostgreSQL для обновления статистики используется:
```
ANALYZE orders;
```

8. **Проверить блокировки и ожидания**

Запрос может выполняться медленно не из-за вычислений, а потому что ожидает освобождения блокировки.

**Дополнительные показатели**

- Execution Time — фактическое время выполнения запроса.
    
- Planning Time — время построения плана.
    
- Buffers — информация о чтении и использовании страниц.
    
- Rows — количество обработанных строк.
    
- Loops — количество повторных выполнений узла плана.
    

Главное: оптимизация начинается не с добавления индексов, а с измерения. Сначала нужно определить узкое место через план выполнения, затем изменить запрос, индексы или структуру данных и повторно измерить результат.

## 14. Что такое deadlock и как его избежать?

Deadlock (Взаимная блокировка) — ситуация, когда две или более транзакции ожидают освобождения ресурсов, заблокированных друг другом, из-за чего ни одна из них не может продолжить выполнение.

**Пример**

Есть две транзакции, работающие с двумя строками таблицы.

Транзакция 1:

```
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

-- Ожидает блокировку второй строки
UPDATE accounts
SET balance = balance + 100
WHERE id = 2;
```

Транзакция 2:

```
BEGIN;

UPDATE accounts
SET balance = balance - 200
WHERE id = 2;

-- Ожидает блокировку первой строки
UPDATE accounts
SET balance = balance + 200
WHERE id = 1;
```

Возникает ситуация:

- Транзакция 1 удерживает блокировку строки 1 и ожидает строку 2.
    
- Транзакция 2 удерживает блокировку строки 2 и ожидает строку 1.
    

Обе транзакции ждут друг друга.

**Как СУБД обрабатывает Deadlock?**

PostgreSQL обнаруживает циклическое ожидание с помощью механизма обнаружения взаимных блокировок.

При обнаружении Deadlock одна из транзакций выбирается в качестве жертвы и отменяется с ошибкой.

Другая транзакция получает возможность продолжить выполнение.

**Как избежать Deadlock?**

1. Соблюдать единый порядок блокировки ресурсов.

Например, всегда блокировать счета по возрастанию `id`.

2. Сокращать время выполнения транзакций.

Не выполнять длительные вычисления и внешние HTTP-запросы внутри открытой транзакции.

3. Блокировать только необходимые строки.

Избегать избыточных блокировок.

4. Использовать подходящие индексы.

Это может сократить количество проверяемых записей и время удержания блокировок.

5. Обрабатывать ошибки Deadlock.

Транзакцию необходимо повторить целиком, поскольку СУБД отменяет одну из участвующих транзакций.

Главное: Deadlock возникает из-за циклического ожидания блокировок. Основные способы борьбы — единый порядок захвата ресурсов, короткие транзакции и повторное выполнение отменённых транзакций.

## 15. Объясните, как работает EXPLAIN / EXPLAIN ANALYZE.

EXPLAIN — команда SQL, которая показывает план выполнения запроса, сформированный оптимизатором СУБД.

Позволяет понять, какие операции будут выполняться и каким образом СУБД планирует получать данные.

**EXPLAIN**

```
EXPLAIN
SELECT *
FROM users
WHERE email = 'test@example.com';
```

Показывает предполагаемый план выполнения без фактического исполнения обычного `SELECT`.

Основные элементы плана:

- Seq Scan — последовательное сканирование таблицы.
    
- Index Scan — поиск через индекс с последующим обращением к таблице.
    
- Index Only Scan — получение необходимых данных непосредственно из индекса, если это возможно.
    
- Nested Loop — соединение таблиц через вложенные циклы.
    
- Hash Join — соединение с использованием хеш-таблицы.
    
- Merge Join — соединение отсортированных наборов данных.
    

**EXPLAIN ANALYZE**

```
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'test@example.com';
```

В отличие от обычного `EXPLAIN`, команда действительно выполняет запрос и показывает фактические показатели.

Основные параметры:

- cost — оценочная стоимость выполнения узла.
    
- rows — ожидаемое количество строк.
    
- actual time — фактическое время выполнения.
    
- actual rows — фактическое количество возвращённых строк.
    
- loops — количество выполнений узла.
    

Пример:

```
Index Scan using idx_users_email on users
(cost=0.29..8.30 rows=1 width=64)
(actual time=0.020..0.021 rows=1 loops=1)
```

Это означает:

- используется индекс `idx_users_email`;
    
- оптимизатор ожидал получить одну строку;
    
- фактически была получена одна строка;
    
- узел выполнился один раз.
    

**На что обращать внимание?**

1. Seq Scan

Сам по себе не является проблемой. Для маленьких таблиц или запросов, возвращающих большую часть данных, последовательное сканирование может быть эффективнее индекса.

2. Estimated Rows vs Actual Rows

Если оценочное количество строк сильно отличается от фактического, оптимизатор может выбрать неудачный план.

3. Nested Loop

Может стать дорогим при большом количестве строк, особенно если внутренний поиск не использует индекс.

4. Sort

Сортировка больших объёмов данных может требовать значительных ресурсов и приводить к использованию временных файлов на диске.

5. Buffers

Позволяет оценить работу с буферным кешем и чтение страниц.

**Важный нюанс**

`EXPLAIN ANALYZE` действительно выполняет запрос. Поэтому для `UPDATE`, `DELETE` и других изменяющих операций необходимо учитывать реальные изменения данных.

В PostgreSQL для безопасной проверки можно использовать транзакцию:

```
BEGIN;

EXPLAIN ANALYZE
DELETE FROM users
WHERE id = 100;

ROLLBACK;
```

Главное: `EXPLAIN` показывает предполагаемый план, а `EXPLAIN ANALYZE` выполняет запрос и позволяет сравнить оценки оптимизатора с фактическим поведением.

## 16. Какие бывают типы триггеров и где их применяют?

Триггер (Trigger) — механизм СУБД, который автоматически запускает определённую функцию или действие при наступлении заданного события.

Триггеры используются для автоматизации операций и контроля целостности данных.

**Основные типы триггеров**

1. BEFORE Trigger

Выполняется до операции `INSERT`, `UPDATE` или `DELETE`.

Применяется для:

- проверки данных;
    
- изменения значений перед сохранением;
    
- дополнительной валидации.
    

Пример для PostgreSQL:

```
CREATE FUNCTION set_created_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.created_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER users_before_insert
BEFORE INSERT ON users
FOR EACH ROW
EXECUTE FUNCTION set_created_at();
```

2. AFTER Trigger

Выполняется после выполнения операции.

Применяется для:

- записи истории изменений;
    
- аудита;
    
- обновления связанных данных;
    
- регистрации событий внутри БД.
    

3. INSTEAD OF Trigger

Выполняется вместо исходной операции.

В PostgreSQL используется для представлений (`VIEW`) и позволяет реализовать логику изменения данных через представление.

**По области выполнения**

FOR EACH ROW

Триггер срабатывает отдельно для каждой затронутой строки.

Например, если `UPDATE` изменил 100 строк, триггер выполнится 100 раз.

FOR EACH STATEMENT

Триггер срабатывает один раз на SQL-оператор независимо от количества изменённых строк.

Например, один `UPDATE`, изменивший 100 строк, вызовет такой триггер один раз.

**Недостатки триггеров**

- Скрывают часть бизнес-логики внутри БД.
    
- Усложняют отладку.
    
- Могут приводить к неожиданным побочным эффектам.
    
- При большом количестве триггеров усложняют понимание последовательности изменений.
    

Главное: триггеры полезны для аудита, контроля целостности и автоматических действий на уровне БД. Но бизнес-логику приложения не стоит без необходимости переносить в триггеры, поскольку это усложняет сопровождение системы.

## 17. Виды блокировок в SQL. Что такое оптимистичные и пессимистичные блокировки?

Блокировка (Lock) — механизм СУБД, который ограничивает конкурентный доступ к данным для предотвращения конфликтов между транзакциями.

Блокировки позволяют контролировать, какие операции могут выполняться одновременно.

**Основные виды блокировок**

1. Shared Lock (Разделяемая блокировка)

Используется для чтения данных.

Несколько транзакций могут одновременно получать разделяемые блокировки на один ресурс.

При этом конфликтующая эксклюзивная блокировка не может быть получена до освобождения разделяемых блокировок.

2. Exclusive Lock (Эксклюзивная блокировка)

Используется для изменения данных.

Не позволяет другим транзакциям получить конфликтующую блокировку на тот же ресурс.

3. Row-Level Lock

Блокировка на уровне отдельных строк.

Позволяет нескольким транзакциям изменять разные строки одной таблицы одновременно.

В PostgreSQL:

```
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

`FOR UPDATE` блокирует выбранные строки для конфликтующих операций до завершения транзакции.

4. Table-Level Lock

Блокировка на уровне таблицы.

Ограничивает определённые операции над всей таблицей.

В PostgreSQL существует несколько режимов табличных блокировок, например `ACCESS SHARE`, `ROW EXCLUSIVE`, `ACCESS EXCLUSIVE`.

5. Advisory Lock

Пользовательская блокировка, которая не привязана напрямую к конкретной строке или таблице.

В PostgreSQL:

```
SELECT pg_advisory_lock(12345);
```

Используется для синхронизации операций на уровне приложения через механизм блокировок СУБД.

**Оптимистичная блокировка (Optimistic Locking)**

Предполагает, что конфликты между транзакциями возникают редко.

Вместо предварительной блокировки записи используется проверка версии данных при обновлении.

Пример:

```
UPDATE accounts
SET balance = 500,
    version = version + 1
WHERE id = 1
  AND version = 5;
```

Если другая транзакция уже изменила запись и увеличила `version`, обновление затронет 0 строк.

Приложение обнаружит конфликт и сможет повторить операцию или сообщить об ошибке.

**Пессимистичная блокировка (Pessimistic Locking)**

Предполагает, что конфликт возможен, поэтому данные блокируются заранее.

Пример:

```
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

Пока транзакция удерживает блокировку, другие транзакции не смогут выполнить конфликтующие операции над этой строкой.

**Сравнение**

|Оптимистичная|Пессимистичная|
|---|---|
|Не блокирует запись заранее|Блокирует запись заранее|
|Проверяет версию при обновлении|Контролирует доступ через блокировки|
|Хороша при редких конфликтах|Подходит при частых конфликтах|
|Возможны повторные попытки|Возможны ожидания и Deadlock|

Главное: оптимистичная блокировка обнаруживает конфликт при записи, а пессимистичная предотвращает конфликт за счёт предварительной блокировки ресурса.

## 18. Что такое шардирование/партицирование и для чего?

Шардирование (Sharding) и партицирование (Partitioning) — способы разделения больших объёмов данных на более мелкие части.

Основная цель — упростить работу с большими таблицами, улучшить производительность и масштабируемость.

**Партицирование (Partitioning)**

Партицирование — разделение одной логической таблицы на несколько физических частей (партиций).

Для приложения таблица продолжает выглядеть как единая сущность.

Пример: таблица заказов разделена по месяцам.

```
CREATE TABLE orders (
    id BIGINT,
    created_at DATE,
    amount DECIMAL(10, 2)
)
PARTITION BY RANGE (created_at);
```

Создадим партицию за январь:

```
CREATE TABLE orders_2026_01
PARTITION OF orders
FOR VALUES FROM ('2026-01-01')
TO ('2026-02-01');
```

И за февраль:

```
CREATE TABLE orders_2026_02
PARTITION OF orders
FOR VALUES FROM ('2026-02-01')
TO ('2026-03-01');
```

**Основные виды партицирования**

1. RANGE Partitioning

Разделение по диапазонам значений.

Например:

- заказы за январь;
    
- заказы за февраль;
    
- заказы за март.
    

2. LIST Partitioning

Разделение по конкретным значениям.

Например:

- регион Europe;
    
- регион Asia;
    
- регион America.
    

3. HASH Partitioning

Разделение с помощью хеш-функции.

Позволяет распределить данные по партициям относительно равномерно.

**Преимущества партицирования**

- Partition Pruning — СУБД может исключить ненужные партиции при выполнении запроса.
    
- Упрощает удаление старых данных.
    
- Позволяет обслуживать отдельные части таблицы.
    
- Может улучшить производительность запросов на больших объёмах данных.
    

**Шардирование (Sharding)**

Шардирование — горизонтальное разделение данных между несколькими независимыми узлами или экземплярами БД.

Например:

- Shard 1 — пользователи с `id` от 1 до 1 000 000.
    
- Shard 2 — пользователи с `id` от 1 000 001 до 2 000 000.
    
- Shard 3 — пользователи с `id` от 2 000 001 до 3 000 000.
    

Каждый шард хранится на отдельном сервере или экземпляре БД.

Распределение может выполняться по:

- диапазонам значений;
    
- хешу ключа;
    
- географическому признаку;
    
- другим правилам маршрутизации.
    

**Сравнение**

|Partitioning|Sharding|
|---|---|
|Разделение таблицы на части|Распределение данных между узлами|
|Обычно внутри одной БД|Между несколькими узлами|
|Упрощает обслуживание таблиц|Помогает горизонтально масштабировать систему|
|Обычно прозрачно для приложения|Часто требует маршрутизации запросов|

Недостатки шардирования:

- усложняется выполнение `JOIN`;
    
- сложнее выполнять распределённые транзакции;
    
- появляется проблема равномерного распределения нагрузки;
    
- усложняются резервное копирование и обслуживание;
    
- миграция между шардами может быть дорогостоящей.
    

Главное: партицирование разделяет таблицу на части, а шардирование распределяет данные между независимыми узлами. Первое чаще используется для обслуживания больших таблиц, второе — для горизонтального масштабирования.

## 19. Реплицирование в SQL, как, зачем и какие виды?

Репликация (Replication) — механизм копирования и синхронизации данных между несколькими экземплярами базы данных.

Основная цель — повысить отказоустойчивость, доступность и масштабируемость системы.

**Как работает репликация?**

Обычно существует:

- Primary (Master) — основной узел, принимающий операции записи.
    
- Replica (Standby) — дополнительный узел, получающий изменения от основного.
    

Упрощённая схема:

```
        Application
             |
             v
          Primary
             |
       Replication
          /     \
         v       v
     Replica1  Replica2
```

Приложение отправляет операции записи на Primary, после чего изменения передаются репликам.

**Основные виды репликации**

1. Синхронная репликация (Synchronous)

Основной узел подтверждает транзакцию после получения подтверждения от необходимых реплик в соответствии с настроенной политикой синхронизации.

Преимущества:

- более строгие гарантии сохранности подтверждённых изменений;
    
- меньше вероятность потери данных при отказе основного узла.
    

Недостатки:

- увеличивается задержка записи;
    
- доступность записи может зависеть от доступности реплик.
    

2. Асинхронная репликация (Asynchronous)

Primary подтверждает транзакцию, не дожидаясь применения изменений на репликах.

Преимущества:

- меньше задержка записи;
    
- основной узел меньше зависит от доступности реплик.
    

Недостатки:

- возможна потеря последних подтверждённых изменений при аварийном переключении на отстающую реплику;
    
- возникает replication lag — задержка репликации.
    

**По направлению репликации**

- Primary → Replica — изменения передаются от основного узла к репликам.
    
- Multi-Master — несколько узлов могут принимать записи, что требует механизмов разрешения конфликтов.
    

**Зачем нужна репликация?**

1. High Availability

При отказе основного узла можно переключиться на реплику.

2. Read Scaling

Часть запросов на чтение можно распределять между репликами.

3. Disaster Recovery

Дополнительные копии данных помогают восстановить систему после аварии.

4. Географическое распределение

Реплики можно размещать ближе к пользователям в разных регионах.

**Репликация в PostgreSQL**

PostgreSQL поддерживает физическую и логическую репликацию.

Physical Replication

Передаёт изменения на уровне WAL (Write-Ahead Log), воспроизводя изменения на уровне страниц и структур хранения.

Logical Replication

Передаёт логические изменения данных: `INSERT`, `UPDATE`, `DELETE` и другие поддерживаемые операции.

Используется, например, для репликации отдельных таблиц и интеграции между разными версиями PostgreSQL.

Главное: репликация создаёт копии данных на других узлах. Она повышает доступность и позволяет масштабировать чтение, но сама по себе не заменяет резервное копирование.

## 20. Почему SELECT * — зло в проде?

`SELECT *` — запрос, который возвращает все столбцы таблицы.

```
SELECT *
FROM users;
```

В production-коде обычно рекомендуется явно перечислять необходимые столбцы.

**Основные недостатки**

1. Лишний объём передаваемых данных

Если таблица содержит 30 столбцов, а приложению нужны только 3, остальные данные будут переданы по сети без необходимости.

Это увеличивает:

- сетевой трафик;
    
- потребление памяти;
    
- время обработки результата.
    

2. Нельзя эффективно использовать покрывающие индексы во всех случаях

Если запросу нужны все столбцы, СУБД чаще приходится обращаться непосредственно к данным таблицы.

При явном указании нужных полей иногда можно выполнить `Index Only Scan`.

3. Проблемы при изменении схемы

Если в таблицу добавится новый столбец, `SELECT *` начнёт возвращать его автоматически.

Это может неожиданно повлиять на:

- сериализацию результатов;
    
- ORM;
    
- структуру API-ответов;
    
- обработку данных в приложении.
    

4. Сложнее поддерживать код

Явное перечисление столбцов делает запрос понятнее и показывает, какие данные действительно используются.

**Правильный подход**

Вместо:

```
SELECT *
FROM users
WHERE id = 1;
```

Использовать:

```
SELECT id, name, email
FROM users
WHERE id = 1;
```

Главное: `SELECT *` не является безусловно медленным запросом, но в production-коде явное перечисление столбцов обычно делает запросы эффективнее, предсказуемее и проще в сопровождении.

## 21. Как работает MVCC (PostgreSQL/MySQL InnoDB)?

MVCC (Multi-Version Concurrency Control) — механизм многоверсионного управления конкурентным доступом к данным.

Его основная идея — хранить несколько версий одной строки, чтобы транзакции могли читать согласованный снимок данных, не блокируя друг друга обычными операциями чтения и записи.

**Как работает MVCC?**

Предположим, в таблице есть запись:

|id|balance|
|---|---|
|1|1000|

Транзакция T1 начинает работу и читает баланс:

```
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;
```

Параллельно транзакция T2 изменяет баланс:

```
BEGIN;

UPDATE accounts
SET balance = 1500
WHERE id = 1;

COMMIT;
```

При использовании MVCC T1 продолжает видеть ту версию строки, которая соответствует её снимку данных, а не обязательно последнее изменение T2.

**MVCC в PostgreSQL**

PostgreSQL хранит версии строк непосредственно в таблице.

Каждая версия строки содержит служебные поля:

- `xmin` — идентификатор транзакции, создавшей версию;
    
- `xmax` — идентификатор транзакции, удалившей или заменившей версию;
    
- другие служебные данные, необходимые для управления версиями.
    

При выполнении `UPDATE` PostgreSQL обычно создаёт новую версию строки, а старая становится потенциально ненужной.

Старые версии не удаляются сразу, поскольку они ещё могут быть необходимы другим транзакциям.

Для очистки используется `VACUUM`.

**MVCC в MySQL InnoDB**

InnoDB реализует MVCC с использованием:

- Undo Log — хранит информацию, необходимую для восстановления предыдущих версий строк.
    
- Read View — снимок состояния транзакций, определяющий, какие версии данных доступны для чтения.
    
- Clustered Index — основная структура хранения строк таблицы.
    

При изменении строки InnoDB обновляет текущую версию и сохраняет информацию о предыдущем состоянии в Undo Log.

Если транзакции требуется старая версия строки, InnoDB может восстановить её, используя цепочку undo-записей.

**Сравнение PostgreSQL и InnoDB**

|PostgreSQL|MySQL InnoDB|
|---|---|
|Хранит версии строк в таблице|Использует Undo Log для восстановления старых версий|
|UPDATE обычно создаёт новую версию строки|UPDATE изменяет текущую версию и сохраняет предыдущую в Undo Log|
|VACUUM очищает устаревшие версии|Purge очищает ненужные undo-записи|
|Использует xmin/xmax|Использует Read View и служебные идентификаторы транзакций|

**Преимущества MVCC**

- Чтение обычно не блокирует запись.
    
- Запись обычно не блокирует обычное чтение.
    
- Транзакции могут работать с согласованными снимками данных.
    
- Уменьшается количество конфликтов между читателями и писателями.
    

Главное: MVCC позволяет нескольким транзакциям одновременно работать с разными версиями данных. PostgreSQL хранит версии строк непосредственно в таблице, а InnoDB использует Undo Log для восстановления предыдущих версий.

## 22. Почему индекс может НЕ использоваться?

Наличие индекса не гарантирует, что СУБД будет использовать его при выполнении запроса.

Оптимизатор самостоятельно выбирает план выполнения, основываясь на статистике, стоимости операций и ожидаемом количестве обрабатываемых данных.

**Основные причины**

1. Таблица слишком маленькая

Если таблица содержит несколько десятков строк, последовательное сканирование может быть дешевле обращения к индексу.

2. Запрос возвращает большую часть таблицы

Если условие фильтрации возвращает 70–90% строк, использование индекса может оказаться дороже, чем `Seq Scan`.

Причина: индексный поиск может потребовать большого количества дополнительных обращений к страницам таблицы.

3. Использование функции над индексируемым столбцом

Например:

```
SELECT *
FROM users
WHERE LOWER(email) = 'test@example.com';
```

Обычный индекс по `email` может не использоваться, поскольку условие применяется к результату функции `LOWER()`.

Решение — создать функциональный индекс:

```
CREATE INDEX idx_users_lower_email
ON users(LOWER(email));
```

4. Несоответствие типов данных

Неявное преобразование типов может помешать использованию обычного индекса в некоторых запросах.

Например, если индекс создан по числовому столбцу, а условие приводит его к другому типу.

5. Использование LIKE с ведущим wildcard

```
SELECT *
FROM users
WHERE email LIKE '%gmail.com';
```

Обычный B-Tree не может эффективно искать по произвольному окончанию строки.

Но поиск по префиксу:

```
WHERE email LIKE 'test%'
```

может использовать B-Tree при подходящем операторном классе и настройках локали.

6. Неподходящий порядок столбцов составного индекса

Например, индекс:

```
CREATE INDEX idx_users_status_created
ON users(status, created_at);
```

Может эффективно использоваться для:

```
WHERE status = 'active';
```

Но запрос только по `created_at` может не получить ожидаемой пользы из-за отсутствия ограничения по первому столбцу индекса.

7. Неактуальная статистика

Оптимизатор может неправильно оценить количество строк и выбрать неоптимальный план.

В PostgreSQL:

```
ANALYZE users;
```

Обновляет статистику таблицы.

8. Индекс не подходит для операции

Например, Hash Index подходит для точного сравнения, но не для диапазонного поиска.

**Как проверить причину?**

Использовать:

```
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'test@example.com';
```

Проверить:

- какой план выбрала СУБД;
    
- сколько строк ожидается и сколько возвращается фактически;
    
- насколько дорого обходится последовательное сканирование;
    
- актуальна ли статистика.
    

Главное: индекс может не использоваться, если оптимизатор считает последовательное сканирование дешевле, условие несовместимо с индексом или статистика не отражает реальное распределение данных.

## 23. Что хуже: много индексов или их отсутствие?

Оба варианта могут быть проблемой. Оптимальное количество индексов определяется характером нагрузки и запросами приложения.

**Если индексов слишком мало**

- Поиск может выполняться через `Seq Scan`.
    
- Увеличивается количество прочитанных страниц.
    
- Замедляются `JOIN`, `ORDER BY` и фильтрация.
    
- При больших объёмах данных запросы могут становиться очень дорогими.
    

**Если индексов слишком много**

Каждый индекс необходимо поддерживать при изменении данных.

Например, при выполнении:

```
INSERT INTO users(name, email)
VALUES ('Alex', 'alex@example.com');
```

СУБД должна обновить не только саму таблицу, но и все соответствующие индексы.

Основные недостатки:

- замедляются `INSERT`, `UPDATE`, `DELETE`;
    
- увеличивается потребление дискового пространства;
    
- возрастает нагрузка на обслуживание индексов;
    
- увеличивается количество страниц, которые могут попадать в кеш;
    
- усложняется выбор плана выполнения.
    

**Пример**

Допустим, есть таблица `orders` с 50 миллионами записей.

Основные запросы:

```
SELECT *
FROM orders
WHERE user_id = 100;
```

```
SELECT *
FROM orders
WHERE status = 'completed';
```

```
SELECT *
FROM orders
WHERE user_id = 100
ORDER BY created_at DESC;
```

Для таких запросов можно рассмотреть:

- индекс по `user_id`;
    
- индекс по `status`, если он действительно полезен с учётом распределения значений;
    
- составной индекс `(user_id, created_at)`.
    

Но создавать отдельные индексы по каждому столбцу без анализа нагрузки не стоит.

**Как правильно подходить к индексированию?**

1. Изучить наиболее частые и дорогие запросы.
    
2. Посмотреть планы выполнения через `EXPLAIN ANALYZE`.
    
3. Определить необходимые индексы.
    
4. Проверить влияние на операции записи.
    
5. Удалить неиспользуемые и избыточные индексы после проверки.
    

Главное: отсутствие необходимых индексов замедляет чтение, а их избыток замедляет запись и увеличивает расход ресурсов. Важно не количество индексов, а их соответствие реальным запросам приложения.

## 24. Как работает VACUUM / autovacuum?

VACUUM — механизм PostgreSQL, который очищает таблицы от устаревших версий строк, появившихся в результате `UPDATE` и `DELETE`.

Он необходим из-за особенностей MVCC.

**Почему возникает необходимость в VACUUM?**

В PostgreSQL при обновлении строки обычно создаётся новая версия, а старая помечается как устаревшая.

Например:

```
UPDATE users
SET name = 'Bob'
WHERE id = 1;
```

Условно в таблице появляются две версии:

|id|name|Состояние|
|---|---|---|
|1|Alex|Устаревшая|
|1|Bob|Актуальная|

Старая версия не удаляется сразу, поскольку может быть нужна другим транзакциям, которые продолжают видеть предыдущий снимок данных.

Когда старая версия больше не нужна ни одной транзакции, она становится доступной для очистки.

**VACUUM**

```
VACUUM users;
```

Выполняет очистку устаревших версий строк и позволяет повторно использовать освободившееся пространство внутри таблицы.

При этом обычный `VACUUM` не обязательно уменьшает размер файла таблицы на диске.

**VACUUM FULL**

```
VACUUM FULL users;
```

Выполняет физическую перезапись таблицы, удаляя свободное пространство и возвращая его операционной системе.

Особенности:

- требует дополнительного места на диске;
    
- переписывает таблицу;
    
- требует сильной блокировки `ACCESS EXCLUSIVE`;
    
- может надолго блокировать доступ к таблице.
    

**Autovacuum**

Autovacuum — фоновый механизм PostgreSQL, который автоматически запускает очистку таблиц и обновление статистики.

Он выполняет:

- `VACUUM` — очистку устаревших версий строк;
    
- `ANALYZE` — обновление статистики для оптимизатора.
    

Запуск зависит от настроенных порогов и количества изменений данных.

Упрощённо для обычной таблицы порог VACUUM определяется формулой:

\[ Threshold = Base + ScaleFactor \times N \]

Где:

- `Base` — базовый порог;
    
- `ScaleFactor` — коэффициент от размера таблицы;
    
- `N` — количество строк таблицы.
    

**Что будет, если VACUUM не работает?**

- Накопление устаревших версий строк (Dead Tuples).
    
- Увеличение размера таблиц.
    
- Ухудшение производительности запросов.
    
- Увеличение количества операций чтения.
    
- Риск проблем с переполнением счётчика транзакций (`Transaction ID Wraparound`).
    

Главное: VACUUM освобождает пространство, занимаемое устаревшими версиями строк, для повторного использования. Autovacuum автоматизирует этот процесс и поддерживает актуальность статистики.

## 25. Что такое write amplification?

Write Amplification — явление, при котором одна логическая операция записи приводит к большему количеству физических операций записи на уровне диска или внутренних структур хранения.

То есть приложение записывает небольшое количество данных, но СУБД фактически выполняет значительно больше работы.

**Почему возникает Write Amplification?**

1. Обновление индексов

При изменении строки необходимо обновить не только таблицу, но и соответствующие индексы.

Например:

```
UPDATE users
SET email = 'new@example.com'
WHERE id = 1;
```

Если на `email` создан индекс, СУБД должна поддерживать его актуальность.

2. MVCC

В PostgreSQL `UPDATE` обычно создаёт новую версию строки, а старая остаётся до момента очистки через VACUUM.

В результате физически записывается больше данных, чем изменилось на логическом уровне.

3. Write-Ahead Log (WAL)

PostgreSQL записывает информацию об изменениях в WAL до того, как соответствующие изменённые страницы данных должны быть сохранены на диск.

Это необходимо для восстановления после сбоев, но создаёт дополнительный объём записей.

4. Page Splits

При вставке данных в заполненную страницу B-Tree может потребоваться разделение страницы (Page Split).

Это приводит к дополнительным операциям записи и изменению структуры индекса.

5. Checkpoint

Во время контрольной точки изменённые страницы буферного кеша сбрасываются на диск.

При этом могут возникать дополнительные физические записи.

**Почему это важно?**

Write Amplification влияет на:

- производительность операций записи;
    
- нагрузку на дисковую подсистему;
    
- срок службы SSD;
    
- объём операций ввода-вывода;
    
- стоимость хранения и обслуживания данных.
    

**Как уменьшить Write Amplification?**

- Не создавать избыточные индексы.
    
- Избегать ненужных обновлений строк.
    
- Использовать пакетную запись, когда это уместно.
    
- Правильно настраивать обслуживание индексов.
    
- Учитывать особенности хранения данных и дисковой подсистемы.
    

Главное: Write Amplification означает, что физический объём записей оказывается больше логического объёма изменений. В реляционных СУБД это связано с индексами, MVCC, WAL и внутренним устройством хранения данных.

## 26. READ COMMITTED vs REPEATABLE READ — практическая разница.

Оба уровня изоляции предотвращают Dirty Read, но отличаются тем, насколько стабильный снимок данных получает транзакция.

**READ COMMITTED**

Каждый SQL-оператор получает собственный снимок подтверждённых данных.

Это означает, что два одинаковых `SELECT` внутри одной транзакции могут вернуть разные результаты.

Пример:

Транзакция T1:

```
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;
-- 1000
```

Транзакция T2:

```
BEGIN;

UPDATE accounts
SET balance = 1500
WHERE id = 1;

COMMIT;
```

Транзакция T1 повторяет запрос:

```
SELECT balance
FROM accounts
WHERE id = 1;
-- 1500
```

Второй запрос увидел изменение, подтверждённое T2.

Это называется Non-Repeatable Read.

**REPEATABLE READ**

Транзакция работает с согласованным снимком данных, полученным в соответствии с правилами данного уровня изоляции.

В PostgreSQL снимок фиксируется на первом запросе, который обращается к данным, и сохраняется до завершения транзакции.

Пример:

Транзакция T1:

```
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM accounts
WHERE id = 1;
-- 1000
```

Транзакция T2:

```
BEGIN;

UPDATE accounts
SET balance = 1500
WHERE id = 1;

COMMIT;
```

Транзакция T1 повторяет запрос:

```
SELECT balance
FROM accounts
WHERE id = 1;
-- 1000
```

T1 продолжает видеть данные своего снимка, даже если T2 уже подтвердила изменения.

**Практическая разница**

|READ COMMITTED|REPEATABLE READ|
|---|---|
|Снимок на каждый SQL-оператор|Согласованный снимок на транзакцию|
|Повторное чтение может вернуть другое значение|Повторное чтение сохраняет прежнее значение|
|Меньше ограничений для конкурентного выполнения|Более строгая согласованность чтения|
|По умолчанию в PostgreSQL|Подходит для операций, требующих стабильного снимка|

**Важный нюанс PostgreSQL**

`REPEATABLE READ` в PostgreSQL основан на Snapshot Isolation.

Он предотвращает:

- Dirty Read;
    
- Non-Repeatable Read;
    
- Phantom Read.
    

Но не гарантирует отсутствие всех аномалий конкурентного выполнения, например Write Skew.

Для более строгих гарантий используется `SERIALIZABLE`.

Главное: `READ COMMITTED` получает новый снимок для каждого оператора, а `REPEATABLE READ` в PostgreSQL сохраняет один согласованный снимок на всю транзакцию.

## 27. Когда денормализация лучше нормализации?

Денормализация (Denormalization) — намеренное добавление избыточности в структуру данных для ускорения чтения и уменьшения количества сложных операций объединения таблиц.

В отличие от нормализации, которая уменьшает дублирование, денормализация сознательно допускает его ради производительности.

**Пример нормализованной структуры**

Есть две таблицы:

Users

|id|name|
|---|---|
|1|Alex|
|2|Bob|

Orders

|id|user_id|amount|
|---|---|---|
|1|1|500|
|2|1|700|
|3|2|300|

Чтобы получить имя пользователя и его заказ, необходимо выполнить `JOIN`:

```
SELECT
    users.name,
    orders.amount
FROM orders
JOIN users
    ON users.id = orders.user_id;
```

**Денормализованная структура**

Можно хранить имя пользователя непосредственно в таблице заказов:

|id|user_id|user_name|amount|
|---|---|---|---|
|1|1|Alex|500|
|2|1|Alex|700|
|3|2|Bob|300|

Теперь для получения данных `JOIN` не требуется.

**Когда денормализация оправдана?**

1. Преобладает нагрузка на чтение

Если данные читаются значительно чаще, чем изменяются, денормализация может уменьшить стоимость запросов.

2. Сложные JOIN

Если для получения результата приходится объединять большое количество таблиц, можно рассмотреть предварительное сохранение части данных.

3. Агрегированные данные

Например, вместо постоянного вычисления количества заказов можно хранить счётчик:

```
UPDATE users
SET orders_count = orders_count + 1
WHERE id = 1;
```

4. Аналитические системы

В аналитических БД часто используют денормализованные структуры, например схемы типа Star Schema.

**Недостатки денормализации**

- Дублирование информации.
    
- Увеличение занимаемого места.
    
- Сложнее поддерживать согласованность данных.
    
- Обновление одного значения может требовать изменения нескольких записей.
    
- Возникает риск рассинхронизации данных.
    

**Сравнение**

|Нормализация|Денормализация|
|---|---|
|Уменьшает дублирование|Допускает дублирование|
|Упрощает изменение данных|Может усложнить изменение данных|
|Часто требует JOIN|Может уменьшить количество JOIN|
|Подходит для транзакционных систем|Часто полезна для read-heavy и аналитических нагрузок|

Главное: денормализация оправдана, когда измеренная стоимость чтения и объединения данных становится существенной проблемой. Но её необходимо применять осознанно, поскольку она усложняет поддержку целостности данных.

## 28. Как безопасно делать миграции без даунтайма?

Zero-Downtime Migration — подход к изменению структуры БД, при котором приложение продолжает обслуживать запросы во время миграции без остановки сервиса.

Основная проблема заключается в том, что новая структура БД должна поддерживать одновременно старую и новую версии приложения на протяжении переходного периода.

**Основные принципы**

1. Expand (Расширение)

Сначала добавляем новые элементы схемы, не удаляя старые.

Например, необходимо переименовать столбец `name` в `full_name`.

Вместо немедленного переименования добавляем новый столбец:

```
ALTER TABLE users
ADD COLUMN full_name VARCHAR(255);
```

Старая версия приложения продолжает работать с `name`.

2. Dual Write (Двойная запись)

Временно приложение записывает данные одновременно в старый и новый столбцы.

```
UPDATE users
SET
    name = 'Alex',
    full_name = 'Alex'
WHERE id = 1;
```

Это позволяет поддерживать оба представления данных синхронизированными.

3. Backfill (Перенос старых данных)

Необходимо перенести существующие данные из старого столбца в новый.

```
UPDATE users
SET full_name = name
WHERE full_name IS NULL;
```

В production такую операцию обычно выполняют небольшими пакетами (Batch Processing), чтобы не создавать длительную нагрузку и блокировки.

Например, обрабатывают записи по 1000–10000 штук за итерацию.

4. Switch Reads (Переключение чтения)

После переноса данных приложение начинает читать информацию из нового столбца.

На этом этапе старый столбец пока сохраняется.

5. Contract (Удаление старой структуры)

Когда все экземпляры приложения используют новую структуру, а старые версии больше не работают, можно удалить старый столбец.

```
ALTER TABLE users
DROP COLUMN name;
```

**Общая схема миграции**

Expand

Добавляем новую структуру, сохраняя совместимость со старой.

Dual Write + Backfill

Синхронизируем новые данные и переносим старые.

Switch Reads

Переключаем приложение на новую структуру.

Contract

Удаляем старые столбцы и ограничения.

**Дополнительные правила безопасных миграций**

1. Избегать длительных блокировок

Некоторые DDL-операции могут блокировать таблицу.

В PostgreSQL для создания индекса без блокировки обычных операций записи используется:

```
CREATE INDEX CONCURRENTLY idx_users_email
ON users(email);
```

Важно: `CREATE INDEX CONCURRENTLY` нельзя выполнять внутри обычного блока транзакции.

2. Добавлять ограничения постепенно

Например, ограничение `NOT NULL` на большой таблице может потребовать дополнительной проверки данных.

В PostgreSQL можно сначала добавить `CHECK` через `NOT VALID`, затем проверить существующие записи через `VALIDATE CONSTRAINT`, а после этого установить `NOT NULL`.

3. Использовать обратную совместимость (Backward Compatibility)

Новая версия приложения должна корректно работать со старой схемой БД на переходном этапе.

4. Контролировать длительность транзакций

Длительные транзакции могут удерживать блокировки и мешать выполнению DDL-операций.

5. Проверять миграции на production-подобных данных

Необходимо оценивать время выполнения, блокировки, нагрузку на диск и возможный рост WAL.

Главное: безопасная миграция выполняется постепенно: сначала расширяется схема, затем переносится и синхронизируется информация, после чего приложение переключается на новую структуру и только в конце удаляются старые элементы. Это позволяет обновлять БД без остановки приложения.

## 29. Что будет, если long-running transaction висит часами?

Long-Running Transaction — транзакция, которая остаётся открытой продолжительное время и не выполняет `COMMIT` или `ROLLBACK`.

Такие транзакции могут создавать серьёзные проблемы с производительностью и обслуживанием базы данных.

**Основные проблемы**

1. Удержание блокировок

Если транзакция выполняла операции записи или явно запросила блокировки через `SELECT FOR UPDATE`, она может продолжать удерживать их до завершения транзакции.

Другие транзакции, которым необходимы конфликтующие блокировки, будут ждать.

2. Проблемы с VACUUM в PostgreSQL

Это одна из наиболее важных проблем.

PostgreSQL не может удалять старые версии строк, если они потенциально ещё могут быть видны какой-либо активной транзакции.

Предположим:

1. Транзакция T1 открылась и получила старый снимок данных.
    
2. Транзакция T2 обновила большое количество строк и выполнила `COMMIT`.
    
3. Autovacuum пытается очистить устаревшие версии строк.
    
4. Но T1 всё ещё может нуждаться в старых версиях.
    

В результате VACUUM не может полностью очистить такие версии.

Это приводит к накоплению Dead Tuples.

Последствия:

- увеличивается размер таблиц;
    
- растёт потребление дискового пространства;
    
- ухудшается производительность запросов;
    
- увеличивается нагрузка на обслуживание БД.
    

3. Transaction ID Wraparound

В PostgreSQL используется ограниченное пространство идентификаторов транзакций (`Transaction ID`).

Если старая транзакция слишком долго удерживает горизонт видимости старых версий, VACUUM может не иметь возможности безопасно продвигать заморозку старых транзакций.

В результате возрастает риск достижения предельных значений XID и возникновения необходимости принудительного обслуживания базы.

Это критическая ситуация, поскольку PostgreSQL может ограничить выполнение новых транзакций для предотвращения повреждения данных.

4. Рост WAL

Если транзакция активно изменяет данные или удерживает ресурсы, необходимые для очистки и продвижения служебных механизмов, это может способствовать накоплению WAL и росту занимаемого дискового пространства.

В частности, длительные транзакции могут мешать очистке WAL при наличии связанных с ними replication slots или других удерживающих механизмов.

5. Увеличение потребления ресурсов

Транзакция может удерживать:

- блокировки;
    
- версии строк;
    
- снимки данных;
    
- временные ресурсы;
    
- соединение с БД.
    

**Как обнаружить долгие транзакции в PostgreSQL?**

Можно использовать `pg_stat_activity`:

```
SELECT
    pid,
    usename,
    state,
    now() - xact_start AS transaction_duration,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY transaction_duration DESC;
```

Запрос позволяет увидеть:

- PID процесса;
    
- пользователя;
    
- состояние соединения;
    
- продолжительность транзакции;
    
- выполняемый SQL-запрос.
    

Особенно важно обращать внимание на состояние `idle in transaction`.

Это означает, что транзакция открыта, но в данный момент не выполняет запрос, ожидая дальнейших действий приложения.

**Как бороться с Long-Running Transactions?**

1. Сокращать время жизни транзакций

Не выполнять длительные вычисления и HTTP-запросы внутри транзакции.

2. Не держать транзакцию открытой во время ожидания пользователя

Например, нельзя открывать транзакцию, ждать несколько минут ответа от внешнего API и только после этого выполнять `COMMIT`.

3. Использовать таймауты

В PostgreSQL:

```
SET idle_in_transaction_session_timeout = '60s';
```

Автоматически завершает сессию, которая находится в состоянии `idle in transaction` дольше установленного времени.

Также существуют:

- `statement_timeout` — ограничивает время выполнения SQL-оператора;
    
- `lock_timeout` — ограничивает время ожидания блокировки.
    

4. Контролировать метрики БД

Следить за:

- возрастом самой старой транзакции;
    
- количеством Dead Tuples;
    
- работой Autovacuum;
    
- размером WAL;
    
- количеством заблокированных запросов.
    

Главное: длительная транзакция может удерживать блокировки и старые версии строк, мешать VACUUM и приводить к росту таблиц и WAL. В production важно контролировать время жизни транзакций, использовать таймауты и не выполнять внешние операции внутри открытой транзакции.

Конец раздела SQL. Все 29 вопросов оформлены в едином стиле с предыдущими конспектами.

# ✦ RabbitMQ

## 1. Что такое RabbitMQ и для каких задач его используют?

RabbitMQ — брокер сообщений (Message Broker), обеспечивающий асинхронную передачу сообщений между компонентами системы. Отправитель публикует сообщение в брокер, а получатель забирает его и обрабатывает независимо от отправителя. Это уменьшает связанность сервисов и позволяет им переживать временную недоступность друг друга.

**Основные сценарии использования**
- Асинхронное взаимодействие микросервисов.
- Фоновые задачи: отправка email, генерация отчётов, обработка изображений.
- Разгрузка HTTP API: запрос быстро принимается, тяжёлая работа выполняется в фоне.
- Буферизация нагрузки, когда сообщения поступают быстрее, чем обрабатываются.
- Retry, отложенная обработка и Dead Letter Queue.
- Рассылка одного события нескольким независимым потребителям.

**Пример**

Сервис заказов сохраняет заказ и публикует `order.created`. Сервис уведомлений отправляет email, складской сервис резервирует товар, аналитика обновляет статистику. Сервис заказов не обязан ждать завершения этих операций.

**Преимущества и ограничения**

RabbitMQ даёт гибкую маршрутизацию, подтверждения доставки, очереди и механизмы повторной обработки. Но он не является полноценным долговременным журналом событий для произвольного повторного чтения. Повторная доставка возможна, поэтому обработчики должны быть идемпотентными.

Главное: RabbitMQ — брокер для асинхронного взаимодействия компонентов, особенно полезный для фоновых задач, маршрутизации сообщений и развязки микросервисов.

## 2. Объясните, как работают producer, queue, exchange и consumer.

**Producer** — приложение, создающее и публикующее сообщения. Обычно оно отправляет сообщение в Exchange, указывая routing key и свойства сообщения.

**Exchange** принимает сообщения от Producer и маршрутизирует их в очереди на основании типа Exchange, bindings и routing key. Сам Exchange обычно сообщения не хранит.

**Queue** — очередь, в которой сообщения ожидают обработки. Она может накапливать сообщения, пока Consumer недоступен или не успевает их обрабатывать.

**Consumer** — приложение, получающее сообщения из очереди и обрабатывающее их. После успешной обработки Consumer отправляет ACK. При ошибке сообщение можно отклонить через NACK или Reject.

**Схема взаимодействия**

```text
Producer -> Exchange -> Queue -> Consumer -> ACK
                 routing key + bindings
```

**Пример публикации на Go**

Для Go часто используют `github.com/rabbitmq/amqp091-go`.

```go
conn, err := amqp.Dial("amqp://guest:guest@localhost:5672/")
if err != nil { log.Fatal(err) }
defer conn.Close()

ch, err := conn.Channel()
if err != nil { log.Fatal(err) }
defer ch.Close()

err = ch.ExchangeDeclare("orders", "direct", true, false, false, false, nil)
if err != nil { log.Fatal(err) }

err = ch.Publish("orders", "order.created", false, false, amqp.Publishing{
    ContentType: "application/json",
    DeliveryMode: amqp.Persistent,
    Body: []byte(`{"order_id":123}`),
})
if err != nil { log.Fatal(err) }
```

Успешный возврат `Publish` сам по себе не доказывает, что брокер надёжно сохранил сообщение. Для подтверждения публикации используют Publisher Confirms. Для обнаружения сообщений без подходящей очереди применяют `mandatory` и обработку `Basic.Return`.

Главное: Producer создаёт сообщения, Exchange маршрутизирует их, Queue хранит до обработки, Consumer получает и обрабатывает.

## 3. Какие типы Exchange существуют и в чем разница между ними?

Exchange определяет, в какие очереди попадёт сообщение. В RabbitMQ есть четыре основных типа.

**Direct Exchange** маршрутизирует сообщение в очереди, у которых binding key точно совпадает с routing key. Подходит для точной маршрутизации по типу события.

**Fanout Exchange** отправляет каждое сообщение во все привязанные очереди. Routing key игнорируется. Подходит для широковещательной рассылки.

**Topic Exchange** сопоставляет routing key с шаблоном. Ключ состоит из слов, разделённых точками. `*` означает ровно одно слово, `#` — ноль или более слов.

```text
order.*  -> order.created, order.cancelled
order.#  -> order.created, order.payment.failed
```

**Headers Exchange** маршрутизирует по значениям заголовков сообщения. `x-match = all` требует совпадения всех заданных заголовков, `x-match = any` — хотя бы одного.

|Тип|Правило|Сценарий|
|---|---|---|
|Direct|Точное совпадение routing key|Маршрутизация по типу задачи|
|Fanout|Во все привязанные очереди|Рассылка события нескольким сервисам|
|Topic|Сопоставление с шаблоном|Маршрутизация по категориям событий|
|Headers|Сопоставление по заголовкам|Маршрутизация по набору атрибутов|

Главное: Direct использует точное совпадение, Fanout рассылает всем, Topic поддерживает шаблоны, Headers маршрутизирует по заголовкам.

## 4. Что такое binding и routing key?

**Binding** — правило, связывающее Exchange с Queue и определяющее, какие сообщения могут попасть в эту очередь.

**Routing Key** — строковый ключ, который Producer указывает при публикации. Exchange использует его при маршрутизации, если тип Exchange предполагает работу с ключом.

**Пример**

```text
Exchange: orders
Queue: order_created
Binding key: order.created
Routing key сообщения: order.created
```

При точном совпадении Direct Exchange направит сообщение в `order_created`.

Для Topic Exchange routing key `order.payment.failed` совпадёт с binding `order.payment.*`? Нет, потому что `*` соответствует ровно одному слову. Зато совпадёт с `order.#`.

Одно сообщение может попасть в несколько очередей, если соответствует нескольким bindings. Если не соответствует ни одному, оно может быть отброшено, если не настроена альтернативная маршрутизация и не используется `mandatory` с обработкой возврата.

Главное: Routing key — ключ сообщения, Binding — правило связи Exchange с Queue. Вместе они определяют маршрутизацию.

## 5. Что такое виртуальный хост (vhost) в RabbitMQ?

Vhost (Virtual Host) — логическое пространство внутри RabbitMQ, изолирующее ресурсы брокера. Внутри каждого vhost существуют собственные Exchanges, Queues, Bindings и разрешения пользователей.

**Пример**

```text
/production
/staging
/analytics
```

В разных vhost могут существовать ресурсы с одинаковыми именами, но это будут разные сущности.

**Права доступа**
- Configure — создавать и изменять Exchanges, Queues и Bindings.
- Write — публиковать сообщения в Exchanges.
- Read — получать сообщения из Queues.

Vhost позволяет разделять окружения, приложения и права доступа. Однако это логическая, а не физическая изоляция: vhost одного кластера используют общие CPU, память, диск и сеть.

Главное: Vhost — логическое пространство имён и прав доступа внутри RabbitMQ, позволяющее разделять ресурсы без отдельного кластера для каждого приложения.

## 6. Как обеспечить надёжность доставки сообщений (delivery_mode, подтверждения, ack/nack)?

Надёжность строится из нескольких механизмов: сохранения очереди, сохранения сообщений, подтверждения публикации и подтверждения обработки.

**Durable Queue** сохраняется после перезапуска брокера:

```go
_, err := ch.QueueDeclare("orders", true, false, false, false, nil)
```

**Delivery Mode** определяет, помечено ли сообщение как persistent. `amqp.Persistent` используется для persistent-сообщений:

```go
amqp.Publishing{
    DeliveryMode: amqp.Persistent,
    ContentType: "application/json",
    Body: payload,
}
```

Для сохранения сообщений после перезапуска обычно нужны и durable-очередь, и persistent-сообщения. Реальные гарантии также зависят от типа очереди и конфигурации брокера.

**Publisher Confirms** — подтверждения от брокера Producer-у, что публикация принята. Если соединение оборвалось до получения подтверждения, Producer не всегда знает, принял ли брокер сообщение. Повторная публикация может создать дубликат, поэтому нужен стабильный message ID и идемпотентный Consumer.

**Consumer ACK** подтверждает успешную обработку. При `autoAck = false` Consumer должен отправлять ACK вручную:

```go
for msg := range deliveries {
    if err := process(msg.Body); err != nil {
        _ = msg.Nack(false, true) // requeue
        continue
    }
    _ = msg.Ack(false)
}
```

**ACK / NACK / Reject**
- ACK — сообщение успешно обработано.
- NACK — отклонение одного или нескольких сообщений; можно вернуть их в очередь.
- Reject — отклонение одного сообщения.
- `requeue=true` возвращает сообщение в очередь.
- `requeue=false` не возвращает; при настроенном DLX сообщение может быть перенаправлено туда, иначе удаляется.

**Prefetch** ограничивает число сообщений, выданных Consumer-у без подтверждения:

```go
err := ch.Qos(10, 0, false)
```

Это защищает Consumer от перегрузки и ограничивает количество unacked-сообщений.

RabbitMQ не гарантирует автоматически exactly-once processing. Consumer может выполнить бизнес-операцию и упасть до ACK, после чего сообщение придёт повторно. Поэтому используют idempotency key или таблицу обработанных сообщений.

Главное: durable queue, persistent messages, Publisher Confirms, ручные ACK/NACK и prefetch решают разные части задачи надёжности. Обработка должна быть идемпотентной.

## 7. Расскажите про механизмы очередей: durable vs transient.

**Durable Queue** сохраняет объявление очереди после перезапуска RabbitMQ:

```go
_, err := ch.QueueDeclare("orders", true, false, false, false, nil)
```

**Transient Queue** не сохраняется после перезапуска:

```go
_, err := ch.QueueDeclare("temporary_events", false, true, true, false, nil)
```

Transient-очереди подходят для временных сценариев, где потеря очереди при перезапуске допустима.

**Durable Queue и Persistent Message — не одно и то же**
- Durable относится к объявлению очереди.
- Persistent относится к сообщению.

Для устойчивости сообщений при перезапуске обычно нужны оба свойства.

**Основные типы очередей**
- Classic Queue — классическая очередь RabbitMQ, может быть durable или transient.
- Quorum Queue — реплицируемая очередь на основе Raft, рассчитанная на отказоустойчивость.
- Stream — постоянный журнал сообщений с повторным чтением по смещениям; это отдельная модель, близкая к event log.

Главное: Durable Queue сохраняет саму очередь, Persistent Message помечает сообщение для надёжного хранения. Это разные свойства.

## 8. Чем RabbitMQ отличается от других брокеров сообщений (например, Kafka)?

RabbitMQ — брокер с моделью очередей и маршрутизации. Kafka — распределённая платформа потоковой передачи событий с хранением сообщений в журнале.

**RabbitMQ**
- Основная модель — Exchange, Queue и Consumer.
- Сообщение обычно удаляется из очереди после ACK.
- Гибкая маршрутизация через Direct, Fanout, Topic и Headers.
- Удобен для распределения фоновых задач.
- Поддерживает ACK/NACK, retry, DLX и prefetch.

**Kafka**
- Сообщения записываются в топики, разделённые на партиции.
- Хранение определяется retention-политикой, а не фактом чтения Consumer-ом.
- Consumer отслеживает offset — позицию чтения.
- Несколько Consumer Group могут независимо читать один поток.
- Подходит для event streaming, аналитики и replay событий.

|Критерий|RabbitMQ|Kafka|
|---|---|---|
|Модель|Очереди и маршрутизация|Распределённый журнал событий|
|Подтверждение|ACK сообщения|Фиксация offset|
|Хранение|До обработки, согласно настройкам очереди|По retention-политике|
|Повторное чтение|Не основная модель|Можно переместить offset назад|
|Маршрутизация|Exchange и Binding|Топики и партиции|
|Масштабирование|Очереди и consumers|Партиции и Consumer Groups|

Главное: RabbitMQ удобен для доставки и распределения задач, Kafka — для хранения и обработки потоков событий. Выбор зависит от модели потребления и требований к хранению.

## 9. Какие существуют сценарии отказоустойчивости в RabbitMQ?

Отказоустойчивость (High Availability) — способность системы продолжать работу при отказе отдельных компонентов.

**Кластер RabbitMQ** объединяет несколько узлов. Но наличие кластера само по себе не означает, что каждая очередь автоматически реплицируется на все узлы.

**Quorum Queues** — реплицируемые очереди на основе Raft. Для принятия решений требуется большинство реплик. При трёх репликах большинство — две, поэтому отказ одного узла не обязательно останавливает очередь.

**Publisher Confirms** позволяют Producer-у узнать, что брокер принял публикацию. При потере соединения до подтверждения результат может быть неизвестен. Безопасная стратегия — повторная публикация с тем же ID и идемпотентная обработка.

**Consumer Recovery**: при потере соединения приложение должно восстановить соединение, заново создать каналы, подписки и настройки. Неподтверждённые сообщения могут быть доставлены повторно.

**Инфраструктурные меры**
- Размещать узлы на разных машинах и, по возможности, в разных зонах доступности.
- Контролировать диски, память и сеть.
- Иметь резервные копии конфигурации и план восстановления.
- Тестировать сценарии отказа.
- Для Producer использовать ограниченные попытки подключения и backoff.
- Для критичных событий рассматривать transactional outbox.

Mirrored Classic Queues в старых версиях RabbitMQ были механизмом репликации классических очередей, но в современных версиях удалены. Для реплицируемых очередей используют Quorum Queues.

Главное: отказоустойчивость обеспечивается кластером, Quorum Queues, Publisher Confirms, восстановлением соединений и корректной обработкой повторной доставки.

## 10. Как масштабировать потребителей сообщений в RabbitMQ?

Масштабирование Consumer-ов — увеличение количества процессов, параллельно получающих и обрабатывающих сообщения.

**Несколько Consumer-ов на одной Queue**

RabbitMQ распределяет сообщения между активными потребителями одной очереди с учётом доступного prefetch:

```text
                 Queue
          +--------+--------+
          |        |        |
       Consumer1 Consumer2 Consumer3
```

**Prefetch Count** задаёт число неподтверждённых сообщений, которые брокер может выдать Consumer-у:

```go
err := ch.Qos(10, 0, false)
```

Слишком большой prefetch может привести к тому, что один медленный Consumer удерживает много сообщений. Слишком маленький может снижать пропускную способность. Значение подбирают нагрузочными тестами.

**Worker Pool**: один процесс может обрабатывать сообщения несколькими goroutine. Нужно ограничивать параллелизм и подтверждать сообщение только после завершения его обработки.

**Горизонтальное масштабирование**: запускать несколько экземпляров приложения в Docker, Kubernetes или на разных машинах. Количество экземпляров можно связывать с размером очереди и скоростью поступления сообщений.

**Ограничения**
- БД может стать узким местом.
- Внешние API могут иметь rate limit.
- Увеличение параллелизма повышает нагрузку на CPU и память.
- Порядок завершения обработки несколькими Consumer-ами не гарантируется.

Если требуется порядок по конкретной сущности, можно маршрутизировать сообщения по ключу в отдельные очереди или сериализовать обработку для этого ключа.

Главное: Consumer-ы масштабируются горизонтально и параллельной обработкой, но количество воркеров и prefetch нужно выбирать с учётом downstream-систем и требований к порядку.

## 11. Отличия RabbitMQ vs Kafka

RabbitMQ и Kafka часто сравнивают, но у них разные архитектурные модели.

**RabbitMQ — Message Broker**
- Сообщения маршрутизируются через Exchange.
- Очереди хранят сообщения до обработки.
- Consumer подтверждает обработку через ACK.
- Поддерживаются разные стратегии маршрутизации, retry и DLQ.

**Kafka — Distributed Event Log**
- События записываются в топики и партиции.
- Хранение определяется retention-политикой.
- Consumer читает сообщения по offset.
- Независимые Consumer Group могут читать один топик.
- Можно повторно читать события, пока они не удалены политикой хранения.

**Ключевое отличие**: ACK в RabbitMQ подтверждает обработку конкретной доставки, после чего сообщение обычно удаляется из очереди. В Kafka Consumer фиксирует позицию чтения (offset), а само событие продолжает храниться в топике согласно retention.

**Пример**

Событие `payment.completed` в RabbitMQ можно отправить через Exchange в несколько очередей. В Kafka событие записывается в топик, а независимые Consumer Group читают его каждая со своей позиции.

|Сценарий|RabbitMQ|Kafka|
|---|---|---|
|Фоновые задания|Отлично подходит|Возможно, но часто избыточно|
|Retry и DLQ|Есть развитые механизмы|Часто реализуются приложением и отдельными топиками|
|Replay событий|Не основная модель|Одна из основных возможностей|
|Сложная маршрутизация|Сильная сторона|Обычно реализуется через топики и код потребителей|
|Длительное хранение|Не основное назначение|Поддерживается retention|
|Потоковая аналитика|Не основное назначение|Сильная сторона|

Их можно использовать вместе, например Kafka как event log, RabbitMQ для конкретных фоновых задач. Но два брокера увеличивают сложность инфраструктуры.

Главное: RabbitMQ — брокер доставки и маршрутизации, Kafka — распределённый журнал событий. RabbitMQ удобен для task processing, Kafka — для event streaming и replay.

## 12. Как бороться с message poisoning?

Message Poisoning — ситуация, когда сообщение постоянно вызывает ошибку обработки и многократно возвращается в очередь. Такое сообщение называют Poison Message.

Например, Consumer получает некорректный JSON, падает и отправляет `NACK` с `requeue=true`. Брокер снова доставляет то же сообщение, и цикл повторяется.

**Чем это опасно?** Consumer тратит ресурсы на одно и то же сообщение, очередь хуже обрабатывается, растёт нагрузка на БД и внешние сервисы, остальные сообщения ждут.

**1. Ограничивать количество попыток**

Задать максимальное число обработок. После достижения лимита сообщение отправляется в DLQ.

**2. Использовать Dead Letter Queue**

DLQ — отдельная очередь для сообщений, которые не удалось обработать:

```text
Main Queue -> Consumer
                 | success -> ACK
                 | failure -> Retry
                               | attempts exceeded -> DLQ
```

**3. Разделять ошибки**
- Временные: timeout API, недоступность БД, сетевой сбой, rate limit. Их можно повторять.
- Постоянные: некорректный формат, отсутствующее обязательное поле, неизвестный тип события, нарушение бизнес-правил. Их лучше отправлять в DLQ.

**4. Логировать контекст**: message ID, routing key, тип ошибки, число попыток, время последней обработки и идентификатор Consumer-а.

**5. Предусмотреть ручной разбор**: DLQ позволяет исследовать проблемные сообщения, исправить причину и при необходимости повторно отправить их.

Не стоит бесконечно использовать `NACK(requeue=true)`. Также не следует полагаться только на `x-death` для подсчёта всех возможных повторов: схему retry нужно проектировать явно.

Главное: Message Poisoning устраняется лимитом попыток, разделением временных и постоянных ошибок, DLQ и логированием. Бесконечный requeue — плохая стратегия.

## 13. Как реализовать retry с backoff?

Retry — повторное выполнение операции после временной ошибки. Backoff — увеличение интервала между попытками, чтобы не перегружать систему.

**Fixed Delay** — постоянный интервал между попытками:

```text
1 сек -> 1 сек -> 1 сек -> 1 сек
```

Просто, но при массовом отказе много Consumer-ов могут повторять запросы одновременно.

**Exponential Backoff** — увеличение задержки:

```text
delay = min(initial_delay * 2^attempt, max_delay)
```

Например: 1, 2, 4, 8, 16 секунд.

**Exponential Backoff + Jitter** добавляет случайность:

```text
delay = random(0, min(max_delay, initial_delay * 2^attempt))
```

Это уменьшает вероятность Thundering Herd, когда множество клиентов одновременно повторяют запрос.

**Retry через TTL и Dead Letter Exchange**

Можно создать retry-очереди с разными TTL: `retry_5s`, `retry_30s`, `retry_5m`. После истечения TTL сообщение через DLX возвращается в основную очередь.

```text
Main Queue -> Consumer -> temporary error
                              |
                              v
                         Retry Queue
                           TTL 5 sec
                              |
                              v
                         Dead Letter Exchange
                              |
                              v
                           Main Queue
```

**Пример объявления retry-очереди на Go**

```go
args := amqp.Table{
    "x-message-ttl":             int32(5000),
    "x-dead-letter-exchange":    "orders",
    "x-dead-letter-routing-key": "order.process",
}

_, err := ch.QueueDeclare(
    "orders.retry.5s",
    true, false, false, false, args,
)
if err != nil { log.Fatal(err) }
```

При ошибке Consumer публикует сообщение в retry-маршрут и подтверждает исходное только после подтверждения новой публикации брокером. Для этого нужны Publisher Confirms: иначе между ACK исходного сообщения и публикацией повторной версии можно потерять задачу.

**Ограничение попыток**

```text
Attempt 1 -> 5 sec
Attempt 2 -> 30 sec
Attempt 3 -> 5 min
Attempt 4 -> DLQ
```

Повторять нужно только временные ошибки. Для постоянных ошибок лучше сразу использовать DLQ. TTL + DLX — распространённый способ отложенной доставки, но его поведение и ограничения нужно проверять для выбранной версии и типа очереди.

Главное: Retry с backoff позволяет повторять временно неудачные операции без постоянной нагрузки. Используют exponential backoff с jitter, лимит попыток и DLQ.

## 14. Когда RabbitMQ — плохой выбор?

**1. Нужен долговременный журнал событий.** Если события нужно хранить и многократно читать разными потребителями, Kafka часто подходит лучше.

**2. Нужны высокий throughput и потоковая аналитика.** При огромном потоке событий, вычислениях над потоками и масштабировании через партиции стоит рассмотреть Kafka или streaming-платформы.

**3. Нужен произвольный replay.** В Kafka можно перемещать offset и повторно читать сохранённые события. В RabbitMQ повторное чтение уже подтверждённых сообщений не является штатной моделью.

**4. Нужен строгий глобальный порядок.** Несколько Consumer-ов могут обрабатывать сообщения параллельно, поэтому порядок завершения не гарантируется. Потребуется сериализация или разделение потоков по ключам.

**5. Брокер избыточен.** Для небольшой системы с парой фоновых задач может хватить таблицы задач в БД или уже имеющейся очереди.

**6. Нет ресурсов на эксплуатацию.** RabbitMQ требует мониторинга, контроля диска и памяти, настройки отказоустойчивости, обновлений, резервного копирования и обработки DLQ.

|Требование|Что рассмотреть|
|---|---|
|Долговременный журнал событий|Kafka|
|Потоковая обработка|Kafka, Flink|
|Простая фоновая задача|Очередь задач или БД|
|Распределённая маршрутизация|RabbitMQ|
|Хранение и replay событий|Kafka|

Главное: RabbitMQ плохой выбор, когда нужен долговременный event log, произвольное повторное чтение, потоковая аналитика или эксплуатационная стоимость не оправдана. Технологию выбирают под требования.

## 15. Как мониторить лаги и залипшие очереди?

Мониторинг нужен, чтобы обнаруживать ситуации, когда сообщения поступают быстрее, чем обрабатываются, Consumer-ы перестают работать или сообщения долго остаются неподтверждёнными. В RabbitMQ нет полного аналога Kafka Consumer Lag в виде одного универсального offset-расхождения: состояние оценивают по метрикам очередей и потребителей.

**Основные метрики**

**Ready Messages** — количество сообщений, ожидающих получения Consumer-ом. Постоянный рост означает, что потребители не справляются или не работают.

**Unacked Messages** — количество доставленных, но ещё не подтверждённых сообщений. Высокое значение может указывать на медленную обработку, зависших Consumer-ов, большой prefetch или долгие внешние запросы.

**Consumer Count** — число активных потребителей. Ноль Consumer-ов при растущей очереди — повод для алерта.

**Publish Rate** — скорость поступления сообщений.

**Deliver / Ack Rate** — скорость доставки и подтверждения. Если Publish Rate стабильно выше Ack Rate, очередь накапливается.

**Message Age** — возраст самого старого сообщения. Даже небольшая очередь может быть проблемной, если сообщения ждут слишком долго.

**DLQ Size** — количество сообщений в Dead Letter Queue. Рост может указывать на ошибки обработки или проблемы зависимостей.

**Management API**

RabbitMQ Management Plugin предоставляет UI и HTTP API. Например:

```bash
curl -u guest:guest http://localhost:15672/api/queues
```

В ответе полезны поля `messages_ready`, `messages_unacknowledged`, `messages`, `consumers`, а также статистика скоростей, если она включена и доступна.

**Пример диагностики**

|Метрика|Значение|
|---|---:|
|Ready|50 000|
|Unacked|2 000|
|Consumers|10|
|Publish Rate|500 msg/sec|
|Ack Rate|100 msg/sec|

Сообщения поступают значительно быстрее, чем обрабатываются. Нужно проверить количество Consumer-ов, CPU и память, задержки БД и внешних API, prefetch, блокировки и зависшие операции.

**Инструменты**
- RabbitMQ Management UI — очереди, соединения, каналы и потребители.
- RabbitMQ Prometheus Plugin — экспорт метрик.
- Prometheus — сбор и хранение метрик.
- Grafana — дашборды и алерты.
- Логи приложения — ошибки и длительность обработки.

**Полезные алерты**
- Ready Messages растёт дольше заданного интервала.
- Возраст самого старого сообщения превышает SLA.
- Unacked долго остаётся высоким.
- У очереди нет активных Consumer-ов.
- Быстро растёт DLQ.
- Ack Rate существенно ниже Publish Rate.
- Брокеру не хватает памяти или дискового пространства.

Большой размер очереди сам по себе не всегда означает аварию: после краткого всплеска нагрузки очередь может разгрузиться. Важны динамика, возраст сообщений и соответствие скорости обработки требованиям.

Главное: отслеживай Ready, Unacked, Consumer Count, Publish Rate, Ack Rate, возраст сообщений и DLQ. Это помогает найти узкое место в брокере, Consumer-ах, БД или внешних сервисах.

# ✦ Kafka

## 1. Что такое Apache Kafka и для чего он используется?

Apache Kafka — распределённая платформа для публикации, хранения и обработки потоков событий (event streaming platform). Она позволяет сервисам передавать события друг другу, хранить их заданное время и независимо читать нескольким потребителям.

В отличие от классической очереди, где сообщение обычно удаляется после ACK, Kafka хранит события в журнале согласно retention-политике. Потребитель самостоятельно отслеживает позицию чтения.

**Сценарии использования**

- Асинхронное взаимодействие микросервисов и event-driven архитектура.
- Сбор и обработка событий из разных систем.
- Передача данных между сервисами и хранилищами.
- Потоковая аналитика и CDC-пайплайны.
- Хранение событий для последующего повторного чтения (replay).

**Пример:** сервис заказов публикует `order.created`. Событие независимо читают уведомления, аналитика, биллинг и склад.

Главное: Kafka — распределённая платформа потоковой передачи событий, подходящая для надёжной передачи, хранения и независимой обработки больших потоков данных.

## 2. Какие основные компоненты Kafka (topics, brokers, producers, consumers)?

**Topic** — логический канал, в который записываются сообщения: `orders`, `payments`, `user-events`. Topic разделён на partitions.

**Broker** — сервер Kafka, который хранит партиции и обслуживает Producer-ов и Consumer-ов. Несколько брокеров образуют кластер.

**Producer** — приложение, публикующее сообщения в topic. При отправке оно выбирает partition с помощью key, partitioner или явного указания.

**Consumer** — приложение, читающее и обрабатывающее сообщения. Обычно работает в consumer group и отслеживает offset.

```text
Producer -> Kafka Cluster -> Topic -> Partitions -> Consumer Group
                  |                         |       /    |    \\
               Brokers                   P0 P1 P2    C1   C2   C3
```

**Дополнительные компоненты:** Controller управляет метаданными и состоянием кластера (в современных кластерах используется KRaft); Kafka Connect интегрирует внешние системы; Schema Registry хранит схемы сообщений; Kafka Streams — библиотека потоковой обработки.

Главное: Topic — логический поток событий, Broker — сервер Kafka, Producer публикует сообщения, Consumer читает их, а partitions распределяют хранение и обработку.

## 3. Что такое partition и зачем он нужен?

Partition — упорядоченная часть topic, представляющая собой последовательный журнал сообщений. Каждая партиция имеет лидера и может иметь реплики на других брокерах. Сообщения получают offsets, уникальные в пределах партиции.

**Зачем нужны partitions?**

1. Масштабирование хранения по брокерам.
2. Параллельная обработка разными Consumer-ами группы.
3. Сохранение порядка внутри одной партиции.
4. Распределение нагрузки.

```text
Topic: orders
Partition 0: [0] [1] [2] [3]
Partition 1: [0] [1] [2]
Partition 2: [0] [1] [2] [3] [4]
```

**Как выбирается partition?** Если указан key, Producer обычно использует partitioner, чтобы одинаковые ключи попадали в одну партицию. Без key распределение зависит от partitioner и версии клиента. Можно указать partition явно.

Если key — `order_id`, события одного заказа будут попадать в одну партицию. Количество partitions влияет на параллелизм, ресурсы кластера и распределение ключей. Его увеличение может изменить соответствие key и partition при стандартном partitioner.

Главное: Partition — единица параллелизма и репликации Kafka. Порядок гарантируется внутри партиции, поэтому key и количество partitions нужно выбирать осознанно.

## 4. Как Kafka обеспечивает устойчивость при отказах (replication)?

Kafka реплицирует партиции между брокерами.

- **Leader** — реплика, обслуживающая чтение и запись.
- **Followers** — реплики, копирующие данные лидера.
- **ISR (In-Sync Replicas)** — реплики, достаточно синхронизированные с лидером и пригодные для безопасного выбора нового лидера.

**Replication Factor** — число копий партиции. Например, `replication.factor=3` означает лидера и две follower-реплики.

**Параметр acks у Producer:**

- `acks=0` — подтверждение не ожидается.
- `acks=1` — подтверждает лидер после записи на своей стороне.
- `acks=all` — ждёт подтверждения всеми текущими репликами из ISR с учётом `min.insync.replicas`.

Для критичных данных используют `acks=all`, подходящий replication factor и `min.insync.replicas`.

```properties
replication.factor=3
min.insync.replicas=2
```

Если ISR меньше минимума, запись с `acks=all` отклоняется, а не принимается с ослабленной гарантией.

**Unclean Leader Election:** выбор отстающей реплики повышает доступность, но может привести к потере подтверждённых данных. При приоритете сохранности данных его обычно отключают.

Главное: Kafka использует leader/follower-репликацию и ISR. Для надёжной записи важны `acks=all`, `min.insync.replicas` и корректный replication factor.

## 5. Что такое consumer group и как она работает?

Consumer Group — группа Consumer-ов, совместно читающих topic. Kafka распределяет partitions между участниками. В одной группе одна partition в каждый момент назначается не более чем одному активному Consumer-у.

```text
Topic: orders (P0 P1 P2 P3)
Consumer Group:
C1 -> P0, P1
C2 -> P2, P3
```

Группы позволяют масштабировать обработку. Один topic могут независимо читать `notification-group`, `analytics-group` и `billing-group`; каждая группа имеет собственные committed offsets.

Если Consumer-ов больше, чем partitions, лишние участники простаивают. При отказе Consumer-а Kafka запускает rebalance и перераспределяет его партиции.

Главное: Consumer Group масштабирует обработку topic. Каждая partition назначается одному Consumer-у внутри группы, но разные группы могут независимо читать один поток событий.

## 6. Объясните разницу между at least once, at most once и exactly once delivery semantics.

Delivery Semantics определяет гарантии доставки и обработки.

**At-most-once:** сообщение обрабатывается ноль или один раз. Дубликатов не ожидается, но возможна потеря. Например, Consumer фиксирует offset до обработки и падает после commit.

**At-least-once:** сначала выполняется обработка, затем commit offset. Если приложение упадёт между этими действиями, сообщение будет прочитано повторно. Потеря менее вероятна, но возможны дубликаты.

**Exactly-once:** результат отражается ровно один раз в пределах определённой транзакционной границы. Kafka умеет атомарно записывать результаты в Kafka и фиксировать offsets входных сообщений. Это не распространяется автоматически на PostgreSQL или HTTP API.

|Семантика|Потеря|Дубликаты|
|---|---|---|
|At-most-once|Возможна|Не ожидаются в рамках схемы|
|At-least-once|Избегают при корректном порядке|Возможны|
|Exactly-once|Предотвращается в границах механизма|Предотвращаются в границах механизма|

Главное: At-most-once допускает потерю, at-least-once — дубликаты, exactly-once действует только в пределах поддерживаемой транзакционной границы.

## 7. Что такое offset и как он управляется?

Offset — порядковый номер сообщения внутри конкретной partition. Он позволяет Consumer-у отслеживать позицию чтения и продолжать после перезапуска.

```text
Partition 0:  A  B  C  D  E  F
Offset:       0  1  2  3  4  5
                       ^
```

Kafka хранит committed offsets в служебном topic `__consumer_offsets`. Offset фиксируется отдельно для пары consumer group и partition.

**Автоматический commit:** при `enable.auto.commit=true` клиент периодически фиксирует offsets. Это удобно, но commit может произойти раньше бизнес-обработки и привести к пропуску события.

**Ручной commit:** при `enable.auto.commit=false` приложение само выбирает момент:

```text
Read -> Process -> Commit offset
```

Для at-least-once обычно сначала выполняют бизнес-операцию, затем commit. Committed offset обычно обозначает следующую позицию чтения: после обработки offset 10 часто фиксируется 11.

**Consumer Lag** — разница между последним доступным offset и позицией Consumer Group. Большой lag означает отставание.

Главное: Offset — позиция чтения внутри partition. Момент его фиксации определяет, с какого места Consumer продолжит работу, и влияет на семантику доставки.

## 8. Как работает лидерство и репликация в кластере Kafka?

Каждая partition имеет одну лидерскую реплику и follower-реплики.

**Leader** обслуживает запись и, как правило, чтение. **Follower** копирует записи с лидера. Достаточно синхронизированные реплики входят в ISR.

**Запись:** Producer отправляет запись лидеру; лидер добавляет её в журнал; followers копируют данные; Producer получает подтверждение в зависимости от `acks`.

**Отказ лидера:** если брокер недоступен, контроллер инициирует выбор нового лидера из допустимых реплик, обычно из ISR.

**Controller** управляет состоянием кластера, назначением лидеров и изменениями состава брокеров. В современных версиях используется KRaft с quorum контроллеров; в старых инсталляциях применялся ZooKeeper.

Главное: Leader обслуживает партицию, Followers реплицируют данные, ISR определяет синхронизированные реплики, Controller управляет лидерством и состоянием кластера.

## 9. Что такое log compaction и зачем он нужен?

Log Compaction — механизм, при котором для каждого key со временем сохраняется последнее актуальное значение, а старые версии того же ключа могут быть удалены.

**Пример**

До compaction:

```text
user-1 -> John
user-2 -> Alice
user-1 -> John Smith
user-3 -> Bob
```

После compaction может остаться:

```text
user-1 -> John Smith
user-2 -> Alice
user-3 -> Bob
```

**Для чего используется?** Хранение последнего состояния сущностей, синхронизация справочников, восстановление состояния приложения и changelog для stateful stream processing.

**Tombstone** — запись с key и `value=null`, обозначающая удаление ключа. Она хранится в течение настроенного периода, после чего может быть удалена при compaction.

Compaction не выполняется мгновенно, старые записи некоторое время могут оставаться в сегментах. Для полезной семантики последнего значения нужен key.

Главное: Log Compaction позволяет хранить последнее известное значение для каждого ключа. Это полезно для changelog, синхронизации и восстановления состояния сущностей.

## 10. Чем Kafka отличается от классического брокера сообщений (RabbitMQ)?

**RabbitMQ:** модель очередей и маршрутизации; Exchange направляет сообщения в очереди; Consumer подтверждает обработку ACK; после подтверждения сообщение обычно удаляется; есть routing, retry, TTL и DLQ.

**Kafka:** модель распределённого журнала событий; сообщения записываются в topic и partitions; Consumer отслеживает offset; сообщения хранятся согласно retention-политике; разные consumer groups независимо читают один поток; поддерживается replay.

|Критерий|RabbitMQ|Kafka|
|---|---|---|
|Модель|Очереди и маршрутизация|Распределённый log|
|Подтверждение|ACK сообщения|Commit offset|
|Хранение|Обычно до обработки|По retention-политике|
|Повторное чтение|Не основная модель|Штатная возможность|
|Маршрутизация|Exchange и bindings|Topic, partition, key|
|Типичные задачи|Фоновые задачи, task queue|Event streaming, event log|

RabbitMQ удобен для распределения заданий между воркерами, Kafka — для хранения потока событий, независимого потребления и replay.

Главное: RabbitMQ в первую очередь доставляет сообщения через очереди, Kafka хранит поток событий в распределённом журнале. Выбор зависит от требований к хранению, повторному чтению и маршрутизации.

## 11. Какие стратегии обработки ошибок в Kafka вы знаете?

Ошибки бывают временными, постоянными и инфраструктурными.

**1. Retry.** Повтор полезен при временных ошибках: timeout API, недоступность БД, сетевые сбои, rate limit. Нужно ограничивать число попыток и использовать backoff.

**2. Retry Topic.** Вместо немедленного повтора сообщение публикуется в отдельный topic:

```text
orders -> Consumer
              |
         temporary error
              |
              v
         orders.retry
              |
              v
         Retry Consumer
```

Можно создать несколько retry topic с разными задержками: `retry-1m`, `retry-10m`, `retry-1h`.

**3. Dead Letter Topic (DLT/DLQ).** После исчерпания попыток сообщение отправляют в отдельный topic. Сохраняют исходное сообщение, key, исходные topic/partition/offset, количество попыток и причину ошибки.

**4. Пропуск сообщения.** Для некритичных событий иногда допустимо залогировать ошибку и продолжить. Это должно быть осознанным бизнес-решением.

**5. Остановка Consumer-а.** Если ошибка указывает на системную проблему или нарушение инвариантов, безопаснее остановить обработку и поднять alert.

**6. Идемпотентность.** Retry может привести к повторной доставке, поэтому обработчик должен безопасно переносить повтор события.

Если Consumer публикует сообщение в retry topic и затем фиксирует исходный offset, публикация должна быть подтверждена. Иначе можно зафиксировать исходное сообщение, не сохранив retry-копию. Для Kafka-to-Kafka сценариев можно использовать транзакции.

Главное: Типичная стратегия — ограниченный retry с backoff, затем DLT. Важно не потерять сообщение при переносе в retry и обеспечить идемпотентность обработчика.

## 12. Объясните, что такое Kafka Connect.

Kafka Connect — платформа интеграции Kafka с внешними системами без написания отдельного Producer или Consumer для каждого источника и приёмника.

**Source Connector** читает данные из внешней системы и публикует их в Kafka.

**Sink Connector** читает сообщения из Kafka и отправляет их во внешнюю систему.

**Worker** — процесс Kafka Connect, запускающий коннекторы и их задачи.

**Task** — единица работы коннектора; несколько tasks позволяют распараллелить обработку.

```text
PostgreSQL -> Source Connector -> Kafka Topic
                                      |
                                      v
                              Sink Connector
                                      |
                                      v
                                Elasticsearch
```

**Режимы работы:** Standalone — один процесс, чаще для разработки и простых сценариев; Distributed — несколько Worker-ов, распределение задач и более высокая доступность.

Применяется для CDC из БД, загрузки данных в аналитические хранилища, интеграции Kafka с внешними системами и репликации данных.

Главное: Kafka Connect — платформа интеграции Kafka с внешними системами через Source и Sink коннекторы. Она уменьшает количество собственного интеграционного кода.

## 13. Зачем нужен Schema Registry (Avro/Protobuf) в Kafka-экосистеме?

Schema Registry — отдельный сервис, который хранит и версионирует схемы сообщений Producer-ов и Consumer-ов. Если Producer меняет структуру сообщения, другие сервисы могут перестать его читать. Registry помогает управлять контрактами и проверять совместимость изменений.

**Популярные форматы**

- Avro — компактный бинарный формат с явной схемой.
- Protobuf — формат сериализации с описанием сообщений в `.proto`.
- JSON Schema — схема для JSON-сообщений.

**Schema Evolution — изменение схемы с сохранением совместимости.** Основные режимы:

- BACKWARD — новая схема может читать данные, записанные по предыдущей схеме.
- FORWARD — предыдущая схема может читать данные, записанные по новой схеме.
- FULL — выполняются оба направления совместимости.
- NONE — проверка совместимости отключена.

Точное поведение зависит от режима и правил конкретного формата.

**Пример Avro-схемы**

```json
{
  "type": "record",
  "name": "Order",
  "fields": [
    {"name": "id", "type": "long"},
    {"name": "status", "type": "string"}
  ]
}
```

Producer и Consumer используют schema ID, чтобы определить, по какой схеме сериализовано сообщение.

Главное: Schema Registry управляет контрактами сообщений и совместимостью их версий. Avro и Protobuf позволяют передавать структурированные данные компактно и контролировать эволюцию схем.

## 14. Как масштабировать продюсеров и потребителей?

Kafka масштабируется горизонтально за счёт брокеров, partitions, Producer-ов и Consumer-ов.

**Масштабирование Producer-ов**

Можно запускать несколько экземпляров приложения. Для повышения пропускной способности используют batching (пакетную отправку), compression (сжатие), асинхронную отправку и настройки `linger.ms`, `batch.size`, `buffer.memory`. Важны partitioner и key. Нужно контролировать `max.in.flight.requests.per.connection` и повторы, если важен порядок.

**Масштабирование Consumer-ов**

Consumer-ы запускаются в одной consumer group, Kafka распределяет между ними partitions:

```text
Topic: orders
P0 P1 P2 P3 P4 P5

C1 -> P0, P1
C2 -> P2, P3
C3 -> P4, P5
```

Максимальный параллелизм одной группы для topic ограничен числом partitions.

На масштабирование влияют число partitions, количество Consumer-ов, скорость обработки, производительность брокеров и downstream-систем, размер сообщений и настройки batching/compression.

Главное: Producer-ы масштабируются количеством экземпляров и настройками batching/compression, Consumer-ы — количеством partitions и участников группы. Для одной группы число одновременно работающих Consumer-ов с topic ограничено количеством его партиций.

## 15. Какие есть ограничения и недостатки Kafka?

1. **Сложность эксплуатации.** Нужно управлять брокерами, дисками, репликацией, partitions, сетевыми соединениями, обновлениями и мониторингом.
2. **Требования к ресурсам.** Kafka использует диск, сеть, память и файловые дескрипторы. Большое количество partitions увеличивает нагрузку.
3. **Порядок событий.** Глобального порядка между partitions нет. Если порядок важен, нужно правильно выбирать key.
4. **Rebalance.** Изменение состава Consumer Group может вызывать перераспределение partitions и временную остановку обработки.
5. **Повторная обработка.** At-least-once может приводить к дубликатам. Обработчики должны быть идемпотентными.
6. **Не всегда подходит для простых очередей задач.** Для гибкой маршрутизации, TTL и ACK/NACK на уровне отдельных сообщений RabbitMQ может быть удобнее.
7. **Ошибки конфигурации.** Неправильные `acks`, `min.insync.replicas`, replication factor или retention могут привести к потере данных либо недостаточной доступности.
8. **Эволюция схем.** Без контроля схем изменение формата сообщений может ломать потребителей.

Главное: Kafka требует продуманного partitioning, настройки репликации, мониторинга и эксплуатации. Она оправдана для потоковой передачи, хранения и повторного чтения событий, но может быть избыточной для простой очереди задач.

## 16. Что будет если у нас 5 партиций и 6 консьюмеров? А если наоборот?

В одной consumer group одна partition назначается не более чем одному активному Consumer-у.

**5 partitions и 6 consumers:** пять Consumer-ов получат по одной партиции, шестой останется без назначения.

```text
P0 -> C1
P1 -> C2
P2 -> C3
P3 -> C4
P4 -> C5
     C6 -> idle
```

**6 partitions и 5 consumers:** один Consumer получит две партиции, остальные — по одной. Точное распределение зависит от assignor.

Максимальное число одновременно активных Consumer-ов для одного topic в группе ограничено количеством partitions.

Главное: При 5 партициях и 6 Consumer-ах один будет простаивать. При 6 партициях и 5 Consumer-ах один Consumer получит две партиции.

## 17. Как обеспечить уникальность данных в разных системах?

Kafka сама по себе не обеспечивает глобальную уникальность бизнес-сущностей между системами. Это задача архитектуры данных и обработки событий.

**1. Уникальный идентификатор события.** Каждое событие должно иметь уникальный `event_id`:

```json
{
  "event_id": "01JXYZ...",
  "event_type": "order.created",
  "order_id": 123,
  "occurred_at": "2026-11-15T10:00:00Z"
}
```

**2. Уникальные ограничения в БД**

```sql
CREATE TABLE processed_events (
    event_id UUID PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL
);
```

Проверка и изменение бизнес-данных должны выполняться в одной транзакции.

**3. Идемпотентная операция.** Повторное выполнение не должно создавать повторный бизнес-эффект. Для финансовой операции можно использовать idempotency key.

**4. Единый источник идентификаторов.** Если сущность создаётся в нескольких системах, нужно договориться о стратегии: UUID, ULID или централизованный ID.

**5. Разделять event_id и entity_id.** `event_id` идентифицирует событие; `entity_id` — бизнес-сущность. У одной сущности может быть много событий.

Producer Idempotence предотвращает определённые дубликаты публикации в Kafka, но не заменяет бизнес-идемпотентность между системами.

Главное: Для уникальности нужны стабильные идентификаторы событий и сущностей, уникальные ограничения в хранилищах и идемпотентная бизнес-обработка. Kafka не обеспечивает глобальную уникальность самостоятельно.

## 18. Как outbox pattern связан с Kafka?

Transactional Outbox решает проблему двойной записи (Dual Write Problem): сервису нужно сохранить данные в БД и опубликовать событие в Kafka.

**Проблема:** сервис сохраняет заказ в PostgreSQL, затем публикует `order.created`. Если БД сохранила заказ, а Kafka недоступна, событие не будет опубликовано. Обратная ситуация тоже опасна: событие опубликовано, но транзакция БД откатилась.

**Как работает Outbox?**

Сервис записывает бизнес-данные и событие в outbox-таблицу в рамках одной транзакции БД.

```text
Application
    |
PostgreSQL Transaction
    +---- orders
    +---- outbox
              |
        Outbox Publisher
              |
             Kafka
```

**Пример таблицы**

```sql
CREATE TABLE outbox (
    id UUID PRIMARY KEY,
    aggregate_id UUID NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    published_at TIMESTAMP
);
```

**Алгоритм**

1. Начать транзакцию.
2. Сохранить заказ.
3. Добавить событие в outbox.
4. Закоммитить транзакцию.
5. Фоновый процесс читает неопубликованные записи.
6. Публикует их в Kafka.
7. После подтверждения помечает записи опубликованными.

Бизнес-изменение и запись события фиксируются атомарно. Но дубликаты возможны: Publisher может опубликовать сообщение и упасть до обновления `published_at`. Поэтому нужны стабильный ID и идемпотентные потребители.

**Как читать outbox?**

- Polling Publisher — периодически выбирает неопубликованные записи.
- CDC — отслеживает изменения через журнал транзакций, например с помощью Debezium.

Главное: Outbox связывает транзакцию бизнес-БД с последующей публикацией в Kafka. Он предотвращает потерю события между записью в БД и отправкой в брокер, но обычно допускает дубликаты.

## 19. Почему ordering гарантируется только внутри partition?

Kafka гарантирует порядок записей внутри одной partition, потому что она представляет собой последовательный журнал с возрастающими offsets. Между разными partitions общего порядка нет.

```text
Partition 0: A -> B -> C
Partition 1: D -> E -> F
```

Порядок A, B, C и D, E, F сохраняется внутри своих партиций. Но глобальная последовательность между A и D не определена: Consumer-ы могут читать партиции параллельно, а скорость обработки отличаться.

**Как сохранить порядок для сущности?**

Использовать одинаковый key для всех событий одной сущности. Например, `order_id`: события конкретного заказа попадут в одну partition.

**Что может нарушить порядок на уровне приложения?**

Даже если Kafka доставила записи в правильном порядке, Consumer может обрабатывать их параллельно в goroutine и завершить операции в другом порядке. Для сохранения порядка нужно сериализовать обработку сообщений соответствующей партиции или ключа.

Главное: Kafka гарантирует порядок внутри partition, но не между партициями. Для порядка событий одной сущности используйте единый key и не распараллеливайте их обработку без контроля.

## 20. Что будет при rebalance consumer group?

Rebalance — процесс перераспределения partitions между Consumer-ами одной группы. Он происходит при изменении состава группы или назначения партиций.

**Причины**

- Новый Consumer присоединился к группе.
- Consumer завершил работу или потерял соединение.
- Consumer перестал отправлять heartbeat.
- Изменилось количество partitions.
- Изменились подписки участников.

**Как происходит?**

1. Координатор обнаруживает изменение состава группы.
2. Участники проходят процедуру перераспределения.
3. Старые назначения отзываются.
4. Вычисляется новое распределение.
5. Consumer-ы получают partitions и продолжают с committed offsets.

```text
До:
C1 -> P0, P1
C2 -> P2, P3

После подключения C3:
C1 -> P0, P1
C2 -> P2
C3 -> P3
```

**Чем опасен rebalance?**

- Временно прекращается обработка некоторых партиций.
- Может увеличиться lag.
- Незавершённая обработка может привести к повторной доставке.
- Частые rebalance снижают пропускную способность.

**Как уменьшить проблемы?**

- Правильно настраивать heartbeat и session timeout.
- Не блокировать Consumer долгими операциями между poll.
- Использовать cooperative sticky assignment, если поддерживается клиентом и конфигурацией.
- Корректно завершать Consumer и освобождать ресурсы.
- Не запускать и не останавливать экземпляры без необходимости.

Главное: Rebalance перераспределяет partitions между участниками группы. Он нужен для отказоустойчивости и масштабирования, но частые rebalance вызывают паузы обработки и рост lag.

## 21. Как избежать duplicate processing?

Duplicate Processing — повторная обработка одного сообщения. В Kafka она возможна при at-least-once семантике.

**Почему возникают дубликаты?**

1. Consumer обработал сообщение, но упал до commit offset.
2. После rebalance сообщение было назначено другому Consumer-у.
3. Producer повторно отправил сообщение после неопределённого результата запроса.
4. Outbox Publisher повторно опубликовал событие после сбоя.

**1. Идемпотентный Consumer**

Повторная обработка события не должна создавать повторный бизнес-эффект.

**2. Таблица обработанных событий**

```sql
CREATE TABLE processed_events (
    event_id UUID PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL DEFAULT now()
);
```

Обработка события и запись его ID выполняются в одной транзакции:

```text
BEGIN
  INSERT event_id
  UPDATE business_data
COMMIT
```

Если `event_id` уже существует, событие не применяется повторно.

**3. Kafka Producer Idempotence**

`enable.idempotence=true` защищает от определённых дубликатов при повторной отправке записей Producer-ом в Kafka. Это не защищает от повторной бизнес-обработки в Consumer-е.

**4. Транзакции Kafka**

Kafka Transactions позволяют атомарно записывать сообщения в Kafka и фиксировать offsets в Kafka-to-Kafka обработке.

**5. Правильный порядок commit**

Для at-least-once сначала выполняют бизнес-обработку, затем commit offset. Это может привести к повтору после сбоя, но позволяет не пропустить необработанное сообщение.

Главное: Не полагайтесь только на Kafka для устранения всех дубликатов. Используйте стабильный event_id, уникальные ограничения в БД, транзакции и идемпотентную бизнес-логику.

## 22. Exactly-once — где реально работает, а где маркетинг?

Exactly-once часто понимают как гарантию, что сообщение во всей распределённой системе будет обработано ровно один раз. Это слишком широкое утверждение. Kafka поддерживает exactly-once semantics в определённых сценариях работы с самой Kafka.

**Kafka-to-Kafka**

1. Consumer читает сообщения из входного topic.
2. Приложение обрабатывает их.
3. Producer записывает результат в выходной topic.
4. В одной Kafka-транзакции фиксируются выходные сообщения и offsets входных сообщений.

Если транзакция не завершилась успешно, результаты не будут видны потребителям с `read_committed`.

**Механизмы**

- `enable.idempotence=true` — защита от определённых дубликатов при повторной отправке.
- `transactional.id` — идентификатор транзакционного Producer-а.
- `beginTransaction`, `sendOffsetsToTransaction`, `commitTransaction` — API транзакционной публикации.
- `isolation.level=read_committed` — Consumer читает только записи завершённых транзакций.

**Где не работает автоматически?**

Если Consumer записывает данные в PostgreSQL, вызывает HTTP API, отправляет email или списывает деньги во внешней системе, Kafka не может автоматически включить эти действия в свою транзакцию.

Например, Consumer списал деньги, но упал до commit offset. При повторной доставке он может списать деньги ещё раз.

**Как решают проблему?**

- Идемпотентность операций.
- Уникальные idempotency key.
- Транзакции в целевой БД.
- Таблица обработанных событий.
- Transactional Outbox/Inbox.

Главное: Exactly-once в Kafka-to-Kafka сценариях можно обеспечить транзакциями и `read_committed`. Для внешних систем всё равно нужны идемпотентность и собственные механизмы согласованности.

## 23. Почему commit offset ≠ обработка события?

Commit offset означает, что Kafka сохранила позицию чтения Consumer Group. Это не означает, что бизнес-операция успешно завершилась. Kafka не знает, записывает ли Consumer данные в БД, вызывает API или отправляет уведомление.

**Опасный сценарий: commit до обработки**

```text
1. Consumer читает сообщение
2. Commit offset
3. Consumer падает
4. Бизнес-операция не выполнена
5. Kafka считает сообщение прочитанным
```

Событие может быть пропущено приложением.

**At-least-once: обработка до commit**

```text
1. Consumer читает сообщение
2. Выполняет бизнес-операцию
3. Consumer падает до commit
4. Kafka повторно доставляет сообщение
5. Бизнес-операция может выполниться повторно
```

Здесь появляется риск дубликата, но событие не будет считаться обработанным до фиксации offset.

**Как сделать надёжнее?**

Если операция выполняется в БД, в одной транзакции можно:

1. Проверить и записать `event_id` в таблицу обработанных событий.
2. Изменить бизнес-данные.
3. Зафиксировать транзакцию.
4. После этого commit offset в Kafka.

Если приложение упадёт после транзакции БД, но до commit offset, событие придёт повторно. Уникальный `event_id` позволит обнаружить повтор и не применить операцию второй раз.

Главное: Commit offset фиксирует позицию чтения, а не результат внешней бизнес-операции. Порядок обработки и commit, а также идемпотентность определяют надёжность Consumer-а.

## 24. Как выбрать key для partitioning?

Key определяет, в какую partition будет направлено сообщение при использовании стандартной key-based стратегии Producer-а. Он влияет на порядок событий и распределение нагрузки.

**1. Выбирать ключ по сущности, для которой важен порядок**

Для событий заказа: `key = order_id`. События одного заказа будут попадать в одну partition.

**2. Избегать горячих ключей**

Если большая часть сообщений имеет один key, они будут направляться в одну partition. Это создаёт hot partition: одна партиция перегружена, остальные недоиспользуются.

**3. Учитывать кардинальность и распределение**

Хороший ключ обычно имеет много различных значений и равномерное распределение. `country` может быть плохим ключом, если большинство событий относится к одной стране. `user_id` или `order_id` часто распределяют нагрузку лучше, но выбор зависит от требований к порядку.

**4. Не использовать случайный key, если важен порядок сущности**

Случайный key распределяет нагрузку, но события одной сущности могут попасть в разные partitions.

**5. Учитывать изменение числа partitions**

При стандартном hash partitioner увеличение числа partitions может изменить соответствие key и partition. События одного ключа, опубликованные до и после изменения, могут оказаться в разных партициях.

Главное: Key выбирают исходя из сущности, для которой важен порядок. Нужно учитывать равномерность распределения, риск hot partition и последствия изменения числа partitions.

## 25. Как бы ты отлаживал потерю событий, если метрики "зелёные"?

Если бизнес утверждает, что события теряются, а метрики Kafka выглядят нормально, нужно проследить путь конкретного события от источника до конечного эффекта. Зелёные метрики брокера не доказывают, что бизнес-событие действительно обработано.

**1. Проверить источник события**

- Было ли событие создано?
- Зафиксировалась ли бизнес-транзакция?
- Записано ли событие в outbox?
- Не потерялось ли событие до вызова Producer-а?

**2. Проверить публикацию**

- Получил ли Producer успешный результат отправки?
- Обрабатываются ли callbacks и ошибки?
- Используются ли `acks=all` и idempotent producer?
- Нет ли ошибок сериализации?
- Не отправляется ли сообщение не в тот topic?

Логировать `event_id`, topic, key, partition и offset после успешной публикации.

**3. Проверить наличие события в Kafka**

Найти конкретный `event_id` в topic, проверить partition и offset. Проверить кластер и topic, retention, log compaction, альтернативный topic и записи с тем же key в compacted topic.

**4. Проверить Consumer Group**

- Та ли группа читает topic?
- Какой committed offset у группы?
- Какой end offset у partition?
- Есть ли lag?
- Не произошёл ли commit до завершения обработки?
- Нет ли частых rebalance?

**5. Проверить обработку в приложении**

- Не отбрасывает ли код сообщение из-за фильтра или валидации?
- Нет ли ошибки десериализации?
- Не завершается ли обработчик без записи в БД?
- Не теряются ли ошибки в goroutine?
- Не подтверждается ли сообщение до завершения обработки?

**6. Проверить внешнюю систему**

Проверить выполнение SQL-запроса, rollback транзакции, уникальные ограничения, ошибочную дедупликацию и перезапись результата более поздним процессом.

**7. Проверить корреляцию и трассировку**

У каждого события должен быть стабильный `event_id` или correlation ID, который попадает в логи Producer-а, Consumer-а и внешних операций.

```text
event_id -> Source / Outbox
         -> Producer -> topic / partition / offset
         -> Consumer Group
         -> Business Handler
         -> Database / External API
```

**8. Воспроизвести проблему**

Если событие найдено в Kafka, но не обработано, его можно безопасно воспроизвести в тестовой среде или отдельной consumer group. В production нельзя бездумно сбрасывать offsets или повторно публиковать события: это может вызвать массовую повторную обработку.

**Что сделать в первую очередь**

1. Взять конкретный потерянный `event_id`.
2. Проверить его наличие в outbox или источнике.
3. Проверить результат публикации и координаты topic/partition/offset.
4. Убедиться, что Consumer Group дошла до нужного offset.
5. Проверить логи обработки и транзакцию целевой БД.
6. Сопоставить время события, commit offset и бизнес-эффект.

Главное: При расследовании «потери» событий нужно проследить один event_id по всей цепочке. Метрики Kafka показывают здоровье брокера и потоки сообщений, но не гарантируют, что бизнес-операция в конечной системе завершилась.

# ✦ CI/CD

## 1. Что такое CI/CD и зачем он нужен?

CI/CD — набор практик и автоматизированных процессов, которые помогают регулярно проверять, собирать, тестировать и доставлять изменения программного обеспечения.

**CI (Continuous Integration)** — непрерывная интеграция изменений в общую кодовую базу с автоматической проверкой.

**CD (Continuous Delivery / Continuous Deployment)** — автоматизация подготовки и выпуска приложения в окружения.

**Зачем нужен CI/CD?**

- Быстрее и безопаснее доставлять изменения.
- Находить ошибки как можно раньше.
- Уменьшать количество ручных операций.
- Делать сборки воспроизводимыми.
- Снижать риск релизов за счёт небольших изменений.
- Быстрее откатывать неудачные версии.
- Обеспечивать единый процесс для всей команды.

**Пример**

Разработчик отправляет Pull Request. CI запускает форматирование, линтеры, unit-тесты и сборку. После merge в основную ветку pipeline собирает Docker-образ, публикует его в registry и может развернуть приложение в staging или production.

```text
Commit / Pull Request
        |
        v
   CI: checks + tests
        |
        v
      Build
        |
        v
   Artifact / Image
        |
        v
   Deploy to staging
        |
        v
   Approval / Deploy
        |
        v
    Production
```

Главное: CI/CD автоматизирует путь от изменения кода до работающего приложения. Это повышает скорость поставки изменений и снижает количество ошибок, связанных с ручными действиями.

## 2. В чём разница между Continuous Integration, Continuous Delivery и Continuous Deployment?

Эти понятия связаны, но описывают разные уровни автоматизации процесса поставки.

**Continuous Integration (CI)**

Разработчики часто интегрируют изменения в общую ветку. Каждое изменение автоматически проверяется: запускаются тесты, линтеры, сборка и другие проверки.

Цель — быстро обнаружить проблемы интеграции, пока изменение небольшое.

**Continuous Delivery**

После CI приложение автоматически собирается и подготавливается к выпуску. Артефакт можно развернуть в production, но сам production-релиз обычно требует ручного подтверждения или решения ответственного лица.

**Continuous Deployment**

Каждое изменение, прошедшее все автоматические проверки, автоматически разворачивается в production без отдельного ручного подтверждения.

**Сравнение**

|Практика|Что автоматизировано|Ручной шаг|
|---|---|---|
|Continuous Integration|Интеграция, сборка, проверки и тесты|Решение о merge может оставаться за разработчиком|
|Continuous Delivery|Подготовка релиза и доставка до готового к production состояния|Обычно подтверждение production-деплоя|
|Continuous Deployment|Весь путь до production|Нет обязательного ручного подтверждения релиза|

**Пример**

1. Разработчик создаёт Pull Request.
2. CI запускает проверки.
3. После merge создаётся артефакт.
4. Continuous Delivery останавливается на этапе готового релиза и ждёт approval.
5. При Continuous Deployment успешный pipeline сам выкатывает версию в production.

Главное: CI проверяет и интегрирует изменения, Continuous Delivery автоматически подготавливает релиз, а Continuous Deployment автоматически выпускает каждое прошедшее проверки изменение в production.

## 3. Какие основные этапы CI/CD-pipeline?

Pipeline — последовательность автоматизированных этапов, которые выполняются после изменения кода или по другому заданному триггеру.

Конкретный набор этапов зависит от проекта, но типичный pipeline backend-сервиса выглядит так:

**1. Trigger**

Запуск pipeline при push, создании Pull Request, merge, создании тега или вручную.

**2. Checkout**

Получение исходного кода из Git-репозитория.

**3. Static Analysis**

Проверка качества кода без запуска приложения:

- форматирование;
- линтеры;
- статический анализ;
- проверка зависимостей;
- поиск потенциальных уязвимостей.

**4. Tests**

Запуск unit-тестов, integration-тестов и других проверок, предусмотренных pipeline.

**5. Build**

Компиляция приложения и создание артефакта. Для Go это может быть бинарный файл, для контейнерного приложения — Docker image.

**6. Security Checks**

Проверка зависимостей, контейнерного образа и конфигураций на известные уязвимости. Секреты также проверяются на случайное попадание в репозиторий.

**7. Publish Artifact**

Публикация артефакта в registry или хранилище сборок. Артефакту присваивается версия или неизменяемый идентификатор, например commit SHA.

**8. Deploy**

Развёртывание в тестовое, staging или production-окружение.

**9. Smoke Tests и Monitoring**

Проверка доступности приложения после деплоя, health checks и наблюдение за ошибками и метриками.

**Пример pipeline**

```text
Push / Pull Request
        |
     Checkout
        |
 Format + Lint
        |
   Unit Tests
        |
Integration Tests
        |
      Build
        |
 Security Checks
        |
 Publish Image
        |
 Deploy to Staging
        |
  Smoke Tests
        |
 Production Deploy
        |
  Health Checks
```

**Пример команд для Go**

```bash
gofmt -w .
go vet ./...
go test ./...
go test -race ./...
go build ./...
```

В реальном CI форматирование обычно сначала проверяют, а не молча изменяют код: например, сравнивают результат `gofmt` с исходными файлами и завершают pipeline ошибкой при расхождении.

Главное: Pipeline обычно включает получение кода, статические проверки, тесты, сборку, security checks, публикацию артефакта, деплой и проверку работоспособности.

## 4. Какие инструменты CI/CD вы знаете (GitHub Actions, GitLab CI, Jenkins, CircleCI и др.) и когда какой использовать?

Инструменты CI/CD автоматизируют выполнение pipeline: запускают команды, тесты, сборки и деплой по заданным правилам.

**GitHub Actions**

Встроен в GitHub и использует YAML-файлы в `.github/workflows`.

Подходит, если код хранится в GitHub и нужен тесно интегрированный CI/CD с Pull Requests, Actions Marketplace и GitHub-hosted или self-hosted runners.

**GitLab CI/CD**

Встроен в GitLab. Pipeline описывается в `.gitlab-ci.yml`, выполнение обеспечивают GitLab Runners.

Удобен, если GitLab используется как единая платформа для репозиториев, merge requests, registry, security checks и CI/CD.

**Jenkins**

Гибкий сервер автоматизации с большим количеством плагинов и возможностью тонко настраивать инфраструктуру и pipeline.

Подходит для сложных корпоративных процессов, интеграции с большим количеством внутренних систем и случаев, когда нужен полный контроль над CI-инфраструктурой. Требует самостоятельного обслуживания.

**CircleCI**

Облачная и self-hosted платформа CI/CD с конфигурацией pipeline в YAML. Может быть удобна командам, которым нужны готовые механизмы параллельных сборок, кеширования и интеграций.

**Другие инструменты**

- TeamCity — CI/CD-сервер с развитой интеграцией в экосистему JetBrains.
- Buildkite — платформа оркестрации pipeline с возможностью выполнять задачи на собственной инфраструктуре.
- Argo CD — инструмент GitOps-доставки приложений в Kubernetes.
- Tekton — Kubernetes-native фреймворк для построения CI/CD pipeline.

**Сравнение**

|Инструмент|Когда использовать|Особенность|
|---|---|---|
|GitHub Actions|Проекты на GitHub|Встроен в GitHub|
|GitLab CI/CD|Проекты на GitLab|Единая DevOps-платформа|
|Jenkins|Сложная корпоративная инфраструктура|Гибкость и большой набор плагинов|
|CircleCI|Команды, которым нужен готовый CI-сервис|Облачные и self-hosted варианты|
|TeamCity|Инфраструктура с инструментами JetBrains|Развитые возможности сборки|
|Argo CD|Доставка в Kubernetes по GitOps|Синхронизация состояния кластера с Git|

**Как выбирать?**

Учитывают место хранения кода, требования безопасности, необходимость self-hosted runners, стоимость, интеграции, масштаб pipeline, поддержку Kubernetes и компетенции команды.

Главное: Универсально лучшего инструмента нет. Для GitHub-проектов часто удобен GitHub Actions, для GitLab — GitLab CI, Jenkins полезен при сложной кастомной инфраструктуре, а Argo CD решает задачу GitOps-доставки в Kubernetes.

## 5. Что такое trunk-based development и как он связан с CI/CD?

Trunk-Based Development — подход к разработке, при котором разработчики часто интегрируют небольшие изменения в одну основную ветку (trunk, обычно `main`).

Вместо долгоживущих feature-веток используются короткоживущие ветки или непосредственные небольшие коммиты в trunk с обязательными автоматическими проверками.

**Как выглядит процесс?**

1. Разработчик создаёт небольшую задачу.
2. Вносит изменение в короткоживущей ветке.
3. Открывает Pull Request.
4. CI запускает тесты, линтеры и сборку.
5. После успешных проверок изменение быстро вливается в `main`.
6. Pipeline собирает и при необходимости доставляет новую версию.

```text
        Feature A
           |
main ------+------------------------>
              ^
        Feature B
           |
       Short-lived
          branch
```

**Связь с CI/CD**

Trunk-based development хорошо сочетается с CI/CD, потому что небольшие изменения часто интегрируются и быстро проходят автоматические проверки. Это уменьшает вероятность конфликтов и проблем от долгоживущих веток.

**Feature Flags**

Если функциональность ещё не готова для пользователей, её можно скрыть за feature flag. Код уже находится в основной ветке, но функция включается отдельно от деплоя.

**Преимущества**

- Меньше сложных merge-конфликтов.
- Частая интеграция изменений.
- Быстрая обратная связь от CI.
- Небольшие и более понятные релизы.
- Проще поддерживать актуальную основную ветку.

**Риски и условия**

- Основная ветка должна оставаться в рабочем состоянии.
- Нужны быстрые и надёжные автоматические тесты.
- Незавершённую функциональность нужно изолировать feature flags.
- Изменения схем БД и контрактов должны быть совместимыми с предыдущими версиями приложения.

Главное: Trunk-based development строится вокруг частой интеграции небольших изменений в основную ветку. CI обеспечивает быстрые проверки, а CD помогает регулярно и безопасно доставлять эти изменения.

## 6. Какие стратегии развертывания существуют (blue/green, canary, rolling)?

Стратегия deployment определяет, как новая версия приложения заменяет старую и как распределяется пользовательский трафик во время обновления.

**1. Rolling Deployment**

Новая версия постепенно заменяет старые экземпляры приложения.

```text
Начало:  v1  v1  v1  v1
Шаг 1:   v2  v1  v1  v1
Шаг 2:   v2  v2  v1  v1
Шаг 3:   v2  v2  v2  v1
Конец:   v2  v2  v2  v2
```

Преимущества:
- Не требуется поднимать полную вторую копию окружения.
- Обновление происходит постепенно.
- Подходит для оркестраторов вроде Kubernetes.

Недостатки:
- Некоторое время одновременно работают разные версии.
- Нужно сохранять совместимость API и схем БД.
- Rollback может быть сложнее, если миграции необратимы.

**2. Blue/Green Deployment**

Есть два окружения: Blue (текущая версия) и Green (новая версия). Новая версия разворачивается отдельно, проверяется, после чего трафик переключается на неё.

```text
             Load Balancer
                   |
             Переключение
              /        \
          Blue v1    Green v2
          (старое)    (новое)
```

Преимущества:
- Быстрое переключение обратно на старую версию.
- Новую версию можно проверить до переключения трафика.
- Уменьшается время простоя при корректной настройке.

Недостатки:
- Требуются ресурсы для двух окружений.
- Нужно учитывать совместимость общей БД и внешних зависимостей.
- Переключение трафика не отменяет уже выполненные побочные эффекты.

**3. Canary Deployment**

Новая версия сначала получает небольшую долю реального трафика. Если метрики и ошибки в норме, долю постепенно увеличивают.

```text
100% traffic
     |
     +-- 95% -> v1
     +--  5% -> v2 (canary)

После проверки:
     +-- 50% -> v1
     +-- 50% -> v2

Затем:
     +-- 100% -> v2
```

Преимущества:
- Позволяет проверить новую версию на реальном трафике.
- Ограничивает масштаб возможной проблемы.
- Можно автоматически остановить rollout при ухудшении метрик.

Недостатки:
- Нужны маршрутизация трафика и хорошая наблюдаемость.
- Требуется корректно сравнивать метрики версий.
- Необходимо учитывать совместимость версий и данных.

**Сравнение**

|Стратегия|Принцип|Основной плюс|Основной минус|
|---|---|---|---|
|Rolling|Постепенная замена экземпляров|Не нужна полная вторая среда|Версии временно сосуществуют|
|Blue/Green|Переключение между двумя средами|Быстрый возврат трафика|Дополнительные ресурсы|
|Canary|Постепенное увеличение доли трафика|Ограничение риска релиза|Сложнее маршрутизация и мониторинг|

Главное: Rolling постепенно заменяет экземпляры, Blue/Green переключает трафик между двумя средами, Canary выпускает новую версию на небольшую долю трафика и расширяет её после проверки.

## 7. Как встроить автоматизированное тестирование в CI/CD-pipeline?

Автоматизированные тесты запускаются на разных этапах pipeline. Чем раньше обнаруживается ошибка, тем дешевле её исправить.

**1. На Pull Request**

Обычно запускают быстрые проверки:

- форматирование;
- линтеры и статический анализ;
- unit-тесты;
- проверку сборки;
- часть integration-тестов, если они достаточно быстрые.

Успешное прохождение обязательных проверок может быть условием merge.

**2. После merge в основную ветку**

Запускают более полный набор:

- unit-тесты;
- integration-тесты с реальными зависимостями в контейнерах;
- проверки миграций;
- security scanning;
- сборку артефакта или Docker image.

**3. На staging**

После деплоя выполняют:

- smoke-тесты;
- API/e2e-тесты;
- проверку health endpoints;
- тестирование взаимодействия с зависимыми сервисами;
- при необходимости нагрузочные тесты.

**Пример pipeline для Go**

```bash
gofmt -w .
go vet ./...
go test ./...
go test -race ./...
go build ./...
```

Integration-тесты могут поднимать PostgreSQL, Redis или Kafka в Docker-контейнерах, например через Testcontainers.

**Пример последовательности**

```text
Pull Request
    |
Lint + Static Analysis
    |
Unit Tests
    |
Build
    |
Integration Tests
    |
Merge
    |
Build Artifact
    |
Deploy to Staging
    |
Smoke / E2E Tests
    |
Production Deploy
```

**Важные практики**

- Не запускать все тесты только после деплоя: быстрые проверки должны блокировать merge.
- Разделять быстрые и медленные тесты.
- Сохранять отчёты и логи при падении.
- Изолировать тестовые данные и внешние зависимости.
- Не считать тест успешным, если он был пропущен или не смог подключиться к зависимости.
- Не допускать, чтобы flaky-тесты постоянно блокировали релизы.

Главное: Unit-тесты и статические проверки запускают как можно раньше, integration-тесты — на этапе проверки изменений, а smoke и e2e — после развёртывания в тестовое окружение.

## 8. Какие метрики важны для оценки качества CI/CD-pipeline (build time, success rate и др.)?

Метрики CI/CD помогают понять, насколько быстро, стабильно и безопасно команда доставляет изменения.

**1. Build Time**

Время выполнения pipeline или отдельных этапов. Долгие сборки замедляют обратную связь разработчикам.

Полезно отдельно измерять время тестов, сборки, скачивания зависимостей и деплоя.

**2. Pipeline Success Rate**

Доля успешных запусков pipeline. Частые падения могут указывать на нестабильные тесты, проблемы инфраструктуры или ошибки в коде.

**3. Failure Rate и причины падений**

Важно не только считать неуспешные запуски, но и классифицировать причины: ошибка кода, flaky test, нехватка ресурсов runner-а, недоступность registry или внешней зависимости.

**4. Deployment Frequency**

Как часто команда выпускает изменения в production.

**5. Lead Time for Changes**

Время от коммита или начала работы над изменением до его попадания в production. Нужно заранее определить точки начала и окончания измерения.

**6. Change Failure Rate**

Доля production-деплоев, после которых потребовалось исправление: rollback, hotfix или другая remediation-работа.

**7. Mean Time to Recovery (MTTR)**

Среднее время восстановления после неудачного изменения или инцидента.

Deployment Frequency, Lead Time for Changes, Change Failure Rate и MTTR относятся к известным DORA-метрикам эффективности поставки ПО.

**Сводная таблица**

|Метрика|Что показывает|
|---|---|
|Build Time|Скорость pipeline|
|Success Rate|Стабильность запусков|
|Failure Rate|Частоту неудачных запусков|
|Deployment Frequency|Частоту production-релизов|
|Lead Time for Changes|Скорость доставки изменения|
|Change Failure Rate|Долю проблемных релизов|
|MTTR|Скорость восстановления|

**Важный нюанс**

Нельзя оптимизировать только скорость pipeline. Если убрать важные тесты ради сокращения build time, можно ускорить выпуск дефектов. Метрики нужно рассматривать вместе: скорость, стабильность и последствия релизов.

Главное: Оценивают время сборки, успешность pipeline, частоту деплоев, lead time, долю неудачных изменений и время восстановления. Хороший CI/CD не просто быстрый, а предсказуемый и безопасный.

## 9. Как управлять секретами и ключами в CI/CD?

Секреты — чувствительные данные, которые используются pipeline и приложениями: пароли, API-токены, SSH-ключи, сертификаты, credentials для registry и облачных платформ.

Их нельзя хранить в открытом виде в Git-репозитории или напрямую прописывать в YAML-конфигурациях pipeline.

**1. Secret Store**

Использовать встроенное хранилище секретов CI/CD-платформы или внешний менеджер:

- GitHub Actions Secrets;
- GitLab CI/CD Variables;
- HashiCorp Vault;
- AWS Secrets Manager;
- Azure Key Vault;
- Google Secret Manager.

**2. Минимальные привилегии**

Каждый pipeline должен получать только те секреты и права, которые необходимы для конкретной задачи.

Например, job для запуска unit-тестов не должен иметь production credentials.

**3. Короткоживущие credentials**

По возможности использовать временные токены и федерацию идентификации (OIDC), а не постоянные ключи. Так снижается риск ущерба при утечке.

**4. Маскирование логов**

Секреты не должны попадать в вывод команд, логи, артефакты и сообщения об ошибках. Маскирование полезно, но не заменяет осторожную работу с секретами.

**5. Ротация**

Ключи и пароли нужно регулярно менять, а при подозрении на утечку — немедленно отзывать и перевыпускать.

**6. Разделение окружений**

Production, staging и development должны использовать разные секреты и разные уровни доступа.

**Пример использования переменной окружения**

```yaml
steps:
  - name: Deploy
    run: ./deploy.sh
    env:
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```

Не следует выводить значение `DEPLOY_TOKEN` через `echo` или передавать его в команды так, чтобы оно оказалось в логах или списке процессов.

**Важный нюанс**

Pipeline, выполняющий код из недоверенного Pull Request, не должен получать секреты production. Иначе злоумышленник может изменить скрипт сборки и попытаться вывести секреты наружу.

Главное: Секреты хранят в Secret Store или менеджере секретов, выдают по принципу минимальных привилегий, разделяют по окружениям, ротируют и не допускают их попадания в логи и артефакты.

## 10. Что такое «flaky test» и как с ним бороться?

Flaky Test — тест, который при одинаковом коде и условиях может то проходить, то падать без реального изменения проверяемой функциональности.

Такой тест делает CI/CD непредсказуемым: разработчики перестают доверять результатам pipeline и могут игнорировать реальные ошибки.

**Основные причины**

- Зависимость от времени и таймингов.
- Использование `time.Sleep` вместо ожидания условия.
- Гонки данных и проблемы конкурентного доступа.
- Общие тестовые данные между тестами.
- Зависимость от порядка запуска тестов.
- Нестабильные внешние сервисы и сеть.
- Неправильная очистка ресурсов.
- Недостаток ресурсов на CI runner-е.

**Пример плохого теста на Go**

```go
func TestWorker(t *testing.T) {
    go startWorker()
    time.Sleep(100 * time.Millisecond)

    if !isReady() {
        t.Fatal("worker is not ready")
    }
}
```

Тест зависит от скорости машины и планировщика. На медленном runner-е он может падать.

Лучше ожидать конкретное условие с ограниченным timeout:

```go
deadline := time.After(2 * time.Second)

for !isReady() {
    select {
    case <-deadline:
        t.Fatal("worker is not ready")
    default:
        time.Sleep(10 * time.Millisecond)
    }
}
```

В реальном коде предпочтительнее использовать явный канал готовности, callback или другой синхронизационный механизм, а не опрашивать состояние.

**Как бороться?**

1. Найти тест, который нестабилен при повторных запусках.
2. Изолировать тестовые данные и окружение.
3. Убрать зависимости от случайного порядка и времени.
4. Правильно синхронизировать goroutine.
5. Мокировать нестабильные внешние зависимости или поднимать их в контролируемом окружении.
6. Собирать логи и артефакты при падении.
7. Временно помечать нестабильный тест как quarantined, но обязательно заводить задачу на исправление.

Повторный запуск теста может помочь отличить случайный сбой от постоянного, но не должен маскировать проблему бесконечными retries.

Главное: Flaky test — нестабильный тест, результат которого меняется без изменения кода. Нужно устранять недетерминированность, изолировать данные и зависимости, а не просто перезапускать тест до зелёного результата.

## 11. Как сделать rollback при неудачном деплое?

Rollback — возврат приложения к предыдущей стабильной версии после неудачного релиза.

Причиной могут быть рост ошибок, падение доступности, увеличение latency, ошибки бизнес-операций или неуспешные smoke-тесты.

**1. Хранить версионированные артефакты**

Каждая сборка должна иметь уникальный идентификатор: version, tag или commit SHA. Не следует полагаться на перезаписываемый Docker tag `latest`.

**2. Проверять приложение после деплоя**

После развёртывания запускают smoke-тесты и проверяют:

- readiness и liveness;
- HTTP 5xx;
- latency;
- ошибки приложения;
- ключевые бизнес-метрики.

**3. Автоматически инициировать rollback**

Если проверки не проходят или метрики превышают допустимые пороги, pipeline или система доставки может остановить rollout и вернуть предыдущую версию.

**4. Использовать стратегии, упрощающие возврат**

- Blue/Green — переключить трафик обратно на Blue.
- Canary — прекратить увеличение трафика и вернуть его на стабильную версию.
- Rolling — повторно развернуть предыдущий образ на обновлённых экземплярах.

**5. Учитывать миграции БД**

Откат приложения не всегда означает, что можно откатить схему БД. Новая версия могла добавить колонку или изменить данные.

Поэтому часто используют подход expand-and-contract:

1. Добавить новую схему так, чтобы старый и новый код могли работать одновременно.
2. Развернуть новую версию.
3. Перевести весь трафик.
4. После периода совместимости удалить старые поля и код отдельным изменением.

**Пример**

```text
Deploy v2
   |
Health checks
   |
   +-- Success -> Finish
   |
   +-- Failure -> Rollback to v1
```

**Важный нюанс**

Rollback приложения не отменяет уже выполненные внешние эффекты: отправленные сообщения, платежи или изменения в других системах. Для таких случаев нужны компенсирующие операции и корректная обработка событий.

Главное: Для rollback нужны неизменяемые версионированные артефакты, проверки после деплоя и заранее подготовленный путь возврата. Миграции БД и внешние побочные эффекты должны быть совместимы с откатом.

## 12. В чём разница между hosted и self-hosted CI/CD?

Hosted и Self-hosted описывают, где выполняются задачи pipeline и кто отвечает за инфраструктуру runner-ов.

**Hosted Runners**

Runner-ы предоставляются CI/CD-платформой и запускаются в инфраструктуре провайдера.

Преимущества:
- Не нужно самостоятельно обслуживать машины.
- Быстро начать работу.
- Провайдер отвечает за обновление и базовое обслуживание.
- Удобно масштабировать выполнение задач в рамках доступных лимитов.

Недостатки:
- Ограничения по ресурсам и времени выполнения.
- Зависимость от доступности и тарифов провайдера.
- Не всегда есть доступ к внутренним сетям компании.
- Меньше контроля над окружением.

**Self-hosted Runners**

Runner-ы устанавливаются и обслуживаются самой компанией: на виртуальных машинах, физических серверах или в Kubernetes.

Преимущества:
- Контроль над инфраструктурой и окружением.
- Доступ к внутренним сетям и системам.
- Можно использовать специализированное оборудование.
- Можно настраивать ресурсы и зависимости под проект.

Недостатки:
- Нужно самостоятельно обновлять и защищать runner-ы.
- Нужно масштабировать и мониторить инфраструктуру.
- Требуется изоляция задач и контроль очистки окружения.
- Компрометация runner-а может затронуть внутренние системы.

**Сравнение**

|Критерий|Hosted|Self-hosted|
|---|---|---|
|Обслуживание|Провайдер|Команда|
|Контроль окружения|Ограниченный|Высокий|
|Доступ к внутренней сети|Обычно ограничен|Можно настроить|
|Масштабирование|Часто проще|Нужно организовать|
|Безопасность|Часть ответственности провайдера|Большая ответственность команды|

**Практический выбор**

Для небольшого проекта обычно удобнее hosted runner. Для корпоративной инфраструктуры с закрытыми сетями, особыми требованиями безопасности или тяжёлыми сборками может понадобиться self-hosted.

Self-hosted runner нельзя бездумно использовать для выполнения недоверенного кода из внешних Pull Request: job может получить доступ к файлам, токенам и сети runner-а.

Главное: Hosted runner обслуживает провайдер, self-hosted — сама команда. Выбор зависит от требований к контролю, безопасности, доступу к инфраструктуре и стоимости эксплуатации.

## 13. Что такое тестовое покрытие (test coverage)?

Test Coverage — метрика, показывающая, какая часть кода была выполнена во время запуска тестов.

Для Go стандартный инструмент — `go test` с флагами coverage.

```bash
go test ./... -cover
```

Чтобы получить профиль покрытия:

```bash
go test ./... -coverprofile=coverage.out
go tool cover -func=coverage.out
go tool cover -html=coverage.out
```

**Что показывает coverage?**

Обычно измеряют покрытие операторов (statement coverage): какая доля исполняемых операторов была затронута тестами.

Например, покрытие 80% означает, что тесты выполнили примерно 80% учитываемых операторов в измеряемом наборе пакетов.

**Почему 100% coverage не гарантирует качество?**

- Код мог выполниться, но результат не проверялся assertions.
- Тест мог не проверять граничные случаи.
- Не проверены ошибки и альтернативные ветки.
- Не проверено взаимодействие компонентов.
- Тесты могут быть написаны так, что подтверждают неправильное поведение.

**Что важно покрывать?**

- Бизнес-критичную логику.
- Обработку ошибок.
- Граничные значения.
- Ветвления и альтернативные сценарии.
- Конкурентный код и обработку отмены контекста, если они есть.
- Регрессионные сценарии, в которых ранее возникали баги.

**Пример**

```go
func Discount(price int, isPremium bool) int {
    if isPremium {
        return price * 90 / 100
    }
    return price
}
```

Если тест проверяет только `isPremium=true`, строка возврата исходной цены не будет покрыта. Но даже 100% покрытия этой маленькой функции не доказывает, что все бизнес-требования учтены.

Главное: Test coverage показывает, какая часть кода выполнялась во время тестов. Это полезный индикатор пробелов, но не показатель полноты или качества тестирования сам по себе.

## 14. Какие бывают типы тестов (unit, integration, e2e) и где их запускать в pipeline?

Тесты отличаются масштабом проверяемой системы и количеством реальных зависимостей.

**1. Unit Tests**

Проверяют небольшую единицу кода изолированно: функцию, метод или компонент. Зависимости обычно заменяются mock/stub или простыми тестовыми реализациями.

Пример для Go:

```go
func TestCalculateTotal(t *testing.T) {
    got := CalculateTotal(100, 2)
    want := 200

    if got != want {
        t.Fatalf("got %d, want %d", got, want)
    }
}
```

Особенности:
- Быстрые.
- Легко запускать часто.
- Удобны для проверки бизнес-правил и граничных случаев.

**Где запускать:** на каждом Pull Request и при изменениях в основной ветке.

**2. Integration Tests**

Проверяют взаимодействие нескольких компонентов: приложения с PostgreSQL, Redis, Kafka, файловой системой или внешним API.

Например, тест репозитория может реально записать данные в PostgreSQL и прочитать их обратно.

Особенности:
- Медленнее unit-тестов.
- Требуют тестовой инфраструктуры.
- Проверяют реальные контракты между компонентами.

Для Go можно использовать Docker/Testcontainers, чтобы поднимать зависимости на время теста.

**Где запускать:** на Pull Request, если набор достаточно быстрый; иначе на отдельном этапе pipeline после unit-тестов и сборки. Критичные integration-тесты должны блокировать релиз.

**3. End-to-End (E2E) Tests**

Проверяют систему целиком через интерфейс, API или пользовательский сценарий. Например, создать заказ через HTTP API, дождаться обработки события и проверить результат в системе.

Особенности:
- Максимально близки к реальному сценарию.
- Проверяют интеграцию множества компонентов.
- Обычно медленнее и сложнее в поддержке.
- Могут быть чувствительны к нестабильности окружения.

**Где запускать:** на staging или отдельном тестовом окружении после деплоя. Небольшой набор критичных smoke/e2e-сценариев может быть обязательным перед production.

**Сравнение**

|Тип теста|Что проверяет|Скорость|Типичный этап pipeline|
|---|---|---|---|
|Unit|Отдельную функцию или компонент|Высокая|Каждый Pull Request|
|Integration|Взаимодействие с реальными зависимостями|Средняя|PR или отдельный этап CI|
|E2E|Полный пользовательский/бизнес-сценарий|Низкая|Staging перед релизом|

**Тестовая пирамида**

```text
          /      \
         /  E2E   \          Мало, медленные
        /----------\
       /Integration \    Среднее количество
      /--------------\
     /   Unit Tests   \ Много, быстрые
    /------------------\
```

Пирамида означает, что обычно большая часть тестов — быстрые unit-тесты, меньше integration-тестов и ещё меньше дорогих e2e-тестов.

Главное: Unit-тесты проверяют изолированную логику, integration — взаимодействие компонентов, e2e — систему целиком. Быстрые тесты запускают раньше и чаще, полные сценарии — на тестовом окружении перед выпуском.

# ✦ Docker

## 1. Что такое Docker и какую проблему он решает по сравнению с VM?

Docker — платформа контейнеризации: она позволяет упаковать приложение, его зависимости и настройки запуска в образ (image), а затем запускать этот образ в изолированном контейнере.

Главная проблема, которую решает Docker, — различия окружений. Без контейнеризации приложение может работать на машине разработчика, но падать на тестовом или production-сервере из-за другой версии runtime, библиотек, системных пакетов или конфигурации.

**Контейнеры и виртуальные машины**

| Критерий | Контейнер | Виртуальная машина |
|---|---|---|
| Изоляция | Процессы изолируются средствами ядра ОС | Отдельная виртуальная ОС поверх гипервизора |
| Ядро | Использует ядро хоста | Имеет собственное гостевое ядро |
| Размер | Обычно меньше | Обычно значительно больше |
| Запуск | Обычно быстрый | Обычно медленнее |
| Ресурсы | Меньше накладных расходов | Выше накладные расходы на гостевую ОС |
| Изоляция | Разделяет ядро хоста | Обычно обеспечивает более сильную границу изоляции |

Контейнер — не миниатюрная виртуальная машина. Это обычный процесс или группа процессов на хосте, которым Linux предоставляет изолированные представления ресурсов и ограничивает доступ.

**За счёт чего работает контейнеризация**

- **Namespaces** изолируют PID, сеть, mount points, IPC, hostname и другие пространства имён.
- **cgroups** позволяют учитывать и ограничивать CPU, память и другие ресурсы.
- **Capabilities**, seccomp и механизмы безопасности ОС ограничивают привилегии процесса.
- **Union filesystem** позволяет собирать файловую систему контейнера из слоёв образа и отдельного writable layer.

Docker — не единственный способ запускать контейнеры. Это экосистема инструментов для сборки образов, управления контейнерами, сетями и томами.

**Пример**

```bash
docker build -t my-api:1.0 .
docker run --rm -p 8080:8080 my-api:1.0
```

Первая команда собирает образ, вторая запускает контейнер и публикует порт 8080 хоста на порт 8080 контейнера.

**Главное:** Docker делает окружение приложения воспроизводимым и упрощает доставку между средами. Контейнеры легче VM, потому что используют ядро хоста, но это также означает, что граница изоляции у них другая.

## 2. Как устроен Docker image (layers, Union FS)?

Docker image — неизменяемый шаблон, из которого создаются контейнеры. Образ состоит из последовательности слоёв (layers), каждый из которых содержит изменения файловой системы.

Обычно инструкции Dockerfile, меняющие файловую систему, создают слои. Например, `FROM`, `RUN`, `COPY` и `ADD` могут формировать слои. Метаданные образа также хранятся в конфигурации, но не каждая инструкция Dockerfile создаёт отдельный файловый слой.

**Как работают слои**

Допустим, Dockerfile выглядит так:

```dockerfile
FROM golang:1.24
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN go build -o /app/server ./cmd/server
```

Условно образ содержит базовый слой Go, слой с файлами зависимостей, слой с загруженными модулями, слой с исходным кодом и слой с результатом сборки.

Слои переиспользуются между образами. Если два образа используют один и тот же базовый слой, Docker может хранить его один раз.

**Union filesystem**

Union filesystem объединяет несколько слоёв в единое представление файловой системы. Контейнер видит обычную файловую систему, хотя физически она собрана из read-only слоёв образа и отдельного writable layer контейнера.

При изменении файла из нижнего слоя обычно применяется механизм copy-on-write: файл копируется в верхний writable layer, и изменение происходит уже там. Удаление файла из нижнего слоя представляется специальной записью whiteout, скрывающей исходный файл.

**Почему это полезно**

- Повторно используемые слои уменьшают объём хранения и ускоряют сборку.
- Неизменяемые слои упрощают распространение и кэширование образов.
- Один image можно использовать для создания множества контейнеров с отдельными writable layers.

**Посмотреть слои образа**

```bash
docker image history my-api:1.0
docker image inspect my-api:1.0
```

`docker image history` показывает историю слоёв и соответствующие инструкции сборки. Это не всегда полный список всех файловых изменений, но хороший инструмент для первичной диагностики размера образа.

**Главное:** образ — это набор переиспользуемых read-only слоёв. При запуске контейнера поверх них появляется отдельный writable layer, поэтому изменения одного контейнера не меняют исходный image или другие контейнеры.

## 3. Чем CMD отличается от ENTRYPOINT?

`ENTRYPOINT` задаёт основную исполняемую команду контейнера, а `CMD` — команду по умолчанию или аргументы по умолчанию для неё. Обе инструкции могут быть переопределены при запуске, но делают это по-разному.

**Формы записи**

- Exec form: `ENTRYPOINT ["./server"]`
- Shell form: `ENTRYPOINT ./server`
- Exec form: `CMD ["--port=8080"]`
- Shell form: `CMD ./server --port=8080`

Для серверных контейнеров обычно предпочтительна exec form: процесс запускается напрямую, без промежуточного shell, и корректнее получает сигналы.

**Как они сочетаются**

```dockerfile
ENTRYPOINT ["/app/server"]
CMD ["--port=8080"]
```

Команда по умолчанию будет такой:

```bash
/app/server --port=8080
```

Если запустить:

```bash
docker run my-api:1.0 --port=9090
```

то аргументы из `CMD` заменятся, и будет выполнено:

```bash
/app/server --port=9090
```

Если указать команду после имени образа, она заменяет `CMD` и в обычном случае переопределяет `ENTRYPOINT` только через специальные параметры вроде `--entrypoint`.

**Практическое сравнение**

| Инструкция | Назначение | Что происходит при `docker run IMAGE args` |
|---|---|---|
| Только `CMD` | Команда по умолчанию | Команда CMD заменяется |
| Только `ENTRYPOINT` | Основная команда | Аргументы добавляются к ENTRYPOINT |
| `ENTRYPOINT` + `CMD` | Команда и аргументы по умолчанию | Аргументы CMD заменяются |

**Пример для Go-сервиса**

```dockerfile
FROM gcr.io/distroless/static-debian12
WORKDIR /
COPY --from=build /out/server /server
ENTRYPOINT ["/server"]
CMD ["--config=/etc/my-api/config.yaml"]
```

Важно: shell form может привести к тому, что PID 1 станет shell-процессом, а приложение окажется его дочерним процессом. В таком случае сигналы могут обрабатываться не так, как ожидается. Если shell всё же нужен, используйте `exec`:

```dockerfile
ENTRYPOINT ["sh", "-c", "exec /app/server"]
```

**Главное:** `ENTRYPOINT` — что запускаем, `CMD` — аргументы или команда по умолчанию. Для долгоживущих сервисов обычно удобно задавать исполняемый файл через `ENTRYPOINT` в exec form.

## 4. В чём разница между COPY и ADD и когда что использовать?

Обе инструкции переносят файлы в образ, но у `ADD` есть дополнительные возможности.

| Возможность | COPY | ADD |
|---|---:|---:|
| Копирование локальных файлов и каталогов из build context | Да | Да |
| Автоматическая распаковка локального tar-архива | Нет | Да |
| Получение удалённого URL | Нет | Да, с ограничениями и особенностями |
| Получение файлов из Git-репозитория | Нет | Поддерживается современным BuildKit в определённых формах |

`COPY` выполняет понятное копирование. `ADD` может делать дополнительные преобразования, из-за чего поведение Dockerfile становится менее очевидным.

**Рекомендация**

Используйте `COPY` по умолчанию. Берите `ADD`, только если действительно нужна его специфическая функциональность, например автоматическая распаковка локального tar-архива.

**Пример**

```dockerfile
WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .
```

Для архива:

```dockerfile
ADD assets.tar.gz /app/assets/
```

Docker распакует локальный tar-архив в указанное место при соблюдении условий инструкции.

**Важный нюанс build context**

```bash
docker build -t my-api .
```

Точка означает, что build context — текущий каталог. `COPY` не может копировать произвольные файлы с хоста за пределами build context. Для исключения лишних файлов используйте `.dockerignore`:

```dockerignore
.git
.env
*.log
tmp/
bin/
```

Не добавляйте секреты в build context: даже если вы не копируете их явно, лучше исключить их из контекста сборки.

**Главное:** `COPY` — безопасный и предсказуемый выбор для большинства задач. `ADD` используйте осознанно, когда нужны его дополнительные возможности.

## 5. Почему порядок инструкций в Dockerfile критичен?

Порядок инструкций влияет на кэширование слоёв, скорость сборки и размер итогового образа. Docker переиспользует результаты предыдущих инструкций, если инструкция и необходимые ей входные данные не изменились.

Если ранний слой инвалидирован, последующие слои обычно тоже приходится пересобирать. Поэтому часто меняющиеся файлы не стоит копировать до шагов, которые можно кэшировать независимо от них.

**Неудачный вариант**

```dockerfile
FROM golang:1.24 AS build
WORKDIR /app
COPY . .
RUN go mod download
RUN go build -o /server ./cmd/server
```

Изменение любого файла в проекте меняет результат `COPY . .`. Поэтому Docker может повторно выполнить `go mod download`, хотя `go.mod` и `go.sum` не менялись.

**Более удачный вариант**

```dockerfile
FROM golang:1.24 AS build
WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 go build -o /server ./cmd/server
```

Теперь изменение обычного исходного файла не инвалидирует слой загрузки зависимостей. Он пересобирается, только если меняются `go.mod`, `go.sum` или сама инструкция/окружение этого шага.

**Дополнительные практики**

- Сначала копируйте lock-файлы и манифесты зависимостей, затем исходники.
- Объединяйте связанные операции в один `RUN`, если это уменьшает ненужные слои и не ухудшает читаемость.
- Удаляйте временные файлы в том же `RUN`, в котором они создаются, иначе они останутся в нижнем слое.
- Используйте `.dockerignore`, чтобы не отправлять в build context `.git`, локальные бинарники, логи и секреты.
- Не меняйте без необходимости базовый образ или аргументы сборки, от которых зависит кэш.

**Главное:** сначала размещайте стабильные входные данные, затем часто меняющиеся. Это позволяет переиспользовать дорогие слои и не скачивать Go-зависимости при каждом изменении исходников.

## 6. Что такое Docker cache и как он ломается?

Docker cache — механизм повторного использования результатов предыдущих шагов сборки. Если Docker считает, что инструкция и её входные данные не изменились, он использует ранее созданный результат вместо повторного выполнения операции.

Кэш особенно важен для дорогих шагов: установки системных пакетов, загрузки зависимостей и компиляции.

**Что инвалидирует кэш**

- Изменение инструкции Dockerfile.
- Изменение файлов, участвующих в `COPY` или `ADD`.
- Изменение значений `ARG` или других параметров, влияющих на шаг.
- Изменение базового образа или его digest.
- Изменение предыдущего слоя: последующие шаги уже не могут опереться на старую цепочку.
- Явное отключение кэша через `--no-cache`.

**Пример проблемы**

```dockerfile
COPY . .
RUN go mod download
```

Любое изменение файла в контексте копирования может привести к повторному выполнению `go mod download`.

Лучше:

```dockerfile
COPY go.mod go.sum ./
RUN go mod download
COPY . .
```

**Полезные команды**

```bash
# Обычная сборка с использованием кэша
docker build -t my-api .

# Принудительная сборка без обычного build cache
docker build --no-cache -t my-api .

# Подробный вывод сборки с BuildKit
docker build --progress=plain -t my-api .

# Очистка неиспользуемого build cache
docker builder prune
```

`--no-cache` не означает, что Docker обязательно заново скачает все базовые образы. Для обновления базового образа используют, например:

```bash
docker build --pull -t my-api .
```

В CI кэш можно сохранять между запусками с помощью возможностей BuildKit, например `--cache-from` и `--cache-to`.

**Главное:** кэш ломается, когда меняется инструкция или её вход. Правильное разбиение `COPY` и осмысленный порядок инструкций позволяют не пересобирать неизменившиеся части приложения.

## 7. Multistage build — зачем и как использовать?

Multistage build — техника, при которой Dockerfile содержит несколько стадий сборки (`FROM`). Артефакты из одной стадии можно копировать в другую через `COPY --from=...`.

Это позволяет использовать тяжёлый образ с компиляторами и инструментами для сборки, а в финальный образ положить только готовый бинарник и необходимые runtime-файлы.

**Без multistage**

Если собирать и запускать приложение в одном образе `golang`, в production-образе могут остаться Go toolchain, исходники, кэш модулей и другие ненужные инструменты.

**Пример для Go**

```dockerfile
# Стадия сборки
FROM golang:1.24 AS build
WORKDIR /src

COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/server ./cmd/server

# Финальный образ
FROM gcr.io/distroless/static-debian12:nonroot
WORKDIR /
COPY --from=build /out/server /server

EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/server"]
```

**Что здесь происходит**

1. На стадии `build` используется образ с Go toolchain.
2. Загружаются зависимости и компилируется бинарник.
3. Финальная стадия начинается с минимального runtime-образа.
4. В неё копируется только бинарник.
5. Приложение запускается от непривилегированного пользователя.

**Нюансы**

- Если приложение использует CGO, ему могут понадобиться системные динамические библиотеки. Тогда `CGO_ENABLED=0` может быть неприменим, а `static`-образ — неподходящим.
- Нужно учитывать CA certificates, timezone data и другие runtime-файлы, если приложение их использует.
- Минимальный образ уменьшает поверхность атаки, но усложняет диагностику: внутри может не быть shell и стандартных утилит.
- Для отладки можно использовать отдельный debug target или временно собирать образ на базе более полного runtime-образа.

**Сборка конкретной стадии**

```bash
docker build --target build -t my-api-build .
```

**Главное:** multistage build отделяет инструменты разработки от runtime-окружения. В production попадает только то, что действительно нужно для запуска приложения.

## 8. Почему контейнеры считаются «лёгкими», но могут жрать память?

Контейнеры лёгкие в сравнении с виртуальными машинами с точки зрения накладных расходов на виртуализацию и отдельную гостевую ОС. Но они не отменяют потребление ресурсов самим приложением.

Контейнер с Go-сервисом использует память на:

- heap и stack Go-программы;
- goroutine stacks;
- runtime, GC и метаданные аллокатора;
- буферы, кэши и структуры приложения;
- сетевые соединения и очереди;
- memory-mapped файлы и page cache;
- shared libraries и другие системные ресурсы.

**Почему память может расти**

- Утечка ссылок: объекты остаются достижимыми и не собираются GC.
- Неограниченные очереди, кэши или буферы.
- Слишком много goroutine или соединений.
- Большие batch-операции и всплески нагрузки.
- Неверно заданные memory limits.
- Особенности учёта памяти: cgroups учитывают не только Go heap, но и часть другой памяти процесса/ядра, например page cache.

**Ограничения ресурсов**

```bash
docker run --memory=512m --cpus=1.5 my-api:1.0
```

Это задаёт контейнеру лимит памяти и ограничение CPU. Если контейнер превысит memory limit, ядро может инициировать OOM kill.

**Диагностика**

```bash
docker stats
docker inspect my-api
```

Для Go-приложения полезно смотреть метрики `runtime.MemStats`, heap profile и goroutine profile через `pprof`, а также сопоставлять их с метриками контейнера и cgroup.

Важно различать:
- **Go heap** — память, управляемая Go runtime.
- **RSS** — физическая память процесса в resident set.
- **Container memory usage** — учёт памяти на уровне cgroup, который может отличаться от heap и RSS.

**Главное:** контейнер не делает приложение экономным автоматически. Он изолирует и ограничивает ресурсы, но потребление памяти определяется приложением, нагрузкой и настройками лимитов.

## 9. Что такое bind mount vs volume?

Оба механизма позволяют хранить данные вне writable layer контейнера и подключать их к файловой системе контейнера. Отличается то, кто управляет расположением и жизненным циклом данных.

| Критерий | Bind mount | Docker volume |
|---|---|---|
| Источник | Конкретный путь на хосте | Объём, которым управляет Docker |
| Путь хранения | Выбирает пользователь | Обычно управляется Docker |
| Удобство для разработки | Очень удобно для исходников и hot reload | Удобно для постоянных данных |
| Переносимость | Зависит от структуры хоста | Обычно проще управлять через Docker |
| Управление | В основном вручную | Через `docker volume` |

**Bind mount**

```bash
docker run --rm \
  -v "$PWD:/app" \
  -w /app \
  golang:1.24 go test ./...
```

Текущий каталог хоста подключается в `/app` контейнера. Изменения видны с обеих сторон.

**Volume**

```bash
docker volume create postgres-data

docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=secret \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:17
```

Docker управляет volume `postgres-data`. Он переживёт удаление контейнера, если сам volume не удалить.

**Современный синтаксис `--mount`**

```bash
docker run --mount type=volume,src=postgres-data,dst=/var/lib/postgresql/data postgres:17
```

Для bind mount:

```bash
docker run --mount type=bind,src="$PWD/config",dst=/app/config,readonly my-api
```

**Важные нюансы**

- Bind mount может скрыть файлы, уже существующие в каталоге контейнера, куда его подключили.
- Bind mount зависит от путей и прав доступа на хосте.
- Volume не следует считать резервной копией: его данные тоже нужно отдельно бэкапить.
- Для production-хранилища важно продумать backup, восстановление, права, шифрование и размещение данных.

**Главное:** bind mount подключает конкретный путь хоста, volume — управляемое Docker хранилище. Для исходников при локальной разработке часто удобен bind mount, для данных БД — volume или внешнее persistent storage.

## 10. Как правильно передавать конфигурацию и секреты в контейнер?

Конфигурацию нужно отделять от образа. Один и тот же image должен по возможности запускаться в dev, staging и production с разными настройками, не требуя пересборки.

**Конфигурация**

Обычные параметры можно передавать через environment variables:

```bash
docker run -d \
  -e APP_ENV=production \
  -e HTTP_PORT=8080 \
  -e DATABASE_HOST=postgres \
  my-api:1.0
```

Или через env-файл:

```bash
docker run --env-file .env my-api:1.0
```

Env-файл удобен для локальной разработки, но его нельзя бездумно коммитить в репозиторий.

**Секреты**

Пароли, токены и приватные ключи — отдельная категория данных. Не следует:

- вшивать секреты в Dockerfile через `ENV` или `ARG`;
- копировать `.env` с production-секретами в image;
- передавать секреты в аргументах командной строки, где они могут попасть в историю или process list;
- печатать их в логах;
- хранить их в открытом виде в CI variables без ограничений доступа.

`ARG` предназначен для параметров сборки и не является безопасным хранилищем секретов. Секреты, использованные при сборке, нужно передавать через специальные механизмы BuildKit secrets.

**Docker Compose secrets**

```yaml
services:
  api:
    image: my-api:1.0
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

В поддерживаемых сценариях secret предоставляется контейнеру как файл, а не как обычная переменная окружения. Реальные возможности и уровень защиты зависят от платформы и способа запуска Compose/Swarm.

В production предпочтительнее использовать специализированное хранилище секретов: Vault, облачный Secret Manager, Kubernetes Secrets с корректно настроенным шифрованием и RBAC или аналогичное решение.

**Пример чтения секрета в Go**

```go
password, err := os.ReadFile("/run/secrets/db_password")
if err != nil {
    return fmt.Errorf("read database password: %w", err)
}

dbPassword := strings.TrimSpace(string(password))
```

**Главное:** образ не должен содержать окружение и секреты конкретного деплоя. Конфигурацию передавайте при запуске, а секреты — через специализированный secret management, ограничивая доступ и исключая утечки в логи и артефакты.

## 11. Почему нельзя хранить state внутри контейнера?

Контейнеры проектируются как заменяемые экземпляры. Их можно остановить, пересоздать, масштабировать или удалить при деплое. Writable layer контейнера не предназначен для долговременного хранения важных данных.

Если приложение записывает данные только внутрь контейнера, при его удалении эти данные могут быть потеряны.

**Что должно быть stateless**

В stateless-сервисе локальная файловая система не является источником истины. Состояние хранится во внешних системах:

- данные приложения — PostgreSQL, MySQL или другая БД;
- кэш — Redis или аналог;
- файлы — object storage или persistent volume;
- события и очереди — Kafka, RabbitMQ и другие брокеры;
- сессии — внешнее хранилище или подписанные токены, в зависимости от архитектуры.

**Почему это важно для масштабирования**

Представим, что запущены три экземпляра API:

```text
          Load Balancer
          /     |     \
       API-1  API-2  API-3
          \     |     /
        PostgreSQL / Redis
```

Если пользовательская сессия хранится в памяти API-1, следующий запрос может попасть в API-2, который ничего о ней не знает. Внешнее хранилище позволяет всем экземплярам работать с общим состоянием.

**Что можно хранить локально**

Временные файлы, кэш, сокеты и промежуточные данные допустимы, если приложение корректно переживает их потерю и умеет пересоздавать. Для постоянных данных используют volumes или внешнее хранилище, но даже volume требует резервного копирования и стратегии восстановления.

**Главное:** контейнер должен быть заменяемым без потери бизнес-данных. Постоянное состояние храните вне его writable layer, а локальные данные используйте только как временные или воспроизводимые.

## 12. Как дебажить контейнер, который падает сразу после старта?

Если контейнер завершается сразу после запуска, сначала нужно выяснить код выхода и причину завершения, затем проверить конфигурацию, команду запуска, зависимости и логи.

**Пошаговая диагностика**

1. Посмотреть состояние и exit code:

```bash
docker ps -a
docker inspect my-api
```

В `docker inspect` полезны `State.ExitCode`, `State.Error`, `State.OOMKilled`, `State.FinishedAt` и `State.StartedAt`.

2. Посмотреть stdout/stderr:

```bash
docker logs my-api
docker logs --tail=200 -f my-api
```

3. Проверить итоговую команду и настройки:

```bash
docker inspect --format='{{.Path}} {{json .Args}}' my-api
docker inspect --format='{{json .Config.Env}}' my-api
```

Не публикуйте вывод с секретами: переменные окружения могут содержать чувствительные значения.

4. Запустить контейнер в foreground:

```bash
docker run --rm -it my-api:1.0
```

Так проще увидеть ошибку запуска.

5. Проверить конфигурацию, сеть и зависимости. Например, сервис может завершаться, потому что не может подключиться к PostgreSQL, не находит файл конфигурации или слушает неверный адрес.

6. Проверить OOM:

```bash
docker inspect --format='OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}' my-api
docker stats
```

7. Если образ минимальный и в нём нет shell, использовать debug-образ/отдельную debug-стадию или временно собрать образ с диагностическими утилитами.

**Типичные причины**

| Симптом | Возможная причина |
|---|---|
| Exit code 1 | Ошибка приложения или конфигурации |
| Exit code 127 | Не найдена команда или исполняемый файл |
| Exit code 126 | Команда найдена, но не может быть выполнена |
| Exit code 137 | Часто SIGKILL; возможен OOM kill |
| Exit code 139 | Часто ошибка сегментации |
| `exec format error` | Неподходящая архитектура бинарника или неверный формат |
| Контейнер сразу `Exited` | Приложение завершилось или команда запуска неверна |

Код выхода — подсказка, а не окончательный диагноз. Например, 137 означает завершение через SIGKILL, но сам по себе не доказывает, что причиной был OOM.

**Главное:** начните с `docker ps -a`, `docker logs` и `docker inspect`. Смотрите exit code, OOMKilled, команду запуска и конфигурацию, а затем воспроизводите проблему в foreground.

## 13. Что происходит при docker stop (SIGTERM / SIGKILL)?

Команда `docker stop` просит контейнер корректно завершиться. Docker отправляет основному процессу контейнера сигнал остановки, по умолчанию `SIGTERM`, ждёт заданный timeout, а затем отправляет `SIGKILL`, если процесс не завершился.

**Последовательность**

```text
docker stop container
        |
        v
     SIGTERM
        |
        v
Приложение завершает работу
        |
        +---- завершилось вовремя ---> контейнер остановлен
        |
        +---- timeout истёк ---------> SIGKILL
                                      |
                                      v
                               процесс принудительно убит
```

По умолчанию timeout обычно составляет 10 секунд для Linux-контейнеров; его можно изменить:

```bash
docker stop --time 30 my-api
```

Для отправки другого сигнала можно использовать `docker stop --signal=...` в поддерживаемых версиях Docker.

**Что должен делать Go-сервис на SIGTERM**

- прекратить принимать новые запросы;
- начать graceful shutdown HTTP-сервера;
- дождаться завершения активных запросов в разумных пределах;
- остановить фоновые worker'ы и потребителей очередей;
- закрыть соединения и ресурсы;
- завершить процесс до истечения stop timeout.

**Пример**

```go
ctx, stop := signal.NotifyContext(
    context.Background(),
    syscall.SIGINT,
    syscall.SIGTERM,
)
defer stop()

server := &http.Server{
    Addr:    ":8080",
    Handler: handler,
}

go func() {
    if err := server.ListenAndServe(); err != nil &&
        !errors.Is(err, http.ErrServerClosed) {
        log.Printf("http server error: %v", err)
    }
}()

<-ctx.Done()

shutdownCtx, cancel := context.WithTimeout(
    context.Background(),
    8*time.Second,
)
defer cancel()

if err := server.Shutdown(shutdownCtx); err != nil {
    log.Printf("graceful shutdown failed: %v", err)
}
```

В production нужно согласовать timeout приложения и `docker stop --time`: приложение должно успеть завершить работу раньше, чем Docker применит `SIGKILL`.

**Важен PID 1**

Процесс PID 1 в контейнере имеет особое значение для доставки и обработки сигналов. Использование exec form в `ENTRYPOINT` помогает запускать приложение непосредственно как основной процесс. Если используется shell-обёртка, она должна корректно передавать сигналы, например через `exec`.

**Главное:** `docker stop` сначала отправляет SIGTERM и даёт приложению время на graceful shutdown, затем при необходимости применяет SIGKILL. Сервис должен уметь корректно завершать запросы, worker'ы и соединения.

## 14. Почему latest — плохая практика?

Тег `latest` не означает «самая свежая стабильная версия». Это обычный изменяемый тег, который может указывать на разные версии образа в разное время.

**Проблема воспроизводимости**

Допустим, Dockerfile содержит:

```dockerfile
FROM postgres:latest
```

Сегодня `latest` указывает на одну версию PostgreSQL, а через некоторое время — на другую. Повторная сборка того же Dockerfile может получить другое окружение без изменения исходного кода.

Это создаёт проблемы:

- сборки становятся невоспроизводимыми;
- staging и production могут незаметно использовать разные версии;
- обновление может принести несовместимые изменения;
- сложнее расследовать инциденты и откатываться;
- невозможно однозначно понять, какой именно образ был развернут.

**Лучше фиксировать версию**

```dockerfile
FROM postgres:17.2
```

Для более строгой фиксации можно использовать digest:

```dockerfile
FROM postgres:17.2@sha256:<digest>
```

Digest идентифицирует конкретный содержательный образ. В реальном Dockerfile вместо placeholder должен быть настоящий digest из доверенного registry.

**Как обновлять правильно**

1. Выбрать конкретную версию.
2. Проверить release notes и совместимость.
3. Обновить тег или digest в контролируемом изменении.
4. Собрать образ и прогнать тесты.
5. Развернуть через staging/canary или другой безопасный процесс.
6. Зафиксировать версию, использованную в production.

Версионирование не отменяет обновления безопасности. Напротив, фиксированная версия позволяет обновлять зависимости осознанно и отслеживать, что именно поменялось.

**Главное:** `latest` — подвижная метка, а не гарантия стабильности. Фиксируйте версии, а для максимальной воспроизводимости — digest, и обновляйте образы контролируемо.

## 15. Какие security-риски есть у Docker (root, capabilities, image provenance)?

Контейнеризация не означает автоматическую безопасность. Контейнеры разделяют ядро хоста, поэтому уязвимость ядра, чрезмерные привилегии или опасная конфигурация контейнера могут привести к компрометации хоста или других workloads.

**1. Запуск от root**

По умолчанию процесс внутри контейнера часто запускается от root. Это не всегда означает root на хосте благодаря user namespaces и другим механизмам изоляции, но увеличивает последствия уязвимости и неправильной конфигурации.

Рекомендации:
- создавать отдельного непривилегированного пользователя;
- использовать `USER` в Dockerfile;
- по возможности включать user namespace remapping или rootless mode;
- не запускать приложение с правами root без необходимости.

Пример:

```dockerfile
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]
```

**2. Linux capabilities**

Root в Linux — набор привилегий, часть которых представлена capabilities. Контейнеру не нужно автоматически выдавать все возможности.

Опасные примеры:
- `CAP_SYS_ADMIN` — очень широкая привилегия, иногда описывается как «почти root»;
- `CAP_NET_ADMIN` — управление сетевыми настройками;
- `CAP_SYS_PTRACE` — возможность трассировки процессов.

Для минимизации привилегий:

```bash
docker run \
  --cap-drop=ALL \
  --security-opt=no-new-privileges:true \
  my-api:1.0
```

Если приложению действительно нужна конкретная capability, добавляйте только её через `--cap-add`.

**3. Privileged containers**

Не используйте `--privileged` без крайней необходимости. Такой режим существенно расширяет доступ контейнера к устройствам и возможностям хоста, ослабляя изоляцию.

**4. Образы и image provenance**

Даже безопасный Dockerfile не спасёт, если базовый образ содержит вредоносный или уязвимый компонент.

Практики:
- использовать доверенные registry и официальные/проверенные образы;
- фиксировать версии и digest;
- сканировать образы на CVE;
- минимизировать количество пакетов и размер runtime-образа;
- подписывать образы и проверять подписи;
- использовать SBOM (Software Bill of Materials), чтобы понимать состав образа;
- проверять происхождение сборки (provenance/attestations), источник кода и pipeline;
- защищать CI/CD, registry и учётные данные для публикации.

Инструменты экосистемы: Trivy, Grype, Docker Scout, Syft для SBOM, Cosign для подписывания и проверки образов. Выбор инструмента зависит от инфраструктуры и процесса поставки.

**5. Другие риски**

- Монтирование `/var/run/docker.sock`: доступ к Docker socket часто фактически даёт возможность управлять контейнерами и получать высокий уровень контроля над хостом.
- Чрезмерно широкие bind mounts, например монтирование `/` хоста.
- Секреты в слоях образа, build args, логах и CI artifacts.
- Устаревшее ядро хоста и уязвимости container runtime.
- Отсутствие ограничений CPU, памяти, PID и дискового пространства.
- Небезопасные сетевые настройки и открытые порты.
- Запуск контейнера с отключёнными seccomp/AppArmor/SELinux-профилями без обоснования.

**Минимальный security-чеклист**

| Практика | Зачем |
|---|---|
| Non-root user | Уменьшить последствия компрометации |
| `--cap-drop=ALL` | Убрать ненужные привилегии |
| `no-new-privileges` | Запретить получение дополнительных привилегий через exec |
| Не использовать `--privileged` | Сохранить изоляцию |
| Минимальный runtime image | Сократить поверхность атаки |
| Сканирование и SBOM | Выявлять уязвимости и состав образа |
| Подпись и provenance | Проверять происхождение и целостность артефакта |
| Не монтировать Docker socket без необходимости | Не отдавать контейнеру контроль над Docker daemon |
| Лимиты CPU, RAM и PID | Ограничить влияние runaway-процессов |
| Обновление Docker Engine и ядра | Закрывать известные уязвимости |

**Главное:** безопасность Docker строится на принципе минимальных привилегий и доверии к цепочке поставки образа. Запускайте приложение не от root, сбрасывайте ненужные capabilities, избегайте privileged-режима, сканируйте и проверяйте происхождение образов.

# ✦ Kubernetes

## База и архитектура

### **1. Что такое Kubernetes и зачем он нужен?**

Kubernetes (K8s) — платформа оркестрации контейнеризированных приложений. Docker помогает собрать образ и запустить контейнер, а Kubernetes управляет множеством контейнеров на множестве узлов: размещает их, следит за состоянием, масштабирует, обновляет и предоставляет сетевой доступ.

Основная идея — **декларативное управление**. Разработчик описывает желаемое состояние, например три реплики API, а контроллеры постоянно приводят фактическое состояние к нему. Если Pod упал, Kubernetes создаёт замену.

Ключевые возможности:
- scheduling — выбор Node для Pod;
- self-healing — восстановление нужного количества Pod'ов;
- scaling — ручное и автоматическое изменение реплик;
- service discovery и балансировка трафика;
- rolling updates и rollback;
- управление конфигурацией, секретами и ресурсами.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: example.com/api:1.4.2
          ports:
            - containerPort: 8080
```

**Главное:** Kubernetes поддерживает желаемое состояние приложения в кластере: размещает, перезапускает, масштабирует и обновляет workloads.

### **2. Основные компоненты control plane (API Server, Scheduler, Controller Manager, etcd).**

Control plane — управляющая часть Kubernetes. Она принимает запросы, хранит состояние кластера и координирует работу узлов.

| Компонент | Назначение |
|---|---|
| kube-apiserver | Центральный API, аутентификация, авторизация, admission и валидация |
| etcd | Распределённое key-value хранилище состояния |
| kube-scheduler | Выбирает Node для Pod без назначенного узла |
| kube-controller-manager | Запускает контроллеры, согласующие actual и desired state |
| cloud-controller-manager | Интеграция с API облачного провайдера |

Упрощённый поток создания Pod:

```text
kubectl apply
    |
    v
API Server ---> etcd (сохранение объекта)
    |
    v
Scheduler ---> выбор Node
    |
    v
API Server ---> назначение Node
    |
    v
kubelet на Node ---> container runtime ---> контейнер
```

API Server — основной интерфейс управления. Scheduler учитывает requests, taints/tolerations, affinity и доступность ресурсов. Контроллеры постоянно наблюдают за объектами и создают/удаляют ресурсы для достижения желаемого состояния.

На Node работают kubelet (агент узла), container runtime (например, containerd или CRI-O) и обычно kube-proxy либо заменяющий его сетевой dataplane.

**Главное:** API Server принимает запросы, etcd хранит состояние, Scheduler выбирает узел, Controller Manager поддерживает желаемое состояние, а kubelet обеспечивает запуск Pod'ов на Node.

### **3. Что такое Pod и почему это минимальная единица?**

Pod — минимальная единица размещения и планирования в Kubernetes. Он содержит один или несколько тесно связанных контейнеров, которые совместно используют сетевое пространство и могут подключать общие volumes. Обычно в Pod находится один основной контейнер.

Контейнеры одного Pod:
- имеют общий network namespace и IP Pod;
- могут обращаться друг к другу через `localhost`;
- могут монтировать общие volumes;
- планируются на один Node и имеют общий жизненный цикл Pod, хотя контейнеры могут перезапускаться отдельно.

```text
Pod
+---------------------------+
| app container :8080       |
| sidecar container :15000  |
| shared network namespace  |
| optional shared volumes   |
+---------------------------+
```

Sidecar может собирать логи, проксировать трафик или выполнять вспомогательную работу. Не следует объединять в один Pod независимые микросервисы только потому, что так проще их запускать.

Pod эфемерен: при пересоздании он получает новый UID и может получить другой IP. Для стабильного доступа используют Service.

**Главное:** Pod — единица scheduling. Контейнеры внутри него разделяют сеть и могут разделять тома, поэтому Pod подходит для тесно связанных компонентов.

### **4. Чем Deployment отличается от StatefulSet и DaemonSet?**

Это контроллеры для разных типов приложений.

| Характеристика | Deployment | StatefulSet | DaemonSet |
|---|---|---|---|
| Назначение | Stateless-приложения | Stateful-приложения | Агент на каждом подходящем Node |
| Идентичность | Реплики взаимозаменяемы | Стабильные ordinal-имена | Обычно один Pod на Node |
| Хранилище | Часто внешнее/общее | Часто отдельный PVC на реплику | Зависит от агента |
| Пример | Go API, frontend | БД, Kafka-компонент | log-agent, node-exporter |

Deployment удобен, когда реплики взаимозаменяемы: например, пять экземпляров Go API за Service.

StatefulSet даёт стабильные имена (`db-0`, `db-1`), предсказуемую идентичность и шаблоны отдельных PVC. Но сам по себе не обеспечивает репликацию и консистентность БД: это ответственность самой БД.

DaemonSet обеспечивает Pod на каждом подходящем узле, например для мониторинга или сбора логов.

**Главное:** Deployment — stateless, StatefulSet — стабильная идентичность и storage для stateful workloads, DaemonSet — агент на каждом подходящем узле.

### **5. ReplicaSet — зачем он вообще нужен, если есть Deployment?**

ReplicaSet поддерживает заданное число Pod'ов, соответствующих selector'у. Если Pod удалился или упал, ReplicaSet создаёт замену.

Deployment управляет ReplicaSet'ами и добавляет управление версиями, rollout, историей обновлений и rollback.

```text
Deployment
  +-- ReplicaSet v1 --> старые Pod'ы
  +-- ReplicaSet v2 --> новые Pod'ы
```

Во время обновления Deployment создаёт новый ReplicaSet и постепенно меняет число реплик старого и нового. Обычно ReplicaSet напрямую не создают: им управляет Deployment.

```bash
kubectl get deployments
kubectl get replicasets
kubectl get pods
kubectl describe deployment api
```

**Главное:** ReplicaSet поддерживает количество Pod'ов, Deployment управляет ReplicaSet'ами, версиями и обновлениями.

## Сеть и доступ

### **1. Как работает networking в Kubernetes (Pod-to-Pod, Service)?**

Сетевая модель Kubernetes предполагает, что Pod'ы могут обмениваться трафиком друг с другом по IP без NAT между Pod IP. Эту связность реализует CNI-плагин, например Calico, Cilium или Flannel.

Каждый Pod получает IP, но Pod эфемерен: после пересоздания адрес может измениться. Поэтому клиенты обычно обращаются не к Pod IP, а к Service — стабильному виртуальному IP и DNS-имени.

```text
Client Pod
   |
   v
Service api
   +----> Pod 10.1.2.10
   +----> Pod 10.1.3.14
   +----> Pod 10.1.4.21
```

Service обычно выбирает Pod'ы по labels. Контроллеры формируют EndpointSlice со списком адресов и портов подходящих endpoints. Сетевой dataplane направляет трафик к ним.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
    - port: 80
      targetPort: 8080
```

NetworkPolicy может ограничивать Pod-to-Pod трафик, если используемый CNI поддерживает эти политики.

```bash
kubectl get pods -o wide
kubectl get svc
kubectl get endpointslices
kubectl describe svc api
```

**Главное:** CNI обеспечивает сетевую связность Pod'ов, Service даёт стабильный адрес и направляет трафик к подходящим Pod'ам.

### **2. Виды Service (ClusterIP, NodePort, LoadBalancer).**

Service предоставляет стабильный доступ к группе Pod'ов.

| Тип | Доступность | Сценарий |
|---|---|---|
| ClusterIP | Внутри кластера | Внутренние API и БД |
| NodePort | Через порт на IP каждого Node | Внешний доступ через узлы |
| LoadBalancer | Через внешний LB инфраструктуры | Публикация сервиса наружу |

**ClusterIP** — тип по умолчанию, создаёт виртуальный IP внутри кластера.

**NodePort** открывает порт на каждом Node. Диапазон по умолчанию обычно 30000–32767, но настраивается.

**LoadBalancer** запрашивает внешний балансировщик у cloud provider или другого интеграционного компонента. В bare-metal кластере может понадобиться MetalLB.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  type: LoadBalancer
  selector:
    app: api
  ports:
    - port: 80
      targetPort: 8080
```

`LoadBalancer` не означает, что Kubernetes сам умеет создать внешний LB в любой среде. NodePort часто используется как часть реализации LoadBalancer.

**Главное:** ClusterIP — внутренний адрес, NodePort — порт на узлах, LoadBalancer — внешний балансировщик, предоставляемый инфраструктурой.

### **3. Что такое Ingress и чем он отличается от Service?**

Ingress — API-объект с правилами HTTP/HTTPS-маршрутизации извне к Service. Сам объект Ingress трафик обычно не обрабатывает: нужен Ingress Controller, например NGINX Ingress Controller или Traefik.

- Service даёт стабильную точку доступа к Pod'ам.
- Ingress описывает маршруты по hostname и path.
- Ingress Controller реализует эти правила как reverse proxy/load balancer.

```text
Internet
   |
Ingress Controller
   +-- api.example.com --> Service api --> API Pods
   +-- shop.example.com -> Service shop -> Shop Pods
```

Пример:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 80
```

TLS-сертификат можно подключить через Secret в `spec.tls`. Для более расширяемой маршрутизации развивается Gateway API; его поддержку нужно проверять у выбранного контроллера.

**Главное:** Service направляет трафик к Pod'ам, Ingress описывает внешнюю HTTP(S)-маршрутизацию к Service, а Ingress Controller фактически обрабатывает запросы.

### **4. Как работает DNS внутри кластера?**

Обычно DNS в кластере обслуживает CoreDNS. Он позволяет обращаться к Service по имени, а не по IP.

Формат полного имени Service:

```text
<service>.<namespace>.svc.<cluster-domain>
```

Например: `orders.production.svc.cluster.local`. Из того же namespace обычно достаточно `orders`, из другого — `orders.production`.

```text
Pod application
   |
   | DNS query: orders.production
   v
CoreDNS
   |
   v
Service DNS record
   |
   v
ClusterIP
```

Для обычного Service DNS возвращает ClusterIP. Для headless Service (`clusterIP: None`) DNS может возвращать адреса отдельных endpoints.

Диагностика:

```bash
kubectl exec -it api-pod -- cat /etc/resolv.conf
kubectl run dns-test --rm -it --image=busybox:1.36   --restart=Never -- nslookup orders.production.svc.cluster.local
```

Типовые проблемы: CoreDNS не работает, указан неверный namespace, NetworkPolicy блокирует DNS, неправильно настроен `dnsPolicy` или Service не имеет endpoints. DNS-разрешение и доступность backend'ов нужно проверять отдельно.

**Главное:** CoreDNS обеспечивает service discovery. Используйте DNS-имя Service, а не изменяющийся IP Pod'а.

## Конфигурация и секреты

### **1. ConfigMap vs Secret — в чём разница и риски?**

ConfigMap предназначен для несекретной конфигурации, Secret — для чувствительных данных: паролей, токенов и сертификатов.

| Критерий | ConfigMap | Secret |
|---|---|---|
| Назначение | Обычные настройки | Чувствительные значения |
| Представление | Строковые данные | `data` (base64) или `stringData` |
| Пример | LOG_LEVEL, URL | DB_PASSWORD, API_TOKEN |
| Защита | Не предназначен для секретов | Требует RBAC и encryption at rest |

Пример ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
data:
  LOG_LEVEL: info
  HTTP_PORT: "8080"
```

Пример Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: api-secret
type: Opaque
stringData:
  DB_PASSWORD: change-me
```

Secret можно передать через `secretKeyRef` как env или смонтировать файлом. Base64 — кодирование, а не шифрование. Доступ к Secrets нужно ограничивать RBAC, не коммитить реальные секреты в Git и не выводить их в логи.

**Главное:** ConfigMap — для обычных настроек, Secret — для чувствительных данных, но защита Secret зависит от прав доступа и настроек шифрования.

### **2. Почему Secrets в Kubernetes не являются безопасными по умолчанию?**

Kubernetes Secret — механизм доставки чувствительных данных workload'ам, но не полноценный vault. Поле `data` кодируется Base64, что не является шифрованием. Encryption at rest для etcd необходимо отдельно настроить и проверить для конкретного кластера.

Риски:
- широкие RBAC-права `get`, `list`, `watch` позволяют читать Secrets;
- привилегированный доступ к Node или kubelet может открыть доступ к смонтированным данным;
- секреты могут утечь через логи, дампы, env и CI/CD;
- YAML с Secret может попасть в Git;
- без encryption at rest данные в etcd могут храниться незашифрованными.

Защита:
1. Включить encryption at rest и обеспечить управление ключами.
2. Выдавать минимальные RBAC-права, не давать приложениям доступ ко всем Secrets.
3. Использовать namespaces и разделение полномочий.
4. Не печатать секреты в логах.
5. Рассмотреть Vault, облачный Secret Manager, External Secrets Operator или Secrets Store CSI Driver.
6. Настроить аудит обращений к API.

**Главное:** Secret не равен зашифрованному хранилищу. Нужны encryption at rest, строгий RBAC, защита узлов и безопасная интеграция с secret manager.

### **3. Как обновлять конфигурацию без рестарта Pod'ов?**

Способ зависит от того, как конфигурация передана приложению и умеет ли оно перечитывать настройки.

Если ConfigMap/Secret смонтирован как volume, kubelet со временем обновляет файлы в volume. Приложение должно обнаружить изменение и перечитать файл — например, через filesystem notifications или периодический reload.

```yaml
volumes:
  - name: config
    configMap:
      name: api-config
containers:
  - name: api
    volumeMounts:
      - name: config
        mountPath: /etc/api
        readOnly: true
```

Обновление не мгновенное: есть задержка синхронизации kubelet. Приложение должно учитывать особенности projected volume и замену symlink.

Если ConfigMap/Secret передан через environment variables, работающий процесс не получит новые значения автоматически. Для применения изменений нужен перезапуск Pod.

Распространённый вариант — checksum конфигурации в annotation Pod template. При изменении checksum меняется шаблон Deployment и происходит rolling restart:

```yaml
spec:
  template:
    metadata:
      annotations:
        checksum/config: "calculated-sha256"
```

| Способ | Перезапуск | Условие |
|---|---|---|
| Volume + reload | Не обязателен | Приложение перечитывает файл |
| Env variables | Нужен | Новое окружение при старте процесса |
| Checksum annotation | Rolling restart | Автоматизированный rollout |

**Главное:** hot reload возможен через файлы и поддержку reload в приложении. Env не обновляются в уже запущенном процессе; checksum обычно запускает контролируемый rolling restart.

## Ресурсы и стабильность

### **1. Requests vs Limits — что будет, если их не указать?**

`requests` — запрашиваемый ресурс, который Scheduler учитывает при размещении Pod. `limits` — верхнее ограничение потребления ресурса контейнером.

| Ресурс | Request | Limit |
|---|---|---|
| CPU | Учитывается при scheduling; влияет на долю CPU при конкуренции | CPU throttling при достижении quota |
| Memory | Учитывается при scheduling | При превышении возможен OOM kill |

Пример:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

`250m` CPU — четверть ядра, `1` — одно ядро.

Если requests не заданы, Scheduler может недооценить потребность и переплотнить Node. Без memory limit контейнер не ограничен заданным лимитом, но остаются ограничения узла и риск eviction/OOM. Без CPU limit контейнер может использовать свободный CPU сверх request, но при конкуренции его доля зависит от настроек.

QoS-классы:
- Guaranteed — requests равны limits для CPU и memory всех контейнеров Pod;
- Burstable — заданы некоторые requests/limits, но не выполнены условия Guaranteed;
- BestEffort — requests и limits CPU/memory не заданы.

`LimitRange` и admission policy могут назначать defaults, но полагаться на это без знания политики кластера не стоит.

```bash
kubectl describe pod api-xxxxx
kubectl top pod
kubectl top node
```

**Главное:** requests влияют на размещение и долю ресурсов, limits ограничивают потребление. Их отсутствие может привести к плохому scheduling и нестабильности соседних workloads.

### **2. OOMKilled — почему происходит и как диагностировать?**

OOMKilled означает, что процесс контейнера был завершён OOM Killer из-за нехватки памяти или превышения memory limit cgroup.

Причины: утечка памяти, неограниченный кэш/буфер, слишком много goroutine или одновременных запросов, большие batch-операции, резкий рост нагрузки, слишком низкий limit. Потребление cgroup может быть больше Go heap: учитываются также native allocations, mmap и часть page cache.

Диагностика:

```bash
kubectl describe pod api-xxxxx
kubectl get pod api-xxxxx -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}'
kubectl logs api-xxxxx --previous
kubectl top pod api-xxxxx --containers
```

Для Go:
- сравнить heap, allocs, goroutine count с RSS и cgroup memory;
- снять heap profile через `pprof`;
- проверить неограниченные очереди, кэши и соединения;
- сопоставить память с RPS, размером запросов и batch size;
- проверить memory limit и запас на память вне Go heap.

Увеличение limit может временно помочь, но не исправляет утечку. Не путайте OOMKilled (завершение контейнера) с Evicted (удаление Pod kubelet'ом из-за давления ресурсов узла).

**Главное:** проверьте `describe`, `lastState`, предыдущие логи и метрики. В Go сравнивайте heap с RSS/cgroup: причина может быть не только в управляемой Go памяти.

### **3. Liveness vs Readiness vs Startup probes — зачем три?**

Probes — проверки состояния контейнера, которые kubelet использует для управления перезапуском и допуском трафика.

| Probe | Вопрос | Действие при неуспехе |
|---|---|---|
| Liveness | Процесс жив или завис? | После порога неудач контейнер перезапускается |
| Readiness | Можно ли отправлять трафик? | Pod исключается из готовых endpoints Service |
| Startup | Завершилась ли долгая инициализация? | До успеха startup другие probes не выполняются; после порога контейнер перезапускается |

Пример:

```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 5
  failureThreshold: 30
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
```

`/health/live` должен проверять жизнеспособность процесса. Не стоит включать туда проверку каждой внешней зависимости: краткий сбой БД может вызвать массовые рестарты API. `/health/ready` отвечает, может ли экземпляр обслуживать запросы. `/health/startup` — завершилась ли инициализация.

Можно использовать HTTP, TCP, exec, а в поддерживаемых версиях — gRPC probes.

**Главное:** startup защищает медленный старт, liveness перезапускает зависшее приложение, readiness управляет трафиком. Не смешивайте их назначения.

## Прод и эксплуатация

### **1. Как происходит rolling update Deployment'а?**

Rolling update постепенно заменяет Pod'ы старой версии новыми. Deployment создаёт новый ReplicaSet, увеличивает количество новых Pod'ов и уменьшает старые, ориентируясь на доступность и параметры стратегии.

- `maxSurge` — сколько дополнительных Pod'ов можно создать сверх `replicas`.
- `maxUnavailable` — сколько Pod'ов может быть недоступно во время обновления.

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 1
```

Для пяти реплик это разрешает временно иметь одну дополнительную реплику и одну недоступную в процессе rollout. Реальный темп зависит от readiness, ресурсов и состояния кластера.

```bash
kubectl set image deployment/api api=example.com/api:1.5.0
kubectl rollout status deployment/api
kubectl rollout history deployment/api
kubectl rollout undo deployment/api
```

Backend-приложение должно корректно завершаться по SIGTERM, а readiness должна пропускать трафик только после готовности. Новая и старая версии должны быть совместимы со схемой БД во время rollout. Миграции обычно делают по expand-and-contract: сначала совместимое расширение схемы, затем обновление приложения, позже удаление старых полей.

**Главное:** Deployment меняет версию через новый ReplicaSet и постепенную замену Pod'ов. Надёжность зависит от probes, graceful shutdown, ресурсов и обратной совместимости БД.

### **2. Что такое HPA и на основе каких метрик он работает?**

HPA (Horizontal Pod Autoscaler) автоматически меняет число реплик Deployment или StatefulSet. Это горизонтальное масштабирование, в отличие от VPA, который помогает менять requests ресурсов отдельных Pod'ов.

Источники метрик:
- resource metrics — CPU и memory, обычно через Metrics Server;
- custom metrics — метрики Kubernetes-объектов или приложений через adapter;
- external metrics — внешние сигналы, например длина очереди.

Пример HPA по CPU:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

Упрощённая формула:

```text
desiredReplicas = ceil(currentReplicas * currentMetric / targetMetric)
```

Например, 3 реплики при загрузке 140% и цели 70% дают `ceil(3 * 140 / 70) = 6`.

Для Go backend CPU не всегда отражает нагрузку. Полезны RPS, latency, число активных запросов, длина очереди или Kafka consumer lag. Для них нужны custom/external metrics. Также важно правильно задать requests, иначе CPU utilization относительно requests может быть некорректной или недоступной.

```bash
kubectl get hpa
kubectl describe hpa api
kubectl top pods
```

**Главное:** HPA меняет число Pod'ов по CPU, memory или custom/external metrics. Выбирайте сигнал, отражающий реальную нагрузку, и учитывайте capacity БД и других зависимостей.

### **3. Почему Pod может не стартовать, хотя image существует?**

Наличие образа в registry не гарантирует успешный запуск Pod. Ошибка может произойти на этапе scheduling, скачивания image, подготовки volume, создания контейнера или старта процесса.

| Состояние | Возможная причина |
|---|---|
| Pending | Не хватает ресурсов, taints/affinity, PVC не готов |
| ImagePullBackOff | Registry недоступен, неверные credentials/tag |
| CreateContainerConfigError | Не найден Secret/ConfigMap или ключ |
| ContainerCreating | Volume, CNI, sandbox или runtime |
| CrashLoopBackOff | Процесс запускается и завершается |
| RunContainerError | Ошибка создания/запуска контейнера |
| Running, NotReady | Не проходит readiness probe |

Первые команды:

```bash
kubectl get pod api-xxxxx -o wide
kubectl describe pod api-xxxxx
kubectl get events --sort-by=.lastTimestamp
kubectl logs api-xxxxx
```

Если Pending — проверяйте Node, requests, affinity и taints. Если ImagePullBackOff — image name/tag, `imagePullSecrets`, сеть Node до registry и архитектуру образа. Если CreateContainerConfigError — наличие Secret/ConfigMap и нужных ключей. Если контейнер падает — `logs --previous`, exit code и конфигурацию запуска.

Образ, который есть на ноутбуке разработчика, может отсутствовать на Node кластера: локальный Docker cache не гарантирует доступность registry.

**Главное:** начните с `kubectl describe pod` и Events, чтобы определить этап сбоя, затем проверяйте scheduling, image pull, конфигурацию, volumes и команду запуска.

### **4. Как дебажить Pod в CrashLoopBackOff?**

CrashLoopBackOff означает, что контейнер многократно завершается, а kubelet увеличивает задержку перед новой попыткой запуска. Это не первопричина, а состояние backoff.

Алгоритм:
1. Посмотреть Pod и события.
2. Получить логи предыдущего запуска.
3. Проверить exit code, reason, restart count и OOMKilled.
4. Проверить probes, command/args, env, ConfigMap/Secret и mounts.
5. Проверить доступность БД, Kafka, DNS и других зависимостей.
6. Сопоставить сбой с последним релизом и при необходимости сделать rollback.

```bash
kubectl get pod api-xxxxx -o wide
kubectl describe pod api-xxxxx
kubectl logs api-xxxxx --previous
kubectl get events --sort-by=.lastTimestamp
kubectl rollout history deployment/api
kubectl rollout undo deployment/api
```

Для Pod с несколькими контейнерами укажите `-c container-name`. Если контейнер слишком быстро завершается, можно использовать debug Pod с похожей конфигурацией или ephemeral container:

```bash
kubectl debug -it pod/api-xxxxx --image=busybox:1.36 --target=api
```

Типовые причины для Go API: неверный env, недоступная БД, ошибка инициализации, отсутствующий CA bundle/config, несовместимая архитектура бинарника, OOM или слишком агрессивная liveness probe.

**Главное:** `CrashLoopBackOff` — следствие повторных падений. Начинайте с `describe`, `logs --previous`, exit code и OOMKilled, затем проверяйте конфигурацию, probes и зависимости.

### **5. Что хранится в etcd и почему его потеря — катастрофа?**

etcd — распределённое strongly consistent key-value хранилище, используемое Kubernetes для хранения состояния и конфигурации объектов API.

В etcd хранятся:
- Pods, Deployments, ReplicaSets, StatefulSets, Jobs;
- Services, EndpointSlices и сетевые объекты;
- ConfigMaps и Secrets;
- Namespaces, ServiceAccounts и RBAC;
- Nodes, PVC, PV, StorageClass;
- экземпляры Custom Resources и другие объекты API.

Сами данные внешних систем в etcd не хранятся. Например, содержимое PostgreSQL на persistent volume — не данные etcd; в etcd хранится описание Kubernetes-объектов, связанных с workload и storage.

При потере etcd API Server не может нормально читать и записывать состояние. Создание и изменение объектов, работа контроллеров и управление кластером нарушаются. Уже запущенные контейнеры могут некоторое время продолжать работать, но управляющая плоскость теряет состояние.

В production etcd обычно использует нечётное число участников, например 3 или 5, и quorum. Для трёх участников нужны два доступных участника, чтобы продолжать принимать записи.

Нужны регулярные snapshots, отдельное защищённое хранение backup и проверка восстановления. Пример команды (параметры TLS зависят от установки):

```bash
ETCDCTL_API=3 etcdctl snapshot save snapshot.db   --endpoints=https://127.0.0.1:2379   --cacert=/etc/kubernetes/pki/etcd/ca.crt   --cert=/etc/kubernetes/pki/etcd/server.crt   --key=/etc/kubernetes/pki/etcd/server.key
```

Для восстановления в актуальных версиях etcd применяется `etcdutl snapshot restore`.

**Главное:** etcd хранит состояние Kubernetes API, включая workloads, конфигурацию и Secrets. Потеря etcd лишает кластер управляющего состояния, поэтому нужны quorum, защищённые snapshots и регулярно проверяемый план восстановления.
