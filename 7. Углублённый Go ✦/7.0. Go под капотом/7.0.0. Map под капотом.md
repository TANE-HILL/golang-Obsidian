# 1. Назначение map

[[1.1.7. Map в Go - устройство и особенности|Map]] — структура данных для хранения пар *«ключ — значение»* с операциями:
- вставка значения по ключу;
- получение значения по ключу;
- удаление значения по ключу.

**Основная цель реализации** — эффективно выполнять эти операции независимо от общего количества элементов.

## Почему недостаточно простого перебора

Если хранить пары в списке и последовательно сравнивать ключи, поиск требует в худшем случае проверить все элементы:

- временная сложность поиска — `O(n)`;
- увеличение количества элементов увеличивает время поиска.

Для ускорения используется хеш-таблица.

## 2. Хеш-таблица и хеш-функция

Хеш-таблица распределяет записи по группам — **бакетам** (_buckets_). Поиск сначала определяет бакет, после чего ищет ключ внутри него.

**Хеш-функция** преобразует ключ в хеш, который используется для выбора бакета.

Ключевые требования к хеш-функции в изложении источника:

- **Равномерность:** записи должны распределяться по бакетам достаточно равномерно.
- **Быстрота:** вычисление хеша не должно становиться узким местом.
- **Детерминированность:** один и тот же ключ при одинаковых условиях должен приводить к одному и тому же результату хеширования.
- **Устойчивость к намеренному подбору коллизий:** усложняет злоумышленнику создание набора ключей, перегружающих один бакет.

Если много ключей попадает в один бакет, поиск внутри него замедляется. Поэтому равномерность распределения важна для производительности.

## 3. Типы и операции runtime

В рассматриваемой реализации runtime выполняет операции с ключами и значениями разных типов через информацию о типах и универсальные указатели.

### Дескрипторы типов

Информация о типе нужна runtime, чтобы выполнять необходимые операции над значениями. В описании источника она включает, в частности:

- размер значения;
- способ сравнения значений (`equal`);
- функцию хеширования;
- другую информацию, необходимую для работы с типом.

У `map` есть информация о типе ключа и типе значения.

### Почему здесь не используются дженерики

Дженерики в Go позволяют писать обобщённый код, но, согласно источнику, встроенная `map` в рассматриваемой реализации Go 1.18 не реализована как пользовательская обобщённая функция. Для работы с типами runtime использует дескрипторы типов и указатели, а не дженерики или интерфейсы в качестве основного механизма доступа к значениям.

### Операции доступа

Источник выделяет три основные runtime-операции:

- `mapaccess1` — получение значения;
- `mapaccess2` — получение значения и признака наличия ключа;
- `mapassign` — запись значения;
- `mapdelete` — удаление значения.

При обращении вида `v := m[k]` runtime получает значение через внутреннюю функцию доступа, а затем использует сведения о типе, чтобы вернуть значение нужного типа. В варианте `v, ok := m[k]` дополнительно возвращается признак наличия ключа.

## 4. Внутренняя структура map в Go 1.18

В материале структура условно делится на заголовок и набор бакетов.

### Заголовок (`hmap`)

Хранит общую информацию о map, в том числе:

- количество элементов;
- логарифм по основанию 2 от количества основных бакетов (`B`);
- случайное значение, используемое в механизмах хеширования;
- указатель на массив бакетов;
- служебные данные для управления ростом и состоянием map.

Количество основных бакетов в описанной реализации связано с параметром `B`:

\[ \text{количество бакетов} = 2^B \]

Хранение `B`, а не самого количества бакетов, позволяет использовать его в побитовых вычислениях.

### Выбор бакета: младшие биты хеша

Для определения бакета используется хеш ключа и маска, соответствующая количеству бакетов.

Если количество бакетов равно \(2^B\), индекс можно получить операцией:

\[ \text{bucketIndex} = \text{hash} \ \&\ (2^B - 1) \]

Маска \(2^B - 1\) содержит `B` младших единичных битов. Побитовое AND оставляет только нужные младшие биты хеша.

Пример: при четырёх бакетах \(B = 2\), маска равна `0b11`, поэтому используются два младших бита.

### Устройство бакета

В описанной реализации один основной бакет содержит до **8 записей**. Внутри него находятся:

- метаданные, включающие старшие биты хешей (_top hash_);
- слоты ключей;
- слоты значений;
- ссылка на дополнительный бакет при переполнении.

Сначала проверяются короткие значения `top hash`. Они позволяют быстро пропустить слоты, которые заведомо не соответствуют искомому ключу. Если метаданные совпали, выполняется полноценное сравнение ключей.

Ключи и значения в бакете размещены раздельно: сначала область ключей, затем область значений. Источник связывает такой layout с выравниванием типов и экономией памяти.

## 5. Как работает поиск

Обобщённая последовательность поиска в реализации, рассмотренной в видео:

1. Проверить, существует ли map и содержит ли она элементы.
2. Вычислить хеш искомого ключа с помощью функции, связанной с типом ключа.
3. Получить индекс основного бакета из младших битов хеша.
4. Перейти к нужному бакету.
5. Сравнить `top hash` в его слотах с соответствующими битами хеша.
6. Для подходящих слотов сравнить реальные ключи.
7. При совпадении вернуть значение; если ключ не найден, вернуть нулевое значение. В варианте с двумя результатами также возвращается `ok`.

В реализации Go 1.18 при поиске учитываются и дополнительные бакеты, а во время роста map — состояние переноса данных.

## 6. Переполнение бакета

Если в основном бакете уже заняты 8 слотов и требуется разместить ещё одну запись, в рассматриваемой реализации используется дополнительный бакет, связанный с исходным.

Дополнительные бакеты позволяют хранить записи, не помещающиеся в основные слоты, но длинные цепочки переполнения ухудшают производительность поиска и других операций.

Поэтому runtime отслеживает заполненность map и может увеличить таблицу, а не полагаться только на дополнительные бакеты.

## 7. Рост map и эвакуация данных

В описанной реализации Go 1.18 рост map связан с коэффициентом заполнения и количеством переполненных бакетов.

- При слишком высокой заполненности растёт вероятность переполнения бакетов.
- При слишком низкой заполненности расходуется больше памяти, чем необходимо.
- В материале указан порог коэффициента заполнения **6,5 элемента на основной бакет в среднем** для запуска роста в рассматриваемой реализации.

При росте создаётся массив основных бакетов большего размера — в описанном случае вдвое больше прежнего. Данные из старых бакетов постепенно переносятся в новые. Этот процесс называется **эвакуацией**.

Эвакуация выполняется постепенно во время операций записи и удаления, а не обязательно целиком за один момент. Пока перенос не завершён, runtime должен учитывать данные в старой и новой таблицах, поэтому некоторые операции могут временно выполняться медленнее.

> Число `6,5`, устройство бакетов и описанный механизм роста — детали реализации Go 1.18 из источника, а не гарантии спецификации языка.

## 8. Зачем заранее указывать размер map

Если ожидаемое количество записей известно, можно задать приблизительную начальную ёмкость при создании:

```
m := make(map[string]int, 1000)
```

Это позволяет runtime выделить структуру подходящего размера заранее и снизить вероятность дополнительных затрат на рост и перенос данных во время заполнения.

Указанная ёмкость — подсказка о предполагаемом количестве элементов, а не ограничение максимального размера map. Фактическое поведение выделения памяти зависит от реализации Go.

## 9. Почему нельзя взять указатель на элемент map

Нельзя напрямую получить адрес элемента map, например:

```
p := &m["key"] // ошибка компиляции
```

Причина связана с тем, что внутреннее расположение элементов не стабильно: при росте и эвакуации записи могут перемещаться между бакетами. Указатель на конкретное место хранения мог бы стать недействительным или указывать уже не на актуальное расположение значения.

Получить значение из map можно обычным чтением:

```
v := m["key"]
```

Если значение нужно изменять через указатель, можно хранить в map указатели:

```
m := map[string]*User{}
```

Тогда перемещается сама запись с указателем, а объект, на который он указывает, хранится отдельно.

## 10. Почему порядок обхода map не гарантирован

Порядок обхода map не определён языковым контрактом. На него не следует полагаться и нельзя использовать map как упорядоченную коллекцию.

В реализации, описанной в источнике, обход проходит по бакетам и учитывает их внутреннюю организацию. Начальная позиция обхода выбирается с использованием генератора случайных чисел runtime, поэтому порядок может отличаться между обходами.

Если нужен отсортированный вывод, ключи следует отдельно собрать и отсортировать. `fmt.Println` в примере видео выдаёт отсортированное представление map за счёт логики форматирования, а не потому, что сама map хранит ключи в отсортированном порядке.

## 11. Основные выводы

- `map` реализует хеш-таблицу: хеш ключа помогает выбрать бакет, а затем выполняется проверка ключа.
- В реализации Go 1.18 основной бакет вмещает до 8 записей; переполнение обслуживается дополнительными бакетами.
- Младшие биты хеша используются для выбора бакета, а старшие — для предварительной проверки слотов.
- При росте map данные эвакуируются в новый массив бакетов; это может временно увеличить стоимость операций.
- Предварительная оценка размера map помогает уменьшить количество ростов и переносов.
- Элементы map нельзя адресовать напрямую, поскольку их размещение может изменяться.
- Порядок обхода map не гарантирован. Для сортированного результата нужна отдельная сортировка.
- Внутреннее устройство — деталь реализации и зависит от версии Go; спецификация языка не гарантирует конкретную организацию бакетов или алгоритм роста.
