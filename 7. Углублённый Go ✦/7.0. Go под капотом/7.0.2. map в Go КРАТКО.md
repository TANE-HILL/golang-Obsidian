## 1. **Общая информация**

- `map` — хэш-таблица, хранящая пары ключ-значение.    
- Для определения места хранения элемента используется хэширование ключа.
- Средняя [[7.1.0. Асимптотический анализ#3. Основные классы сложности|сложность поиска]], вставки и удаления — **`O(1)`** *(константная)*. 
- В худшем случае [[7.1.0. Асимптотический анализ#3. Основные классы сложности|сложность]] может приближаться к **`O(n)`** *(линейная)*, например при большом количестве коллизий.
- Map не потокобезопасна *(не обеспечивает синхронизацию конкурентного доступа)*.

## **2. Старая реализация map *(до [[1.1.0. Go Basics|Go]] 1.24)***

**Основана на [[7.2.3. Бакеты|бакетах]] *(buckets)*.**
**Bucket** — группа слотов для хранения пар _«ключ — значение»_ внутри хеш-таблицы.

**Внутренняя структура:**
- `hmap` — основная структура, управляющая map.
- `buckets` — массив основных бакетов.
- `bmap` — отдельный бакет, содержащий до 8 пар ключ-значение.
- `tophash` — массив из 8 байтов, содержащий старшие биты хэшей для предварительной проверки ключей.
- `overflow` — ссылка на следующий бакет при переполнении текущего.

**Механизм поиска:**
1. Вычисляется хэш ключа.
2. По младшим битам хэша определяется бакет.
3. Проверяются значения `tophash`.
4. При совпадении отпечатка сравниваются реальные ключи.
5. Если ключ не найден, проверяется следующий overflow bucket.

**Рост map *(Growth)*:**
- При достижении порога загрузки или чрезмерном количестве overflow buckets происходит рост/перестройка map.
- При обычном росте количество бакетов увеличивается вдвое.
- При Same-size grow количество бакетов остаётся прежним, но структура перестраивается для уменьшения overflow buckets.
- `Evacuation` — постепенный перенос элементов из старых бакетов в новые.
- При удвоении количества бакетов используется больше битов хэша, поэтому элементы могут попасть в другие бакеты.
- Перенос выполняется постепенно при последующих операциях с map *(incremental evacuation)*.

## 3. **Новая реализация map *([[1.1.0. Go Basics|Go]] 1.24+)***

**Основана на алгоритме Swiss Tables.**

**Внутренняя структура:**
- Данные организованы в группах *(groups)*.
- Каждая группа содержит 8 слотов для хранения ключей и значений.
- `Control bytes` — метаданные, описывающие состояние слотов и содержащие 7-битный отпечаток H2.
- Хэш разделяется на две части:
    - `H1` *(57 бит)* — определяет начальную позицию поиска и используется при probing.
    - `H2` *(7 бит)* — используется для предварительной проверки потенциальных совпадений.

**Механизм поиска:**
1. Вычисляется хэш ключа.
2. H1 определяет начальную группу.
3. H2 сравнивается с control bytes группы.
4. Определяются потенциальные совпадения.
5. Выполняется сравнение реальных ключей.
6. Если ключ не найден, поиск продолжается через probing.

**Главные отличия от старой реализации:**

| <center><u>Старая map</u></center> | <center><u>Новая map</u></center>                       |
| ---------------------------------- | ------------------------------------------------------- |
| **Бакеты**                         | **Группы по 8 слотов**                                      |
| **Overflow buckets**               | **Probing**                                                 |
| **Tophash**                        | **Control bytes**                                           |
| **Incremental evacuation**         | **Directory и механизм роста на основе extendible hashing** |

Главное преимущество **Swiss Tables** — более эффективная организация поиска за счёт групповой проверки метаданных и сокращения количества сравнений реальных ключей.

## **4. Конкурентный доступ к map**

**Обычная map не потокобезопасна.**

| <center><u>Сценарий</u></center>              | <center><u>Безопасно?</u></center> |
| --------------------------------------------- | ---------------------------------- |
| **Одна горутина читает и записывает**         | *Да*                                 |
| **Несколько горутин только читают**           | *Да, если никто не изменяет map*     |
| **Одна горутина пишет, другая читает**        | *Нет*                                |
| **Несколько горутин одновременно записывают** | *Нет*                                |

**Почему возникает проблема:**
- Изменение map затрагивает её внутреннее состояние.
- Конкурентное чтение и запись могут вызвать Data Race.
- Runtime обнаруживает некоторые случаи конкурентного доступа и может вызвать fatal error (`concurrent map read and map write`).
- Это не полноценная замена Race Detector.

**Способы синхронизации:**
- `sync.Mutex` — обеспечивает эксклюзивный доступ.
- `sync.RWMutex` — позволяет нескольким горутинам одновременно читать, но запись выполняется эксклюзивно.
- `sync.Map` — специализированная потокобезопасная структура.

## **5. sync.Map**

**`sync.Map` — потокобезопасная map из стандартного пакета `sync`.**

**Основные методы:**

| <center><u>Метод</u></center> | <center><u>Назначение</u></center>           |
| ----------------------------- | -------------------------------------------- |
| **`Store`**                   | *Записать значение*                            |
| **`Load`**                    | *Прочитать значение*                           |
| **`LoadOrStore`**             | *Записать, если ключ отсутствует*              |
| **`Delete`**                  | *Удалить ключ*                                 |
| **`Range`**                   | *Перебрать элементы*                           |
| **`LoadAndDelete`**           | *Получить и удалить значение*                  |
| **`CompareAndSwap`**          | *Заменить значение при совпадении с ожидаемым* |
| **`CompareAndDelete`**        | *Удалить значение при совпадении*              |

**Когда предпочтительнее sync.Map:**
1. Значение для ключа записывается один раз, после чего преимущественно читается.
2. Несколько горутин работают с непересекающимися наборами ключей.

**Когда предпочтительнее обычная map + Mutex/RWMutex:**
- В большинстве остальных сценариев.
- Когда нужна типобезопасность.
- Когда необходимо выполнять несколько операций над map под одной общей блокировкой.
- Когда нужна более гибкая логика синхронизации.

>**`sync.Map` не является универсальной заменой обычной map и не гарантирует лучшую производительность.**
