# **Виды архитектур ИС**

## **Файл-сервер**
Устаревшая архитектура ИС.
**Клиент обращается за данными -> сервер отдаёт данные в сыром виде.**
*Например: Google Drive, Dropbox.*
## **Peer to Peer *(P2P)***
**Нет централизованного сервера. Каждый узел является и клиентом и сервером.**
*Например: torrent, blockchain.*
## **Клиент-сервер**
**Клиент обращается за данными -> сервер фильтрует, ищет нужные данные и отдаёт результат.**
Клиент не загружается лишней логикой, работу выполняет сервер.
*Используется чаще всего.*

### **Классы масштабирования**

#### **Вертикальное**
- Стоимость увеличения ресурсов растет не линейно, относительно увеличения их мощности *(возможен downtime)*. Также невозможно масштабироваться бесконечно.
	*Например: обновление железа сервера. Мощнее процессор, больше ОЗУ и т.п.*
- <u>Преимущество</u>: простота масштабирования;
- <u>Существенный минус</u>: с ростом сервера каждое следующее вертикальное масштабирование будет стоить сильно дороже.
#### **Горизонтальное**
- Увеличение производительности за счёт добавления новых серверов *(узлов)* в систему.
- Чаще всего происходит без каких-то проблем;
- <u>Преимущество</u>: практически неограниченная возможность масштабирования, можно постепенно добавлять ресурсы по мере роста нагрузки.
- <u>Существенный минус</u>: усложнение архитектуры системы. Необходимо распределять нагрузку между серверами *(Load Balancing)*, синхронизировать данные и учитывать возможные сетевые задержки.
- Особенность: требует поддержки распределённой архитектуры *(например, микросервисов)*.

### **Stateless and Statefull**

Когда мы говорим про масштабирование, сервисы делятся на две категории.
#### **Stateless *(без состояния)***
- Сервис не хранит данные между запросами.
- Все необходимые данные хранятся во внешней БД или Redis.
- Преимущество: легко масштабировать — можно просто добавлять новые серверы.
- Пример: несколько одинаковых экземпляров Go API за Load Balancer.
#### **Stateful *(с состоянием)***
- Сервис хранит данные между запросами (например, в своей оперативной памяти).
- Минус: сложнее масштабировать — нужно синхронизировать данные между серверами.
- Пример: сервер хранит пользовательские сессии у себя в памяти.

**Главное отличие:** Stateless — любой сервер может обработать запрос. Stateful — серверу может понадобиться состояние, сохранённое ранее на нём же.

### **Latency и Response Time**

**Response Time включает в себя Latency.**
#### **Latency *(Задержка)***
- Время, которое требуется для передачи запроса от клиента до сервера (или между серверами).
- Зависит от расстояния, сетевой нагрузки и скорости передачи данных.
- Пример: клиент отправил запрос, сервер получил его через 50 мс.
#### **Response Time *(Время ответа)***
- Полное время от отправки запроса клиентом до получения готового ответа.
- Включает сетевые задержки, обработку запроса сервером и передачу ответа обратно.
- Пример: запрос дошёл до сервера за 50 мс, обработка заняла 100 мс, ответ вернулся за 50 мс. Response Time = 200 мс.

**Главное отличие:**
- Latency — задержка передачи данных.
- Response Time — сколько времени пользователь ждёт готовый ответ.
