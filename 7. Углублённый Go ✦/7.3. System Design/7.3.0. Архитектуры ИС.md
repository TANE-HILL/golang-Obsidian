# Виды архитектур ИС

## Файл-сервер
Устаревшая архитектура ИС.
**Клиент обращается за данными -> сервер отдаёт данные в сыром виде.**
*Например: Google Drive, Dropbox.*
## Peer to Peer (P2P)
**Нет централизованного сервера. Каждый узел является и клиентом и сервером.**
*Например: torrent, blockchain.*
## Клиент-сервер
**Клиент обращается за данными -> сервер фильтрует, ищет нужные данные и отдаёт результат.**
Клиент не загружается лишней логикой, работу выполняет сервер.
*Используется чаще всего.*

### SLA / SLO / SLI
- **SLA *(Service Level Agreement)*** - соглашение, которое заключается с клиентами;
- **SLO *(Service Level Objectives)*** - цели, которые нужно решить, чтобы выполнить SLA;
- **SLI *(Service Level Indicators)*** - показатели системы.

## Масштабирование

Заранее должны быть предусмотрены разумные способы решения возникающих при росте системы проблем.

![[Pasted image 20261104142150.png]]

### Классы масштабирования

#### Вертикальное
- Стоимость увеличения ресурсов растет не линейно, относительно увеличения их мощности *(возможен downtime)*. Также невозможно масштабироваться бесконечно.
	*Например: обновление железа сервера. Мощнее процессор, больше ОЗУ и т.п.*
- <u>Преимущество</u>: простота масштабирования;
- <u>Существенный минус</u>: с ростом сервера каждое следующее вертикальное масштабирование будет стоить сильно дороже.
#### Горизонтальное
- Увеличение производительности за счёт добавления новых серверов *(узлов)* в систему.
- Чаще всего происходит без каких-то проблем;
- <u>Преимущество</u>: практически неограниченная возможность масштабирования, можно постепенно добавлять ресурсы по мере роста нагрузки.
- <u>Существенный минус</u>: усложнение архитектуры системы. Необходимо распределять нагрузку между серверами *(Load Balancing)*, синхронизировать данные и учитывать возможные сетевые задержки.
- Особенность: требует поддержки распределённой архитектуры *(например, микросервисов)*.
