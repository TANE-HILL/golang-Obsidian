# **Стек и куча** *(Stack and Heap)*

**Стек и куча** — области памяти, которые используются во время выполнения программы. В [[1.1.0. Go Basics|Go]] место размещения данных выбирает компилятор, в том числе на основе **escape analysis**.
	**Escape analysis** — анализ компилятором [[1.1.0. Go Basics|Go]], определяющий, может ли [[1.1.1. Переменные|переменная]] использоваться за пределами своей области видимости. На его основе компилятор решает, где разместить данные: в стеке или куче.

---
## **Стек** *(Stack)*

Стек хранит данные, связанные с активными вызовами функций: например, локальные переменные и служебную информацию вызова.

- У каждой горутины есть собственный стек.
- Стек горутины может увеличиваться по мере необходимости.
- Память освобождается при завершении соответствующего вызова функции или исчезновении области жизни данных.
- Обычно выделение и освобождение памяти на стеке обходится дешевле, чем работа с кучей и сборщиком мусора.

## **Куча** *(Heap)*

Куча используется для данных, которым необходимо жить за пределами текущего вызова функции или которые должны оставаться доступными из других частей программы.

- Данные в куче могут переживать функцию, в которой были созданы.
- Память в куче управляется сборщиком мусора (GC): он освобождает объекты, которые больше недостижимы.
- Выделение в куче может иметь дополнительные затраты на управление памятью и сборку мусора.
---
## Как Go выбирает место размещения?

В Go нельзя надёжно определить размещение переменной только по тому, где она объявлена или используется `new`/`make`. Компилятор анализирует, может ли значение «убежать» за пределы области, где оно создано (**escape analysis**).

```
func local() int {
    x := 10
    return x
}
```

`x` может храниться на стеке: наружу возвращается значение, а не ссылка на `x`.

```
func pointer() *int {
    x := 10
    return &x
}
```

Здесь указатель на `x` возвращается вызывающему коду, поэтому `x` обычно размещается в куче, чтобы оставаться доступным после завершения `pointer`.

Это упрощённые примеры: фактическое размещение зависит от оптимизаций компилятора.

## Стек и куча: сравнение

|Свойство|Стек|Куча|
|---|---|---|
|Типичные данные|Данные вызовов функций, локальные значения|Объекты, которые должны пережить вызов или быть доступны из разных мест|
|Время жизни|Обычно связано с вызовом функции|Пока объект достижим и нужен программе|
|Управление памятью|Автоматически при завершении области вызова|Управляется GC|
|Стоимость|Обычно дешевле|Может требовать дополнительных затрат на выделение и GC|
|Область использования|Отдельный стек у каждой горутины|Общая область памяти, доступная горутинам при наличии ссылок|

## Важные уточнения

- **Не все локальные переменные находятся на стеке.** Переменная может быть размещена в куче, если проходит escape analysis.
- **Не все значения, созданные через `new` или `make`, обязательно находятся в куче.** Компилятор может оптимизировать размещение.
- **Куча не означает «медленно», а стек — «всегда быстро».** Реальная производительность зависит от контекста и оптимизаций.
- **GC не освобождает объект сразу после последнего использования в исходном коде.** Он освобождает память, когда объект больше не достижим, во время циклов сборки мусора.
- Указатель на значение сам по себе не доказывает, что значение обязательно находится в куче: решение зависит от анализа компилятора.

## Как посмотреть escape analysis

Команда компилятора:

```
go build -gcflags=-m .
```

Она выводит диагностические сообщения о решениях компилятора, включая то, какие значения «убегают» в кучу.
