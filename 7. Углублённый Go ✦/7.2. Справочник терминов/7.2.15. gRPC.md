# gRPC

## 1. Что такое gRPC?

**gRPC** — фреймворк для удалённого вызова процедур *(RPC, Remote Procedure Call)*.
Он позволяет одному [[2.2.2. Микросервисы и монолит|сервису]] вызывать метод другого [[2.2.2. Микросервисы и монолит|сервиса]] почти так же, как обычную [[1.1.5. Функции и передача данных|функцию]], хотя вызов происходит по сети.

Например, сервис **`OrderService`** вызывает **`UserService.GetUser()`**, чтобы получить данные пользователя. Вызов проходит через сеть, поэтому возможны задержки, тайм-ауты и сетевые ошибки.

**gRPC часто используют для взаимодействия между backend-сервисами и микросервисами.**

## 2. Как работает gRPC?

**В типичном случае используются три основные составляющие:**
- **Protocol Buffers *(Protobuf)*** — формат описания [[1.6.2. REST API|API]] и сериализации сообщений.
- **HTTP/2** — транспортный протокол, по которому передаются вызовы и ответы.
- **Сгенерированный код** — клиентские и серверные типы и методы, создаваемые из `.proto`-файла.

**Общий процесс:**
1. Разработчик описывает сообщения и методы сервиса в файле `.proto`.
2. `protoc` и плагины генерируют код для нужного языка, например Go.
3. Сервер реализует сгенерированный интерфейс.
4. Клиент использует сгенерированный stub/client и вызывает метод.
5. Сообщение сериализуется в Protobuf и отправляется по HTTP/2.
6. Сервер десериализует запрос, выполняет метод и возвращает ответ или статус ошибки.

Вызов выглядит как обычный метод, но фактически это сетевой запрос: он может завершиться ошибкой, не выполниться вовремя или быть отменён.

## 3. Protocol Buffers и `.proto`

**Protocol Buffers *(Protobuf)*** — механизм описания структур данных и их компактной бинарной сериализации. Файл `.proto` служит контрактом между клиентом и сервером.

**Пример:**
```proto
syntax = "proto3";

package users;
option go_package = "example.com/myapp/gen/users";

service UserService {
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
}

message GetUserRequest {
  int64 id = 1;
}

message GetUserResponse {
  int64 id = 1;
  string name = 2;
  string email = 3;
}
```

**Здесь:**
- `service` описывает набор RPC-методов.
- `rpc` описывает метод и типы его запроса и ответа.
- `message` описывает структуру данных.
- `id = 1`, `name = 2` — номера полей в бинарном формате. Их нужно считать частью контракта: нельзя бездумно менять или переиспользовать номера уже опубликованных полей.
- `go_package` задаёт Go import path для сгенерированного кода.

Protobuf обычно компактнее [[1.6.0.1. ~ JSON ~|JSON]] и имеет строгую схему.
Но бинарный формат менее удобен для чтения человеком, чем [[1.6.0.1. ~ JSON ~|JSON]].

### Генерация кода

**Для [[1.1.0. Go Basics|Go]] обычно используют:**
- `protoc` — компилятор `.proto`;
- `protoc-gen-go` — генератор типов Protobuf;
- `protoc-gen-go-grpc` — генератор клиентского и серверного кода gRPC.

Команды и конфигурация генерации зависят от проекта. Сгенерированный код обычно не редактируют вручную: меняют `.proto` и запускают генерацию снова.

## 4. Клиент и сервер в [[1.1.0. Go Basics|Go]]

После генерации кода сервер реализует метод сервиса, а клиент вызывает его через gRPC-соединение.

Упрощённый пример серверного метода:

```
func (s *Server) GetUser(
    ctx context.Context,
    req *pb.GetUserRequest,
) (*pb.GetUserResponse, error) {
    if req.GetId() <= 0 {
        return nil, status.Error(codes.InvalidArgument, "id must be positive")
    }

    return &pb.GetUserResponse{
        Id:    req.GetId(),
        Name:  "Alex",
        Email: "alex@example.com",
    }, nil
}
```

`pb` здесь — пакет со сгенерированными типами. `Server` должен реализовать интерфейс, сгенерированный для `UserService`.

Вызов на клиенте выглядит примерно так:

```
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

resp, err := client.GetUser(ctx, &pb.GetUserRequest{Id: 42})
if err != nil {
    // Обработать ошибку RPC
    return
}

fmt.Println(resp.GetName())
```

Клиент передаёт `context.Context`, чтобы задать deadline, отмену и передать метаданные. В реальном проекте адрес, TLS, создание соединения и регистрация сервера оформляются отдельно.

## 5. Четыре вида RPC

gRPC поддерживает четыре типа вызовов.

### 1. Unary RPC

Один запрос — один ответ. По форме напоминает обычный HTTP API-вызов.

```
rpc GetUser(GetUserRequest) returns (GetUserResponse);
```

Применение: получить пользователя, создать заказ, проверить статус.

### 2. Server streaming

Клиент отправляет один запрос, сервер возвращает поток сообщений.

```
rpc WatchOrders(WatchOrdersRequest) returns (stream OrderUpdate);
```

Применение: подписка на обновления, поток событий с сервера.

### 3. Client streaming

Клиент отправляет поток сообщений, сервер возвращает один ответ.

```
rpc UploadChunks(stream DataChunk) returns (UploadSummary);
```

Применение: загрузка данных частями или отправка серии измерений.

### 4. Bidirectional streaming

Клиент и сервер отправляют потоки сообщений независимо друг от друга в рамках одного RPC.

```
rpc Chat(stream ChatMessage) returns (stream ChatMessage);
```

Применение: двусторонний обмен сообщениями, интерактивные потоки данных.

Streaming не означает, что сообщения обязательно обрабатываются одновременно в бизнес-логике: это зависит от реализации. Порядок сообщений сохраняется внутри соответствующего потока, но приложение должно само определять правила обработки и завершения.

## 6. Почему HTTP/2?

gRPC использует HTTP/2, который поддерживает несколько независимых потоков запросов и ответов на одном соединении (multiplexing). Это уменьшает необходимость создавать отдельное TCP-соединение для каждого вызова и хорошо подходит для частого общения между сервисами.

HTTP/2 также поддерживает заголовки и двоичные кадры, а gRPC использует собственный протокол поверх HTTP/2 для сообщений и статусов.

Важно: HTTP/2 сам по себе не гарантирует низкую задержку и не устраняет все сетевые проблемы. На производительность влияют размер сообщений, сериализация, сеть, нагрузка и настройки соединений.

## 7. Ошибки и статус-коды

В [[1.1.0. Go Basics|Go]] gRPC-метод обычно возвращает `response, error`.

**Для ошибок RPC используется система статус-кодов gRPC, например:**
- `codes.InvalidArgument` — *запрос содержит некорректный аргумент.*
- `codes.NotFound` — *сущность не найдена.*
- `codes.Unauthenticated` — *не пройдена аутентификация.*
- `codes.PermissionDenied` — *недостаточно прав.*
- `codes.DeadlineExceeded` — *истёк deadline.*
- `codes.Unavailable` — *сервис временно недоступен.*
- `codes.Internal` — *внутренняя ошибка сервера.*

**Пример:**
```Go
return nil, status.Error(codes.NotFound, "user not found")
```

**На клиенте можно извлечь статус:**
```Go
resp, err := client.GetUser(ctx, req)
if err != nil {
    st, ok := status.FromError(err)
    if ok {
        fmt.Println(st.Code(), st.Message())
    }
    return
}
```

Не следует отдавать клиенту внутренние детали, секреты или stack trace. Сообщение ошибки должно быть полезным, но безопасным.

## 8. Deadline, timeout и отмена через [[1.4.2. sync пакет (WaitGroup, Mutex, Atomic, Pool, Context)#🔹 Что такое `context`|context]]

Сетевой вызов не должен бесконечно ждать ответа.
**В [[1.1.0. Go Basics|Go]] для RPC обычно передают `context.Context` с deadline или timeout:**
```Go
ctx, cancel := context.WithTimeout(parentCtx, 2*time.Second)
defer cancel()

resp, err := client.GetUser(ctx, req)
```
- **Deadline** — крайний момент времени, к которому вызов должен завершиться.
- **Timeout** — длительность ожидания до отмены; на практике его часто задают через `context.WithTimeout`.
- **Cancellation** — отмена операции, например если клиент больше не нуждается в результате.

Deadline и отмена передаются по цепочке вызовов, если код корректно передаёт контекст дальше. Серверный обработчик должен учитывать `ctx.Done()` и не продолжать ненужную работу.

Не нужно создавать `context.Background()` внутри каждого метода вместо принятого контекста: это может разорвать распространение отмены и deadline.

## 9. Metadata и interceptors

### Metadata

**Metadata** — набор ключ-значение, который передаётся вместе с RPC, отдельно от основного Protobuf-сообщения.

**Может использоваться для:**
- передачи токена аутентификации;
- request ID и trace ID;
- служебной информации о запросе.

Не следует помещать секреты в обычные логи. Для передачи токенов нужен защищённый канал, обычно TLS.

### Interceptors

**Interceptor** — обёртка вокруг RPC-вызова, похожая по назначению на middleware в [[1.6.1. HTTP-сервер|HTTP-сервисе]].

- **Unary interceptor** — для обычных RPC *«запрос — ответ»*.
- **Stream interceptor** — для потоковых RPC.

В interceptor удобно выносить логирование, метрики, трассировку, проверку аутентификации и общую обработку ошибок, чтобы не дублировать этот код в каждом методе.

## 10. Безопасность

Для production-сервисов обычно используют TLS, чтобы шифровать трафик и проверять подлинность сервера. Для идентификации клиента могут применяться токены или взаимный **TLS *(mTLS)***, в зависимости от архитектуры.

**Важно различать:**
- **Аутентификацию** — кто обращается к сервису.
- **Авторизацию** — какие действия этому субъекту разрешены.

Само использование gRPC не обеспечивает авторизацию автоматически: проверки доступа нужно реализовать или подключить отдельно.

## 11. Повторные попытки *(retries)* и идемпотентность

Временные сетевые сбои иногда можно пережить повторным вызовом. Но повторять запросы бездумно опасно: сервер мог выполнить операцию, а ответ потерялся по дороге.

Например, повторный запрос *«списать 100 рублей»* может привести к двойному списанию, если операция не защищена от повторов.

**Поэтому:**
- повторные попытки настраивают для подходящих временных ошибок;
- учитывают deadline и ограничивают количество попыток;
- используют backoff, то есть паузу между попытками;
- для изменяющих состояние операций предусматривают идемпотентность или idempotency key.

**Идемпотентная операция** при повторном выполнении с теми же параметрами приводит к тому же конечному состоянию, что и однократное выполнение. Не каждый RPC автоматически безопасно повторять.

## 12. Преимущества и недостатки

### Преимущества

- Строгий контракт API на основе `.proto`.
- Компактная бинарная сериализация Protobuf.
- Генерация типизированного клиентского и серверного кода.
- Поддержка server/client/bidirectional streaming.
- HTTP/2 и удобная передача metadata, deadline и статусов.
- Подходит для внутреннего взаимодействия микросервисов.

### Недостатки

- Бинарные сообщения сложнее читать и отлаживать вручную, чем [[1.6.0.1. ~ JSON ~|JSON]].
- Для браузеров может понадобиться gRPC-Web или дополнительный gateway.
- Нужно управлять `.proto`, генерацией и совместимостью схем.
- Для публичного API, которым удобно пользоваться напрямую из браузера или через `curl`, REST/JSON иногда проще.
- Сетевые ошибки, дедлайны, безопасность и повторные попытки всё равно требуют грамотной обработки.

## 13. gRPC или REST?

| <center><u>Критерий</u></center> | <center><u>gRPC</u></center>      | <center><u>REST/JSON</u></center>      |
| -------------------------------- | --------------------------------- | -------------------------------------- |
| **Контракт**                     | *Обычно `.proto`, строгая схема*    | *Часто OpenAPI, но зависит от проекта*   |
| **Формат данных**                | *Обычно бинарный Protobuf*          | *Обычно JSON*                            |
| **Транспорт**                    | *HTTP/2 для классического gRPC*     | *Часто HTTP/1.1 или HTTP/2*              |
| **Генерация кода**               | *Стандартный сценарий*              | *Возможна, но зависит от инструментов*   |
| **Streaming**                    | *Поддерживается на уровне RPC*      | *Обычно реализуется другими механизмами* |
| **Читаемость вручную**           | *Ниже*                              | *Выше*                                   |
| **Типичное применение**          | *Внутренние вызовы между сервисами* | *Публичные API, веб-клиенты, интеграции* |

Это не жёсткое правило. И gRPC, и REST можно использовать в разных архитектурах; выбор зависит от клиентов, требований к контракту, streaming, инструментов и удобства эксплуатации.

## 14. Частые вопросы на собеседовании

**Чем gRPC отличается от REST?**  
gRPC — RPC-фреймворк с контрактом Protobuf, генерацией кода и поддержкой потоковых вызовов поверх HTTP/2. REST обычно строится вокруг HTTP-ресурсов и часто использует JSON. gRPC удобен для типизированного взаимодействия между сервисами, REST — для многих публичных API и веб-интеграций.

**Зачем нужен `.proto`?**  
Он описывает сообщения и методы сервиса. По нему генерируются типы, клиентский код и серверный интерфейс, благодаря чему клиент и сервер используют общий контракт.

**Какие виды RPC есть?**  
Unary, server streaming, client streaming и bidirectional streaming.

**Зачем передавать context?**  
Чтобы управлять deadline и отменой вызова, а также передавать связанные с запросом значения, например metadata через соответствующие API.

**Что такое interceptor?**  
Обёртка вокруг RPC-вызова, где удобно реализовать общую логику: логирование, метрики, трассировку или аутентификацию.

**Что будет, если RPC вернул ошибку?**  
Клиент должен обработать `error` и, если это gRPC status, проверить код. Например, `NotFound` может означать отсутствие сущности, а `Unavailable` — временную недоступность сервиса.

**Можно ли автоматически повторять любой запрос?**  
Нет. Операция могла выполниться на сервере, даже если ответ не дошёл до клиента. Повторы должны учитывать тип ошибки, deadline и идемпотентность операции.

## 15. Короткий ответ для собеседования

gRPC — это фреймворк для удалённого вызова методов между сервисами. Контракт описывается в `.proto` с помощью Protocol Buffers, после чего генерируется типизированный клиентский и серверный код. В классическом gRPC запросы передаются по HTTP/2, а формат Protobuf обеспечивает компактную сериализацию. Поддерживаются четыре вида вызовов: unary, server streaming, client streaming и bidirectional streaming. В Go важно корректно обрабатывать статус-коды, передавать `context` с deadline и отменой, а для общей логики использовать interceptors. gRPC часто выбирают для взаимодействия между микросервисами, тогда как REST/JSON нередко удобнее для публичных API и браузерных клиентов.
