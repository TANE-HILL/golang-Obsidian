# Интерфейсы в [[1.0. Go Basics|Golang]]

Представь, что ты пишешь приложение, где нужно работать с хранилищем данных — сохранять и получать пользователей.

Сначала ты используешь **файлы**, потом решаешь перейти на **базу данных**.

Если код напрямую зависит от реализации (например, от файловой системы), тебе придётся менять всё.

<u>Но если ты опишешь поведение хранилища через интерфейс, то можно будет:</u>
- **легко менять реализацию (файлы, база, сеть);**
- **писать тесты без настоящей базы, используя mock-хранилище — поддельную реализацию, которая хранит данные в памяти.**

#### **Интерфейсы позволяют писать код, независимый от конкретных реализаций**, что делает программы гибкими и легко тестируемыми.

# Что такое интерфейс

**Интерфейс (interface)** — это [[1.2. Типы данных|тип]], который описывает **набор [[1.8. Структуры и методы#Разница между методами и 1.5. Функции и передача данных функциями|методов]]**, не реализуя их.

**Пример:**
```go
type Shape interface {
    Area() float64
}
```
Здесь интерфейс `Shape` говорит:
> «Любой тип, у которого есть метод Area() float64, реализует этот интерфейс.»

# Реализация интерфейса

Если [[1.2. Типы данных|тип]] (например, [[1.8. Структуры и методы|структура]]) **умеет выполнять все методы**, указанные в интерфейсе — он **считается реализующим этот интерфейс.** Ничего специально “подключать” или “наследовать” не нужно: **[[1.0. Go Basics|Go]] сам понимает, что [[1.2. Типы данных|тип]] подходит под интерфейс.**

---
# <font color="#ff0000">Примеры</font>
#### Программа:
```go
type Shape interface {
    Area() float64
}
<center></center>
type Rectangle struct {
    Width, Height float64
}

// Метод, который считает площадь
func (r Rectangle) Area() float64 {
    return r.Width * r.Height
}
```
Теперь структура `Rectangle` **реализует интерфейс `Shape`**, потому что у неё есть метод `Area()`, как указано в интерфейсе.

#### Как это работает на практике:
```go
func printArea(s Shape) {
    fmt.Println("Площадь:", s.Area())
}

func main() {
    rect := Rectangle{Width: 4, Height: 5}
    printArea(rect)
}
```
**Вывод:**
```
Площадь: 20
```

**Пояснение:**
- Интерфейс `Shape` — это “договор”: у типа должен быть метод `Area()`
- У `Rectangle` этот метод есть → значит, он “умеет быть фигурой”.
- Мы можем передавать `Rectangle` в функцию, где ожидается `Shape`.

Функция `printArea` не знает, какой именно объект передан.
Она работает с интерфейсом, то есть **с поведением, а не с реализацией**.
#### Ещё пример:
```go
type Circle struct {
    Radius float64
}

func (c Circle) Area() float64 {
    return 3.14 * c.Radius * c.Radius
}
```

Теперь и `Circle`, и `Rectangle` реализуют один и тот же интерфейс `Shape`.

Они **разные внутри**, но **ведут себя одинаково снаружи** — оба умеют считать площадь.

---
> *В Go не нужно “объявлять”, что структура реализует интерфейс. Достаточно, чтобы в ней были нужные методы.*
> *Всё остальное Go делает сам.*
---

## Практический пример: <font color="#ff0000">mock-хранилище</font>

Представим интерфейс, описывающий работу с пользователями:
```go
type UserStore interface {
    Save(name string)
    GetAll() []string
}
```

**Это “договор”, который говорит:**
> *Любой тип, у которого есть методы Save() и GetAll(), считается **хранилищем пользователей**.*

<u>Теперь можно создать разные реализации этого интерфейса:</u>

### 1. Настоящее хранилище (например, база данных)

```go
type DBStore struct{}

func (d DBStore) Save(name string) {
    fmt.Println("Сохраняем в базу:", name)
}

func (d DBStore) GetAll() []string {
    return []string{"Аня", "Игорь"}
}
```
#### Разбор:
- `DBStore` — это структура, которая _символически_ представляет базу данных.
- Метод `Save()` просто выводит сообщение, будто сохраняет данные в базу.
- Метод `GetAll()` возвращает список пользователей, как будто мы читаем их из БД.
- Методы принимают **значение** (`DBStore`), а не указатель, потому что мы **ничего не меняем внутри структуры**.

### 2. Mock-хранилище для тестов

```go
type MockStore struct {
    data []string
}

func (m *MockStore) Save(name string) {
    m.data = append(m.data, name)
}

func (m *MockStore) GetAll() []string {
    return m.data
}
```

#### `MockStore` — это “поддельное” хранилище (mock).
- Оно не сохраняет данные в базу, а просто держит их **в памяти** (в слайсе `data`).
- Такие “моки” часто используют для **тестирования кода**: можно проверить, как программа работает, не подключаясь к реальной базе данных.
- Методы работают **через указатель (`MockStore`)**, потому что внутри мы **меняем данные** — добавляем новые имена в `data`.
- Если бы метод принимал не указатель, а копию (`MockStore`), изменения происходили бы только внутри копии, а настоящие данные не сохранялись бы.

#### Как использовать оба варианта:
```go
func RegisterUser(store UserStore, name string) {
    store.Save(name)
    fmt.Println("Пользователи:", store.GetAll())
}

func main() {
    db := DBStore{}
    mock := &MockStore{}

    RegisterUser(db, "Вася")
    RegisterUser(mock, "Петя")
}
```
**Вывод:**
```Run
Сохраняем в базу: Вася
Пользователи: [Аня Игорь]
Пользователи: [Петя]
```

#### Что здесь важно понять:

| **Интерфейс `UserStore`**  | задаёт _поведение_, а не реализацию                     |
| -------------------------- | ------------------------------------------------------- |
| **`DBStore`**              | имитирует работу с настоящей базой                      |
| **`MockStore`**            | хранит данные в памяти — удобно для тестов и отладки    |
| **Функция `RegisterUser`** | работает с любым типом, который умеет `Save` и `GetAll` |
**Главная идея:**
Интерфейс делает код **гибким и универсальным**.
Ты можешь использовать реальное хранилище, мок или что угодно другое — функция `RegisterUser` от этого **не изменится**.

## Пустой ~ <font color="#ff0000">interface{}</font> ~ и ~ <font color="#ff0000">any</font> ~

Пустой интерфейс — это интерфейс **без [[1.8. Структуры и методы|методов]]**:
```go
interface{}
```
Любой тип подходит под него, потому что он не требует ни одного метода.

С Go 1.18 появился синоним:
```go
type any = interface{}
```

#### Пустой интерфейс нужен в двух случаях:
1. Когда нужно принимать **значения любого [[1.2. Типы данных|типа]]**.
2. Когда [[1.8. Структуры и методы|структура]] или [[1.5. Функции и передача данных|функция]] должны быть **универсальными**.

**Пример:**
```go
func PrintAny(v any) {
    fmt.Printf("Тип: %T, Значение: %v\n", v, v)
}

PrintAny(42)
PrintAny("Привет")
PrintAny(true)
```
**Вывод:**
```Run
Тип: int, Значение: 42
Тип: string, Значение: Привет
Тип: bool, Значение: true
```

Здесь `fmt.Println()` может печатать всё подряд — он принимает `interface{}` (или `any`).

#### Пример: срез с элементами разных типов:
```go
values := []any{42, "Go", 3.14, true}

for _, v := range values {
    fmt.Printf("Тип: %T, Значение: %v\n", v, v)
}
```
**Вывод:**
```Run
Тип: int, Значение: 42
Тип: string, Значение: Go
Тип: float64, Значение: 3.14
Тип: bool, Значение: true
```

# Внутреннее устройство интерфейса

Интерфейс хранит **две части**:
1. **Type** — тип значения (например, `int`, `string`, `User`).
2. **Value** — само значение.

**Пример:**
```go
var i interface{} = 42
```
**В памяти это будет:**
```
i = (type: int, value: 42)
```

Интерфейс — это как коробка с биркой:
- на бирке написано, что внутри (`int`);
- а внутри лежит само значение (`42`).

### Пример 1. Интерфейс как “коробка с биркой”

```go
package main

import "fmt"

func main() {
    var box any // пустой интерфейс — может хранить что угодно

    box = 10
    fmt.Println("В коробке:", box)
    // type = int, value = 10

    box = "GoLang"
    fmt.Println("Теперь в коробке:", box)
    // type = string, value = "GoLang"

    box = 3.14
    fmt.Println("А теперь:", box)
    // type = float64, value = 3.14
}
```

---
#### *Что происходит:*
- *`box` — это **интерфейсная переменная** (пустой интерфейс `any`).*
- *Она может хранить **значение любого типа**.*
- *Каждый раз Go запоминает:*
    - *какой **тип** внутри (`int`, `string`, `float64`);*
    - *и само **значение**.*

---

**Вывод:**
```
В коробке: 10
Теперь в коробке: GoLang
А теперь: 3.14
```

### Пример 2. Почему `nil` не всегда `nil`

А теперь давай посмотрим, как эта “коробка” ведёт себя, когда внутри `nil`.

```go
package main

import "fmt"

type Animal interface{}
type Dog struct{}

func IsNil(i interface{}) bool {
    return i == nil
}

func main() {
    var a Animal   // интерфейс без значения
    var d *Dog     // указатель на Dog, но nil

    fmt.Println(IsNil(a)) // ?
    fmt.Println(IsNil(d)) // ?
}
```
**Вывод:**
```
true
false
```

---
#### Почему так?

|Переменная|Type|Value|Результат|
|---|---|---|---|
|`a` (`Animal`)|`nil`|`nil`|✅ `true`|
|`d` (`*Dog`)|`*Dog`|`nil`|❌ `false`|

---
> *Интерфейс в Go — это коробка, где хранится не только значение, но и **информация о том, что это за тип**.*
---
# Type Assertion — получение значения из интерфейса

Когда мы кладём что-то в интерфейс (`interface{}`), Go **забывает конкретный тип**, чтобы можно было хранить _что угодно_.

Это удобно для универсального кода, но иногда нам нужно **вернуть исходный тип** — например, взять строку из `interface{}` и использовать как `string`.

Для этого и существует **type assertion** — механизм, который позволяет сказать:
> “Я знаю, что внутри лежит значение типа X — достань его”.

---
#### Без type assertion:
```go
var data any = "GoLang"
fmt.Println(data + " — язык программирования") // ❌ ошибка
```
Go не знает, что внутри `data` — строка.
Он видит только интерфейс и говорит:
> “Я не умею складывать interface с string”.

---

### ✅ С type assertion
Чтобы вернуть значение как строку, используем утверждение типа (`type assertion`):

```go
value := data.(string)
fmt.Println(value + " — язык программирования")
```
Теперь Go понимает, что `value` — это `string`.

---

### Общий синтаксис

```go
value, ok := iface.(TargetType)
```

- `iface` — интерфейсная переменная;
- `TargetType` — тип, который ожидаем внутри;
- `ok` — флаг: `true`, если тип совпал, иначе `false`.

---

### Пример с проверкой

```go
var x any = "GoLang"

str, ok := x.(string)
if ok {
    fmt.Println("Это строка:", str)
} else {
    fmt.Println("Это не строка!")
}
```

**Вывод:**

```
Это строка: GoLang
```

---

### Ошибка без проверки

Если не проверить `ok`, а тип не совпадёт — будет **паника**:

```go
var x any = 10
str := x.(string) // panic: interface conversion: int is not string
```

Поэтому, если ты не уверен в типе — **всегда используй `, ok`-вариант**.

> Type assertion нужен, чтобы “достать” значение из интерфейса и вернуть его исходный тип.
> 
> Без него Go не понимает, как с ним работать, ведь внутри `interface{}` тип скрыт.

---

## Type Switch — выбор действий по типу

Если нужно обработать несколько разных типов, удобно использовать **type switch**:

```go
func Describe(v any) {
    switch val := v.(type) {
    case int:
        fmt.Println("Целое число:", val)
    case string:
        fmt.Println("Строка длиной", len(val))
    case bool:
        fmt.Println("Булево значение:", val)
    default:
        fmt.Println("Неизвестный тип")
    }
}

Describe(42)
Describe("GoLang")
Describe(true)
```

**Вывод:**

```
Целое число: 42
Строка длиной 6
Булево значение: true
```

Внутри каждого `case` переменная `val` уже имеет **конкретный тип**.

## Интерфейсы внутри структур

Интерфейсы можно использовать как поля структур, чтобы определять **поведение**.

Пример:

```go
type Logger interface {
    Log(message string)
}

type ConsoleLogger struct{}

func (c ConsoleLogger) Log(message string) {
    fmt.Println("[LOG]:", message)
}

type Server struct {
    Name   string
    Logger Logger
}

func (s Server) Start() {
    s.Logger.Log("Сервер " + s.Name + " запущен")
}

srv := Server{
    Name:   "MainServer",
    Logger: ConsoleLogger{},
}

srv.Start()
```

**Вывод:**

```
[LOG]: Сервер MainServer запущен
```

💡 Интерфейсы часто применяются именно так —

для добавления **гибкого поведения** без жёсткой привязки к конкретным типам.

---

## Интерфейсы и композиция

Интерфейсы можно **объединять**, чтобы описывать составное поведение.

Пример:

```go
type Reader interface {
    Read() string
}

type Writer interface {
    Write(data string)
}

type ReadWriter interface {
    Reader
    Writer
}
```

Теперь любой тип, у которого есть методы `Read()` и `Write()`,

автоматически реализует `ReadWriter`.

---

## Интерфейсы внутри структур

Интерфейс можно использовать как **поле структуры**, чтобы задать **поведение**, которое структура может выполнять. Это полезно, если структура должна “что-то делать”,

но мы пока не знаем, _как именно_ — интерфейс просто описывает, _что нужно уметь_.

---

### Пример

```go
package main

import "fmt"

// Интерфейс описывает, что кто-то умеет говорить
type Speaker interface {
    Speak()
}

// Тип Person умеет говорить по-своему
type Person struct {
    Name string
}

func (p Person) Speak() {
    fmt.Println("Привет, я", p.Name)
}

// Тип Robot тоже умеет говорить, но по-другому
type Robot struct{}

func (r Robot) Speak() {
    fmt.Println("Бип-буп. Я робот.")
}

// Структура Chatroom может "общаться" с тем, кто умеет говорить
type Chatroom struct {
    Member Speaker
}

func (c Chatroom) Start() {
    c.Member.Speak()
}

func main() {
    // В чат добавляем человека
    chat1 := Chatroom{Member: Person{Name: "Аня"}}
    chat1.Start()

    // А теперь робота
    chat2 := Chatroom{Member: Robot{}}
    chat2.Start()
}
```

**Вывод:**

```
Привет, я Аня
Бип-буп. Я робот.
```

---

### Пояснение

- `Speaker` — это **интерфейс**, он говорит:
    
    > “Кто угодно, у кого есть метод Speak(), может быть спикером.”
    
- `Person` и `Robot` — разные типы, но оба **реализуют** этот интерфейс.
    
- `Chatroom` — структура, у которой есть поле `Member` типа `Speaker`.
    
    Ей всё равно, _кто именно внутри_ — человек или робот.
    
    Главное, что этот кто-то умеет `Speak()`.
    

Это и есть **гибкость интерфейсов** — одна структура (`Chatroom`) может работать с разными типами, не зная их устройство.

---

**Простыми словами:**

> Интерфейс в структуре — это “контакт”, куда можно подключить любой тип,
> 
> если он подходит по “форме” (то есть имеет нужный метод).

---

## Интерфейсы и композиция

Интерфейсы можно **объединять**, чтобы описывать сложное поведение

из нескольких простых частей.

Например, если кто-то умеет **читать** и **писать**,

мы можем объединить эти два умения в один интерфейс.

---

### Пример

```go
package main

import "fmt"

// Один интерфейс — чтение
type Reader interface {
    Read()
}

// Второй — запись
type Writer interface {
    Write()
}

// Новый интерфейс объединяет оба
type ReadWriter interface {
    Reader
    Writer
}

// Тип Notebook умеет и читать, и писать
type Notebook struct{}

func (n Notebook) Read() {
    fmt.Println("Читаю запись...")
}
func (n Notebook) Write() {
    fmt.Println("Делаю новую запись...")
}

func main() {
    var rw ReadWriter = Notebook{}
    rw.Read()
    rw.Write()
}
```

**Вывод:**

```
Читаю запись...
Делаю новую запись...
```

---

### Что здесь происходит

- `Reader` — кто умеет читать.
- `Writer` — кто умеет писать.
- `ReadWriter` — **комбинация** двух интерфейсов.
- `Notebook` реализует оба метода, значит, подходит под `ReadWriter`.

---

**Простыми словами:**

> Интерфейсы можно складывать, как кубики.
> 
> Из простых действий (`Read`, `Write`)
> 
> можно собрать более “умного” исполнителя (`ReadWriter`).
