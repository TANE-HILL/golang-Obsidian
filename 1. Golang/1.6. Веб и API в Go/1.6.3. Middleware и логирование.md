
# Почему нужна прослойка ~ <font color="#ff0000">middleware</font> ~

В нашем проекте [[1.6.2. REST API#<u>Как будет устроен проект</u>|Task Manager]] каждый обработчик сейчас выглядит примерно так:
```go
func getTasks(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodGet {
        http.Error(w, "Метод не поддерживается", http.StatusMethodNotAllowed)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(tasks)
}

func createTask(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodPost {
        http.Error(w, "Метод не поддерживается", http.StatusMethodNotAllowed)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode("Новая задача создана")
}
```

Если приглядеться, видно, что часть кода **повторяется**:
- проверка метода (`if r.Method != ...`);
- установка заголовков (`w.Header().Set(...)`);
- единый формат ошибок (`http.Error(...)`).

Проблема в том, что **эти куски копируются во все обработчики**.

Если потом нужно что-то изменить (например, добавить логирование или проверку токена), придётся править десятки функций.

# ~ <font color="#ff0000">middleware</font> ~ простыми словами

Middleware решает эту проблему.
Это как **охранник у входа в офис**:
> Каждый запрос сначала проходит через охранника, который может записать, кто пришёл, проверить пропуск и только потом впустить к менеджеру задач.

То есть middleware — **это "прослойка" между пользователем и обработчиком.**

#### Пример без кода:
- Ты заходишь в офис → охранник записывает: "Пришёл человек в 09:02".
- Он проверяет пропуск → всё ок.
- Ты идёшь к менеджеру (handler), чтобы обсудить задачу.
- После встречи охранник записывает: "Ушёл в 09:10".
#### Пример в коде:
```go
func LoggingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        fmt.Printf("➡️ %s %s — запрос получен\n", r.Method, r.URL.Path)

        next.ServeHTTP(w, r) // передаём запрос дальше в обработчик

        fmt.Println("✅ Ответ отправлен клиенту")
    })
}
```
Этот код:
1. **Логирует запрос** — выводит метод и путь (например, `GET /tasks`).
2. **Вызывает следующий обработчик** (`next.ServeHTTP`).
3. После его выполнения пишет в лог, что ответ отправлен.
#### Что такое "изменить контекст"?
Иногда middleware может не просто что-то напечатать, а добавить **дополнительные данные** в контекст запроса — например, `request_id`, имя пользователя или время старта.

Тогда эти данные можно достать внутри обработчика, чтобы, например, включить их в ответ или лог.

Но до этого мы дойдём позже — в уроке про **Context**.

Сейчас главное понять, что middleware может:
- что-то **сделать до обработчика** (лог, проверка, заголовок);
- что-то **сделать после него** (записать результат, время, ошибки).

Сейчас мы расширим наш проект **Task Manager**, добавив в него:
1. **Middleware для логирования** всех запросов.
    → Будем записывать метод, путь и время выполнения каждого запроса.
2. **Middleware для защиты от паник** (`RecoveryMiddleware`).
    → Даже если где-то случится ошибка, сервер не упадёт, а вернёт `500`.
3. (Дополнительно) Middleware, который добавляет **ID запроса**
    → Это поможет отслеживать запросы в логах.

# Middleware для логирования

#### Что он должен делать:
- Запоминать, **когда пришёл запрос**;
- Выводить **метод**, **путь** и **время обработки**;
- Передавать запрос дальше в обработчик.

#### Код `logging.go`:
```go
package middleware

import (
    "log"
    "net/http"
    "time"
)

// LoggingMiddleware — логирует все запросы
func LoggingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        // Передаём запрос дальше по цепочке
        next.ServeHTTP(w, r)
        // После завершения обработки логируем результат
        log.Printf("%s %s — %v", r.Method, r.URL.Path, time.Since(start))
    })
}
```
#### Пояснения построчно:
1. Заголовок файла и импорты
- `package middleware` — объявляем пакет.
    Файл лежит в папке `middleware`, поэтому пакет так и называется.
    Из других файлов мы будем вызывать `middleware.LoggingMiddleware(...)`.
- Импортируем:
    - `log` — чтобы писать сообщения в консоль;
    - `net/http` — чтобы работать с обработчиками HTTP;
    - `time` — чтобы замерить длительность обработки запроса.
2. Сигнатура функции:
	`func LoggingMiddleware(next http.Handler) http.Handler`
- Это **фабрика-обёртка**: она **принимает** "следующий обработчик" (`next`)
    и **возвращает новый обработчик**, уже обёрнутый логированием.
- Почему так? Чтобы можно было обернуть **любой** обработчик (или целый роутер) одним и тем же логером.
- Ключевая идея: **middleware ничего не знает** о конкретной логике хендлера. Он просто: "перед" → "после".
3. Возврат `http.HandlerFunc(...)`:
```go
return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    ...
})
```
- `http.HandlerFunc` — адаптер, который превращает обычную функцию `func(w,r)` в объект `http.Handler`. Это стандартный приём в Go.
- Внутри — наша анонимная функция, в которой мы делаем всю работу: лог до/после и вызов `next`.
4. Засекаем время начала:
	`start := time.Now()`
- Сохраняем "момент старта", чтобы потом посчитать, **сколько заняла обработка**.
5. Передаём запрос дальше:
	`next.ServeHTTP(w, r)`
- Это **самый важный вызов**: он запускает настоящий обработчик (например, `getTasks`) или даже целый маршрутизатор (`mux`).
- Всё, что делает твой хендлер (чтение тела, работа с БД, формирование JSON, запись ответа) — выполняется **между** нашим `start := [time.Now](<http://time.Now>)()` и логом ниже.
4. Логируем результат после обработки:
	`log.Printf("%s %s — %v", r.Method, r.URL.Path, time.Since(start))`
- `r.Method` — метод запроса (`GET`, `POST`, ...).
- `r.URL.Path` — путь (`/tasks`, `/tasks/2`, ...).
- `time.Since(start)` — сколько заняла обработка (например, `3.42ms`).
- В итоге в терминале будут строчки вроде:
```
GET /tasks — 2.01ms
POST /tasks — 1.17ms
DELETE /tasks/2 — 4.83ms
```

# **Порядок выполнения** - <u>очень важно</u>

Для одного запроса, например `GET /tasks`, шаги такие:
1. Middleware: засекаем время → `start := time.Now()`
2. **Вызываем твой хендлер** → `next.ServeHTTP(w, r)`
3. Когда хендлер ДОПИШЕТ ответ — возвращаемся в middleware
4. Middleware: считаем длительность → `time.Since(start)`
5. Печатаем лог → `log.Printf(...)`
6. Готово — ответ уже отправлен клиенту.

То есть **лог "после" печатается только когда хендлер полностью отработал**.

#### Как подключить логирование к нашему проекту:

Middleware — это отдельный кусок логики, но чтобы он реально работал, его нужно **подключить** к нашему серверу.
Делается это через **обёртку** вокруг маршрутов или всего сервера.
Сейчас посмотрим два способа и разберём, как именно они отличаются.

# Вариант 1
#### Логирование на весь сервер (через ~ <font color="#ff0000">ServeMux</font> ~)

**Раньше** наш сервер выглядел так:
```go
package main

import (
    "fmt"
    "net/http"
)

func main() {
    http.HandleFunc("/tasks", getTasks)
    http.HandleFunc("/tasks/", getTaskByID)

    fmt.Println("Сервер запущен на <http://localhost:8080>")
    http.ListenAndServe(":8080", nil)
}
```
Go здесь **автоматически создаёт маршрутизатор внутри**, потому что мы передаём `nil` в `ListenAndServe`.

**Теперь** добавим **явный ~ <font color="#ff0000">mux</font> ~ (маршрутизатор)** и **обернём его** в логирование:
```go
package main

import (
    "fmt"
    "net/http"
    "your_project/middleware" // импортируем наш пакет с логированием
)

func main() {
    mux := http.NewServeMux() // создаём маршрутизатор

    mux.HandleFunc("/tasks", getTasks)
    mux.HandleFunc("/tasks/", getTaskByID)

    // Оборачиваем маршрутизатор в middleware
    loggedMux := middleware.LoggingMiddleware(mux)

    fmt.Println("Сервер запущен на <http://localhost:8080>")
    http.ListenAndServe(":8080", loggedMux)
}

```

---

### Что изменилось и зачем

|Было|Стало|
|---|---|
|`http.HandleFunc(...)` регистрирует пути "глобально"|`mux.HandleFunc(...)` регистрирует пути в нашем маршрутизаторе|
|В `ListenAndServe` передавали `nil`, и Go сам создавал внутренний `mux`|Теперь мы передаём **свой `mux`**, чтобы иметь над ним полный контроль|
|Не было логов|Каждый запрос теперь логируется: метод, путь и время выполнения|

---

### Как теперь работает сервер

1. Когда приходит запрос (например, `GET /tasks`), он попадает в `loggedMux`.
    
2. `loggedMux` запускает наш **LoggingMiddleware**.
    
3. Middleware выводит:
    
    ```
    ➡️ GET /tasks — запрос получен
    ```
    
4. Потом он вызывает настоящий обработчик (`getTasks`).
    
5. Когда обработчик закончит, middleware снова пишет:
    
    ```
    ✅ GET /tasks — 3.27ms
    ```
    
6. Клиент получает ответ, а ты — аккуратный лог в консоли.
    

---

### Почему нужен `mux`

В ранней версии, где был `nil`, маршрутизатор создавался автоматически внутри Go.

Ты не мог его "обернуть" или изменить.

Теперь у нас `mux := http.NewServeMux()` —

и это **тот же самый маршрутизатор**, только мы его **создали явно**.

Теперь можно:

- добавлять middleware;
- делать цепочки middleware;
- комбинировать разные обработчики (например, `/api`, `/admin`);
- и вообще управлять потоком запросов вручную.

## Вариант 2 — логирование только для одного пути

Иногда логирование нужно не везде.

Например, ты хочешь писать логи только для `/tasks`,

но не трогать `/health` или `/metrics`.

Для этого можно **оборачивать отдельные обработчики**:

```go
package main

import (
    "fmt"
    "net/http"
    "your_project/middleware"
)

func main() {
    // Оборачиваем только один путь
    http.Handle("/tasks", middleware.LoggingMiddleware(http.HandlerFunc(getTasks)))

    // Остальные пути — обычные
    http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "OK")
    })

    fmt.Println("Сервер запущен на <http://localhost:8080>")
    http.ListenAndServe(":8080", nil)
}

```

---

### Что происходит здесь

|Этап|Описание|
|---|---|
|`http.Handle(...)`|Регистрирует путь `/tasks` с middleware|
|`LoggingMiddleware(http.HandlerFunc(getTasks))`|Оборачивает `getTasks` в логирование|
|`/health` остаётся обычным|Не логируется, чтобы не засорять консоль|

---

### Разница между подходами

|Подход|Применение|Преимущества|Недостатки|
|---|---|---|---|
|**Весь `mux`**|Логируются все маршруты|Просто и удобно|Логи на все запросы, даже ненужные|
|**Один путь**|Логирование выборочно|Гибко, можно включать по нужде|Придётся писать больше кода вручную|

---

### Что выбрать в учебном проекте

В нашем **Task Manager** лучше использовать **вариант с `mux`** —

так мы сразу заложим правильную архитектуру и сможем добавлять новые middleware позже:

например, `RecoveryMiddleware`, `AuthMiddleware`, `RequestIDMiddleware` и т.д.

## Частые вопросы

**Почему лог "после", а не "до"?**

Мы хотим знать ВРЕМЯ ОБРАБОТКИ. Его можно посчитать только после того, как хендлер завершился.

**А если хендлер упадёт (panic)?**

Тогда лог "после" может не выполниться.

Для этого есть второй middleware — `RecoveryMiddleware`, который ловит паники и возвращает `500`.

Мы добавим его следующим шагом и поставим **перед** логированием.

**Можно ли добавить в лог ещё статус-код?**

Да, но для этого нужно "обёртку над `ResponseWriter`", чтобы перехватить код ответа.

Это уже следующий уровень — сделаем после `RecoveryMiddleware`.

---

## RecoveryMiddleware

Тогда двигаемся логично дальше — после логирования обычно идёт **второй базовый middleware** —

это **RecoveryMiddleware**, который защищает твой сервер от падений (паник).

Когда в Go-программе где-то случается **panic**, сервер по умолчанию просто падает с ошибкой,

и все активные запросы обрываются.

В продакшене это недопустимо — вместо падения нужно вернуть **500 Internal Server Error**

и записать ошибку в лог.

Давай разберём этот middleware пошагово и понятно

---

## Зачем нужен `RecoveryMiddleware`

Представь, что один из обработчиков случайно вызывает ошибку:

```go
func getTasks(w http.ResponseWriter, r *http.Request) {
    panic("что-то пошло не так") // ошибка в коде
}
```

Если запустить сервер и перейти на `/tasks`, ты увидишь:

```
panic: что-то пошло не так
```

и сервер **упадёт полностью**. Все остальные маршруты перестанут работать.

Чтобы такого не происходило, мы добавляем "страховку" — middleware,

который ловит паники и превращает их в безопасный ответ с кодом `500`.

---

## Создаём RecoveryMiddleware

Создай новый файл:

`middleware/recovery.go`

```go
package middleware

import (
    "log"
    "net/http"
)

// RecoveryMiddleware — перехватывает паники и не даёт серверу упасть
func RecoveryMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // Перехватываем панику, если она произойдёт
        defer func() {
            if err := recover(); err != nil {
                log.Printf("❌ Паника: %v", err)
                http.Error(w, "Внутренняя ошибка сервера", http.StatusInternalServerError)
            }
        }()

        // Передаём запрос дальше
        next.ServeHTTP(w, r)
    })
}

```

---

## Пошаговый разбор

- `defer func() { ... }()` — откладывает выполнение функции до выхода из текущего блока.
    
    Даже если случится panic — эта функция выполнится.
    
- `recover()` — встроенная функция Go, которая **ловит панику**, если она произошла.
    
    Если паники нет, она возвращает `nil`.
    
- `log.Printf("❌ Паника: %v", err)` — записывает ошибку в консоль, чтобы ты знал, где проблема.
    
- `http.Error(w, "Внутренняя ошибка сервера", http.StatusInternalServerError)` —
    
    отправляет пользователю аккуратный ответ с кодом `500`,
    
    вместо того чтобы останавливать программу.
    

### 1) Сигнатура функции

```go
func RecoveryMiddleware(next http.Handler) http.Handler
```

- **Вход:** `next http.Handler` — _следующий этап обработки_, обычно это твой маршрутизатор (`mux`) или конкретный обработчик.
- **Выход:** `http.Handler` — _новый обработчик_, который уже **обёрнут** нашей защитой от паник.

Идея простая: этот middleware принимает "что-то, что умеет обрабатывать HTTP" и возвращает "то же самое", но **с надёжной прослойкой**.

---

### 2) Что значит `return http.HandlerFunc(func(...){ ... })`

```go
return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { ... })
```

Отдаём наружу "обработчик", внутри которого — наша логика защиты.

---

### 3) Блок `defer ... recover()`

```go
defer func() {
    if err := recover(); err != nil {
        log.Printf("❌ Паника: %v", err)
        http.Error(w, "Внутренняя ошибка сервера", http.StatusInternalServerError)
    }
}()
```

- `defer` — "выполнить позже, при выходе из функции".
    
    Сработает **всегда**, даже если внутри произошла паника.
    
- `recover()` — специальная функция Go, которая **ловит панику**, если она была.
    
    Если паники нет — вернёт `nil`.
    
- Если паника была:
    
    - пишем в лог причину;
    - отправляем клиенту **500 Internal Server Error**, чтобы сервер **не упал**, а ответил корректно.

Важно: `recover()` ловит **только** в том месте стека, где он вызван.

Поэтому он должен быть **в этой же функции**, оборачивающей `next.ServeHTTP`.

---

### 4) Зачем `next.ServeHTTP(w, r)`

```go
next.ServeHTTP(w, r)
```

- `next` — это тот "следующий" обработчик, который ты передал в middleware.
    
    Это может быть:
    
    - твой `mux` с кучей маршрутов;
    - или конкретный хендлер.
- `ServeHTTP(w, r)` — это **запуск** следующего этапа обработки запроса.
    
    По сути: "передать эстафету дальше".
    
- Вся реальная логика (чтение JSON, доступ к данным, формирование ответа) происходит **внутри** этого вызова.
    
- Если где-то **внутри** этой логики случится паника, наш `defer ... recover()` её поймает, и сервер **не упадёт**.
    

---

## Порядок выполнения (таймлайн для одного запроса)

Предположим, запрос приходит на `GET /tasks`, а в `getTasks` случайно есть `panic`.

1. Заходит в **нашу обёртку** (`RecoveryMiddleware(...).ServeHTTP`).
    
2. Ставится "ловушка" на панику: `defer func(){ if recover() ... }()`.
    
3. Вызывается **следующий обработчик**: `next.ServeHTTP(w, r)`.
    
4. Внутри `getTasks` происходит `panic("что-то пошло не так")`.
    
5. Управление возвращается в наш `defer` — `recover()` ловит панику.
    
6. Мы пишем лог и возвращаем пользователю **500**:
    
    ```
    Внутренняя ошибка сервера
    ```
    
7. Сервер **продолжает работать**, другие маршруты живы.
    

---

## Подключаем RecoveryMiddleware

Теперь подключим оба middleware — `Recovery` и `Logging` — **вместе и в правильном порядке**.

---

## Как это сделать

В файле `main.go`:

```go
package main

import (
    "fmt"
    "net/http"
    "your_project/middleware"
)

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("/tasks", getTasks)
    mux.HandleFunc("/tasks/", getTaskByID)

    // Шаг за шагом создаём цепочку middleware
    handler := mux
    handler = middleware.LoggingMiddleware(handler)
    handler = middleware.RecoveryMiddleware(handler)

    fmt.Println("Сервер запущен на <http://localhost:8080>")
    http.ListenAndServe(":8080", handler)
}

```

Здесь мы **последовательно оборачиваем маршрутизатор** в прослойки:

1. `LoggingMiddleware` — первым добавляется логирование всех запросов.
2. `RecoveryMiddleware` — вторым добавляется защита от паник.
3. В конце у нас получается общий обработчик `handler`, который запускается в `ListenAndServe`.

> Это и есть "цепочка middleware" — каждый слой вызывает следующий, добавляя свою функцию.

---

## Почему порядок важен

Middleware выполняются **снаружи внутрь**, как слои луковицы

```
Запрос → Recovery → Logging → Handlers
```

1. **RecoveryMiddleware** стоит снаружи — он ловит любые паники, происходящие в коде внутри.
2. **LoggingMiddleware** идёт после — чтобы всё равно записать лог даже при ошибке.
3. В самом центре — твои обработчики (`getTasks`, `createTask`, и т.д.).

Если перепутать порядок (например, поставить Recovery _внутрь_ Logging),

паника может случиться раньше, чем лог успеет выполниться — и лог просто не запишется.

## Как логи используют на практике

В реальных проектах логирование — это не просто печать в консоль.

Это целая система наблюдения за сервером.

### 1. Расширенные поля логов

В лог часто добавляют:

- **статус-код ответа** (например, `200`, `404`, `500`);
- **время запроса** (latency);
- **IP клиента**;
- **идентификатор запроса** (request ID);
- **имя пользователя** (если авторизован);
- **ошибку**, если была.

Пример структурированного лога:

```json
{
  "time": "2025-10-19T19:32:14Z",
  "method": "GET",
  "path": "/tasks",
  "status": 200,
  "duration_ms": 2.14,
  "ip": "127.0.0.1"
}
```

---

### 2. Библиотеки и системы логирования

В реальных компаниях почти никто не использует `log.Printf` напрямую.

Вместо этого применяют библиотеки, которые:

- поддерживают **уровни логов** (`INFO`, `WARN`, `ERROR`);
- умеют писать логи **в файлы, Elastic, Loki, Grafana** и другие системы;
- форматируют вывод в **JSON**;
- автоматически добавляют контекст (request ID, user ID и т.п.).

Наиболее популярные библиотеки в Go:

- **`zap`** — быстрая и популярная от Uber;
- **`zerolog`** — компактная и производительная;
- **`logrus`** — удобная для читаемого вывода, часто используется в старых проектах.

---

### 3. Пример "промышленного" подхода

```go
[logger.Info](<http://logger.Info>)().
    Str("method", r.Method).
    Str("path", r.URL.Path).
    Int("status", status).
    Dur("latency", time.Since(start)).
    Msg("handled request")

```

Вывод:

```
{"level":"info","method":"GET","path":"/tasks","status":200,"latency":"3.2ms","msg":"handled request"}

```

Такой формат легко читают системы мониторинга (Grafana, Loki, Kibana),

и можно отслеживать статистику по ошибкам, скорости и пользователям.

## Что ты должен понять после этого урока

Middleware — это "прослойка" между клиентом и твоим кодом.

Она может:

- логировать запросы;
- проверять токены;
- добавлять данные в контекст;
- ловить паники и защищать сервер.

Middleware образуют **цепочку**, где каждый слой вызывает следующий через `next.ServeHTTP(w, r)`.

Правильный порядок — важен: Recovery всегда снаружи, Logging — ближе к обработчикам.

Логи — это не просто текст в терминале, а **инструмент наблюдения**:

они помогают анализировать ошибки, производительность и нагрузку на сервер.

В будущем вместо `log.Printf` ты будешь использовать профессиональные логеры (`zap`, `zerolog`)

и отправлять данные в систему мониторинга.
