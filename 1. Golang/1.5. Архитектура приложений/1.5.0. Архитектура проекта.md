# Зачем нужна <font color="#ff0000">архитектура</font>

Когда проект маленький — можно писать всё в одном файле:
```go
package main
import "fmt"
func main() {
    var users []string
    users = append(users, "Аня")
    fmt.Println(users)
}
```
Но если нужно:
- добавить сохранение в файл,
- потом базу данных,
- потом проверки и фильтры...
**всё быстро превращается в хаос.**

**Любое изменение ломает код.** Чтобы этого не происходило, программисты делят код на **слои**, каждый из которых отвечает **только за своё**.

---
## Слои приложения ~ <font color="#ff0000">Handler</font>, <font color="#ff0000">Service</font>, <font color="#ff0000">Repository</font> ~

<u>Архитектура</u> — это просто способ **разделить обязанности**.
Теперь разберём каждый слой отдельно.
```
Запрос → Handler → Service → Repository → База данных
                      ↑
                  Ответ клиенту
```

# 1. ~ <font color="#ff0000">Handler</font> ~ (или Delivery)

Это “*входная дверь*” в приложение.
Он принимает запросы — от **пользователя, HTTP, CLI, Telegram-бота** — не важно.

#### <font color="#ff0000">Handler</font>:
- получает входные данные;
- вызывает нужный метод бизнес-логики (Service);
- формирует ответ.

#### Пример:
```go
package handler
import (
    "fmt"
    "myapp/internal/service"
)
type UserHandler struct {
    service *service.UserService
}
func NewUserHandler(s *service.UserService) *UserHandler {
    return &UserHandler{service: s}
}
func (h *UserHandler) CreateUser(name string) {
    err := h.service.Register(name)
    if err != nil {
        fmt.Println("Ошибка:", err)
        return
    }
    fmt.Println("Пользователь успешно создан")
}
```
💬 Здесь `UserHandler` <u>ничего не знает о БД</u> — он просто передаёт имя в сервис и сообщает результат.

# 2. ~ <font color="#ff0000">Service</font> ~

Это **сердце приложения**, его "мозг".
Здесь живёт бизнес-логика: правила, проверки, валидация и сценарии.

<u>Сервис не знает, как данные хранятся</u> — он знает только, _что можно сохранить или получить пользователя_.
#### Пример:
```go
package service
import (
    "errors"
    "myapp/internal/repository"
)
type UserService struct {
    repo repository.UserRepository
}
func NewUserService(r repository.UserRepository) *UserService {
    return &UserService{repo: r}
}
func (s *UserService) Register(name string) error {
    if name == "" {
        return errors.New("имя не может быть пустым")
    }
    return s.repo.Save(name)
}
```
Здесь `UserService` использует [[1.2.1. Интерфейсы в Go|интерфейс]] `UserRepository`, а не конкретную реализацию. <u>Это значит, что он не знает</u> — <u>в памяти, в файле или в базе</u>. Главное, чтобы там был метод `Save()`.
# 3. ~ <font color="#ff0000">Repository</font> ~ (или Storage)

Repository отвечает за **хранение данных**.
Он знает, _как_ сохранить пользователя — в файл, в память, в базу и т.д.

#### Пример:
```go
package repository
import "fmt"
type UserRepository interface {
    Save(name string) error
}
type MemoryRepo struct {
    data []string
}
func NewMemoryRepo() *MemoryRepo {
    return &MemoryRepo{data: []string{}}
}
func (r *MemoryRepo) Save(name string) error {
    r.data = append(r.data, name)
    fmt.Println("Сохранили в память:", name)
    return nil
}
```
Это простейшее хранилище в памяти. Позже можно сделать `FileRepo` или `PostgresRepo`, не меняя код выше.

# <u>Как слои взаимодействуют</u>

Когда у нас есть все три части, можно собрать приложение в `main.go`.
#### main.go:
```go
package main
import (
    "myapp/internal/handler"
    "myapp/internal/service"
    "myapp/internal/repository"
)
func main() {
    repo := repository.NewMemoryRepo()      // нижний слой
    service := service.NewUserService(repo) // зависимость передаётся вверх
    h := handler.NewUserHandler(service)    // и ещё выше

    h.CreateUser("Аня")
}
```
#### Что происходит:
1. **Создаём <u>хранилище</u> ( ~ <font color="#ff0000">repository</font> ~ )** — где будут сохраняться данные.
2. **Создаём <u>сервис</u> ( ~ <font color="#ff0000">service</font> ~ )** и передаём в него репозиторий.
3. **Создаём <u>обработчик</u> ( ~ <font color="#ff0000">handler</font> ~ )**, передаём в него сервис.
4. **Запускаем** <u>обработчик</u>, который вызывает логику и сохраняет пользователя.

**Поток данных:**
```
Handler → Service → Repository → Память
```

# Как устроены зависимости

Теперь разберём, что такое зависимости и почему мы их “внедряем”.
<u>Зависимость</u> — это то, без чего объект не может работать.

```go
type UserService struct {
    repo UserRepository
}
```
Здесь `UserService` **зависит** от `UserRepository`.
Без него сервис не может сохранить данные.

#### Как передаются зависимости?
В [[1.1.0. Go Basics|Go]] зависимости передаются **вручную через конструкторы**.

#### Что такое конструктор в [[1.1.0. Go Basics|Go]]
<u>Конструктор</u> — это просто [[1.1.5. Функции и передача данных|функция]], которая создаёт объект ([[1.2.0. Структуры и методы|структуру]]) и возвращает его в готовом виде.
Она обычно начинается с `New...` и возвращает **указатель** на структуру (`*Type`).
#### Пример самого простого конструктор:
```go
type User struct {
    Name string
}

// Конструктор
func NewUser(name string) *User {
    return &User{Name: name}
}
```
- `User` — структура, описывающая пользователя.
- `NewUser` — создаёт нового пользователя, заполняет поля и возвращает ссылку на него (`User`).

#### Почему возвращается ссылка User?
Потому что мы хотим работать с **одним и тем же объектом**, а не с его копией.

```go
u1 := NewUser("Аня")
u2 := u1
u2.Name = "Игорь"
fmt.Println(u1.Name) // "Игорь" — потому что это один и тот же объект
```
Если бы мы вернули не `*User`, а `User`, то `u1` и `u2` стали бы разными копиями.

#### Что значит “передать зависимость в конструктор”?

Теперь пример посерьёзнее — с зависимостью.
У нас есть 3 слоя: обработчик, сервис и репозиторий:
#### 1. <font color="#ff0000">Repository</font> (нижний слой):
```go
package repository
import "fmt"
type UserRepository interface {
    Save(name string)error
}
type MemoryRepo struct {
    data []string
}
// Конструктор: создаёт хранилище в памяти
func NewMemoryRepo() *MemoryRepo {
    return &MemoryRepo{data: []string{}}
}
func (r *MemoryRepo) Save(name string) error {
    r.data = append(r.data, name)
    fmt.Println("Сохранили в память:", name)
    return nil
}
```
Этот слой умеет только **сохранять** данные.
Пока он хранит их в памяти, но позже можно заменить на `FileRepo` или `DBRepo`.
#### 2. <font color="#ff0000">Service</font> (средний слой):
```go
package service
import (
    "errors"
    "myapp/internal/repository"
)
type UserService struct {
    repo repository.UserRepository
}
// Конструктор принимает репозиторий и “встраивает” его внутрь сервиса
func NewUserService(r repository.UserRepository) *UserService {
    return &UserService{repo: r}
}
func (s *UserService) Register(name string) error {
    if name == "" {
        return errors.New("имя не может быть пустым")
    }
    return s.repo.Save(name)
}
```
Здесь сервис **не создаёт репозиторий сам** — ему его **передают извне через конструктор**. Так `UserService` не зависит от конкретного способа хранения данных.
#### 3. <font color="#ff0000">Handler</font> (верхний слой):
```go
package handler
import (
    "fmt"
    "myapp/internal/service"
}
type UserHandler struct {
    service *service.UserService
}
// Конструктор принимает сервис и сохраняет его внутри
func NewUserHandler(s *service.UserService) *UserHandler {
    return &UserHandler{service: s}
}
func (h *UserHandler) CreateUser(name string) {
    err := h.service.Register(name)
    if err != nil {
        fmt.Println("Ошибка:", err)
        return
    }
    fmt.Println("Пользователь успешно создан")
}
```
`UserHandler` не знает ни про базы, ни про память — он просто вызывает метод `Register` у сервиса. Всё, что ему нужно, передаётся в конструкторе `NewUserHandler`.
#### Как это соединяется в <font color="#ff0000">main.go</font>:
```go
package main
import (
    "myapp/internal/handler"
    "myapp/internal/service"
    "myapp/internal/repository"
)
func main() {
    // 1️⃣ Создаём репозиторий (нижний слой)
    repo := repository.NewMemoryRepo()
    // 2️⃣ Передаём репозиторий в сервис (через конструктор)
    srv := service.NewUserService(repo)
    // 3️⃣ Передаём сервис в хендлер (через конструктор)
    h := handler.NewUserHandler(srv)
    // 4️⃣ Вызываем логику
    h.CreateUser("Аня")
}
```

#### Что происходит пошагово:
1. **`NewMemoryRepo()`**
    создаёт объект `MemoryRepo` — это конкретное хранилище.
2. **`NewUserService(repo)`**
    получает готовый `repo` и вставляет его внутрь `UserService`.
    Теперь сервис может вызывать `repo.Save()`.
3. **`NewUserHandler(srv)`**
    получает готовый `srv` и вставляет его внутрь `UserHandler`.
    Теперь хендлер может вызывать `srv.Register()`.
4. **`h.CreateUser("Аня")`**
    вызывает метод сервиса, который сохраняет пользователя в хранилище.

#### Проверим на практике.
Давай убедимся, что все слои действительно работают с **одним хранилищем**, а не с копиями.
#### main.go:
```go
package main
import (
    "fmt"
    "myapp/internal/handler"
    "myapp/internal/service"
    "myapp/internal/repository"
)
func main() {
    repo := repository.NewMemoryRepo()
    srv := service.NewUserService(repo)
    h := handler.NewUserHandler(srv)
    // напрямую через репозиторий
    repo.Save("Оля")
    // через сервис (который использует тот же репозиторий)
    srv.Register("Ваня")
    // через хендлер (через все уровни)
    h.CreateUser("Игорь")
    fmt.Println("Текущее состояние хранилища:", repo)
}
```
**Вывод:**
```
Сохранили в память: Оля
Сохранили в память: Ваня
Сохранили в память: Игорь
Текущее состояние хранилища: &{[Оля Ваня Игорь]}
```

#### Что это показывает:
- Мы трижды вызвали разные уровни приложения:
    1. `repo.Save("Оля")` — напрямую (нижний слой);
    2. `srv.Register("Ваня")` — через бизнес-логику;
    3. `h.CreateUser("Игорь")` — через хендлер.
- Но все они добавили данные **в одно и то же хранилище**.
- Потому что `repo`, `srv.repo` и `h.service.repo` — это **один и тот же объект в памяти**.

---

**Вывод:**
> Благодаря передаче зависимостей через конструкторы (`NewUserService`, `NewUserHandler`) все части программы работают **с одной общей сущностью**, а не с разными копиями.

Именно это делает архитектуру связной и предсказуемой.

# Структура проекта

```
/myapp
│
├── cmd/
│   └── main.go
│
└── internal/
    ├── handler/
    │   └── user_handler.go
    ├── service/
    │   └── user_service.go
    ├── repository/
    │   └── user_repository.go
    └── model/
        └── user.go
```
Каждый пакет отвечает **за одну часть логики**. Handler не знает, как работает Repository, а Repository не знает, кто его вызывает.
