# Зачем нужна <font color="#ff0000">архитектура</font>

Когда проект маленький — можно писать всё в одном файле:
```go
package main
import "fmt"
func main() {
    var users []string
    users = append(users, "Аня")
    fmt.Println(users)
}
```
Но если нужно:
- добавить сохранение в файл,
- потом базу данных,
- потом проверки и фильтры...
**всё быстро превращается в хаос.**

**Любое изменение ломает код.** Чтобы этого не происходило, программисты делят код на **слои**, каждый из которых отвечает **только за своё**.

---
## Слои приложения ~ <font color="#ff0000">Handler</font>, <font color="#ff0000">Service</font>, <font color="#ff0000">Repository</font> ~

<u>Архитектура</u> — это просто способ **разделить обязанности**.
Теперь разберём каждый слой отдельно.
```
Запрос → Handler → Service → Repository → База данных
                      ↑
                  Ответ клиенту
```

# 1. ~ <font color="#ff0000">Handler</font> ~ (или Delivery)

Это “*входная дверь*” в приложение.
Он принимает запросы — от **пользователя, HTTP, CLI, Telegram-бота** — не важно.

#### <font color="#ff0000">Handler</font>:
- получает входные данные;
- вызывает нужный метод бизнес-логики (Service);
- формирует ответ.

#### Пример:
```go
package handler
import (
    "fmt"
    "myapp/internal/service"
)
type UserHandler struct {
    service *service.UserService
}
func NewUserHandler(s *service.UserService) *UserHandler {
    return &UserHandler{service: s}
}
func (h *UserHandler) CreateUser(name string) {
    err := h.service.Register(name)
    if err != nil {
        fmt.Println("Ошибка:", err)
        return
    }
    fmt.Println("Пользователь успешно создан")
}
```
💬 Здесь `UserHandler` <u>ничего не знает о БД</u> — он просто передаёт имя в сервис и сообщает результат.

# 2. ~ <font color="#ff0000">Service</font> ~

Это **сердце приложения**, его "мозг".
Здесь живёт бизнес-логика: правила, проверки, валидация и сценарии.

<u>Сервис не знает, как данные хранятся</u> — он знает только, _что можно сохранить или получить пользователя_.
#### Пример:
```go
package service
import (
    "errors"
    "myapp/internal/repository"
)
type UserService struct {
    repo repository.UserRepository
}
func NewUserService(r repository.UserRepository) *UserService {
    return &UserService{repo: r}
}
func (s *UserService) Register(name string) error {
    if name == "" {
        return errors.New("имя не может быть пустым")
    }
    return s.repo.Save(name)
}
```
Здесь `UserService` использует [[1.2.1. Интерфейсы в Go|интерфейс]] `UserRepository`, а не конкретную реализацию. <u>Это значит, что он не знает</u> — <u>в памяти, в файле или в базе</u>. Главное, чтобы там был метод `Save()`.
# 3. ~ <font color="#ff0000">Repository</font> ~ (или Storage)

Repository отвечает за **хранение данных**.
Он знает, _как_ сохранить пользователя — в файл, в память, в базу и т.д.

#### Пример:
```go
package repository
import "fmt"
type UserRepository interface {
    Save(name string) error
}
type MemoryRepo struct {
    data []string
}
func NewMemoryRepo() *MemoryRepo {
    return &MemoryRepo{data: []string{}}
}
func (r *MemoryRepo) Save(name string) error {
    r.data = append(r.data, name)
    fmt.Println("Сохранили в память:", name)
    return nil
}
```
Это простейшее хранилище в памяти. Позже можно сделать `FileRepo` или `PostgresRepo`, не меняя код выше.
