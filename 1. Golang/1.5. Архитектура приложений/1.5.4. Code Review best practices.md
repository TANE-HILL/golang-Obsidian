# Зачем нужен Code Review

<u>Code Review (ревью кода)</u> — это когда твой коллега **просматривает твой код** перед тем, как он попадёт в основную ветку проекта.

Звучит просто, но на деле — <mark style="background:rgba(240, 200, 0, 0.2)">это **один из самых мощных инструментов обучения и контроля качества** в команде.</mark>

#### Зачем вообще кому-то смотреть твой код?

1. <u>Чтобы найти ошибки, которые ты не заметил.</u>
    Даже опытные программисты пропускают очевидные баги, когда “замыливается глаз”.
2. <u>Чтобы сделать код понятным для других.</u>
    В команде код читают чаще, чем пишут — ревью помогает поддерживать единый стиль.
3. <u>Чтобы делиться знаниями.</u>
    Через ревью разработчики учатся друг у друга — замечают приёмы, фишки, новые подходы.
4. <u>Чтобы формировать “коллективное владение кодом”.</u>
    После ревью код понимает не только автор, но и вся команда.

#### Что бывает, если ревью пропускать:
- В коде появляются **незамеченные баги**.
- Каждый пишет **в своём стиле** — проект теряет структуру.
- Только один человек понимает, “как это работает”.
- Исправления становятся дорогими и болезненными.
#### Проект превращается в хаос, где никто не хочет ничего трогать.

---
# Как выглядит процесс <font color="#ff0000">Code Review</font>

1. Разработчик создаёт **pull request (PR)** — предложение “влить” свой код.
2. Другие участники (ревьюеры) **смотрят изменения и** комментируют.
3. Автор **вносит исправления** и снова отправляет на ревью.
4. После одобрения код попадает в основную ветку.

---
# Как правильно делать <font color="#ff0000">Code Review</font>

#### <u>1. Смотри не на строки, а на смысл</u>

Ревью — это не “проверка запятых”.

Сосредоточься на логике:
- понятна ли идея функции;
- нет ли дублирования;
- можно ли упростить код;
- обрабатываются ли ошибки.

#### Пример
❌ Плохо:
> “Ты поставил не тот отступ.”

✅ Хорошо:
> “Можно вынести повторяющийся код в отдельную функцию — это упростит тестирование.”

#### <u>2. Комментируй доброжелательно</u>

Цель ревью — **помочь улучшить код**, а не доказать, кто умнее.

Пиши нейтрально и по делу:

|Было|Лучше так|
|---|---|
|“Что за ужасный нейминг?”|“Можно переименовать переменную, чтобы лучше отражала суть.”|
|“Ты неправильно сделал!”|“Похоже, тут может быть ошибка, посмотри, пожалуйста.”|
**Хорошее ревью — это не критика, а диалог.**

#### <u>3. Хвали за удачные решения</u>

Не ограничивайся замечаниями.
Если в коде есть что-то классное — **обязательно скажи об этом**:
> “Отличная идея использовать интерфейс — код читается проще.”
> “Классно, что добавил проверку на nil — это спасёт от паники.”

**Положительная обратная связь мотивирует писать лучше.**

#### <u>4. Делай ревью небольшими частями</u>

Ревью 50 строк — просто.
Ревью 500 строк — пытка.

Совет:
> Делай частые и маленькие PR.
> Ревьюировать по чуть-чуть — эффективнее, чем по тонне кода за раз.

#### <u>5. Проверяй не только код, но и контекст</u>

**Хорошее ревью включает вопросы:**
- зачем это изменение вообще нужно;
- покрыты ли кейсы тестами;
- соответствует ли код общей архитектуре проекта;
- нет ли нарушений принципов (DRY, KISS, SOLID).

# Что делать после ревью

1. Исправь комментарии.
2. Объясни, почему не все предложения принял (если есть причина).
3. Поблагодари за ревью — это тоже часть командной культуры.

---
# Так зачем вообще <font color="#ff0000">Code Review</font>, если есть <font color="#ff0000">линтеры</font>?

Ответ простой:
	**линтеры видят код, но не понимают смысл.**

А ревьюер — наоборот: он читает не “текст программы”, а **логику и намерение автора**.

---
# Разница между линтером и ревьюером

| <u>Линтер проверяет</u>        | <u>Ревьюер проверяет</u>            |
| ------------------------------ | ----------------------------------- |
| “Можно ли скомпилировать код?” | “Правильно ли он решает задачу?”    |
| Отступы, стиль, дубли          | Потенциальные баги и плохие решения |
| Механические ошибки            | Логические ошибки                   |
| Синтаксис                      | Смысл                               |
| Без контекста                  | В контексте проекта                 |

# <u>Реальный пример ревью</u>: программа работает, но ведёт себя странно

Автор пишет код, который должен запускать несколько воркеров и считать, сколько задач они выполнили:
```go
package main

import (
	"fmt"
)

type Worker struct {
	ID int
}

func (w Worker) DoWork(tasks <-chan int, done chan<- bool, counter *int) {
	for t := range tasks {
		fmt.Printf("Worker %d doing task %d\n", w.ID, t)
		*counter++
	}
	done <- true
}

func main() {
	tasks := make(chan int, 5)
	done := make(chan bool)
	var counter int

	for i := 1; i <= 3; i++ {
		w := Worker{ID: i}
		go w.DoWork(tasks, done, &counter)
	}

	for t := 1; t <= 5; t++ {
		tasks <- t
	}
	close(tasks)

	for i := 1; i <= 3; i++ {
		<-done
	}

	fmt.Println("Tasks completed:", counter)
}

```
#### Программа компилируется, линтер ничего не замечает.

И даже работает!
Но если запустить её несколько раз — результат будет **разный**:
```
Tasks completed: 3
Tasks completed: 5
Tasks completed: 4
```
#### Комментарии ревьюера (реальное ревью)

|Замечание|Почему это важно|
|---|---|
|**“Переменная `counter` изменяется из нескольких горутин без синхронизации.”**|Это классическая **гонка данных**. Go может посчитать неправильное значение, даже если всё “выглядит” нормально.|
|**“Передача `counter` по указателю выглядит небезопасно.”**|Лучше использовать `sync/atomic` или `sync.Mutex`, чтобы избежать одновременных записей.|
|**“Канал `done` используется для ожидания, но не масштабируется.”**|Если воркеров станет 1000, канал легко можно переполнить. Лучше использовать `sync.WaitGroup`.|
|**“`Worker.DoWork` ничего не возвращает, ошибки не обрабатываются.”**|Даже если всё идёт не так, программа просто “молча” работает. Хорошей практикой считается возвращать `error` или логировать сбои.|
|**“`fmt.Printf` из разных горутин выводит строки вперемешку.”**|Это не критично, но делает лог нечитаемым. Стоит добавить мьютекс для консоли или буферизацию вывода.|
#### После исправлений код стал таким:
```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type Worker struct {
	ID int
}

func (w Worker) DoWork(tasks <-chan int, wg *sync.WaitGroup, counter *int64) {
	defer wg.Done()
	for t := range tasks {
		fmt.Printf("Worker %d doing task %d\n", w.ID, t)
		atomic.AddInt64(counter, 1)
	}
}

func main() {
	tasks := make(chan int, 5)
	var counter int64
	var wg sync.WaitGroup

	for i := 1; i <= 3; i++ {
		w := Worker{ID: i}
		wg.Add(1)
		go w.DoWork(tasks, &wg, &counter)
	}

	for t := 1; t <= 5; t++ {
		tasks <- t
	}
	close(tasks)

	wg.Wait()
	fmt.Println("Tasks completed:", counter)
}
```

#### Что изменилось — и почему это настоящий результат ревью:

|Было|Стало|Почему лучше|
|---|---|---|
|`counter` — обычный `int`|`int64` + `atomic.AddInt64`|безопасно при работе из горутин|
|`done` — канал|`WaitGroup`|понятнее и безопаснее|
|нет контроля завершения|`defer wg.Done()`|гарантированное завершение|
|небезопасный вывод|всё в рамках `fmt.Printf` одной горутины|меньше накладных эффектов|
|нет возврата ошибок|теперь можно легко добавить логирование|гибкость на будущее|

#### <u>Почему линтер бы это не поймал</u>

Потому что:
- гонка данных не всегда видна при статическом анализе (Go Race Detector ≠ линтер);
- код корректен по синтаксису;
- нет "неиспользуемых" переменных или стиля;
- логика нарушена **на уровне архитектуры**, а не синтаксиса.

# Ещё типичные случаи, которые находят именно на ревью

|Пример|Что не так|
|---|---|
|Функция делает “всё подряд”: и читает, и пишет, и логирует|Нарушение принципа _Single Responsibility_|
|Используется `panic` вместо возврата ошибки|Программа падает вместо нормальной обработки|
|Канал создаётся без буфера, хотя должен быть буферизован|Потенциальная блокировка|
|Горутина навсегда зависает на `range`|Утечка горутин|
|Мьютекс забыли `Unlock` в `return`|Deadlock, который линтер не поймает|
|Функция возвращает указатель на локальную переменную|После выхода из функции данные “висят в воздухе”|
