# Зачем нужен стиль кода

Как только проект становится <u>командным</u>, стиль превращается в **правила общения между программистами**.

Иначе:
- один пишет `user_id`, другой `userId`;
- один ставит табы, другой пробелы;
- кто-то выравнивает отступы, кто-то нет.
<u>Всё вроде работает, но код становится трудным для чтения.</u>

[[1.1.0. Go Basics|Go]] решает эту проблему очень просто:
	В Go есть **единый стандарт стиля** и **инструменты, которые следят за ним автоматически**.

---
# Go сам форматирует код: ~ <font color="#ff0000">gofmt</font> ~

В Go есть инструмент gofmt, который приводит код к **единому виду**.
Это избавляет от споров «как правильно» — все делают **одинаково**.
#### Пример:
Ты написал вот так:
```go
func main( ) {fmt.Println( "Hi" )}
```
Запускаешь:
```bash
gofmt -w .
```
Go сам превращает код в аккуратный и читаемый вариант:
```go
func main() {
	fmt.Println("Hi")
}
```

Что делает `gofmt`:
- расставляет отступы (табами);
- выравнивает блоки кода;
- убирает лишние пробелы и скобки.

> <font color="#ff0000">go fmt ./...</font> — <u>встроенная команда Go, которая форматирует весь проект сразу.</u>

# <font color="#ff0000">Линтер</font> и для чего он нужен

Когда человек пишет код, он часто делает **мелкие, незаметные ошибки**.

**Например:**
- <u>забыл проверить</u> ошибку из `os.Open()`;
- <u>объявил</u> переменную, но <u>не использовал</u> её;
- написал <u>цикл</u>, который <u>никогда не завершится</u>;
- или просто выбрал <u>непонятное имя функции</u>.

Такие ошибки **не ломают компиляцию**, но делают код небезопасным, запутанным и трудным для поддержки.

<font color="#ff0000">Линтер</font> — это программа, которая **анализирует твой код** и говорит:

> «Вот здесь что-то подозрительно. Возможно, ошибка или нарушение стиля.»

То есть линтер — это **автоматический редактор и наставник**, который читает твой код и подсказывает, где стоит улучшить.

# Как работает <font color="#ff0000">линтер</font>

Линтер не запускает программу — он просто **читаeт исходники и ищет**:
1. типичные ошибки *(например, неиспользуемые переменные)*;
2. несоответствие правилам языка и стиля;
3. потенциально опасные конструкции.

Он не исправляет код сам, а показывает **подсказки** - где нужно что-то поменять и почему.
#### 📄 Пример
Допустим, ты написал:
```go
func main() {
    x := 10
    fmt.Println("Привет")
}
```
Программа скомпилируется, но линтер скажет:
```
main.go:2:2: x declared but not used (unused)
```

Это значит:
> “Ты создал переменную x, но нигде не используешь — вероятно, ошибка.”

# Чем <font color="#ff0000">линтер</font> отличается от ~ <font color="#ff0000">go fmt</font> ~

- `go fmt` просто **делает код аккуратным** (выровняет, расставит отступы).
- Линтер же **понимает смысл кода** и подсказывает, где можно улучшить.

---
# Основной инструмент ~ <font color="#ff0000">golangci-lint</font> ~

Теперь, когда ты понял, что такое линтер, разберём **главный инструмент** для [[1.1.0. Go Basics|Go]] — `golangci-lint`.

`golangci-lint` — это **“суперлинтер”**, который объединяет десятки маленьких проверок в один инструмент.

#### Вместо того чтобы запускать десятки утилит по отдельности, <u>он запускает их все сразу</u> и показывает результат в одном отчёте.

#### Примеры проверок, которые выполняет <font color="#ff0000">golangci-lint</font>:
- неиспользуемые переменные (`unused`);
- забытые проверки ошибок (`errcheck`);
- дублирование кода (`dupl`);
- переменные с одинаковыми именами (`shadow`);
- нарушение правил именования (`stylecheck`);
- подозрительные операции (`staticcheck`).

Идея простая:
> Линтер не ругается просто ради строгости — он учит тебя писать код так, как пишут опытные разработчики Go.

---
# <u>Установка</u> ~ <font color="#ff0000">golangci-lint</font> ~

```bash
go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest
```
Проверь:
```bash
golangci-lint version
```

---
# <u>Быzстрый запуск</u> ~ <font color="#ff0000">golangci-lint</font> ~

В корне проекта:
```bash
golangci-lint run
```
Если всё хорошо — программа ничего не выведет.
Если есть проблемы — ты увидишь подсказки:
```
main.go:10:2: var result is unused (unused)
main.go:15:15: Error return value is not checked (errcheck)
```

---
# <u>Настройка линтера</u> ~ <font color="#ff0000">golangci-lint</font> ~

Создай в корне проекта файл `.golangci.yml` — это его конфигурация.
Пример минимального конфига:
```yaml
run:
  timeout: 3m
  tests: true

linters:
  enable:
    - govet
    - errcheck
    - staticcheck
    - unused
    - stylecheck
    - dupl

issues:
  exclude-use-default: false
```

Теперь при запуске `golangci-lint run` линтер будет проверять только указанные правила.

# Автоматическая проверка в IDE

#### **В VS Code или GoLand линтер можно интегрировать прямо в редактор.**

Тогда ошибки будут подсвечиваться **в реальном времени** — как орфографические ошибки в тексте.

---
# Пример плохого и хорошего кода

**Плохо:**
```go
func calc(a,b int) int {
c:=a+b
return c }
```

**Хорошо (после `go fmt` и линтера):**
```go
func calc(a, b int) int {
	c := a + b
	return c
}
```

Если бы переменная `c` не использовалась, линтер выдал бы ошибку:
```
calc.go:2:2: c declared but not used (unused)
```

---
# Частые ошибки, которые ловит линтер

| Ошибка                                  | Что значит                                              |
| --------------------------------------- | ------------------------------------------------------- |
| `declared but not used`                 | переменная объявлена, но не используется                |
| `Error return value is not checked`     | не проверена ошибка                                     |
| `ineffectual assignment`                | значение присвоено, но не используется                  |
| `exported function should have comment` | публичная функция без документации                      |
| `shadow`                                | переменная перекрывает уже существующую с тем же именем |
| `dupl`                                  | повторяющийся фрагмент кода                             |

---
# Как настроить линтер под проект

Если линтер слишком строгий, можно выключить отдельные проверки:
```yaml
linters:
  disable:
    - dupl
    - gocyclo  # сложность функций
```
Или исключить конкретные файлы/папки:
```yaml
exclude-dirs:
  - vendor
  - internal/mocks
```

# Когда запускать линтер

Проверять код полезно **не вручную**, а **автоматически** — чтобы ничего не забывать.

#### Есть два удобных способа это делать:

#### <u>1. Перед каждым коммитом (pre-commit hook)</u>

Когда ты работаешь с Git (системой контроля версий), каждый раз перед тем, как “зафиксировать” изменения (`git commit`), можно автоматически запускать команды вроде:
```bash
go fmt ./...
golangci-lint run ./...
```

Это делается через **pre-commit hook** — небольшой файл, который говорит Git:
> “Перед сохранением кода — проверь, что всё отформатировано и без ошибок.”

Так ты не случайно не отправишь “грязный” код в репозиторий.

#### <u>2. В системах CI/CD</u>

Когда проект хранится на GitHub, GitLab или других платформах, можно настроить **автоматическую проверку кода при каждой загрузке изменений**.

⚙️ CI/CD (Continuous Integration / Continuous Delivery) — это системы, которые **сами выполняют команды** вроде:
```bash
go fmt ./...
golangci-lint run ./...
```

Каждый раз, когда ты пушишь код, они проверяют его качество и выдают отчёт.

Смысл один и тот же:
> чтобы линтеры запускались автоматически, а не “по настроению”.
