# Зачем нужны паттерны

[[1.11. Ошибки и обработка ошибок|Ошибки]] в [[1.0. Go Basics|Go]] — значения. Но **без согласованных приёмов** (как их создавать, передавать, разворачивать и показывать пользователю) код быстро превращается в хаос: теряется контекст, возникает двойное логирование, в API “утекают” приватные детали.

Дальше — <u>практичные паттерны</u>, которые повышают читаемость, улучшают диагностику и делают поведение предсказуемым.

---
# Карта паттернов
- **Sentinel-ошибки** для предсказуемых веток
- **Именованные (экспорт/неэкспорт) ошибки пакета**
- **Кастомные типы ошибок** с дополнительными полями
- **Оборачивание `%w`** и восстановление причины через `errors.Is/As/Unwrap`
- **Границы обработки**: где логировать, где только передавать
- **Нормализация ошибок для внешних клиентов** (скрываем детали)
- **Классификация: retryable / not found / validation**
- **Юнит-тестирование ошибок**: `Is`/`As` вместо сравнения строк

---
# <u>Паттерн 1</u>: <font color="#ff0000">Sentinel</font>-ошибки (ожидаемые ветки)

Когда <u>исход заранее известен</u> (*например, “не найдено”, “нет прав”, “деление на ноль”*), удобно объявить **одну разделяемую переменную-ошибку** и проверять её через `errors.Is`.

#### Пример:
```go
package auth

import (
	"errors"
)

var ErrUnauthorized = errors.New("unauthorized") // sentinel

func CanAccess(userRole string) error {
	if userRole != "admin" {
		return ErrUnauthorized
	}
	return nil
}

```

```go
package main

import (
	"errors"
	"fmt"

	"example.com/app/auth"
)

func main() {
	if err := auth.CanAccess("user"); err != nil {
		switch {
		case errors.Is(err, auth.ErrUnauthorized):
			fmt.Println("Доступ запрещён (нужна роль admin)")
		default:
			fmt.Println("Неожиданная ошибка:", err)
		}
		return
	}
	fmt.Println("OK")
}

```

#### Построчно (<u>ключевое</u>):
- `var ErrUnauthorized = errors.New(...)` — **один общий экземпляр** ошибки.
- `return ErrUnauthorized` — вызывающий код сможет проверить **через `errors.Is`**.
- `errors.Is(err, auth.ErrUnauthorized)` — сработает **даже если ошибку обернут `%w`** в другом месте.
#### Вывод:
Sentinel-ошибки упрощают **ветвление по ожидаемым сценариям**. Хороши там, где состояние действительно одно и то же по смыслу в разных местах кода.

# <u>Паттерн 2</u>: Именованные ошибки пакета (экспорт/неэкспорт)

Держи ошибки **рядом с пакетом**, который их генерирует.

Экспортируй те, которые должны быть видимы клиентам пакета; приватные — оставляй неэкспортируемыми.
#### Пример:
```go
// package repo
package repo

import "errors"

var (
	// Видна снаружи: клиенты могут реагировать отдельно
	ErrNotFound = errors.New("repo: not found")

	// Внутренняя деталь: лэйаут таблиц, индексы и т.д.
	errConstraint = errors.New("repo: constraint violation")
)

```
### Построчно (<u>ключевое</u>):
- `ErrNotFound` — **экспорт**: клиенты пакета могут делать `errors.Is(err, repo.ErrNotFound)`.
- `errConstraint` — **деталь реализации**: не утекает наружу.
#### Вывод:
Явно показывай, **на что клиентам можно опираться**, а что — может измениться без предупреждения.

# <u>Паттерн 3</u>: Кастомные типы ошибок (контекст в полях)

Когда одной фразы мало, добавляй **структуру** с полями (ID, входные данные, код доменной ошибки). Проверяй тип через `errors.As`.
#### Пример:
```go
package billing

import (
	"fmt"
)

type OverdraftError struct {
	AccountID string
	Amount    int64
	Balance   int64
}

func (e *OverdraftError) Error() string {
	return fmt.Sprintf("overdraft: account=%s amount=%d balance=%d",
		e.AccountID, e.Amount, e.Balance)
}

func Charge(account string, amount, balance int64) error {
	if amount > balance {
		return &OverdraftError{AccountID: account, Amount: amount, Balance: balance}
	}
	return nil
}

```

```go
package main

import (
	"errors"
	"fmt"

	"example.com/app/billing"
)

func main() {
	if err := billing.Charge("A-42", 1500, 700); err != nil {
		var oe *billing.OverdraftError
		if errors.As(err, &oe) {
			fmt.Printf("Недостаточно средств: счёт=%s, попытка=%d, баланс=%d\n",
				oe.AccountID, oe.Amount, oe.Balance)
			return
		}
		fmt.Println("Иная ошибка:", err)
	}
}

```
#### Построчно (ключевое):
- `type OverdraftError struct{...}` — **контекст в полях**.
- `func (e *OverdraftError) Error()` — реализует `error`.
- `errors.As(err, &oe)` — безопасно извлекаем конкретный тип **даже если были обёртки**.
#### Вывод:
Кастомные ошибки дают **богатый контекст для логов/метрик** и точные ветки обработки.

# <u>Паттерн 4</u>: Оборачивание ~ <font color="#ff0000">%w</font> + <font color="#ff0000">Is</font>/<font color="#ff0000">As</font>/<font color="#ff0000">Unwrap</font> ~

Каждый раз, когда прокидываешь ошибку вверх, **добавляй контекст** через `fmt.Errorf("...: %w", err)`.

Так ты получишь “мини-стек-трейс” в строке и возможность находить первопричину.

#### Пример:
```go
package users

import (
	"database/sql"
	"errors"
	"fmt"
)

var ErrUserNotFound = errors.New("users: not found")

func FindByEmail(db *sql.DB, email string) (int64, error) {
	var id int64
	if err := db.QueryRow("SELECT id FROM users WHERE email=$1", email).Scan(&id); err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			// Сохраняем семантику нашей доменной ошибки
			return 0, fmt.Errorf("FindByEmail: %w", ErrUserNotFound)
		}
		return 0, fmt.Errorf("FindByEmail: query failed: %w", err)
	}
	return id, nil
}
```

```go
package service

import (
	"errors"
	"fmt"

	"example.com/app/users"
)

func EnsureUserExists(email string) error {
	_, err := users.FindByEmail(db, email)
	if err != nil {
		// Добавляем уровень сервиса
		return fmt.Errorf("EnsureUserExists: %w", err)
	}
	return nil
}
```

```go
package api

import (
	"errors"
	"log"
	"net/http"

	"example.com/app/users"
	"example.com/app/service"
)

func GetProfile(w http.ResponseWriter, r *http.Request) {
	if err := service.EnsureUserExists(r.FormValue("email")); err != nil {
		// На границе (HTTP) мы решаем, что логировать и что показывать
		if errors.Is(err, users.ErrUserNotFound) {
			http.Error(w, "user not found", http.StatusNotFound)
			return
		}
		log.Printf("GetProfile: %v", err) // логируем с контекстом из всей цепочки
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	w.WriteHeader(http.StatusOK)
}
```
#### Построчно (ключевое):
- `fmt.Errorf("...: %w", err)` — **обёртка**: накапливаем контекст.
- На уровне `users` конвертируем низкоуровневое `sql.ErrNoRows` в **домашний** `ErrUserNotFound`.
- На уровне `api` — **последняя миля**: решаем, **что логировать**, что вернуть клиенту, не раскрывая деталей БД.

#### Вывод:
Оборачивай ошибку на каждом смысловом уровне.
Используй `errors.Is/As`, чтобы **доставать смысл**, а не парсить строки.

# <u>Паттерн 5</u>: Граница обработки (<font color="#ff0000">log-once</font>)

**Логируй один раз — на внешней границе** (например, в HTTP- или CLI-слое).
Внутренние уровни **добавляют контекст** и возвращают ошибку выше, но не логируют её повторно.

#### Пример-антипаттерн (двойное логирование):
```go
func repoOp() error {
	if err := doSQL(); err != nil {
		log.Println("repoOp:", err) // ❌
		return fmt.Errorf("repoOp: %w", err)
	}
	return nil
}

func apiHandler() {
	if err := repoOp(); err != nil {
		log.Println("api:", err) // ❌ будет продублированная запись в логи
	}
}
```
#### Исправление:
```go
func repoOp() error {
	if err := doSQL(); err != nil {
		return fmt.Errorf("repoOp: %w", err) // ✅ без логирования здесь
	}
	return nil
}

func apiHandler() {
	if err := repoOp(); err != nil {
		log.Println("api:", err) // ✅ логируем здесь один раз
	}
}
```
#### Вывод:
Держи **единственную точку логирования** для каждой ошибки. Это избавляет от шума в логах и дублирования.

# <u>Паттерн 6</u>: Нормализация ошибок для внешних клиентов

Внутренние сообщения (SQL, пути файлов, секреты) не должны **утекать** наружу.
На публичной границе **переведи** ошибку в безопасный ответ.
#### Пример:
```go
// внутри
if err := repo.CreateUser(u); err != nil {
	return fmt.Errorf("CreateUser: %w", err) // добавили контекст и прокинули дальше
}

```

```go
// HTTP-граница
if err != nil {
	switch {
	case errors.Is(err, repo.ErrDuplicate):
		http.Error(w, "email already in use", http.StatusConflict)
	default:
		log.Printf("CreateUser failed: %v", err)
		http.Error(w, "internal error", http.StatusInternalServerError)
	}
	return
}

```
#### Вывод:
Разделяй **внутренние причины** (для логов) и **внешние формулировки** (для клиента/пользователя).

# <u>Паттерн 7</u>: Классификация ошибок (retryable / not found / validation)

Иногда нужно **решение по стратегии**: повторить, прекратить, попросить пользователя исправить данные.
#### Вариант A — через интерфейс:
```go
type Retryable interface{ Retryable() bool }

type NetError struct{ Err error }
func (e NetError) Error() string   { return "network: " + e.Err.Error() }
func (e NetError) Retryable() bool { return true }

func doCall() error {
	// ...
	return NetError{Err: io.EOF}
}

func handler() {
	err := doCall()
	var r Retryable
	switch {
	case errors.As(err, &r) && r.Retryable():
		// план: повторить
	case errors.Is(err, ErrNotFound):
		// 404
	default:
		// обычная обработка
	}
}

```
#### Вариант B — через набор доменных ошибок:
```go
var (
	ErrValidation = errors.New("validation")
	ErrNotFound   = errors.New("not found")
	ErrRetryable  = errors.New("retryable")
)

```

Дальше — `errors.Is` для ветвления.
#### Вывод:
Заранее **реши стратегию** для классов ошибок. Это снимает хаос “а что делать дальше?”.

---
# <u>Паттерн 8</u>: Оборачивание — “сколько контекста добавлять”

Хорошее правило: **имя функции + действие + короткий смысл**.
#### Пример:
```go
return fmt.Errorf("FindUser: db query failed: %w", err)

```

Плохо:
- “ошибка БД” — расплывчато;
- слишком длинные рассказы в строке — шумно;
- дублирование одинакового текста на каждом уровне.
#### Вывод:
Добавляй **столько контекста, сколько нужно**, чтобы понять: где упали и почему. Без лишней воды.

---
# <u>Паттерн 9</u>: Тестирование ошибок — `Is/As`, а не строки

Не сравнивай `err.Error()` со строкой — это хрупко.
Используй `errors.Is/As`.
#### Пример:
```go
func TestFindByEmail_NotFound(t *testing.T) {
	_, err := users.FindByEmail(db, "nope@example.com")
	if !errors.Is(err, users.ErrUserNotFound) {
		t.Fatalf("expected ErrUserNotFound, got %v", err)
	}
}

```
#### Вывод:
Тесты привязываются к **семантике ошибки**, а не к формулировке текста.

---
# <u>Паттерн 10</u>: Не превращай ошибки в `panic`

(Коротко, без повторения теории про `panic`.)
В доменном/интеграционном коде отдавай предпочтение **возврату ошибок**.

`panic` оставь для **неисправимых инвариантов** (например, некорректная инициализация, которую нельзя обработать локально).
#### Вывод:
Ошибки — для ожидаемых нештатных ситуаций; `panic` — для действительно фатальных инцидентов.
