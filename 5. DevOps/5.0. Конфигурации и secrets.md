# Зачем нужны конфигурации

Когда ты только начинаешь писать приложение, всё работает **локально** — на твоём компьютере: один порт, одна база, один API-ключ.

В таком случае многие просто пишут настройки **прямо в коде**:
```go
db, _ := sql.Open("postgres", "postgres://admin:123@localhost:5432/app")
```

И на локальном компьютере это, кажется, работает отлично.
Но как только появляется **тестовый сервер** или **продакшен**, всё ломается.

---
## Почему?

Потому что **на каждом окружении** параметры разные:

| Среда                  | Что меняется                                           |
| ---------------------- | ------------------------------------------------------ |
| **Локально *(dev)***   | База `localhost`, порт 8080, тестовый API-ключ         |
| **Тест *(stage)***     | Другая БД, отдельный логин, другие пути                |
| **Продакшен *(prod)*** | Совсем другие пароли, защищённые токены, другие адреса |

Если настройки *“вшиты”* в код, придётся:
- постоянно переписывать строки подключения под каждую среду;
- пересобирать бинарник при каждом изменении;
- следить, чтобы никто случайно не залил в репозиторий реальные пароли.

---
# Что такое конфигурации

**Конфигурация *(configuration)*** — это набор **настроек, которые описывают, как приложение должно работать в текущем окружении.**

| <center><u>Тип конфигурации</u></center> | <center><u>Пример</u></center>                        | <center><u>Для чего нужна</u></center>              |
| ---------------------------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| **Подключения**                          | <center>`DB_URL`, `REDIS_URL`</center>                | *Пути и пароли к базам, кэшам, очередям*            |
| **Порты и адреса**                       | <center>`APP_PORT=8080`, `HOST=0.0.0.0`</center>      | *Где запустить сервер и как к нему подключиться*    |
| **Окружение *(environment)***            | <center>`APP_ENV=dev` / `prod`</center>               | *Определяет режим работы — локально, тест или прод* |
| **Secrets *(секреты)***                  | <center>`JWT_SECRET`, `API_KEY`</center>              | *Токены, пароли, приватные ключи*                   |
| **Логирование**                          | <center>`LOG_LEVEL=debug` / `info`</center>           | *Контроль уровня детализации логов*                 |
| **Фичи и флаги**                         | <center>`ENABLE_METRICS=true`</center>                | *Включают или выключают определённые возможности*   |
| **Сервисы и API**                        | <center>`PAYMENT_URL=https://api.stripe.com`</center> | *Адреса внешних интеграций*                         |

Например:
```
DB_URL=postgres://user:pass@localhost:5432/app
APP_PORT=8080
APP_ENV=dev
JWT_SECRET=mysecret
```
- Они могут отличаться для dev, stage и prod, но сам код программы остаётся одним и тем же.

---
## Почему нельзя хранить конфигурации в коде

1. **Безопасность.** 
    Если ты напишешь пароль или токен прямо в [[1.1.0. Go Basics|Go]]-файле, он попадёт в [[4.0. Основы Git - коммиты, ветки, merge|Git]]. Даже если вы используете [[4.1. Работа с GitLab - репозиторий, merge requests, code review|GitLab]], в компании может быть десятки разработчиков и CI-сервисов с доступом — один случайный пуш, и чувствительные данные останутся в истории репозитория навсегда.

2. **Управляемость.**
    Менять пароль БД должен не разработчик в коде, а DevOps или администратор — в настройках окружения.

3. **Портируемость.**
    Один и тот же код можно запустить в любом окружении, просто подставив нужные переменные окружения.

---
## Решение проблемы конфигураций

Мы уже разобрались, что **вшивать настройки прямо в код** — плохая идея. Пароли, адреса баз и токены не должны меняться в исходниках, потому что код должен быть **одинаковым для всех окружений** — а вот настройки у каждого свои: dev, stage, prod. Значит, нужно хранить эти данные **вне кода**, но так, чтобы приложение могло их подгрузить при запуске.

---
## Где хранить конфигурации

Самый простой и распространённый способ — **переменные окружения**.

Это просто набор “ключ=значение”, который описывает, **с какими настройками сейчас запускается приложение**.

Например:
```bash
DB_URL=postgres://admin:123@localhost:5432/app
APP_ENV=dev
JWT_SECRET=my-secret
```

Но вводить их вручную каждый раз неудобно, поэтому разработчики хранят их в специальном файле — **`.env`**.

---
## Что такое `.env` файл

`.env` — это обычный текстовый файл с настройками для твоего приложения.

Например:
```
DB_URL=postgres://user:pass@localhost:5432/app
APP_ENV=dev
JWT_SECRET=my-local-secret
```

Когда ты запускаешь приложение, библиотека (`godotenv` в Go) читает этот файл и **автоматически подставляет все значения в окружение**.

Таким образом:
- ты не хранишь пароли в коде;
- можешь быстро менять настройки под своё окружение;
- приложение становится универсальным — его можно запустить где угодно.

### Где создавать `.env`

Создай файл с именем `.env` **в корне проекта** — там же, где лежит твой `go.mod` или `cmd/`:
```
myapp/
├── .env
├── go.mod
├── cmd/
├── internal/
```
- Имя файла начинается с точки (`.`) — это **скрытый файл**

---
## Что такое `.env.example`

Файл `.env` обычно содержит **настоящие секреты**, поэтому его нельзя выкладывать в Git.

Чтобы другие разработчики знали, какие переменные нужны, создают шаблон — `.env.example`:
```
DB_URL=
APP_ENV=
JWT_SECRET=
```
- Этот файл **коммитится в репозиторий**.
- Он служит **инструкцией** — показывает, какие ключи требуются.
- Каждый разработчик копирует его под своё окружение:
```bash
cp .env.example .env
```
и заполняет реальные значения локально.

---
### Как это работает на практике

1. Ты клонируешь проект с GitLab/GitHub. В репозитории нет `.env` (он не коммитится).
2. Но есть `.env.example` — шаблон вроде такого:
```
DB_URL=
APP_ENV=
JWT_SECRET=
```
3. Ты копируешь его:
```bash
cp .env.example .env
```
4. Заполняешь свои тестовые значения:
```
DB_URL=postgres://user:pass@localhost:5432/app
APP_ENV=dev
JWT_SECRET=my-secret
```
5. Теперь у тебя есть локальный `.env`, и приложение можно запустить.

---
## Переменные окружения в CI/CD

Когда проект доходит до тестового или продакшн-сервера, `.env` файл **уже не нужен**. В CI/CD *(например, GitLab, GitHub Actions, Jenkins)* эти же переменные задаются прямо в настройках пайплайна.

Например, DevOps настраивает:
```
DB_URL=postgres://admin:prodpass@prod-db:5432/app
APP_ENV=prod
JWT_SECRET=super-secret-prod
```
- Эти значения **не хранятся в коде**, а передаются пайплайном в контейнер при сборке или деплое.

---
## Как это работает на практике

1. **Локально** — ты используешь `.env`
    → приложение берёт настройки из твоего файла.

2. **На сервере** — CI/CD подставляет переменные автоматически    
    → приложение читает их так же, через `os.Getenv`.

3. **Никто вручную не редактирует `.env` на продакшене.**    
    Все переменные окружения управляются DevOps-инженером или самим пайплайном *(в зависимости от политики доступа)*.

---
### Кто управляет конфигурациями

| <u>Среда</u>               | <u>Кто задаёт переменные</u> | <u>Где хранятся</u>           |
| -------------------------- | ---------------------------- | ----------------------------- |
| **Dev *(локально)***       | Разработчик                  | `.env`                        |
| **Stage *(тест)***         | DevOps или CI/CD             | В настройках пайплайна        |
| **Prod *(боевой сервер)*** | DevOps                       | В защищённых переменных CI/CD |

---
### Где хранить конфигурации

|Место|Подходит для|Особенности|
|---|---|---|
|`.env`|локальная разработка|просто и удобно, но не выкладываем в git|
|Переменные окружения в CI/CD|тест и продакшен|задаются в настройках пайплайна|
|Vault, AWS Secrets Manager|продакшен|безопасное централизованное хранение секретов|

---
## Что такое <u>Secrets</u> *(секреты)*

Среди всех конфигураций приложения *(порт, режим окружения, адреса сервисов и т.д.)* есть отдельная категория — **секреты**.

**Секреты** — это чувствительные данные, которые дают доступ к ресурсам:
	базе данных, внешним API, системам авторизации и т.п.
Именно поэтому они требуют особого отношения.

---
### Примеры секретов

- Пароли и логины *(`DB_PASSWORD`, `SMTP_PASS`)*
- Токены и ключи *(`JWT_SECRET`, `API_KEY`, `ACCESS_TOKEN`)*
- Приватные сертификаты *(`PRIVATE_KEY`, `SSL_KEY`)*

---
### Как отличить конфигурации от секретов

| Тип              | Пример                                    | Характеристика                                                     |
| ---------------- | ----------------------------------------- | ------------------------------------------------------------------ |
| **Конфигурации** | `APP_ENV=dev`, `PORT=8080`                | Общие настройки работы приложения *(безопасно показывать)*         |
| **Секреты**      | `DB_PASSWORD=12345`, `JWT_SECRET=mytoken` | Дают доступ к ресурсам, должны храниться только в защищённой среде |

---
### Где хранят секреты

| Среда               | Где хранят                                                     | Кто управляет       |
| ------------------- | -------------------------------------------------------------- | ------------------- |
| **Dev (локально)**  | В `.env` *(не коммитим)*                                       | Разработчик         |
| **Stage / Prod**    | В переменных окружения CI/CD                                   | DevOps              |
| **Крупные проекты** | В Secret Manager *(Vault, Doppler, AWS Secrets Manager и др.)* | DevOps / Cloud Team |

---
### Важно помнить

- **.env** используется только локально — на продакшене его быть не должно.
- **.env.example** не должен содержать настоящих значений секретов — только имена переменных.
- Если `.env` случайно попал в репозиторий — секреты нужно **сразу заменить**, а не просто удалить файл.
