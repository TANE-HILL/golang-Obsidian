# Что такое Kubernetes - K8s

**Kubernetes *(или K8s)*** — это система, которая управляет контейнерами *(обычно Docker)* и **автоматически решает**, где и как их запустить, обновить, перезапустить и масштабировать.

> Если Docker — это коробка, в которую ты упаковываешь приложение, то Kubernetes — это склад, где десятки таких коробок работают вместе.

---
## Проблема без Kubernetes

| <u><center>Ситуация</center></u>                    | <u><center>Проблема</center></u>                 |
| --------------------------------------------------- | ------------------------------------------------ |
| **Несколько контейнеров (Postgres, Redis, GoShop)** | *приходится запускать и следить за каждым вручную* |
| **Сервис упал**                                     | *нужно перезапускать вручную*                      |
| **Рост нагрузки**                                   | *приходится запускать новые контейнеры самому*     |
| **Деплой на несколько серверов**                    | *сложно координировать версии и сети*              |
> То есть без Kubernetes весь деплой и мониторинг — ручная работа DevOps.

---
## Как решает Kubernetes

| <u><center>Возможность</center></u> | <u><center>Что делает</center></u>                          |
| ----------------------------------- | ----------------------------------------------------------- |
| **Оркестрация**                     | *сам управляет запуском контейнеров*                        |
| **Масштабирование**                 | *добавляет/удаляет копии приложения при изменении нагрузки* |
| **Восстановление**                  | *перезапускает контейнеры, если они упали*                  |
| **Сетевое взаимодействие**          | *даёт контейнерам доступ друг к другу через DNS*            |
| **Роллинг-обновления**              | *обновляет приложение без простоя*                          |
| **Мониторинг и health-checks**      | *следит за состоянием сервисов*                             |

---
## Основные понятия Kubernetes

| <u><center>Понятие</center></u> | <u><center>Что это</center></u>                             | <u><center>Аналогия</center></u> |
| ------------------------------- | ----------------------------------------------------------- | -------------------------------- |
| **Cluster *(кластер)***         | *группа серверов (нод), где запускаются контейнеры*         | *“ферма машин”*                  |
| **Node *(нода)***               | *отдельный сервер или виртуалка внутри кластера*            | *“одна машина”*                  |
| **Pod**                         | *минимальная единица запуска — 1 или несколько контейнеров* | *“маленький бокс”*               |
| **Deployment**                  | *описание, сколько Pod’ов и как их обновлять*               | *“план запуска”*                 |
| **Service**                     | *создаёт стабильный IP/доступ к Pod’ам*                     | *“точка входа”*                  |
| **Ingress**                     | *маршрутизация внешнего трафика (HTTP)*                     | *“входные ворота”*               |
| **ConfigMap / Secret**          | *хранение конфигураций и секретов*                          | *“настройки и ключи”*            |

### Cluster

**Cluster** — это совокупность Node, объединённых для совместного запуска и управления приложениями.

Кластер состоит из:

- **Control Plane** — управляющая часть Kubernetes, которая координирует работу кластера.
- **Worker Nodes** — узлы, на которых запускаются приложения.

Kubernetes управляет ресурсами кластера и следит, чтобы фактическое состояние соответствовало желаемому.

**Аналогия:** кластер — это целый склад, состоящий из нескольких рабочих помещений.

### Node (нода)

**Node** — отдельный физический сервер или виртуальная машина внутри кластера Kubernetes.

На Node запускаются Pod'ы с контейнерами приложений.

Scheduler выбирает, на какой Node разместить новый Pod, учитывая доступные ресурсы и ограничения.

На Worker Node работают основные компоненты:

- **kubelet** — обеспечивает запуск и контролирует состояние назначенных Pod'ов.
- **Container Runtime** — непосредственно запускает контейнеры, например `containerd`.

**Аналогия:** Node — это отдельное помещение на складе, в котором размещены рабочие боксы.

### Pod

**Pod** — минимальная развёртываемая единица Kubernetes, внутри которой находится один или несколько контейнеров.

Обычно Pod содержит один основной контейнер. Например, Pod может содержать контейнер с Go REST API.

Несколько контейнеров внутри одного Pod могут совместно использовать сетевое пространство и подключённые тома.

Важно понимать:

- Pod — это не контейнер, а оболочка для одного или нескольких контейнеров.
- Pod запускается на определённой Node.
- Если Pod перестаёт существовать, Kubernetes может создать новый вместо него.
- Pod не предназначен для постоянного хранения данных: для этого используют тома и соответствующие механизмы хранения.

**Аналогия:** Pod — это бокс, внутри которого находится один или несколько контейнеров с приложениями.

### Deployment

**Deployment** — объект Kubernetes, который описывает желаемое состояние приложения и управляет его репликами.

Например, можно указать, что приложение должно работать в трёх экземплярах:

```
spec:
  replicas: 3
```

Kubernetes будет стремиться поддерживать три реплики приложения.

Deployment позволяет:

- задавать количество реплик;
- обновлять приложение;
- управлять историей обновлений и выполнять откат;
- восстанавливать нужное количество Pod'ов при их потере.

Технически Deployment управляет Pod'ами через промежуточный объект **ReplicaSet**, который отвечает за поддержание нужного количества реплик.

**Аналогия:** Deployment — это план производства, в котором указано, сколько экземпляров приложения должно работать и как обновлять их.

### Service

**Service** — объект Kubernetes, который предоставляет стабильную точку доступа к группе Pod'ов.

Проблема заключается в том, что Pod'ы могут пересоздаваться и получать новые IP-адреса. Поэтому обращаться к каждому Pod напрямую неудобно.

Service позволяет обращаться к группе Pod'ов через стабильное имя и IP-адрес, направляя трафик на подходящие экземпляры.

Например, Go API может обращаться к PostgreSQL через имя Service:

```
postgres-service:5432
```

Вместо того чтобы отслеживать IP-адрес конкретного Pod'а с PostgreSQL.

Service также может распределять запросы между несколькими подходящими Pod'ами.

**Аналогия:** Service — это единый номер телефона организации, по которому можно связаться с нужными сотрудниками, не зная их личных номеров.

### Ingress

**Ingress** — объект Kubernetes, который описывает правила маршрутизации внешнего HTTP/HTTPS-трафика к приложениям внутри кластера.

Например, можно настроить маршрутизацию:

```
api.example.com     → Go API
shop.example.com    → GoShop
```

Ingress позволяет описывать правила доступа к разным приложениям через домены и URL-пути.

Важно: **сам объект Ingress не обрабатывает трафик**. Для работы необходим Ingress Controller, который реализует описанные правила.

Ingress обычно используется для HTTP/HTTPS, а не для произвольного сетевого трафика.

**Аналогия:** Ingress — это указатель на входе в здание, который направляет посетителей в нужный отдел.

### ConfigMap / Secret

**ConfigMap** и **Secret** — объекты Kubernetes для хранения данных, необходимых приложениям при запуске.

**ConfigMap** предназначен для несекретных настроек:

- адресов сервисов;
- параметров приложения;
- режимов работы;
- настроек логирования.

Например:

```
APP_ENV=prod
LOG_LEVEL=info
```

**Secret** предназначен для чувствительных данных:

- паролей;
- токенов;
- ключей доступа;
- учётных данных для подключения к базе данных.

Например:

```
DB_USER=postgres
DB_PASSWORD=secret-password
```

Приложение может получать эти данные через переменные окружения или подключённые файлы.

**Важный нюанс:** Secret не становится автоматически зашифрованным только потому, что называется Secret. Для защиты данных необходимо правильно настроить права доступа и, при необходимости, шифрование данных в хранилище Kubernetes.

**Аналогия:**

- ConfigMap — лист с обычными инструкциями.
- Secret — хранилище для конфиденциальных данных, доступ к которому нужно ограничивать.

## Как Kubernetes запускает приложение

1. Ты описываешь приложение в YAML-файле *(например, `deployment.yml`)*.
2. Kubernetes читает этот файл и создаёт **Pod’ы**.
3. Каждый Pod содержит контейнеры *(например, `goshop-api`, `redis`, `postgres`)*.
4. Kubernetes следит, чтобы нужное количество Pod’ов всегда работало.
5. Если Pod “упал” — он автоматически перезапускается.
6. Снаружи доступ обеспечивается через **Service** или **Ingress**.

## Пример: Deployment для GoShop

📄 `deployment-goshop.yml`
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: goshop-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: goshop
  template:
    metadata:
      labels:
        app: goshop
    spec:
      containers:
        - name: goshop
          image: goshop:latest
          ports:
            - containerPort: 8080
          env:
            - name: DB_URL
              value: "postgres://postgres:postgres@postgres:5432/goshop?sslmode=disable"
            - name: APP_ENV
              value: "prod"
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10

```

---
### 🔍 Построчное объяснение

| <u><center>Поле</center></u> | <u><center>Что делает</center></u>                   |
| ---------------------------- | ---------------------------------------------------- |
| **`replicas: 2`**            | *Kubernetes запустит 2 экземпляра (Pod’а) GoShop*      |
| **`selector.matchLabels`**   | *выбирает, какие Pod’ы принадлежат этому Deployment*   |
| **`containers.image`**       | *указывает, какой Docker-образ использовать*           |
| **`env`**                    | *задаёт переменные окружения (как в `.env`)*           |
| **`readinessProbe`**         | *проверяет, что приложение готово обслуживать запросы* |
| **`ports.containerPort`**    | *открывает порт внутри контейнера*                     |

## Пример: Service для доступа к приложению

📄 `service-goshop.yml`
```yaml
apiVersion: v1
kind: Service
metadata:
  name: goshop-service
spec:
  type: NodePort
  selector:
    app: goshop
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 8080
      nodePort: 30080

```
Теперь приложение доступно на порту **30080** на любой ноде кластера:
```
<http://localhost:30080>
```

## Как развернуть локально

1. Установи **Minikube** *(локальный Kubernetes)*:
    https://minikube.sigs.k8s.io/docs/start/
2. Запусти кластер:
```bash
minikube start
```
3. Применяй конфигурации:
```bash
kubectl apply -f deployment-goshop.yml
kubectl apply -f service-goshop.yml
```
4. Проверь состояние:
```bash
kubectl get pods
kubectl get services
```
5. Открой приложение:
```bash
minikube service goshop-service
```

---
## Healthchecks и масштабирование

- Если контейнер не отвечает на `/healthz`, Kubernetes его перезапускает.
- Хочешь больше копий сервиса? Просто измени `replicas`:
```bash
kubectl scale deployment goshop-deployment --replicas=5
```
    → Kubernetes сам поднимет ещё три Pod’а.
