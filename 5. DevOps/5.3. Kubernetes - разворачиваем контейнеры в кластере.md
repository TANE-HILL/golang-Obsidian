# Что такое Kubernetes - K8s

**Kubernetes *(или K8s)*** — это система, которая управляет контейнерами *(обычно [[5.1. Docker и docker-compose|Docker]])* и **автоматически решает**, где и как их запустить, обновить, перезапустить и масштабировать.

> Если [[5.1. Docker и docker-compose|Docker]] — это коробка, в которую ты упаковываешь приложение, то Kubernetes — это склад, где десятки таких коробок работают вместе.

---
## Проблема без Kubernetes

| <u><center>Ситуация</center></u>                    | <u><center>Проблема</center></u>                 |
| --------------------------------------------------- | ------------------------------------------------ |
| **Несколько контейнеров (Postgres, Redis, GoShop)** | *приходится запускать и следить за каждым вручную* |
| **Сервис упал**                                     | *нужно перезапускать вручную*                      |
| **Рост нагрузки**                                   | *приходится запускать новые контейнеры самому*     |
| **Деплой на несколько серверов**                    | *сложно координировать версии и сети*              |
> То есть без Kubernetes весь деплой и мониторинг — ручная работа DevOps.

---
## Как решает Kubernetes

| <u><center>Возможность</center></u> | <u><center>Что делает</center></u>                          |
| ----------------------------------- | ----------------------------------------------------------- |
| **Оркестрация**                     | *сам управляет запуском контейнеров*                        |
| **Масштабирование**                 | *добавляет/удаляет копии приложения при изменении нагрузки* |
| **Восстановление**                  | *перезапускает контейнеры, если они упали*                  |
| **Сетевое взаимодействие**          | *даёт контейнерам доступ друг к другу через DNS*            |
| **Роллинг-обновления**              | *обновляет приложение без простоя*                          |
| **Мониторинг и health-checks**      | *следит за состоянием сервисов*                             |

---
## Основные понятия Kubernetes

| <u><center>Понятие</center></u> | <u><center>Что это</center></u>                             | <u><center>Аналогия</center></u> |
| ------------------------------- | ----------------------------------------------------------- | -------------------------------- |
| **Cluster *(кластер)***         | *группа серверов (нод), где запускаются контейнеры*         | *“ферма машин”*                  |
| **Node *(нода)***               | *отдельный сервер или виртуалка внутри кластера*            | *“одна машина”*                  |
| **Pod**                         | *минимальная единица запуска — 1 или несколько контейнеров* | *“маленький бокс”*               |
| **Deployment**                  | *описание, сколько Pod’ов и как их обновлять*               | *“план запуска”*                 |
| **Service**                     | *создаёт стабильный IP/доступ к Pod’ам*                     | *“точка входа”*                  |
| **Ingress**                     | *маршрутизация внешнего трафика (HTTP)*                     | *“входные ворота”*               |
| **ConfigMap / Secret**          | *хранение конфигураций и секретов*                          | *“настройки и ключи”*            |

# Сущности Kubernetes

## kubectl

`kubectl` — инструмент командной строки для взаимодействия с Kubernetes-кластером.

С его помощью можно создавать и изменять ресурсы, проверять состояние приложений, просматривать логи и диагностировать проблемы.

Основные команды:

```
kubectl get pods
# Показать Pod'ы

kubectl get nodes
# Показать узлы кластера

kubectl get deployments
# Показать Deployment'ы

kubectl describe pod <pod-name>
# Подробная информация о Pod

kubectl logs <pod-name>
# Показать логи Pod

kubectl apply -f app.yaml
# Применить конфигурацию из YAML
```

`kubectl` отправляет запросы API Server, который обрабатывает операции с ресурсами Kubernetes.

## Kubernetes Cluster

**Cluster (кластер)** — совокупность управляющих компонентов и узлов, объединённых для запуска и управления приложениями.

Кластер состоит из:

- **Control Plane** — управляющей части, которая координирует работу кластера.
- **Worker Nodes** — узлов, на которых выполняются приложения.

Kubernetes позволяет управлять приложениями централизованно, даже если они запущены на нескольких узлах.

## Master Node (Control Plane)

**Control Plane** — управляющая часть Kubernetes, отвечающая за состояние и координацию работы кластера.

В её состав входят основные компоненты:

- API Server;
- Scheduler;
- Controller Manager;
- etcd.

На схеме управляющая часть обозначена как Master Node. В современной терминологии чаще используют название **Control Plane**. Её компоненты могут работать на одной или нескольких машинах.

## API Server

**API Server** — центральная точка взаимодействия с Kubernetes.

Он принимает запросы от `kubectl` и других компонентов, проверяет их и обрабатывает операции с объектами кластера.

Например, когда ты применяешь Deployment через `kubectl apply`, запрос поступает в API Server.

Основные задачи:

- предоставление Kubernetes API;
- проверка и обработка запросов;
- взаимодействие с хранилищем состояния кластера;
- предоставление другим компонентам доступа к информации о ресурсах.

API Server не запускает контейнеры самостоятельно.

## Scheduler

**Scheduler (планировщик)** — компонент, который выбирает подходящий Worker Node для нового Pod.

При выборе учитываются:

- доступные CPU и RAM;
- ограничения на размещение;
- метки узлов;
- правила распределения Pod'ов;
- другие условия планирования.

Например, если на одной Node недостаточно ресурсов для Pod, Scheduler может выбрать другую подходящую Node.

**Scheduler выбирает, где разместить Pod, но не запускает контейнеры непосредственно.**

## Controller Manager

**Controller Manager** запускает контроллеры, которые следят за состоянием ресурсов и помогают привести фактическое состояние к желаемому.

Например, если Deployment должен поддерживать три реплики, но работает только два Pod'а, соответствующие контроллеры инициируют создание недостающей реплики.

Контроллеры постоянно наблюдают за состоянием объектов через API Server и реагируют на изменения.

Важно: Controller Manager не занимается непосредственно перезапуском каждого контейнера. За контейнерами внутри Pod на конкретном узле следит kubelet.

## etcd

**etcd** — распределённое хранилище ключ-значение, в котором Kubernetes хранит состояние и конфигурационные данные кластера.

В нём сохраняется информация об объектах Kubernetes, включая Deployment, Pod, Service и другие ресурсы.

Например, когда ты создаёшь Deployment, его описание сохраняется в хранилище через API Server.

Другие компоненты используют информацию о состоянии кластера, чтобы выполнять необходимые действия.

**etcd хранит данные, но не запускает контейнеры и не распределяет Pod'ы по узлам.**

## Worker Node

**Worker Node** — физический сервер или виртуальная машина, на которой запускаются приложения в Kubernetes.

На одной Node может работать несколько Pod'ов, если хватает ресурсов и соблюдаются ограничения размещения.

Основные компоненты Worker Node:

- **kubelet** — обеспечивает запуск и контролирует состояние назначенных Pod'ов;
- **kube-proxy** — реализует сетевые правила для Service, если используется этот компонент;
- **Container Runtime** — непосредственно запускает контейнеры.

Scheduler назначает Pod на подходящую Node, после чего kubelet обеспечивает его запуск.

## kubelet

**kubelet** — агент Kubernetes, работающий на каждой Worker Node.

Он получает через API Server информацию о Pod'ах, назначенных узлу, и обеспечивает их запуск и контроль состояния.

Основные задачи:

- взаимодействие с Container Runtime;
- обеспечение запуска контейнеров в назначенных Pod'ах;
- выполнение проверок состояния контейнеров;
- перезапуск контейнера при необходимости в соответствии с политикой перезапуска Pod.

Если контейнер завершился с ошибкой, kubelet может попытаться запустить его снова.

При этом kubelet не отвечает за глобальное распределение Pod'ов между узлами.

## kube-proxy

**kube-proxy** — компонент, обеспечивающий сетевые правила для Kubernetes Service в конфигурациях, где он используется.

Он помогает направлять сетевой трафик к подходящим Pod'ам, выбранным Service.

Например, несколько Pod'ов могут обслуживать одно приложение, а Service предоставляет единый адрес доступа к ним.

В зависимости от конфигурации кластера сетевые функции могут реализовываться и другими механизмами, поэтому kube-proxy присутствует не в каждом кластере.

## Container Runtime

**Container Runtime** — программное обеспечение, которое непосредственно запускает и управляет контейнерами на Worker Node.

Примеры:

- `containerd`;
- `CRI-O`.

Kubelet взаимодействует с Container Runtime через Container Runtime Interface (CRI).

Runtime отвечает за выполнение контейнеров, а Kubernetes управляет их размещением и желаемым состоянием.

Важно: Docker Engine и Kubernetes — не одно и то же. Kubernetes не требует установки Docker Engine на каждой Worker Node. Например, `containerd` может самостоятельно выполнять роль Container Runtime.

## POD

**Pod** — минимальная развёртываемая единица Kubernetes, содержащая один или несколько контейнеров.

Обычно один Pod содержит один основной контейнер. Несколько контейнеров в одном Pod используют общее сетевое пространство и могут совместно использовать подключённые тома.

Например:

```
Worker Node
└── Pod
    └── Container
        └── Приложение
```

Pod назначается на определённую Node.

Основные особенности:

- Pod получает собственный IP-адрес внутри кластера.
- Контейнеры одного Pod могут взаимодействовать через `localhost`.
- Pod может быть пересоздан, получив новый IP-адрес.
- Для постоянного хранения данных используются тома и соответствующие механизмы хранения.

Для управления Pod'ами обычно используют Deployment, StatefulSet, DaemonSet и другие Workload-ресурсы, а не создают Pod'ы вручную.

## Docker Container

**Контейнер** — изолированный процесс, запускаемый на основе образа, содержащего приложение и необходимые ему зависимости.

В контексте Kubernetes важно понимать разницу между тремя понятиями:

- **Image** — образ, из которого создаётся контейнер.
- **Container** — работающий экземпляр образа.
- **Pod** — объект Kubernetes, внутри которого запускаются один или несколько контейнеров.

Например:

```
Deployment
└── ReplicaSet
    └── Pod
        └── Container
            └── Go API
```

Несмотря на название, Kubernetes не обязательно использует Docker Engine для запуска контейнеров. В современных кластерах часто применяется `containerd`.

## Networking

**Networking (сеть Kubernetes)** — набор механизмов, обеспечивающих сетевое взаимодействие между Pod'ами, Service и внешними клиентами.

Основные принципы:

- Pod'ы получают IP-адреса в сети кластера.
- Pod'ы могут взаимодействовать друг с другом через сеть кластера.
- Service предоставляет стабильную точку доступа к группе Pod'ов.
- Ingress позволяет организовать маршрутизацию HTTP/HTTPS-трафика извне.

Для разработчика важно понимать, как приложения находят друг друга и почему обычно не следует жёстко прописывать IP-адрес конкретного Pod.

## Service

**Service** — объект Kubernetes, предоставляющий стабильную точку доступа к группе Pod'ов.

Pod'ы могут пересоздаваться и получать новые IP-адреса. Service позволяет обращаться к приложению по постоянному имени и IP-адресу, не отслеживая каждый Pod отдельно.

Service выбирает Pod'ы по меткам (`labels`), а затем направляет трафик к подходящим экземплярам.

Основные типы Service:

- **ClusterIP** — доступ к сервису внутри кластера. Используется по умолчанию.
- **NodePort** — открывает определённый порт на узлах кластера.
- **LoadBalancer** — предоставляет внешний балансировщик, если это поддерживается инфраструктурой.
- **ExternalName** — связывает Service с внешним DNS-именем.

Например, приложение может подключаться к PostgreSQL через адрес:

```
postgres-service:5432
```

Здесь `postgres-service` — имя Service, а `5432` — порт базы данных.

## Ingress

**Ingress** — объект Kubernetes, описывающий правила маршрутизации внешнего HTTP/HTTPS-трафика к приложениям внутри кластера.

Например:

```
api.example.com   → Go API
shop.example.com  → GoShop
```

Ingress позволяет направлять запросы к разным приложениям по доменам и URL-путям.

Важно: сам объект Ingress не обрабатывает сетевой трафик. Для реализации правил необходим **Ingress Controller**, например NGINX Ingress Controller.

Ingress обычно используется совместно с Service, через которые организован доступ к Pod'ам.

## Workloads

**Workloads (рабочие нагрузки)** — группа ресурсов Kubernetes, предназначенных для управления запуском приложений и задач.

Основные Workload-ресурсы:

- Deployment;
- ReplicaSet;
- StatefulSet;
- DaemonSet;
- Job;
- CronJob.

Они решают разные задачи: от запуска нескольких копий API до выполнения периодических фоновых операций.

Вместо ручного создания множества Pod'ов разработчик описывает желаемое состояние приложения, а Kubernetes управляет его выполнением.

## Deployment

**Deployment** — ресурс Kubernetes для управления приложениями, которым нужны взаимозаменяемые реплики и контролируемые обновления.

В Deployment можно указать, сколько реплик приложения должно работать:

```
spec:
  replicas: 3 # Поддерживать три реплики приложения
```

Deployment управляет ReplicaSet, а ReplicaSet обеспечивает необходимое количество Pod'ов.

Основные возможности:

- поддержание нужного количества реплик;
- обновление приложения;
- управление процессом обновления;
- откат к предыдущей ревизии при необходимости.

Deployment обычно используют для REST API, веб-приложений и других stateless-сервисов, экземпляры которых не должны иметь собственное уникальное состояние.

## ReplicaSet

**ReplicaSet** — ресурс, который поддерживает заданное количество Pod'ов с определёнными метками.

Например, если ReplicaSet должен поддерживать три Pod'а, а один исчезнет, контроллер создаст замену.

ReplicaSet отвечает за количество реплик, но самостоятельно не предоставляет весь механизм обновлений, который есть у Deployment.

**Обычно ReplicaSet не создают вручную: им управляет Deployment.**

## StatefulSet

**StatefulSet** — Workload-ресурс для приложений, которым необходимы стабильные идентификаторы Pod'ов и, как правило, постоянные тома хранения.

В отличие от Deployment, StatefulSet обеспечивает предсказуемые имена Pod'ов, например:

```
postgres-0
postgres-1
postgres-2
```

Это полезно для распределённых систем, где экземпляры могут отличаться ролью или иметь собственное состояние.

StatefulSet часто применяют для баз данных и других stateful-приложений, но **сам по себе он не обеспечивает репликацию, отказоустойчивость или резервное копирование базы данных**. Для этого нужны дополнительные механизмы.

## DaemonSet

**DaemonSet** — Workload-ресурс, который обеспечивает запуск Pod'а на каждой подходящей Node.

Например, он используется для:

- сбора логов;
- мониторинга узлов;
- запуска сетевых агентов.

Если в кластер добавляется новая подходящая Node, DaemonSet может автоматически создать на ней Pod.

В отличие от Deployment, который управляет заданным количеством реплик, DaemonSet ориентируется на набор подходящих узлов.

## Job

**Job** — Workload-ресурс для выполнения задачи, которая должна завершиться успешно.

Например:

- одноразовая обработка данных;
- импорт данных;
- выполнение миграций базы данных;
- генерация отчёта.

Job создаёт Pod'ы для выполнения задачи и отслеживает результат. В зависимости от настроек он может запускать несколько попыток при неудаче.

В отличие от Deployment, Job предназначен не для постоянно работающего приложения, а для конечной задачи.

## CronJob

**CronJob** — Workload-ресурс для периодического запуска задач по расписанию.

Например, можно настроить ежедневную задачу резервного копирования или периодическую обработку данных.

CronJob создаёт Job в соответствии с расписанием, а Job управляет выполнением задачи в Pod'ах.

Пример:

```
apiVersion: batch/v1
kind: CronJob
metadata:
  name: cleanup
spec:
  schedule: "0 2 * * *" # Запуск каждый день в 02:00
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: cleanup
              image: busybox:latest
              command: ["sh", "-c", "echo cleanup"]
```

В этом примере задача запускается ежедневно в 02:00 по времени, используемому планировщиком Kubernetes для CronJob.

Важно учитывать, что расписание не гарантирует абсолютно точный запуск в заданную секунду. Кроме того, при настройке повторных запусков и параллельности нужно учитывать возможность повторного выполнения задачи. Поэтому периодические задачи желательно проектировать с учётом идемпотентности.

# Архитектура Kubernetes

```
┌─────────────────────────────┐
│      Kubernetes Cluster     │
│ ┌───────────────┐┌────────┐ │
│ │ Control Plane ││ Nodes  │ │
│ │ (управление)  ││(рабочие) │
│ └───────────────┘└────────┘ │
│     ↓ планирует Pods        │
│     ↓ следит за состоянием  │
│     ↓ масштабирует          │
└─────────────────────────────┘
```

## Как Kubernetes запускает приложение

1. Ты описываешь приложение в YAML-файле *(например, `deployment.yml`)*.
2. Kubernetes читает этот файл и создаёт **Pod’ы**.
3. Каждый Pod содержит контейнеры *(например, `goshop-api`, `redis`, `postgres`)*.
4. Kubernetes следит, чтобы нужное количество Pod’ов всегда работало.
5. Если Pod “упал” — он автоматически перезапускается.
6. Снаружи доступ обеспечивается через **Service** или **Ingress**.

---
## Пример: Deployment для GoShop

📄 `deployment-goshop.yml`
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: goshop-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: goshop
  template:
    metadata:
      labels:
        app: goshop
    spec:
      containers:
        - name: goshop
          image: goshop:latest
          ports:
            - containerPort: 8080
          env:
            - name: DB_URL
              value: "postgres://postgres:postgres@postgres:5432/goshop?sslmode=disable"
            - name: APP_ENV
              value: "prod"
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10

```

### 🔍 Построчное объяснение

| <u><center>Поле</center></u> | <u><center>Что делает</center></u>                   |
| ---------------------------- | ---------------------------------------------------- |
| **`replicas: 2`**            | *Kubernetes запустит 2 экземпляра (Pod’а) GoShop*      |
| **`selector.matchLabels`**   | *выбирает, какие Pod’ы принадлежат этому Deployment*   |
| **`containers.image`**       | *указывает, какой Docker-образ использовать*           |
| **`env`**                    | *задаёт переменные окружения (как в `.env`)*           |
| **`readinessProbe`**         | *проверяет, что приложение готово обслуживать запросы* |
| **`ports.containerPort`**    | *открывает порт внутри контейнера*                     |

---
## Пример: Service для доступа к приложению

📄 `service-goshop.yml`
```yaml
apiVersion: v1
kind: Service
metadata:
  name: goshop-service
spec:
  type: NodePort
  selector:
    app: goshop
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 8080
      nodePort: 30080

```
Теперь приложение доступно на порту **30080** на любой ноде кластера:
```
<http://localhost:30080>
```

## Как развернуть локально

1. Установи **Minikube** *(локальный Kubernetes)*:
    https://minikube.sigs.k8s.io/docs/start/
2. Запусти кластер:
```bash
minikube start
```
3. Применяй конфигурации:
```bash
kubectl apply -f deployment-goshop.yml
kubectl apply -f service-goshop.yml
```
4. Проверь состояние:
```bash
kubectl get pods
kubectl get services
```
5. Открой приложение:
```bash
minikube service goshop-service
```

## Healthchecks и масштабирование

- Если контейнер не отвечает на `/healthz`, Kubernetes его перезапускает.
- Хочешь больше копий сервиса? Просто измени `replicas`:
```bash
kubectl scale deployment goshop-deployment --replicas=5
```
    → Kubernetes сам поднимет ещё три Pod’а.
