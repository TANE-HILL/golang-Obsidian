# Зачем нужен Docker

**Когда проект растёт, у него появляются зависимости:**
- база данных *(PostgreSQL)*,
- кэш *(Redis)*,
- брокер сообщений *(Kafka)*,
- а также само [[1.1.0. Go Basics|Go]]-приложение.

Без Docker каждый разработчик должен устанавливать всё это вручную. На разных компьютерах — разные версии и настройки.

В итоге проект:
- у тебя работает,
- у коллеги — нет,
- на сервере — падает.

---
# Что делает Docker

**Docker** решает эту проблему.

Он создаёт **контейнеры** — мини-среды, в которых приложение работает одинаково везде.
> Контейнер — это как “мини-компьютер” с собственными настройками, библиотеками и кодом.

Docker берёт на себя:
- установку зависимостей,
- настройку окружения,
- запуск и связь между сервисами.
---
# Основные понятия Docker

| <u>Понятие</u>              | <u>Что это</u>                                                          | <u>Аналогия</u>           |
| --------------------------- | ----------------------------------------------------------------------- | ------------------------- |
| **Образ *(Image)***         | **Шаблон, по которому создаётся контейнер**                             | *"Фотография" приложения* |
| **Контейнер *(Container)*** | **Запущенная копия образа**                                             | *"Живое" приложение*      |
| **Dockerfile**              | **Файл с инструкциями, как собрать образ**                              | *Рецепт*                  |
| **docker-compose.yml**      | **Файл, который описывает, как запустить несколько контейнеров вместе** | *План сборки системы*     |

---
## Что такое **образ *(Image)***

**Образ** — это *“упаковка”* программы со всем, что ей нужно, чтобы запуститься.
Можно сказать, что образ — это **снимок рабочей среды**:
- сама программа *(например, твой сервер)*;
- зависимости *(библиотеки, файлы конфигурации)*;
- системные утилиты и настройки.

> 💬 Образ — это шаблон.
> Контейнеры создаются на его основе, как пирожки по одному и тому же рецепту.

### Пример

Допустим, у нас есть [[1.6.1. HTTP-сервер|сервер]] на [[1.1.0. Go Basics|Go]]. Чтобы он работал, нужны:
- установленный Go;
- исходники программы;
- библиотеки из `go.mod`.

Мы можем собрать образ, в котором всё это уже есть.
Тогда при запуске Docker просто создаст *“копию”* этого окружения — и всё заработает, где угодно.

### Где хранятся образы

Образы можно хранить в специальных *“реестрах” (registry)*:
- [Docker Hub](https://hub.docker.com/) — как GitHub, но для образов;
- GitLab Registry, GitHub Container Registry, AWS ECR — корпоративные варианты.

Когда ты скачиваешь чужой образ *(`docker pull postgres`)*, ты просто берёшь готовый шаблон из реестра.

### Запомни
- Образ **не выполняется** — он как архив с инструкцией.
- Из одного образа можно запустить **много контейнеров**.
- Образы **не меняются** — чтобы обновить что-то, нужно собрать новый.

---
## Что такое **контейнер *(Container)***

**Контейнер** — это **запущенный экземпляр образа**.
То есть когда **Docker** создаёт контейнер, он просто *“разворачивает”* образ и запускает внутри него приложение.
> Образ — это рецепт. Контейнер — это готовое блюдо.

### Пример

Берём образ [[2.1.0. Подключение PostgreSQL|PostgreSQL]] *(`postgres:15`)* и запускаем контейнер:
```bash
docker run -d -p 5432:5432 postgres:15
```

<u>Что произойдёт:</u>
- Docker скачает *(если нужно)* образ с Docker Hub;
- создаст контейнер *(копию этого образа)*;
- запустит PostgreSQL внутри него.

Теперь у нас есть *“мини-компьютер”*, где крутится база, и он полностью изолирован от твоей системы.

### Свойства контейнера

| <u>Свойство</u>   | <u>Описание</u>                                                |
| ----------------- | -------------------------------------------------------------- |
| **Изолированный** | *Не влияет на основную систему*                                  |
| **Лёгкий**        | *Запускается за секунды*                                         |
| **Временный**     | *Можно удалить и пересоздать в любой момент*                     |
| **Повторяемый**   | *Любой может запустить тот же контейнер — и всё будет одинаково* |

### Что можно делать с контейнерами

| <u>Команда</u>         | <u>Что делает</u>                              |
| ---------------------- | ---------------------------------------------- |
| **`docker run`**       | *Запускает новый контейнер*                    |
| **`docker ps`**        | *Показывает работающие контейнеры*             |
| **`docker stop <id>`** | *Останавливает*                                |
| **`docker rm <id>`**   | *Удаляет*                                      |
| **`docker logs <id>`** | *Показывает логи приложения внутри контейнера* |

### Проблема без контейнеров

До появления Docker приложения устанавливали *“вручную”*:
- скачивали **Postgres, Redis, Python, Go и т.д.**;
- настраивали версии, пути, порты;
- всё ломалось при первой переустановке системы.

#### Что шло не так

| <u>Проблема</u>       | <u>Что происходит</u>                                    |
| --------------------- | -------------------------------------------------------- |
| **Разные версии**     | *У тебя Go 1.22, у коллеги 1.25 — программа не собирается* |
| **Конфликты портов**  | *Два сервиса используют один и тот же порт*                |
| **Зависимости**       | *Разные библиотеки и пакеты в системе*                     |
| **“У меня работает”** | *Самая частая фраза в команде*                             |
| **Разные ОС**         | *На Linux всё ок, а на Windows — падает*                   |
| **Продакшен**         | *На сервере другая конфигурация, и код ведёт себя иначе*   |

### Контейнеризация — решение

**Docker решил все эти проблемы одной идеей:**
> “А давай упакуем приложение вместе с его окружением в отдельную изолированную среду и будем запускать где угодно.”

### Что попадает в контейнер

- сам код программы;
- нужные зависимости и библиотеки;
- системные утилиты;
- переменные окружения;
- настройки портов и путей.

### Что даёт контейнеризация

| <u>Преимущество</u>       | <u>Объяснение</u>                                             |
| ------------------------- | ------------------------------------------------------------- |
| **Одинаковая среда**      | *У всех разработчиков и серверов одна и та же версия окружения* |
| **Изоляция**              | *Каждое приложение работает отдельно, не мешая другим*          |
| **Быстрый запуск**        | *Контейнер поднимается за секунды*                              |
| **Простое удаление**      | *Не нужно “чистить” систему — просто удаляешь контейнер*        |
| **Легко обновлять**       | *Новая версия = новый образ*                                    |
| **Совместимость с CI/CD** | *Контейнер можно деплоить в любую среду без “танцев с бубном”*  |

---
### Главная идея

Без Docker:
> “У меня работает, у тебя — нет.”

С Docker:
> “У всех работает одинаково.”

## Dockerfile

### Что такое Dockerfile

**Dockerfile** — это обычный текстовый файл, в котором описано, **как собрать образ Docker** шаг за шагом.

**Можно думать о нём как о *“рецепте приготовления приложения”*:**
> Какие ингредиенты взять, что установить, какие команды выполнить и как запустить результат.

### Как Docker использует Dockerfile

1. Docker читает твой `Dockerfile`.
2. Выполняет инструкции сверху вниз.
3. На основе этого создаёт **образ *(image)***.
4. Потом ты можешь запустить контейнер из этого образа.

### Что такое бинарник

**Бинарник *(binary)*** — это **скомпилированная версия программы**, то есть готовый исполняемый файл, который можно запускать напрямую, без исходников.

**Например:**
- в Go это `.exe` или просто файл без расширения;

> Когда мы собираем бинарник, мы превращаем код в программу, которую можно запустить даже на сервере, где нет установленного Go.

### Пример для проекта **GoShop**:
```docker
# Этап 1: сборка бинарника
FROM golang:1.25 AS builder
WORKDIR /app
COPY . .
RUN go mod download
RUN go build -o goshop ./cmd/main.go

# Этап 2: минимальный образ для запуска
FROM debian:bookworm-slim
WORKDIR /app
COPY --from=builder /app/goshop .
EXPOSE 8080
CMD ["./goshop"]
```

### Построчное объяснение

| <u>Команда</u>                | <u>Что делает</u>                           |
| ----------------------------- | ------------------------------------------- |
| `FROM golang:1.25 AS builder` | *Берём официальный образ с Go*                |
| `WORKDIR /app`                | *Создаём рабочую папку внутри контейнера*     |
| `COPY . .`                    | *Копируем проект в контейнер*                 |
| `RUN go mod download`         | *Загружаем зависимости*                       |
| `RUN go build`                | *Собираем бинарник приложения*                |
| `FROM debian:bookworm-slim`   | *Второй "чистый" образ — без компилятора*     |
| `COPY --from=builder`         | *Копируем готовый бинарник из первого образа* |
| `EXPOSE 8080`                 | *Открываем порт 8080 для приложения*          |
| `CMD ["./goshop"]`            | *Указываем команду для запуска контейнера*    |

### Почему Dockerfile часто делят на два этапа

Это называется **многоэтапная сборка *(multi-stage build)*** — она делает образы **меньше, быстрее и безопаснее**.

#### Этап 1 — сборка приложения *(build stage)*

Здесь мы используем *“тяжёлый”* образ, где есть всё необходимое для компиляции кода.

Например:
```docker
FROM golang:1.25 AS builder
WORKDIR /app
COPY . .
RUN go mod download
RUN go build -o goshop ./cmd/main.go
```

**Что происходит:**
1. Берём базовый образ `golang:1.25`, где уже установлен Go.
2. Копируем весь проект внутрь контейнера *(`COPY . .`)*.
3. Загружаем зависимости *(`go mod download`)*.
4. Собираем бинарник *(`go build -o goshop`)*.

**Результат** — в контейнере есть файл `goshop` *(готовая программа)*.

#### Этап 2 — запуск приложения *(runtime stage)*

Теперь создаём *“чистый”* контейнер, без компилятора и лишних файлов:
```docker
FROM debian:bookworm-slim
WORKDIR /app
COPY --from=builder /app/goshop .
EXPOSE 8080
CMD ["./goshop"]
```

Что происходит:
1. Берём минимальный образ `debian:bookworm-slim` *(без Go, без исходников)*.
2. Копируем из первого контейнера только бинарник `goshop`.
3. Указываем порт *(`EXPOSE 8080`)*.
4. Задаём команду для запуска *(`CMD ["./goshop"]`)*.

Теперь наш контейнер содержит **только то, что нужно для запуска**, а не для сборки. Он весит меньше и запускается быстрее.

### Зачем нужен многоэтапный подход

|Преимущество|Что это значит|
|---|---|
|🪶 **Меньше размер**|Из контейнера исключаются исходники и инструменты сборки|
|⚡ **Быстрее запуск**|Меньше слоёв — быстрее стартует|
|🔒 **Безопаснее**|Нет исходников и лишних пакетов|
|🧱 **Универсально**|Можно собирать любой язык — Java, Node, Go и т.д.|

### Общий шаблон Dockerfile

Вот типовой шаблон, который подойдёт почти для любого проекта:
```docker
# 1. Базовый образ
FROM <имя-образа>:<версия>

# 2. Рабочая директория внутри контейнера
WORKDIR /app

# 3. Копируем нужные файлы внутрь контейнера
COPY . .

# 4. Устанавливаем зависимости или собираем проект
RUN <команды>

# 5. Указываем порты (если нужно)
EXPOSE <порт>

# 6. Указываем, что запустить при старте контейнера
CMD ["<команда>", "<аргументы>"]
```

## Docker Compose

Если приложение использует несколько сервисов *(Go, PostgreSQL, Redis, Kafka)*, запускать их вручную неудобно. Для этого есть **docker-compose** — инструмент, который запускает все контейнеры одной командой.

Пример `docker-compose.yml` для **GoShop**:
```yaml
version: '3.9'

services:
  # --- PostgreSQL ---
  postgres:
    image: postgres:15
    container_name: goshop-postgres
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: goshop
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

  # --- Redis ---
  redis:
    image: redis:7
    container_name: goshop-redis
    ports:
      - "6379:6379"

  # --- Kafka ---
  zookeeper:
    image: bitnami/zookeeper:3.9
    container_name: zookeeper
    environment:
      - ALLOW_ANONYMOUS_LOGIN=yes
    ports:
      - "2181:2181"

  kafka:
    image: bitnami/kafka:3.7
    container_name: kafka
    depends_on:
      - zookeeper
    environment:
      - KAFKA_BROKER_ID=1
      - KAFKA_CFG_ZOOKEEPER_CONNECT=zookeeper:2181
      - ALLOW_PLAINTEXT_LISTENER=yes
      - KAFKA_CFG_LISTENERS=PLAINTEXT://:9092
      - KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092
    ports:
      - "9092:9092"

  # --- Go-приложение ---
  goshop:
    build: .
    container_name: goshop-api
    ports:
      - "8080:8080"
    depends_on:
      - postgres
      - redis
      - kafka
    env_file:
      - .env

volumes:
  postgres_data:
```

### Разберём ключевые блоки

| <u>Раздел</u>                                                 | <u>Что делает</u>                              |
| ------------------------------------------------------------- | ---------------------------------------------- |
| <center>`services:`</center>                                  | *Список контейнеров, которые нужно запустить*  |
| <center>`postgres`<br>`redis`<br>`kafka`<br>`goshop`</center> | *Отдельные сервисы проекта*                    |
| <center>`image:`</center>                                     | *Указывает, какой базовый образ использовать*  |
| <center>`build:`</center>                                     | *Собирает образ из Dockerfile*                 |
| <center>`ports:`</center>                                     | *Пробрасывает порты наружу*                    |
| <center>`environment:`</center>                               | *Настраивает переменные окружения*             |
| <center>`depends_on:`</center>                                | *Задаёт порядок запуска сервисов*              |
| <center>`env_file:`</center>                                  | *Подключает файл `.env` с настройками проекта* |
| <center>`volumes:`</center>                                   | *Хранит данные PostgreSQL между перезапусками* |

## Как связаны Dockerfile и docker-compose

| Файл                   | Назначение                                      |
| ---------------------- | ----------------------------------------------- |
| **Dockerfile**         | Описывает, как собрать контейнер с приложением  |
| **docker-compose.yml** | Описывает, как запустить все контейнеры проекта |
| **.env**               | Передаёт настройки внутрь контейнеров           |
> Вместе эти файлы создают “мини-инфраструктуру” - с базой, кэшем, брокером и приложением.

## Основные команды Docker

| <center><u>Команда</u></center>      | <center><u>Что делает</u></center>          |
| ------------------------------------ | ------------------------------------------- |
| **`docker build -t goshop .`**       | *Собрать образ по Dockerfile*                 |
| **`docker run -p 8080:8080 goshop`** | *Запустить контейнер*                         |
| **`docker ps`**                      | *Посмотреть работающие контейнеры*            |
| **`docker stop <id>`**               | *Остановить контейнер*                        |
| **`docker rm <id>`**                 | *Удалить контейнер*                           |
| **`docker compose up`**              | *Запустить все сервисы по docker-compose.yml* |
| **`docker compose down`**            | *Остановить и удалить все контейнеры проекта* |

Все образы, контейнеры и данные сохраняются локально

Для Linux:
```
/var/lib/docker/
```
>Тебе не нужно туда лезть — Docker управляет всем сам.
