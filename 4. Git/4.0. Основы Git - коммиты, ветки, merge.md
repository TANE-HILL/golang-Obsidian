# Зачем вообще нужен Git

## Жизненная картина №1 — “Исчезнувшая версия”

Ты пишешь код. Всё работает, но через день решаешь “немного улучшить”, и вдруг всё ломается. Хочешь вернуть старую версию — но её уже нет. Файлы переписаны.

Git решает эту проблему. Он — **машина времени для кода**.

Каждый раз, когда ты делаешь изменения, ты можешь их **зафиксировать** — сделать «снимок» *(коммит)*.

И если что-то пошло не так, ты можешь _вернуться к предыдущему состоянию проекта._

## Жизненная картина №2 — “Работа в команде”

Ты работаешь с другими разработчиками. Один добавляет API, другой меняет структуру базы, третий исправляет баг.

Без Git вы будете постоянно перезаписывать файлы друг друга. Git позволяет каждому работать в **своей ветке**, а потом **аккуратно объединять** изменения.

---
# Что делает Git на самом деле

Git не хранит файлы как простые копии.

Он хранит **снимки состояния проекта** — как если бы ты каждые 5 минут делал архив своей папки.

Каждый коммит — это:
- снимок всех отслеживаемых файлов;
- ссылка на предыдущий снимок *(чтобы выстроить историю)*;
- подпись автора и сообщение о том, что изменилось.

---
## Мини-пример: сохраняем проект Books API в Git

### Шаг 1. Убедись, что проект открыт

Ты уже создавал проект Books [[1.6.2. REST API|API]] — папка с кодом у тебя открыта в GoLand.
Обычно она выглядит примерно так:

```
books-api/
├── go.mod
├── main.go
├── internal/
│   ├── handler/
│   ├── service/
│   └── repository/
```

---
### Шаг 2. Инициализируем репозиторий

Теперь нужно “подключить” Git к этому проекту, чтобы он начал следить за файлами.

Это делается **одной командой** — прямо в терминале GoLand:
```bash
git init
```

Что происходит:
- Git создаёт в корне проекта скрытую папку `.git` — это его “журнал версий”.

Всё, что ты теперь изменяешь, Git будет видеть и предлагать сохранить как новые версии.

---
### Шаг 3. Проверим статус

```bash
git status
```

Git покажет список файлов, за которыми он пока **не следит**:
```
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        go.mod
        main.go
        internal/
```

Это значит: Git видит эти файлы, но пока они не включены в историю.

---
### Шаг 4. Добавляем файлы в индекс

Чтобы Git запомнил текущее состояние проекта, добавим всё под контроль версий:

```bash
git add .
```

- `add` — команда “добавить файлы в индекс” (в черновик перед сохранением);
- `.` — точка означает “добавить всё, что есть в проекте”.

Теперь Git “сфотографировал” все файлы, но пока **не сохранил снимок** в историю.

---
### Шаг 5. Делаем первый коммит

Теперь нужно зафиксировать текущую версию проекта:
```bash
git commit -m "init: первый коммит проекта Books API"
```

Что делает `commit`:
- сохраняет все изменения навсегда в историю Git;
- присваивает им уникальный идентификатор *(hash)*;
- добавляет подпись автора и сообщение *(`m`)*.

---
### Шаг 6. Проверим историю

Посмотрим, что Git сохранил:
```bash
git log --oneline
```

Пример вывода:
```
a1b2c3d init: первый коммит проекта Books API
```

✅ Отлично — первая версия проекта теперь под контролем Git.

---
### Шаг 7. Создаём репозиторий на GitLab

Теперь нужно *“подружить”* локальный репозиторий с удалённым — на GitLab.
1. Зайди в свой аккаунт GitLab.
2. Нажми **“New project” → “Create blank project”**.
3. Введи имя: `books-api`.
4. Нажми **“Create project”**.

GitLab создаст пустой репозиторий и покажет тебе инструкцию с URL, например:
```
<https://gitlab.com/username/books-api.git>
```

---
### Шаг 8. Подключаем GitLab к локальному проекту

Выполни в терминале:
```bash
git remote add origin <https://gitlab.com/username/books-api.git>
```

- `remote add origin` — добавляет “удалённую копию” проекта (GitLab);
- `origin` — принятое имя для основного репозитория;
- ссылка — это адрес твоего проекта на GitLab.

Проверим, что всё добавилось:
```bash
git remote -v
```

Вывод:
```
origin  <https://gitlab.com/username/books-api.git> (fetch)
origin  <https://gitlab.com/username/books-api.git> (push)
```

---
### Шаг 9. Отправляем проект на GitLab

Теперь “зальём” нашу локальную историю в [[4.1. Работа с GitLab - репозиторий, merge requests, code review|GitLab]]:
```bash
git push -u origin main
```

Разберём:
- `push` — отправить изменения на удалённый сервер;
- `u` — привязать ветку `main` к удалённой, чтобы дальше можно было писать просто `git push`;
- `origin` — имя удалённого репозитория;
- `main` — текущая ветка (основная).

---
### Шаг 10. Проверяем результат

Открой страницу проекта на GitLab.
Теперь ты увидишь все файлы из Books API — `main.go`, `go.mod`, папку `internal/` и т.д.

Поздравляю — твой проект теперь под управлением Git и хранится в GitLab.

---
## Что происходит “внутри” после push

Когда ты делаешь `git push`, Git сравнивает твою локальную историю с сервером GitLab.

Если сервер пустой — он принимает всё, что у тебя есть.

Если на сервере уже есть изменения, которых нет у тебя — Git предупредит, и нужно будет *“подтянуть”* обновления через `git pull`.

---
## Основные команды

|Действие|Команда|Что делает|
|---|---|---|
|Инициализация|`git init`|Включает Git в проекте|
|Проверка статуса|`git status`|Показывает отслеживаемые файлы|
|Добавление файлов|`git add .`|Добавляет файлы в индекс|
|Фиксация изменений|`git commit -m "..."`|Создаёт снимок (версию) проекта|
|Привязка к GitLab|`git remote add origin ...`|Подключает удалённый репозиторий|
|Отправка|`git push -u origin main`|Загружает проект на GitLab|

# Ветки — безопасные *“черновики”* для новой работы

## Проблема: как писать код, не ломая рабочую версию

Представь, ты уже написал проект **Books API**, он стабильно работает — обрабатывает запросы, выдаёт список книг. Код лежит в ветке `main`, и именно эта версия сейчас **на продакшене** *(то есть у пользователей)*.

Теперь тебе дали задачу:
> *“Добавь возможность искать книги по автору”*

Ты понимаешь: придётся переписать часть хендлера, обновить репозиторий, внести изменения в тесты.
Но пока ты это делаешь — нельзя ломать рабочую ветку `main`, ведь от неё могут зависеть другие разработчики или сервисы.

## Решение — создать отдельную ветку

Ветка — это **копия текущего состояния проекта**.
Ты начинаешь с того же кода, что и в `main`, но работаешь независимо.
Git создаёт для тебя новую “линию времени”, куда попадут только твои коммиты.

---
### Как это выглядит в жизни разработчика

1. У тебя есть проект:
```
books-api/
├── internal/
│   ├── handler/
│   └── repository/
└── main.go
```

2. Текущая ветка `main` — стабильная.    

Проверим:
```bash
git branch
```

```
* main
```

3. Создаём новую ветку для задачи:

```bash
git branch feature/search-books //создаем новую ветку
git checkout feature/search-books //переключаемся на нее
```
- Теперь ты находишься в ветке `feature/search-books`.    
Это как отдельный “черновик”, где можно менять что угодно, не затрагивая основную ветку.

---
### Что делает Git внутри

- `git branch` просто **создаёт указатель** на текущий коммит.
- `git checkout` **переключает** на него.

То есть ветка — это не новая копия файлов, а просто “указатель на момент истории”.

Git экономно хранит только разницу между снимками.

---
### Вносим изменения в код

Ты добавляешь новую функцию:

```go
// internal/handler/search.go
func (h *Handler) SearchBooks(w http.ResponseWriter, r *http.Request) {
    author := r.URL.Query().Get("author")
    books, err := h.service.FindByAuthor(author)
    if err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    json.NewEncoder(w).Encode(books)
}
```

Сохраняешь, коммитишь:
```bash
git add internal/handler/search.go
git commit -m "feat: добавлен поиск книг по автору"
```

Теперь твой коммит **есть только в ветке `feature/search-books`**.
Ветка `main` о нём ничего не знает.

---
### Проверим, где мы сейчас

```bash
git branch
```

Вывод:
```
* feature/search-books
  main
```

Звёздочка показывает активную ветку.

Если вернуться в `main`:
```bash
git checkout main
```
- ты снова окажешься на **старой версии проекта**, где функции поиска **ещё нет**.

Это ключевая идея Git: каждая ветка — это **изолированная копия истории**, где можно безопасно экспериментировать.

---
### Обновление ветки

Пока ты работал над поиском, кто-то другой мог внести изменения в `main`.

Например, добавить авторизацию. Тогда перед слиянием твоей ветки тебе нужно **обновить** свою копию, чтобы не потерять чужие изменения.

Это делается так:
```bash
git checkout feature/search-books
git rebase main
```

Что происходит:
	Git “переписывает” твои коммиты поверх последних изменений из `main`.

История становится аккуратной и линейной, как будто ты начал писать поиск уже после всех обновлений.

---
### Слияние *(merge)*

Когда фича готова — пора вернуть её в `main`:
```bash
git checkout main
git merge feature/search-books
```
- Теперь все твои изменения “вливаются” в основную ветку.

Если код не конфликтует — Git просто добавит новый коммит слияния.

После этого твою ветку можно удалить:
```bash
git branch -d feature/search-books
```

---
## Конфликт: что это и как решать

Но бывают случаи, когда Git **не может решить сам**, какие изменения оставить.

Например:
- ты в ветке `main` переименовал поле `Book.Title` → `Book.Name`;
- а в ветке `feature/search-books` написал код, который использует старое имя `Book.Title`.

Git понимает, что **оба варианта верны**, но они несовместимы.
Он не может выбрать один без потерь.

Поэтому Git ставит метки прямо в коде — чтобы ты решил сам:
```go
<<<<<<< HEAD
fmt.Println("Title:", book.Name)
=======
fmt.Println("Title:", book.Title)
>>>>>>> feature/search-books
```

---
### Что означают эти строки

| Метка                          | Что значит                                                                  |
| ------------------------------ | --------------------------------------------------------------------------- |
| `<<<<<<< HEAD`                 | Начало твоей текущей версии (той, куда ты сливаешь — в нашем случае `main`) |
| =======                        | Разделитель между версиями                                                  |
| `>>>>>>> feature/search-books` | Конец куска из ветки, которую ты вливаешь                                   |

---
### Как решать конфликт

1. **Открой файл** с конфликтом.    
    Git специально оставляет эти метки, чтобы ты сразу увидел, где именно проблема.

2. **Выбери правильный вариант** — либо из `HEAD`, либо из `feature/search-books`, или даже напиши свой, если нужно объединить обе версии.

Например, оставим только правильное поле:
```go
fmt.Println("Title:", book.Name)
```

3. **Сохрани файл** и отметь конфликт как решённый:
```bash
git add internal/handler/search.go
```

4. **Закрепи результат новым коммитом**:
```bash
git commit -m "fix: разрешён конфликт при merge"
```
- Git создаст новый коммит, где конфликт считается устранённым, и история продолжит развиваться дальше.Как избежать конфликтов


5. **Обновляй свою ветку перед merge**:
```bash
git pull origin main
```
- подтяни последние изменения, прежде чем вносить свои.

6. **Коммить чаще.**
Чем меньше изменений в одном коммите, тем проще Git'у сопоставить версии.

7. **Работай в своих зонах ответственности.**    
    Если ты меняешь `handler`, а кто-то другой — `repository`, конфликты почти исключены.

---
### Как это работает на практике в команде

1. Каждый разработчик берёт задачу из Jira (или GitLab Issues).

2. Создаёт ветку с названием по задаче:
    `feature/BOOKS-123-search`, `fix/BOOKS-101-pagination`.

3. Делает коммиты, пушит ветку на GitLab.

4. Создаёт Merge Request — запрос на объединение в `main`.

5. После ревью и тестов ветка вливается и удаляется.


---
### Ветки в реальном проекте

| Тип ветки   | Назначение                          | Пример имени         |
| ----------- | ----------------------------------- | -------------------- |
| `main`      | стабильная версия, релизы           | `main`               |
| `develop`   | общая ветка для активной разработки | `develop`            |
| `feature/*` | новая функциональность              | `feature/add-search` |
| `fix/*`     | исправление бага                    | `fix/book-count`     |
| `hotfix/*`  | срочный фикс продакшена             | `hotfix/login-error` |
