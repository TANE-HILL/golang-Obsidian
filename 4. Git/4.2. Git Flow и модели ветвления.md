# Зачем нужны модели ветвления

Когда ты работаешь один — всё просто:
- у тебя одна ветка `main`, ты в ней [[4.0. Основы Git - коммиты, ветки, merge|коммитишь, пушишь]], и всё.

Но когда в проекте **несколько разработчиков**, нужны **правила**, чтобы:
- не мешать друг другу;
- понимать, где идёт разработка, а где стабильный код;
- отделять тестирование от релизов;
- выпускать обновления безопасно и предсказуемо.

---
## Проблема без структуры

Представь, что в Books API работают 3 человека:
- Оля делает поиск книг,
- Ваня — регистрацию пользователей,
- а ты исправляешь баг с подсчётом рейтинга.

Все коммитят *“куда придётся”* — кто-то прямо в `main`, кто-то в случайную ветку.

Результат:
- код конфликтует при слиянии;
- непонятно, где тестировать;
- новые фичи ломают продакшен.

Чтобы этого избежать, используют **модель ветвления** — набор правил, определяющих, где ведётся разработка, где тесты, а где стабильный релиз.

---
# Что такое модель ветвления

Модель ветвления *(branching model)* — это **архитектура веток проекта**.

Она описывает:
- какие ветки существуют постоянно (`prod`, `stage`, `dev`);
- какие создаются временно (`feature/*`);
- и как изменения переходят от разработки к релизу.

---
## Основные ветки

| Ветка       | Назначение                                                   |
| ----------- | ------------------------------------------------------------ |
| `prod`      | **продакшн** — код, который реально работает у пользователей |
| `stage`     | **тестовое окружение**, максимально **похожее на продакшен** |
| `dev`       | активная ветка **разработки**, где собираются все фичи       |
| `feature/*` | **временные ветки** для задач и улучшений                    |

---
## Как это работает по шагам

### 1. Разработка фичи

Каждая новая задача начинается **в отдельной ветке** от `dev`:
```bash
git checkout -b feature/add-search dev
```
Разработчик пишет код, коммитит, пушит и создаёт Merge Request в `dev`.
После ревью и одобрения фича вливается в `dev`.

---
### 2. Подготовка к тестам

Когда несколько фич собрались в `dev`, код **вливается в `stage`**:
```bash
git checkout stage
git merge dev
git push
```

На `stage` проводятся:
- интеграционные тесты,
- демонстрации для бизнеса,
- нагрузочные проверки.

Если всё работает — можно выпускать релиз.

---
### 3. Релиз в продакшн

Когда команда уверена в стабильности кода, `stage` вливается в `prod`:
```bash
git checkout prod
git merge stage
git push
```
- 💬 Теперь пользователи видят новый функционал.

После релиза можно отметить версию тегом:
```bash
git tag -a v1.3 -m "Релиз Books API 1.3"
git push origin v1.3
```

---
### 4. Срочный хотфикс

Если на продакшне нашли баг, создаётся ветка **прямо от `prod`**:
```bash
git checkout -b feature/fix-token-bug prod
```

После исправления:
```bash
git commit -m "fix: исправлен баг с токеном"
git merge feature/fix-token-bug dev
git merge feature/fix-token-bug stage
git merge feature/fix-token-bug prod
git branch -d feature/fix-token-bug
```

Баг сразу уходит в продакшен, а исправление синхронизируется со всеми ветками.

---
## 🔁 Визуальная схема ветвления

```
prod     ───●──────────────●────────────→
              ↖             ↖
stage    ─────●──────●──────●───────────→
                ↖      ↖
dev      ───────●──────●────●──────────→
                  ↖
feature/*          ●──●──●

```
- `feature/*` — разработка задач
- `dev` — сборка и интеграция
- `stage` — тесты и проверка
- `prod` — стабильный релиз

---
## Пример на Books API

|Этап|Ветка|Что делаем|
|---|---|---|
|Разработка поиска|`feature/search-books`|создаём новую ветку от `dev`|
|Проверяем локально|`dev`|объединяем фичи, проверяем сборку|
|Тестируем систему|`stage`|тестируем на полном окружении|
|Выпускаем релиз|`prod`|выкатываем обновление пользователям|
|Исправляем баг|`feature/fix-rating`|фиксим от `prod`, вливаем обратно|

---
## Что делает каждая ветка

|Ветка|Назначение|
|---|---|
|**Dev (Development)**|песочница для разработчиков и QA; сюда влетают все фичи|
|**Stage (Pre-prod)**|копия продакшена, где проходят финальные тесты|
|**Prod (Production)**|боевое окружение, доступное пользователям|
|**Feature/**|временные ветки для задач и фиксов|
