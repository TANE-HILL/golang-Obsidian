# Зачем нужен GitLab, если есть Git

[[1.0.1.5. Git|Git]] — это **локальный инструмент**. Он хранит историю и управляет ветками **на твоём компьютере**. Но в команде этого мало.

Нужна платформа, где:
- можно **видеть изменения других**;
- **обсуждать** код;
- **проверять** его перед слиянием;
- **автоматически запускать тесты** и **релизы**.

Эту роль выполняет **GitLab**.

---
# Как устроен рабочий процесс в GitLab

Когда ты работаешь в команде, весь цикл обычно выглядит так:

1. В `main` хранится **чистый и стабильный код**.
2. Для каждой задачи создаётся **своя ветка** *(например, `feature/add-search`)*.
3. После доработки ветка пушится в GitLab.
4. Разработчик создаёт **Merge Request *(MR)*** — запрос *“влить мою ветку в основную”*.
5. Тимлид или коллега делает **code review**: смотрит изменения, оставляет комментарии.
6. После одобрения ветка **сливается в main**.
7. GitLab автоматически запускает тесты и сборку *(через CI/CD)*.

## Мини-пример на проекте Books API

### Шаг 1. Создаём ветку под задачу

Допустим, тебе нужно добавить фильтрацию книг по жанру.
```bash
git checkout -b feature/filter-by-genre
```

Ты добавляешь в `handler` новый эндпоинт и делаешь коммит:
```bash
git add internal/handler/filter.go
git commit -m "feat: фильтрация книг по жанру"
```

### Шаг 2. Отправляем ветку на GitLab

```bash
git push origin feature/filter-by-genre
```

Что делает команда:
- `push` — отправляет ветку на сервер;
- `origin` — GitLab-репозиторий;
- `feature/filter-by-genre` — имя ветки, которая появится в GitLab.

После этого GitLab предложит:
> “Создать Merge Request для этой ветки”.

### Шаг 3. Создаём Merge Request

1. Перейди в свой проект на GitLab.    
2. Перейди во вкладку **Merge Requests** → **New merge request**.
3. Выбери:
    - **source branch** — `feature/filter-by-genre`;
    - **target branch** — `main`.
4. Добавь описание:
```
Добавлен эндпоинт фильтрации книг по жанру
- Новый метод GET /books?genre=...
- Unit-тесты в internal/service/book_test.go
```
5. Назначь **assignee** (кому назначаешь проверку).
6. Нажми **Create merge request**.

### Шаг 4. Ревью и обсуждение

Теперь MR видят другие участники команды. Они могут:
- просмотреть **изменения построчно** (вкладка _Changes_);
- оставить **комментарии прямо в коде**;
- задать вопросы или предложить правки;
- нажать **“Approve”**, если всё ок.

💬 GitLab показывает diff:
	всё зелёное — добавлено
	красное — удалено.

---
#### Пример: комментарий к коду
```go
if genre == "" {
    return errors.New("genre is required")
}
```
Ревьюер может оставить комментарий прямо к строке:
> “А может стоит вернуть 400 Bad Request, а не просто ошибку?”

Ты вносишь правку, коммитишь и пушишь снова:
```bash
git add internal/handler/filter.go
git commit -m "fix: изменён код ошибки при отсутствии жанра"
git push
```
- GitLab автоматически обновит MR — без его пересоздания.
---
### Шаг 5. Завершаем Merge Request

Когда все замечания исправлены:
- Ревьюер нажимает **“Approve”**.
- Тесты проходят (если настроен CI/CD).
- Нажимаешь **Merge**.

GitLab объединяет ветку в `main`, добавляя коммит:
```
Merge branch 'feature/filter-by-genre' into 'main'
```

После успешного merge можно удалить ветку:
```bash
git branch -d feature/filter-by-genre
```

## Структура Merge Request в GitLab

|Раздел|Что содержит|
|---|---|
|**Overview**|Общее описание задачи, теги, статус, кто назначен|
|**Changes**|Разница между ветками — построчные изменения|
|**Commits**|Список всех коммитов в MR|
|**Pipelines**|Результат CI/CD сборки|
|**Discussion**|Комментарии, треды, ответы и резолюции|

## Code Review — как часть командной культуры

Code Review — не “проверка ошибок”, а способ улучшить код всей команды.

Он помогает:
- выровнять стиль кода;
- поймать ошибки до продакшена;
- делиться знаниями и лучшими практиками;
- сделать код понятным для всех.

---
### Советы ревьюеру

- Смотри **на смысл** кода, не только на стиль.
- Если находишь проблему — **предлагай решение**, а не просто указывай на ошибку.
- Хвали за удачные решения — это мотивирует.
- Если не уверен — задавай вопросы, а не ставь блокирующие замечания.

---
### Советы автору MR

- Делай MR небольшими (до 400 строк — идеал).
- Пиши понятные коммит-месседжи.
- В описании MR укажи, что и зачем ты изменил.
- Перед MR — обнови свою ветку (`git pull origin main` ).
- Будь готов к комментариям — это нормально.
