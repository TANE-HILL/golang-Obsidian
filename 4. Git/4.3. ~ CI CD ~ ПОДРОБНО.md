# Задачи, Workflow и CI/CD в IT

## 1. Как идея становится работающей фичей

Разработка программного обеспечения — это не только написание кода. Это последовательный процесс, в котором участвуют бизнес, аналитики, разработчики, тестировщики и DevOps-инженеры.

### 1.1. Зарождение идеи

Работа начинается с потребности бизнеса или пользователя.

**Например:**
- Конверсия падает — нужно выяснить причину и найти способ её повысить.
- Пользователи хотят новую функцию — необходимо оценить её полезность.
- Компания хочет автоматизировать процесс — требуется разработать соответствующую систему.

**Product Owner (PO)** отвечает за ценность продукта и приоритизацию задач. **Product Manager** часто отвечает за продуктовую стратегию и развитие. В зависимости от компании эти роли могут пересекаться.

Аналитики исследуют проблему, собирают требования, изучают данные и помогают определить, какое решение имеет смысл реализовать.

Результат этапа — понимание проблемы и предполагаемого решения.

### 1.2. Discovery: обсуждение и оценка

Идею обсуждают с командой: тимлидом, архитектором, аналитиками и разработчиками.

Основные вопросы:

- **Техническая реализуемость:** можно ли реализовать решение на существующем стеке?
- **Оценка:** сколько времени и ресурсов потребуется?
- **Риски:** какие проблемы могут возникнуть?
- **Архитектура:** какие компоненты системы потребуется изменить?
- **Зависимости:** затронет ли задача другие сервисы, базы данных или команды?
- **Пользовательский интерфейс:** нужны ли макеты дизайнера?

Например, добавление платёжной функции в Go-монолит может потребовать:

- нового HTTP endpoint;
- бизнес-логики в сервисном слое;
- таблицы для хранения платежей;
- интеграции с платёжным провайдером;
- обработки ошибок и повторных запросов;
- unit- и интеграционных тестов.

На этом этапе важно обнаружить потенциальные проблемы до начала разработки.

### 1.3. Декомпозиция и планирование

После обсуждения идея превращается в конкретные задачи, которые обычно ведут в Jira или аналогичной системе.

Основные сущности:

|Сущность|Назначение|Пример|
|---|---|---|
|Epic|Большая цель, объединяющая несколько задач|Запустить реферальную программу|
|User Story|Пользовательский сценарий|Пользователь хочет приглашать друзей по ссылке|
|Task|Конкретная работа|Реализовать endpoint генерации ссылки|
|Subtask|Часть более крупной задачи|Добавить валидацию входных данных|
|Bug|Обнаруженная ошибка|Endpoint возвращает неверный статус|

Пример декомпозиции:

**Epic:** Реферальная программа.

**User Story:** Как пользователь, я хочу получить ссылку, чтобы пригласить друга.

**Технические задачи:**

1. Создать таблицу для хранения реферальных ссылок.
2. Реализовать repository для работы с таблицей.
3. Реализовать бизнес-логику генерации ссылки.
4. Добавить HTTP endpoint.
5. Написать тесты.
6. Обновить документацию API.

У задачи должны быть понятные требования и **Acceptance Criteria** — критерии, по которым можно определить, что работа выполнена корректно.

Например:

- Endpoint возвращает ссылку для авторизованного пользователя.
- Для неавторизованного пользователя возвращается `401 Unauthorized`.
- При ошибке базы данных возвращается корректный ответ.
- Результат соответствует формату API.

### 1.4. Разработка, Code Review и QA

Разработчик берёт задачу и реализует её.

Обычно работа включает:

1. Изучение существующего кода.
2. Проектирование решения.
3. Написание кода.
4. Написание и запуск тестов.
5. Проверку локальной работоспособности.
6. Отправку изменений в Git.
7. Создание Merge Request.
8. Исправление замечаний Code Review.

После этого изменения проходят необходимые автоматические и ручные проверки.

**QA-инженер** проверяет поведение продукта с точки зрения требований, пользовательских сценариев и качества. В зависимости от процесса команды QA может тестировать изменения до или после слияния в основную ветку.

### 1.5. Деплой и мониторинг

После необходимых проверок изменения выпускаются в соответствующее окружение.

После развёртывания команда контролирует:

- логи приложения;
- ошибки и исключения;
- метрики производительности;
- время ответа API;
- нагрузку на CPU и память;
- доступность зависимостей;
- бизнес-метрики.

Для этого могут использоваться Prometheus, Grafana, Sentry и другие инструменты.

Работа не заканчивается после слияния кода: важно убедиться, что изменение корректно работает в реальной среде.

## 2. Жизненный цикл задачи: от To Do до Done

Конкретные статусы зависят от команды, но типичный процесс выглядит следующим образом.

### 2.1. To Do — задача ожидает выполнения

Разработчик выбирает задачу из спринта.

Перед началом необходимо:

- прочитать описание;
- изучить Acceptance Criteria;
- понять ограничения;
- выяснить зависимости;
- уточнить непонятные требования у аналитика, менеджера или тимлида.

Не стоит начинать реализацию, если непонятно, какое поведение считается правильным.

### 2.2. In Progress — разработка

Разработчик обновляет основную ветку и создаёт отдельную ветку для задачи.

```
git switch main
git pull origin main
git switch -c feature/EXAMPLE-9999
```

Здесь `EXAMPLE-9999` — условный идентификатор задачи.

Далее разработчик:

- реализует функциональность;
- пишет unit-тесты;
- проверяет работу приложения;
- запускает тесты;
- анализирует изменения через `git diff`;
- фиксирует законченные логические изменения в коммитах.

Пример:

```
git status
git diff
go test ./...
git add internal/orders/
git commit -m "EXAMPLE-9999 add order endpoint"
```

Коммиты желательно делать по мере завершения логических частей задачи, а не обязательно один раз в конце рабочего дня.

### 2.3. Code Review — проверка кода

Разработчик отправляет ветку в удалённый репозиторий:

```
git push -u origin feature/EXAMPLE-9999
```

Затем создаёт **Merge Request (MR)** в GitLab.

В MR указываются:

- исходная ветка;
- целевая ветка;
- описание изменений;
- ссылка на задачу;
- информация о тестировании;
- при необходимости скриншоты и дополнительные материалы.

Пример:

```
Source branch: feature/EXAMPLE-9999
Target branch: main
```

Коллеги проверяют:

- корректность бизнес-логики;
- архитектуру решения;
- обработку ошибок;
- безопасность;
- читаемость кода;
- тесты;
- соответствие принятым соглашениям.

Если есть замечания, разработчик исправляет код и отправляет новые коммиты в ту же ветку.

```
git add .
git commit -m "EXAMPLE-9999 fix validation"
git push
```

MR обновится автоматически.

Цикл повторяется, пока необходимые замечания не будут устранены и не будут получены требуемые одобрения.

### 2.4. Testing / QA — тестирование

После слияния или на определённом этапе до слияния изменения проверяются в соответствии с процессом команды.

Проверки могут включать:

- автоматические unit-тесты;
- интеграционные тесты;
- функциональные тесты;
- регрессионное тестирование;
- проверку API через Postman;
- нагрузочное тестирование;
- ручную проверку Acceptance Criteria.

Если обнаружен дефект, задача возвращается разработчику. Он исправляет ошибку, после чего необходимые проверки повторяются.

Важно: **QA не обязательно ждёт слияния в `main`**. Некоторые команды тестируют изменения в отдельных окружениях до слияния, другие — после него.

### 2.5. Done — задача завершена

Задачу можно считать завершённой, когда выполнены критерии команды.

Например:

- код написан;
- Code Review пройден;
- автоматические проверки успешны;
- необходимые тесты пройдены;
- изменения слиты;
- приложение развёрнуто, если это предусмотрено процессом;
- Acceptance Criteria выполнены.

После выпуска разработчик может участвовать в анализе логов и метрик, чтобы убедиться в стабильности изменения.

## 3. Git workflow в команде

### 3.1. Зачем нужны ветки

Ветки позволяют разработчикам работать над разными задачами независимо.

Например, в команде работают Борис, Саша и Василий.

В GitLab могут существовать:

```
main
│
├── feature/boris-auth
├── feature/boris-cache
├── feature/sasha-orders
├── feature/sasha-payments
├── feature/vasiliy-api
└── feature/vasiliy-logs
```

Каждый разработчик работает в своём локальном репозитории и создаёт локальные ветки для задач.

При этом удалённые ветки принадлежат общему репозиторию, а не конкретному разработчику.

У разработчика могут быть локально:

- `main`;
- его собственные feature-ветки;
- другие ветки, которые он явно получил или создал.

Для просмотра информации об удалённых ветках используется:

```
git fetch origin
```

Ссылки вида `origin/main` и `origin/feature/boris-auth` показывают известное Git состояние удалённых веток. Они не означают, что все соответствующие ветки автоматически созданы как локальные.

### 3.2. Типичный рабочий процесс

```
1. Обновить main
       ↓
2. Создать feature-ветку
       ↓
3. Написать код и тесты
       ↓
4. Сделать commit
       ↓
5. Отправить ветку на GitLab
       ↓
6. Создать Merge Request
       ↓
7. Code Review + CI
       ↓
8. Исправить замечания
       ↓
9. Слить изменения
       ↓
10. Обновить локальный main
```

Пример команд:

```
git switch main
git pull origin main

git switch -c feature/new-function

# Разработка

git add .
git commit -m "add new function"
git push -u origin feature/new-function
```

После создания и успешного слияния MR:

```
git switch main
git pull origin main
```

Если работа завершена, локальную feature-ветку можно удалить:

```
git branch -d feature/new-function
```

### 3.3. Что делать, если main ушла вперёд

Пока разработчик работает над своей задачей, коллеги могут слить другие изменения в `main`.

Поэтому feature-ветка может отстать от актуальной основной ветки.

Обновить информацию об удалённом репозитории:

```
git fetch origin
```

Переключиться на свою feature-ветку:

```
git switch feature/new-function
```

Перенести свои коммиты поверх актуальной `main`:

```
git rebase origin/main
```

Если возникают конфликты, их нужно разрешить вручную.

**Важно:** rebase переписывает историю коммитов. Если feature-ветка уже опубликована и её используют другие разработчики, перед переписыванием истории необходимо учитывать последствия.

### 3.4. Merge Request и CI

Merge Request — это запрос на интеграцию изменений из одной ветки в другую.

Например:

```
feature/orders → main
```

В MR команда может:

- просматривать изменения;
- оставлять комментарии;
- обсуждать реализацию;
- требовать исправлений;
- проверять статус pipeline;
- устанавливать требования к одобрению;
- выполнять слияние.

**Создание MR не означает автоматического слияния.** MR — это процесс проверки и принятия решения об интеграции изменений.

### 3.5. Нужно ли создавать отдельные ветки test и prod

Не обязательно.

Ветки `main`, `develop`, `release/*`, `test` и `prod` используются в разных моделях ветвления.

Например, в упрощённой модели:

```
feature/*
    ↓
Merge Request
    ↓
main
    ↓
CI/CD
    ↓
staging
    ↓
production
```

Здесь `staging` и `production` — окружения, а не обязательно Git-ветки.

Часто один и тот же код проходит тестовые окружения и затем развёртывается в production. Управление версиями и окружениями выполняется через CI/CD.

# 4. CI/CD: автоматизация разработки

## 4.1. Что такое CI/CD

**CI/CD** — набор практик и инструментов, позволяющих автоматизировать проверку, сборку, подготовку и выпуск программного обеспечения.

Представим, что разработчик добавил новый HTTP endpoint в Go-монолит.

После `git push` нужно проверить:
1. Компилируется ли код.
2. Проходят ли тесты.
3. Нет ли типичных ошибок.
4. Можно ли собрать приложение.
5. Можно ли подготовить его к развёртыванию.

Эти действия можно выполнять вручную, но это медленно и создаёт риск человеческой ошибки.

CI/CD позволяет выполнять их автоматически.

```
Разработчик
     │
     │ git push
     ▼
   GitLab
     │
     ▼
  Pipeline
     │
     ├── Проверки
     ├── Тесты
     ├── Сборка
     └── Подготовка к выпуску
              │
              ▼
        Результат проверок
```

Цель — быстро обнаруживать проблемы и делать выпуск изменений предсказуемым.

## 4.2. CI — Continuous Integration

**Continuous Integration (непрерывная интеграция)** — практика регулярного внесения изменений в общий репозиторий с автоматической проверкой кода.

После отправки изменений CI может автоматически запускать:
```
gofmt -w .
go vet ./...
go test ./...
go build ./...
```

Это лишь пример команд. Например, `gofmt -w .` изменяет файлы на месте, поэтому в CI часто предпочитают отдельную проверку форматирования, не изменяющую рабочую копию.

CI помогает обнаруживать:
- ошибки компиляции;
- упавшие тесты;
- проблемы форматирования;
- типичные ошибки кода;
- несовместимость изменений.

Если pipeline завершается ошибкой, команда видит проблему до того, как изменения попадут в основную ветку или будут выпущены.

**Главная цель CI — регулярно интегрировать изменения и автоматически проверять их качество.**

## 4.3. CD — Continuous Delivery и Continuous Deployment

CD может означать две разные практики.

### Continuous Delivery — непрерывная доставка

Приложение автоматически проходит необходимые проверки, собирается и подготавливается к выпуску.

Для развёртывания в production может требоваться ручное подтверждение.

```
Push
  ↓
Tests
  ↓
Build
  ↓
Подготовка к выпуску
  ↓
Ручное подтверждение
  ↓
Production
```

### Continuous Deployment — непрерывное развёртывание

Если все проверки проходят, изменения автоматически развёртываются в production без отдельного ручного подтверждения на каждом выпуске.

```
Push
  ↓
Tests
  ↓
Build
  ↓
Автоматический Deploy
  ↓
Production
```

|Практика|Что автоматизируется|
|---|---|
|CI|Интеграция изменений и автоматические проверки|
|Continuous Delivery|Подготовка приложения к выпуску|
|Continuous Deployment|Автоматический выпуск в production|

В разговорной речи термином CD иногда обозначают весь процесс доставки и развёртывания. На собеседовании полезно уточнять, какое значение имеется в виду.

# 5. Как устроен GitLab CI/CD

Основные понятия: **Pipeline, Stage, Job и Runner**.

## 5.1. Pipeline

Pipeline — весь автоматизированный процесс для конкретного события.

Например:
```
Pipeline #42
│
├── test
├── build
└── deploy
```

Pipeline описывается в файле `.gitlab-ci.yml`.

Он может запускаться при:
- `git push`;
- создании или обновлении Merge Request;
- создании тега;
- запуске по расписанию;
- ручном запуске.

Фактические условия определяются конфигурацией pipeline.

## 5.2. Stage

Stage — этап pipeline.

Например:

```
stages:
  - test
  - build
  - deploy
```

В обычном случае stages выполняются последовательно:

```
test → build → deploy
```

Если job на этапе `test` завершается ошибкой, jobs следующих этапов обычно не запускаются.

Исключения возможны, например при использовании `when: always` или специальных правил выполнения.

## 5.3. Job

Job — конкретная задача внутри pipeline.

Например:

```
unit-tests:
  stage: test
  script:
    - go test ./...

lint:
  stage: test
  script:
    - go vet ./...

build:
  stage: build
  script:
    - go build ./...
```

Здесь:

- `unit-tests` — имя job;
- `stage: test` — этап, к которому она относится;
- `script` — команды, которые нужно выполнить.

Jobs одного stage могут выполняться параллельно, если доступны необходимые runners и зависимости не требуют другого порядка.

В примере `unit-tests` и `lint` могут выполняться одновременно, а `build` обычно начнётся после успешного завершения предыдущего stage.

## 5.4. GitLab Runner

**GitLab Runner** — программа, которая получает jobs от GitLab и выполняет их.

GitLab хранит конфигурацию и управляет pipeline, а Runner исполняет команды в настроенном окружении.

```
GitLab
   │
   │ Передаёт job
   ▼
GitLab Runner
   │
   ├── Запускает go test ./...
   ├── Запускает go vet ./...
   └── Запускает go build ./...
            │
            ▼
     Возвращает результат
            │
            ▼
      GitLab показывает статус
```

Runner может работать:

- на виртуальной машине;
- на выделенном сервере;
- в Docker-контейнерах;
- в Kubernetes;
- в другом поддерживаемом окружении.

Для выполнения job необходим подходящий Runner. Для Docker executor также требуется корректно настроенное окружение и доступный Docker-образ.

## 5.5. Аналогия

|Понятие|Аналогия|
|---|---|
|Pipeline|Весь производственный процесс|
|Stage|Этап производства|
|Job|Конкретная операция|
|Runner|Исполнитель, который выполняет операцию|
|`.gitlab-ci.yml`|Инструкция для организации процесса|

# 6. `.gitlab-ci.yml`: пишем первый pipeline для Go

## 6.1. Где хранится конфигурация

В корне проекта:

```
GoTracker/
├── .gitlab-ci.yml
├── go.mod
├── go.sum
├── main.go
├── Makefile
├── internal/
└── ...
```

GitLab использует `.gitlab-ci.yml`, чтобы определить:

- какие jobs существуют;
- какие команды они выполняют;
- в каком порядке выполняются этапы;
- когда запускать jobs;
- какие файлы сохранять;
- как передавать зависимости между jobs.

## 6.2. Минимальный pipeline

```
stages:
  - test
  - build

test:
  stage: test
  script:
    - go test ./...

build:
  stage: build
  script:
    - go build ./...
```

Здесь объявлены два этапа: `test` и `build`.

Job `test` запускает тесты всех пакетов проекта.

Job `build` проверяет, что пакеты собираются.

Но для этого Runner должен иметь подходящее окружение с установленным Go.

## 6.3. Указываем окружение с Go

Для Docker executor можно использовать официальный образ Go.

```
image: golang:1.25

stages:
  - test
  - build

test:
  stage: test
  script:
    - go test ./...

build:
  stage: build
  script:
    - go build ./...
```

> [!warning] Версия Go  
> `1.25` здесь используется как пример. Выбирай версию, совместимую с `go.mod` и требованиями проекта. Важно также убедиться, что Runner использует Docker executor или другой executor, поддерживающий выбранное окружение.

Разберём ключевые элементы.

### `image`

```
image: golang:1.25
```

Указывает Docker-образ, в окружении которого выполняются jobs, если Runner настроен на Docker executor.

В образе должны быть доступны необходимые инструменты.

### `stages`

```
stages:
  - test
  - build
```

Объявляет этапы pipeline и их порядок.

### `stage`

```
test:
  stage: test
```

Привязывает job к определённому этапу.

### `script`

```
script:
  - go test ./...
```

Список команд, которые Runner должен выполнить.

## 6.4. Расширенный pipeline для Go

Для Go-проекта можно добавить проверку кода и сборку бинарного файла.

```
image: golang:1.25

stages:
  - test
  - build

variables:
  GOTOOLCHAIN: local

test:
  stage: test
  script:
    - go test ./...

lint:
  stage: test
  script:
    - go vet ./...

build:
  stage: build
  script:
    - go build -o gotracker ./cmd/gotracker
  artifacts:
    paths:
      - gotracker
    expire_in: 1 week
```

Этот пример предполагает, что в проекте существует пакет `./cmd/gotracker`. Если `main.go` находится в корне, команду сборки нужно адаптировать.

Переменная `GOTOOLCHAIN: local` запрещает Go автоматически переключаться на другой toolchain. Она полезна только при соответствующей конфигурации проекта; если она не нужна, её можно убрать.

В примере:

- `test` запускает тесты;
- `lint` запускает `go vet`;
- `build` собирает приложение;
- `artifacts` сохраняет бинарный файл как результат job.

В данном случае `test` и `lint` относятся к одному stage и могут выполняться параллельно. `build` обычно начнётся после их успешного завершения.

# 7. Как запускается pipeline

## 7.1. От `git push` до результата

Допустим, разработчик создал feature-ветку:

```
git switch -c feature/orders
```

Написал код и сделал commit:

```
git add .
git commit -m "add orders endpoint"
```

Отправил изменения:

```
git push -u origin feature/orders
```

Если конфигурация позволяет запуск pipeline для этой ветки, GitLab запускает автоматические проверки.

```
Локальный компьютер
        │
        │ git push
        ▼
      GitLab
        │
        ├── Читает .gitlab-ci.yml
        │
        ├── Создаёт Pipeline
        │
        └── Назначает Jobs Runner
                    │
                    ├── go test ./...
                    ├── go vet ./...
                    └── go build ./...
                             │
                             ▼
                      Результат Jobs
                             │
                             ▼
                       Статус Pipeline
```

Если проверки прошли, pipeline получает статус `passed`.

Если обязательная job завершилась ошибкой, pipeline обычно получает статус `failed`.

Разработчик видит ошибку в GitLab, исправляет код и отправляет новый commit.

## 7.2. Pipeline для Merge Request

Важная часть процесса — автоматические проверки перед слиянием.

Например:

```
feature/orders
      │
      ▼
Merge Request
      │
      ▼
Pipeline
      │
      ├── Tests
      ├── Lint
      └── Build
            │
            ▼
      Все проверки успешны?
          ↙       ↘
        Да         Нет
        │           │
        ▼           ▼
   Можно слить   Исправить код
```

GitLab позволяет настроить обязательные проверки и запретить слияние при неуспешном pipeline.

Но запуск pipeline именно для MR требует соответствующей конфигурации. Один лишь `.gitlab-ci.yml` с jobs не всегда означает, что они автоматически запустятся в контексте Merge Request.

Для этого применяются `rules` и `workflow: rules`.

## 7.3. Пример `rules`

Допустим, нужно запускать тесты при создании Merge Request и при отправке изменений в `main`.

```
test:
  stage: test
  script:
    - go test ./...
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == "main"'
```

Здесь:

- `CI_PIPELINE_SOURCE` — встроенная переменная GitLab, описывающая источник pipeline;
- `CI_COMMIT_BRANCH` — имя ветки для соответствующих типов pipeline;
- `rules` определяет условия запуска job.

При этом важно продумывать правила на уровне всего pipeline, чтобы не создавать ненужные дублирующиеся запуски, например одновременно branch pipeline и MR pipeline.

# 8. Makefile и CI/CD

## 8.1. Зачем нужен Makefile

В Go-проекте разработчики часто выполняют одни и те же команды:

```
go test ./...
go vet ./...
go build ./...
```

Их можно объединить в Makefile.

Например:

```
.PHONY: test lint build

test:
	go test ./...

lint:
	go vet ./...

build:
	go build ./...
```

Теперь разработчик может выполнять:

```
make test
make lint
make build
```

Это делает команды короче и задаёт единый способ выполнения стандартных операций.

## 8.2. Использование Makefile в pipeline

```
image: golang:1.25

stages:
  - test
  - build

test:
  stage: test
  script:
    - make test
    - make lint

build:
  stage: build
  script:
    - make build
```

Теперь локально и в CI используются одинаковые команды.

> [!important] Зависимость от окружения  
> В выбранном окружении Runner должен быть установлен `make`. Если его нет в образе, нужно использовать подходящий образ или подготовить окружение.

## 8.3. Почему это удобно

Без Makefile команды могут дублироваться в нескольких местах.

Например, разработчик запускает один набор команд локально, а CI — другой. Из-за этого локальная проверка может пройти, а pipeline упасть.

Makefile помогает стандартизировать процесс и уменьшить расхождения между локальной разработкой и CI.

# 9. Основные элементы `.gitlab-ci.yml`

|Элемент|Назначение|
|---|---|
|`image`|Выбирает окружение для выполнения job при использовании Docker executor|
|`stages`|Объявляет этапы pipeline|
|`stage`|Определяет этап конкретной job|
|`script`|Содержит команды, которые выполняет job|
|`rules`|Определяет условия запуска job|
|`workflow: rules`|Управляет созданием pipeline в зависимости от условий|
|`variables`|Задаёт переменные окружения|
|`artifacts`|Сохраняет результаты выполнения job|
|`cache`|Позволяет повторно использовать файлы между запусками|
|`needs`|Определяет зависимости jobs и позволяет запускать их независимо от полного завершения предыдущих stages, если зависимости уже готовы|
|`environment`|Описывает окружение, например staging или production|
|`when`|Управляет условиями выполнения job в предусмотренных GitLab сценариях|

## 9.1. Artifacts и Cache — в чём разница

Эти понятия легко перепутать.

**Artifacts** — результаты выполнения job, которые нужно сохранить или передать дальше.

Например:

- собранный бинарный файл;
- отчёт о тестировании;
- отчёт о покрытии кода;
- сгенерированные файлы.

Пример:

```
build:
  stage: build
  script:
    - go build -o gotracker ./cmd/gotracker
  artifacts:
    paths:
      - gotracker
    expire_in: 1 week
```

После успешной job GitLab сможет сохранить файл `gotracker`.

**Cache** — файлы, которые полезно повторно использовать в последующих запусках, чтобы ускорить выполнение.

Например, кэш Go-модулей.

```
variables:
  GOMODCACHE: "$CI_PROJECT_DIR/.go/pkg/mod"

cache:
  paths:
    - .go/pkg/mod/
```

Для Go-проектов кэширование нужно настраивать с учётом используемых путей, версии Go и стратегии ключей.

Главное отличие:

- Artifacts нужны для сохранения и передачи результатов.
- Cache нужен для ускорения повторных запусков.

Кэш не следует использовать как единственное место хранения обязательных результатов сборки: он может быть недоступен или обновлён.

## 9.2. Variables и secrets

Variables позволяют передавать конфигурацию в jobs.

Например:

```
variables:
  APP_ENV: "test"
```

В коде или командах можно использовать переменную окружения:

```
echo "$APP_ENV"
```

Но секреты — пароли, токены, ключи доступа — нельзя хранить в репозитории в открытом виде.

Для этого используют защищённые CI/CD variables, внешние хранилища секретов и настройки доступа.

Нужно учитывать, что защищённые переменные могут быть доступны только в определённых ветках или pipeline, а маскирование не заменяет правильное управление доступом.

## 9.3. `needs`

По умолчанию GitLab организует выполнение jobs по stages.

Но иногда нужно задать более точные зависимости.

Например, job `deploy` зависит от успешной сборки `build` и не должна ждать завершения всех независимых jobs предыдущих этапов.

Для этого может использоваться `needs`.

```
build:
  stage: build
  script:
    - go build -o gotracker ./cmd/gotracker
  artifacts:
    paths:
      - gotracker

deploy:
  stage: deploy
  needs:
    - job: build
      artifacts: true
  script:
    - echo "Deploy application"
```

Это демонстрационный пример. Реальное развёртывание требует дополнительных команд и настроенного окружения.

# 10. Окружения Dev, Stage и Production

Окружение — это среда, в которой работает приложение.

Оно не обязательно соответствует отдельной Git-ветке.

## 10.1. Dev — Development

Среда для разработки и раннего тестирования.

Характеристики:

- могут присутствовать незавершённые функции;
- данные часто тестовые;
- конфигурация может меняться;
- допускается более высокая нестабильность.

Здесь разработчики и QA проверяют функциональность на ранних этапах.

## 10.2. Stage — Staging / Pre-production

Среда для финальной проверки перед production.

Она должна быть максимально похожа на production по важным параметрам:

- конфигурации;
- инфраструктуре;
- интеграциям;
- способу запуска приложения.

Однако staging не всегда является полной копией production и не обязательно использует те же объёмы данных.

Здесь могут проводиться:

- регрессионные тесты;
- интеграционные проверки;
- нагрузочное тестирование;
- демонстрации бизнесу;
- проверки перед выпуском.

## 10.3. Production — Prod

Рабочая среда, в которой приложение обслуживает реальных пользователей.

Здесь особенно важны:

- стабильность;
- безопасность;
- наблюдаемость;
- резервное копирование;
- контролируемое развёртывание;
- возможность отката.

Ошибки в production могут приводить к потере данных, недоступности сервиса и финансовым последствиям.

## 10.4. Как CI/CD использует окружения

Один из возможных процессов:

```
git push
   ↓
CI: тесты, проверки, сборка
   ↓
Успешный pipeline
   ↓
Deploy в Dev
   ↓
Функциональные проверки
   ↓
Deploy в Stage
   ↓
Регрессионные проверки
   ↓
Подтверждение выпуска
   ↓
Deploy в Production
```

Это пример, а не универсальный обязательный порядок.

Некоторые команды автоматически развёртывают каждый commit в тестовое окружение. Другие выпускают изменения через релизные ветки или используют отдельные механизмы продвижения одной и той же собранной версии между окружениями.

**Важный принцип:** желательно проверять и продвигать один и тот же собранный артефакт, а не заново собирать приложение с потенциально отличающимися зависимостями на каждом этапе.

# 11. Стратегии развёртывания

При обновлении приложения важно не только доставить новую версию, но и минимизировать риск простоя.

## 11.1. Canary Deployment

Новая версия сначала получает небольшой процент трафика.

Например:

```
Новая версия
    ↓
1–5% пользователей
    ↓
Проверка ошибок и метрик
    ↓
Постепенное увеличение трафика
    ↓
100% пользователей
```

Если метрики ухудшаются, rollout можно остановить или откатить.

Преимущества:

- ограниченный радиус воздействия ошибки;
- возможность наблюдать за поведением новой версии под реальной нагрузкой;
- постепенное увеличение трафика.

## 11.2. Blue/Green Deployment

Поддерживаются два окружения:

- **Blue** — текущая рабочая версия;
- **Green** — новая версия.

```
              ┌──────────────┐
Трафик ───────► Blue         │
              │ Текущая      │
              │ версия       │
              └──────────────┘

              ┌──────────────┐
              │ Green        │
              │ Новая версия │
              └──────────────┘
```

После проверки новой версии трафик переключается с Blue на Green.

Если возникают проблемы, трафик можно вернуть на Blue, пока старое окружение доступно и совместимо с текущим состоянием данных.

Преимущества:

- быстрое переключение между версиями;
- возможность заранее проверить новую версию;
- упрощённый откат приложения.

Ограничения:

- дополнительные инфраструктурные ресурсы;
- необходимость учитывать совместимость схемы БД;
- переключение не всегда гарантирует мгновенный откат всех побочных эффектов.

# 12. Дополнительные понятия CI/CD

## 12.1. Rollback

**Rollback** — возврат к предыдущей версии приложения или конфигурации после обнаружения проблемы.

Например, после выпуска новой версии резко выросло количество ошибок `500`.

Команда может вернуть предыдущую стабильную версию, если архитектура развёртывания и состояние данных это позволяют.

Важно: rollback приложения не всегда означает автоматический откат изменений базы данных. Миграции должны проектироваться с учётом совместимости и возможного возврата.

## 12.2. Health Check

Health check — проверка состояния приложения.

Например, endpoint:

```
GET /health
```

может сообщать, что приложение запущено.

Более глубокая проверка может учитывать доступность базы данных и других зависимостей.

Health check помогает:

- обнаруживать неработающие экземпляры;
- проверять готовность приложения;
- управлять перезапусками;
- контролировать состояние развёртывания.

Нужно различать:

- **Liveness** — процесс жив и не завис;
- **Readiness** — приложение готово принимать трафик.

## 12.3. Observability

Observability — возможность понимать внутреннее состояние системы по её внешним сигналам.

Основные составляющие:

- **Logs** — события и сообщения приложения;
- **Metrics** — числовые показатели;
- **Traces** — путь запроса через компоненты системы.

Например, после деплоя можно обнаружить:

- рост времени ответа;
- увеличение количества ошибок;
- повышенную нагрузку на базу;
- задержки во внешнем API.

CI/CD доставляет изменения, а observability помогает понять, что происходит после их выпуска.

# 13. Типичные ошибки в CI/CD

### 13.1. Pipeline запускается, но не выполняет нужные проверки

Причина может быть в `rules`, `workflow: rules` или настройках Runner.

Проверяй:

- источник pipeline;
- условия запуска jobs;
- доступность Runner;
- статус jobs;
- логи выполнения.

### 13.2. Локально всё работает, а CI падает

Возможные причины:

- другая версия Go;
- отсутствующая системная зависимость;
- различия в переменных окружения;
- неправильная конфигурация;
- недоступные сервисы;
- тесты, зависящие от локального состояния;
- отсутствие необходимых секретов.

CI должен воспроизводить нужные условия выполнения и выявлять подобные расхождения.

### 13.3. Сборка проходит, но приложение не запускается

`go build` проверяет компиляцию, но не гарантирует корректную работу приложения.

Проблема может проявиться только при запуске:

- отсутствует переменная окружения;
- нет подключения к БД;
- не применены миграции;
- недоступен внешний сервис;
- некорректны права доступа.

Поэтому для серьёзного проекта одной сборки недостаточно.

### 13.4. Секреты попали в репозиторий

Нельзя коммитить:

- пароли;
- приватные ключи;
- access tokens;
- production credentials.

Используй `.gitignore`, CI/CD variables и специализированные хранилища секретов.

Если секрет уже попал в репозиторий, его нужно считать скомпрометированным: отозвать или заменить. Простого удаления из последнего коммита может быть недостаточно.

# 14. Практика: CI/CD для GoTracker

Для закрепления достаточно реализовать простой pipeline, который автоматически тестирует и собирает Go-приложение.

## 14.1. Структура проекта

```
GoTracker/
├── .gitlab-ci.yml
├── Makefile
├── go.mod
├── go.sum
├── cmd/
│   └── gotracker/
│       └── main.go
└── internal/
    ├── handler/
    ├── service/
    └── repository/
```

Структура `cmd/gotracker` приведена как пример. Используй фактическую структуру своего проекта.

## 14.2. Makefile

```
.PHONY: test lint build

test:
	go test ./...

lint:
	go vet ./...

build:
	go build -o gotracker ./cmd/gotracker
```

## 14.3. `.gitlab-ci.yml`

```
image: golang:1.25

stages:
  - test
  - build

test:
  stage: test
  script:
    - make test
    - make lint

build:
  stage: build
  script:
    - make build
  artifacts:
    paths:
      - gotracker
    expire_in: 1 week
```

Перед запуском проверь:

- что `go.mod` соответствует версии Go в образе;
- что в образе установлен `make`;
- что путь `./cmd/gotracker` существует;
- что GitLab Runner доступен для проекта.

## 14.4. Проверка работы

1. Добавь `.gitlab-ci.yml` в репозиторий.
2. Закоммить изменения.
3. Отправь ветку на GitLab.
4. Открой раздел **Build → Pipelines**.
5. Посмотри, какие jobs запустились.
6. Открой логи `test` и `build`.
7. Проверь результат.
8. Создай Merge Request и убедись, что автоматические проверки работают в соответствии с настройками проекта.

## 14.5. Следующие упражнения

### Упражнение 1. Автоматические тесты

Настрой pipeline, который выполняет:

```
go test ./...
```

### Упражнение 2. Тесты и сборка

Добавь stages:

```
test → build
```

Убедись, что при падении обязательной тестовой job сборка не выполняется.

### Упражнение 3. Проверка Merge Request

Настрой pipeline так, чтобы проверки запускались при создании и обновлении MR.

### Упражнение 4. Artifacts

Настрой сохранение собранного бинарного файла.

### Упражнение 5. Подготовка к развёртыванию

Добавь отдельную job, которая запускается только при определённых условиях и имитирует подготовку к выпуску.

Например, можно начать с ручной job для ветки `main`, не выполняющей реальный деплой.

# 15. Вопросы с собеседований

## 15.1. Задачи и workflow

**Что происходит с задачей от момента появления до релиза?**

Идея → Discovery → декомпозиция → задача в трекере → разработка → тестирование → Code Review → Merge Request → CI → слияние → QA и/или staging → релиз → мониторинг.

Конкретный порядок зависит от процесса команды.

**Зачем нужен Code Review?**

Для поиска дефектов, проверки архитектурных решений, поддержания качества и единых стандартов кода, а также обмена знаниями внутри команды.

**Что такое Acceptance Criteria?**

Проверяемые условия, которым должна соответствовать реализация, чтобы задача считалась выполненной.

## 15.2. CI/CD

**Что такое CI?**

Практика регулярной интеграции изменений с автоматической проверкой кода, тестами и сборкой.

**Чем Continuous Delivery отличается от Continuous Deployment?**

При Continuous Delivery приложение готово к выпуску, но production-деплой может требовать ручного подтверждения. При Continuous Deployment успешные изменения автоматически развёртываются в production.

**Что такое Pipeline?**

Набор связанных автоматизированных задач, выполняемых по определённым правилам.

**Что такое Stage?**

Этап pipeline, объединяющий jobs.

**Что такое Job?**

Конкретная задача, которая выполняет заданные команды.

**Что такое Runner?**

Программа, которая получает jobs и выполняет их в настроенном окружении.

**Для чего нужен `.gitlab-ci.yml`?**

Для описания конфигурации pipeline: jobs, stages, команд, условий запуска, артефактов и других параметров.

**Что произойдёт, если тесты упадут?**

Pipeline обычно получит статус `failed`, а последующие обязательные jobs не запустятся. Конкретное поведение зависит от конфигурации.

**Что такое Artifacts?**

Сохранённые результаты выполнения jobs, например бинарные файлы или отчёты.

**Чем Artifacts отличаются от Cache?**

Artifacts предназначены для хранения и передачи результатов, а Cache — для повторного использования файлов и ускорения запусков.

**Можно ли автоматически деплоить в production после каждого push?**

Технически да, но это решение зависит от требований к качеству, безопасности и процессу выпуска. Обычно нужны проверки, ограничения доступа, наблюдаемость и возможность отката.

## 15.3. Практические вопросы

**Как бы ты настроил CI для Go-проекта?**

1. Выбрал подходящий образ Go.
2. Настроил запуск `go test ./...`.
3. Добавил `go vet ./...`.
4. Настроил сборку.
5. Обеспечил запуск проверок для Merge Request.
6. Настроил Runner.
7. При необходимости добавил artifacts, cache и переменные окружения.

**Почему pipeline может падать, хотя локально всё работает?**

Из-за различий в версиях инструментов, зависимостях, конфигурации, переменных окружения, доступности сервисов или особенностей тестов.

**Нужно ли использовать отдельную Git-ветку для production?**

Не обязательно. Production может быть отдельным окружением, в которое развёртывается версия из `main` или релизный артефакт.

> [!summary] Главная мысль  
> Разработчик создаёт изменения в Git, а CI/CD автоматизирует их проверку, сборку и, при соответствующей настройке, выпуск. Pipeline состоит из jobs и stages, которые выполняются Runner. Merge Request позволяет проверить изменения до слияния, а окружения и мониторинг помогают безопасно доставлять новую функциональность пользователям.
