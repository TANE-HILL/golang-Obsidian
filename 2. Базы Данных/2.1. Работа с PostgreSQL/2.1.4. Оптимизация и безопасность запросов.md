# Зачем нужна оптимизация и безопасность запросов

**[[2.1.3. Транзакции|На этом этапе]] у нас есть сервер, который:**
- подключается к PostgreSQL;
- выполняет SQL-запросы через `sqlx`;
- создаёт, читает и изменяет данные.

Теперь задача — сделать так, чтобы он был **быстрым и безопасным**.

Потому что:
- неэффективные запросы = медленный сервер;
- небезопасные запросы = риск SQL-инъекций.

---
## Оптимизация: как понять, что запрос “тормозит”

### Что такое план запроса

Когда ты выполняешь SQL, PostgreSQL не просто “читает таблицу”.

Он **анализирует**, как именно это сделать — по индексам, по сортировке, по фильтрам и т.д.

Для этого есть команда `EXPLAIN`.

---
### Пример 1: простой SELECT

```sql
EXPLAIN SELECT * FROM transactions WHERE amount > 1000;
```
Результат:
```
Seq Scan on transactions  (cost=0.00..25.00 rows=5 width=48)
  Filter: (amount > 1000)
```

Расшифровка:
- **Seq Scan** — последовательное чтение всех строк (медленно на больших таблицах);
- **Filter** — условие отбора;
- **cost=0.00..25.00** — примерная “стоимость” выполнения;
- **rows=5** — ожидаемое количество строк.

---
### Пример 2: с индексом

Создадим индекс:
```sql
CREATE INDEX idx_transactions_amount ON transactions (amount);
```
Теперь:
```sql
EXPLAIN SELECT * FROM transactions WHERE amount > 1000;
```

Результат:
```
Index Scan using idx_transactions_amount on transactions (cost=0.15..8.37 rows=5 width=48)
```

Теперь PostgreSQL использует **индекс** — запрос выполняется быстрее.

---
### Пример 3: `EXPLAIN ANALYZE`

Чтобы увидеть **реальное время выполнения**, добавь `ANALYZE`:
```sql
EXPLAIN ANALYZE SELECT * FROM transactions WHERE amount > 1000
```

**Результат покажет:**
- реальное время выполнения (в миллисекундах);
- сколько строк реально возвращено;
- какие индексы использовались.

---
## Как ускорить запросы в [[1.1.0. Go Basics|Go]]

1. Выбирай только нужные поля, а не `SELECT *`.
2. Добавляй индексы для часто используемых фильтров (`WHERE`, `JOIN`).
3. Не делай много JOIN-ов без нужды.
4. Используй пагинацию (`LIMIT`, `OFFSET`).
5. Проверяй планы через `EXPLAIN ANALYZE` — и оптимизируй по результату.

---
## Разница межу `EXPLAIN` и `EXPLAIN ANALYZE`

|Команда|Что делает|Когда использовать|Пример вывода|
|---|---|---|---|
|**`EXPLAIN`**|Показывает _план выполнения_ запроса, который построил PostgreSQL. Не выполняет сам запрос.|Когда нужно понять, как Postgres будет искать данные (использует ли индекс, делает ли полное сканирование и т.д.)|`Seq Scan on transactions (cost=0.00..25.00 rows=5)`|
|**`EXPLAIN ANALYZE`**|Запускает запрос _на самом деле_ и показывает _реальное время выполнения_ и _количество обработанных строк_.|Когда нужно измерить фактическую производительность и убедиться, что индекс реально ускорил работу.|`Index Scan using idx_amount on transactions (actual time=0.12..0.25 rows=10)`|

## Пример оптимизации

Представь, что в проекте GoFinance у нас много транзакций.

Мы часто делаем выборку по категории:

```sql
SELECT * FROM transactions WHERE category_id = 1;
```

На маленьких данных — всё ок.

Но при 100 000+ строк — запрос начинает “тормозить”.

---

### Шаг 1. Проверяем план запроса

```sql
EXPLAIN ANALYZE SELECT * FROM transactions WHERE category_id = 1;
```

Результат:

```
Seq Scan on transactions  (cost=0.00..25.00 rows=100)
  Filter: (category_id = 1)
```

Это **Sequential Scan** — значит PostgreSQL читает _всю таблицу_, даже если нужно 10 строк.

---

### Шаг 2. Добавляем индекс

```sql
CREATE INDEX idx_transactions_category ON transactions (category_id);
```

---

### Шаг 3. Проверяем снова

```sql
EXPLAIN ANALYZE SELECT * FROM transactions WHERE category_id = 1;
```

Теперь видим:

```
Index Scan using idx_transactions_category on transactions (actual time=0.15..0.25 rows=10)
```

Теперь используется **Index Scan** — запрос стал быстрее в десятки раз.

# Безопасность SQL-запросов в GoFinance

---

Ты уже пишешь **безопасные SQL-запросы**, потому чтотиспользуешь **`sqlx`** и **плейсхолдеры** `$1, $2, $3` вместо прямой подстановки переменных. Разберём по шагам, как именно твой проект защищён и что можно улучшить.

---

## Как было

📄 `internal/db/transaction_repo.go`

```go
query := fmt.Sprintf("SELECT * FROM transactions WHERE category_id = %d", id)
r.db.SelectContext(ctx, &txs, query)
```

❌ Это небезопасно.

Если бы кто-то отправил `id = 1 OR 1=1`,

PostgreSQL вернул бы _все строки_.

---

## Как правильно (и у нас уже так)

📄 `internal/db/transaction_repo.go`

```go
query := `
    SELECT id, category_id, amount, note, created_at
    FROM transactions
    WHERE category_id = $1
    ORDER BY created_at DESC
    LIMIT $2;
`
err := r.db.SelectContext(ctx, &txs, query, categoryID, limit)
```

Теперь:

- параметры передаются **через `$1, $2`** → PostgreSQL сам экранирует значения;
- даже если пользователь подставит вредоносный SQL, он будет воспринят как текст.

---

## Улучшаем код проекта (безопасный и оптимизированный запрос)

Добавим фильтрацию и пагинацию в список транзакций.

📄 `internal/db/transaction_repo.go`

```go
func (r *TransactionRepo) List(ctx context.Context, categoryID, limit int) ([]models.Transaction, error) {
    var txs []models.Transaction

    query := `
        SELECT id, category_id, amount, note, created_at
        FROM transactions
        WHERE ($1 = 0 OR category_id = $1)
        ORDER BY created_at DESC
        LIMIT $2;
    `
    err := r.db.SelectContext(ctx, &txs, query, categoryID, limit)
    return txs, err
}
```

Что изменилось:

- `$1 = 0 OR category_id = $1` — если `categoryID=0`, то выводятся все;
- `LIMIT $2` — ограничиваем количество строк → меньше данных → быстрее;
- плейсхолдеры `$1`, `$2` → **никаких SQL-инъекций**.

---

## Обновляем хендлер

📄 `internal/handlers/transactions.go`

```go
func (h *TransactionHandlers) ListTransactions(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodGet {
        http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
        return
    }

    categoryID, _ := strconv.Atoi(r.URL.Query().Get("category_id"))
    limit, _ := strconv.Atoi(r.URL.Query().Get("limit"))
    if limit == 0 {
        limit = 10
    }

    txs, err := h.repo.List(r.Context(), categoryID, limit)
    if err != nil {
        http.Error(w, "Database error: "+err.Error(), http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(txs)
}
```

Что добавили:

- читаем параметры `category_id` и `limit` из URL (например, `/transactions?category_id=2&limit=5`);
- передаём их в безопасный запрос через `sqlx`;
- возвращаем результат в JSON.

|Что|Как мы сделали|Где|
|---|---|---|
